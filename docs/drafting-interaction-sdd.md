# 基础图形绘制交互设计（SDD）

## 文档定位

本文规定**画一个基础图形时用户要做哪些动作**：线、多段线、矩形、圆、弧、箭头、导线。它是
`drafting-unification-roadmap.md` 的下游——那条路线回答的是「绘图是不是一个模式」「曲线存在
哪里」，本文回答的是「按下去之后发生什么」。

本文**不是**权威规范，权威在 OpenSpec。它的作用是先把整套交互一次想清楚，再拆成若干条各自
可发布、可回退的提案；确认之后另出实现地图。

## 一、三条判据

绘图这一层借鉴 AutoCAD，但判据是**这个任务需要什么**，不是「AutoCAD 怎么做」——用户不熟
AutoCAD（路线图 2026-08-23 由用户校正），公司里只有一部分是 CAD 用户。因此：

1. **精确性不能丢。** 画元器件的本质是「这个引脚必须正好在那里」。对象捕捉、键入坐标、
   角度约束、命令的多步取点——这些是任务需要的，一条都不删。
2. **确认动作能省则省。** CAD 里大量按键是在回答「你确定吗」，而它们的答案永远是「确定」。
   敲 `L` 再敲空格才开始画线，那个空格没有携带任何信息。
3. **数值必须一直看得见、随时改得了。** 画的过程中长度和角度必须在屏幕上，并且可以直接
   键入——这是 AutoCAD 的动态输入，也是 Onshape 画完一条线立刻能打长度的做法。

## 二、统一交互骨架

七条命令共用同一副骨架。差异只在「取几个点」「每个点叫什么」「产出什么几何」三处。

```
启动 ─── 单键快捷键（图面有焦点）
     ├── 工具栏按钮
     └── 命令行敲名字 + Enter
       ↓
取点 ─── 点一下 ──────────────┐        ┐
     └─ 按下拖动、松手 ───────┤        │ 全程显示动态输入：
       ↓                       │        │ 数值字段跟着光标，
       └─ 取够了没有？─── 没够 ┘        │ 可键入、Tab 切换
              │                          │
              └── 够了 / Enter / 右键    │
       ↓                                 │
落地 ─── 逐段落地（LINE）                │
       └─ 一次落地（其余）               ┘
       ↓
善后 ─── 命令产出的对象不进几何编辑（命令还握着光标）

           Escape 随时放弃整条命令
```

### 2.1 启动：单键即执行，不要确认键

**决策：常用绘图命令各绑一个单键快捷键，按下即开始，没有确认键。**

我们已经有这套机制——`DEFAULT_STAGE_SHORTCUTS` 里 `V` 是选择、`F` 是容器、`T` 是文字，全都
按下即生效。绘图命令只是**还没有接上去**：它们今天只有工具栏按钮和命令行两个入口。

**规则：单键快捷键 MUST 同时是该命令的一个别名。** 用户只记一套词。为此要给两条命令补别名：

| 命令 | 今天的别名 | 单键 | 说明 |
| --- | --- | --- | --- |
| `LINE` | `L` | `L` | 已一致 |
| `PLINE` | `PL` | `P` | 补别名 `P` |
| `RECTANGLE` | `REC` | `R` | 补别名 `R`；`Shift+R` 是旋转工具，不冲突 |
| `CIRCLE` | `C` | `C` | 已一致 |
| `ARC` | `A` | `A` | 已一致 |
| `WIRE` | `WI` | `W` | 补别名 `W` |
| `ARROW` | `AR` | `X` | `A` 已被弧占，`X` 空着 |

**快捷键有七个，工具栏按钮只有六个**：`LINE` 与 `PLINE` 共用一个按钮（见 3.2）。快捷键是给
知道自己要什么的人用的，按钮是给在挑的人用的，两者的数量没有必须相等的理由。

**明确拒绝「唯一前缀即执行」**：让命令行在输入唯一匹配某条命令时自动执行。它看起来更省事，
实际要求用户在脑子里维护一张随命令集变化的表——`C` 今天唯一匹配 `CIRCLE`，明天加一条
`CHAMFER` 就变成两个，而用户敲下 `C` 的那一刻分不清会执行哪个。单键快捷键没有这个问题：
`L` 是**绑给** LINE 的一个键，不是 `LINE` 的前缀。

### 2.2 焦点决定字符归谁

常驻命令行 + 单键快捷键会争同一个字符，规则必须写死：

| 状态 | 字母 | 数字与 `@ - . ,` |
| --- | --- | --- |
| 空闲、焦点在图面 | 命令快捷键 | 无意义，忽略 |
| 空闲、焦点在命令行 | 文本 | 文本 |
| **命令进行中、焦点在图面** | 转交动态输入框（关键字与数值都在那里） | 转交动态输入框 |
| 命令进行中、焦点在命令行 | 文本 | 文本 |

第三行是关键：命令一旦跑起来，图面上的可打印字符**自动转交给光标旁的动态输入框**，用户不必
把手移回命令行。这是动态输入真正省事的地方，也是 AutoCAD 开着 DYN 时的行为。

### 2.3 取点：点击与拖动是同一个工具的两种下笔方式（LINE 已确认）

**决策：拖动只是「一口气放两个点」的快捷方式，不是结束信号。命令结不结束，只看它自己的
取点数够了没有。**（路线图决策 9 的落实）

- 按下 → 取一个点
- 松手 → 再取一个点（中途没动过阈值就只算一次点击，只取一个点）
- 取够了没有 → 两点命令（矩形/圆/箭头/导线）此刻已经够了，自然结束；连续取点命令
  （`LINE`/`PLINE`）还没够，接着等下一个点

**这条曾经写反过。** 初稿写的是「拖出来的线松手即结束」，理由是「拖动是一次自带开始与结束
的完整手势」。走一遍 `LINE` 就知道它是错的：画元器件画的是**链**——引脚到接点、接点到母线，
一笔接一笔。松手即结束会让每画一段都要重新按一次 `L`，而用户拖那一下的意图恰恰是「先把这
一段快点定下来」，不是「我画完了」。现在这版还少一条规则：**没有「拖动的命令这样结束、点击
的命令那样结束」这种分叉**，所有命令的结束条件都是同一句话。

代价是两点命令看起来「拖完就结束了」而 `LINE` 不结束，但那不是两套规则——两点命令是取够了，
`LINE` 是没取够。

**弧是例外，只支持点击。** 三个点用一次拖动表达不出来，半拖半点会让用户说不清自己在哪一步。

**已知障碍**（AGENTS.md 已记录）：取点插件优先级 1650 高于绘制插件 1000，两者同时武装时
`pointerdown` 就被取点插件吃掉，拖动永远起不来；而 `pointerdown` 那一刻分不出点还是拖。
真做要改仲裁器的认领时机——让插件能在 `pointerdown` 时「暂缓认领」，等到第一次超过阈值的
`pointermove` 或 `pointerup` 再决定。这是本 SDD 里技术风险最高的一项。

### 2.4 动态输入：数值一直在，随时能改

**决策：取点过程中，光标旁常驻显示这一步的数值字段；Tab 切换，键入即锁定。**

今天取点全程屏幕上**一个数字都没有**（拖容器时的「248 × 144」只服务 `draw-container` 拖拽，
命令取点没接）。这是「画元器件不方便」最直接的一半。

**字段由命令声明，数学由 core 统一做。** 命令不写任何三角函数，宿主不认识任何命令：

| 参数化 | 字段 | 谁用 |
| --- | --- | --- |
| `absolute` | X、Y | 每条命令的第一个点（没有上一个点，量不出任何东西） |
| `polar` | 距离、角度 | LINE / PLINE / ARROW / WIRE 的第 n 点；ARC 的第二、三点 |
| `cartesian` | 宽、高 | RECTANGLE 的对角点 |
| `radius` | 半径（**单字段**） | CIRCLE 的半径点 |
| `diameter` | 直径（**单字段**） | CIRCLE 打了 `D` 之后 |

五种参数化的正反算住 `core`，与 `parseComposeCoordinate` 的极坐标数学是同一份。

**单字段是一等公民，不是「两个字段其中一个只读」**（2026-08-29 修正，初稿写错了）。判据一直
是同一句——**这个数影响结果吗**：矩形轴对齐，角度恒为 0，所以不画角度弧；圆旋转对称，半径点
的角度落在哪儿画出来都一样，所以连那个框都不出。一个永远不影响结果的只读字段比没有更差，
它占着屏幕、占着 `Tab` 的一个去处，却什么也不回答。推论：`Tab` 在 `CIRCLE` 里不接管，
**也没有锁定这一档**——锁定是 `Tab` 的产物。

**正在键入时预览跟着键入的值走，不再跟着光标。** 这一条是画圆逼出来的（单字段命令借不到
「锁定」那一档来表达「这个数已经生效了」），但缺口不是圆特有的：`LINE` 打长度、`RECTANGLE`
打宽度今天同样看不见结果，要按下回车才知道，而那时命令已经结束。候选落点交给预览、十字线、
橡皮筋终点与捕捉标记——就是这条链原本就共用的那个值。缓冲不是可解析数字时（半个坐标、
关键字）退回跟着光标。

**标注量的那一段必须画出来。** 不画它，标注的两条延伸线就从空处伸出来，用户读不出这个数说
的是什么。它**不是**「预览几何与橡皮筋互斥」的例外——那一条禁止的是同一个问题答两遍，而
半径线与圆回答的是两个问题：形状是什么、你落在圆上的哪个点。由谁画取决于它是不是形状的一
部分，因此由提示声明：`LINE` 的预览线就是被量的那一段（不声明），`CIRCLE` 与 `ARC` 第三步
的不在预览几何里（声明）。

**键入一个字段即锁定它，另一个仍跟鼠标**（AutoCAD 的行为）：打 `100` Tab，长度锁死 100，
角度继续跟着光标转；再打 `30` Enter，落点确定。

**直接距离输入**：角度约束开着时，方向已经由鼠标定好，此时**只打一个数字回车**就够了。今天
打裸 `100` 会被三条正则全部拒掉（`x,y` 要逗号、`@dx,dy` 要 `@`、`距离<角度` 要 `<`），落到
关键字分支被拒——这是一个每天都会碰到的缺口。

### 2.5 动态输入长什么样（已确认）

交互稿：[`docs/mockups/drafting-dynamic-input.html`](./mockups/drafting-dynamic-input.html)。
以下是从中提炼的规格，几何全部按 AutoCAD 实机截图量过。

**第一个点**：光标右下角并排两个框，`X` / `Y`，绝对坐标（相对**所属场景**的原点，不是世界
原点——场景就是坐标原点，这是既有约定）。

**第 n 个点**：屏幕上同时有两条标注，各带一个数值框。

| 部件 | 几何 |
| --- | --- |
| 橡皮筋 | 起点 → 当前解算落点（不是裸指针） |
| 长度标注线 | 与橡皮筋**平行**、垂直偏移一段；两端各有一条延伸线，分别引自起点与落点 |
| 长度框 | 落在**标注线的中点**上 |
| 角度参考射线 | 从起点画一条 0° 水平射线 |
| 角度弧 | 从射线扫到橡皮筋，**半径等于当前长度** |
| 角度框 | 落在**弧的中点**上（扫掠的一半处） |
| 标注断开 | 两条标注都在自己那个框的后面断开，不从框底下穿过去 |

**这两行可以收成一句话：框落在自己那条标注的中点上，标注在框后面断开。** 缺口本身就在说
「这个数说的是这条标注」，因此框里只有数字，不放图标。

**短弧退化**：线很短或角度很小的时候弧长会小于框宽，此时框移到弧的**径向外侧**，弧整段画、
不断开。不做这一步的话，框会把整条弧吃掉。

**已知量过、可以直接抄的两个数**：角度框在扫掠一半处、框心到起点的距离与弧半径一致（三张
实机截图分别是 10.6°/11.6°、21.6°/25.7°、9.1°/10.0°，半径差都在 1% 以内）。

**锁定的呈现**：键入一个字段即锁定它（2.4），锁定的框上加锁标记；锁定长度时额外画一个
**半径等于该长度的圆**——指针可以跑到圆外，落点仍钉在圆上，这是「长度已定、方向还在跟鼠标」
唯一说得清楚的画法。

**十字光标是短臂**，臂长按既有规范抄 `CURSORSIZE`（AGENTS.md 已记录），不是横贯全屏。

**拒绝过的三种画法**：

| 拒绝的 | 理由 |
| --- | --- |
| 角度弧用固定小半径（如 40px） | 角度小的时候整条弧退化成几个像素（5° 时约 3.7px），什么都读不出来 |
| 角度框贴在弧的 0° 端 | 0° 端就在起点附近，而长度标注的延伸线也从起点引出，两个框挤在同一小块地方，读不出各自属于哪条标注 |
| 框里放 `↔` / `∠` 图标 | 位置已经把含义说清楚了，图标是同一句话的第二遍 |

### 2.8 角度约束：正交与极轴（已确认）

**决策：角度约束是三态互斥的关 / 正交 / 极轴，默认极轴，两个按钮上工具栏。**

CAD 里真正的**吸附**只有两种——网格捕捉（吸到一张绝对点阵）与对象捕捉（吸到已经画出来的
东西）。正交、极轴追踪、对象捕捉追踪三个不是吸附，它们限制的是**方向**：落点仍在射线上连续
滑动。分清这一点是本节的前提，也是它们在管线里排哪一级的依据。

| | AutoCAD 键 | 我们 | 说明 |
| --- | --- | --- | --- |
| 网格捕捉 | F9 | ✅ | 两轴独立步长 |
| 对象捕捉 | F3 | ✅ | `port > endpoint > midpoint > center > quadrant` |
| 正交 | F8 | ✅ | 无条件投影到水平或竖直 |
| 极轴追踪 | F10 | ✅ **新增** | 按增量角成族追踪，只在容差内投影 |
| 对象捕捉追踪 | F11 | ❌ | 它是对象捕捉的放大器，要先有「已捕获的点」这个概念 |

**三态互斥而不是两个独立布尔。** 正交与极轴回答的是**同一个问题**——这一步的方向怎么被约束。
两个布尔会造出一个「都开」的第四态，而那一态没有正确答案（谁赢？）。因此工具栏那两个按钮是
同一个单选组的两个成员，按下已经按下的那一个就是关掉。

**正交与极轴的差别只有一处：正交无条件投影，极轴只在容差内投影。** 这一处差别决定了默认值：

- 正交默认必须**关**——它永远把点钳到水平或竖直，一开就画不了斜线。
- 极轴默认可以**开**——它不挡任何画法，够不着时完全自由。

而**只有默认开着，最常用的那个约束才真的被用上**。此前角度约束藏在 `F8` 后面、Stage 自己持有，
宿主读不到也就画不出按下态，用户不按那个键就不知道有这回事。工具栏解决的正是可发现性，因此
按下态是必需的，不是装饰。

**命中判据是落点到射线的屏幕距离，不是角度差。** 角度容差在远处会失控：离参考点 500px 时
±3° 就是 ±26px 的捕捉带，用户想画 87° 会被拽到 90°。距离容差恒定，远处反而更精确（500px 处
6px 的带宽只有 0.7°），而近处所有射线本来就几乎重合，吸到哪条都一样。它与拾取框、特征点靶区
是同一个量纲，因此复用同一个 `snapRadius`——「多近算在上面」在这个产品里只该有一个数。

**增量角默认 45°，不照抄 AutoCAD 的 90°。** 照抄的前提是没有理由偏离，而这里有一条：**AutoCAD
的极轴默认是关的，我们默认是开的**。默认开着时增量角要覆盖用户真会画的方向，而 90° 漏掉的正是
接线图上那条斜引线；45° 只多四条射线，容差是几个像素，误吸的代价很小。取值只给 360 的约数
（90 / 45 / 30 / 22.5 / 18 / 15 / 10 / 5）——只有整除 360 的角才能成族铺满一圈。

| 丢掉的 | 理由 |
| --- | --- |
| **附加角表**（AutoCAD 的那张自定义角度清单） | **增量角是「一族」、附加角是「一条」**：填 `37` 只追踪 37° 这一个方向，不给 74°、也不给对面的 217°。这个区别真实且有用，但它需要一整套增删行的编辑面，而眼下没有消费者 |
| 对象捕捉追踪（OTRACK） | 见上表 |

**管线次序改了：网格排到角度约束之前。** 原先是 `对象捕捉 > 正交 > 网格`，现在是
`对象捕捉 > 网格 > 角度约束`。理由与「捕捉命中即短路」逐字相同——**网格把刚约束到 45° 上的点
挪走，等于约束没发生**，角度约束必须是最后一步。

这个次序同时修掉正交的一处静默缺陷：先正交后网格时，已经钉在 `reference.y` 上的那个分量会被
再取整一次，参考点不在格点上时点就被挪离了正交线，而屏幕上只表现为「按着 `F8` 画出来的线还是
斜的」。沿射线的位置因此是**网格点在射线上的投影**——斜射线上不落在格点上，这是对的：那个方向
上本来就没有格点，而长度有动态输入可以精确给出。

**命中时画一条追踪射线。** 不画的话用户只看到点「粘」到了某个方向上，说不清是自己手稳还是有
东西在吸。它属于**标注**那一族（与角度弧的 0° 参考射线同色同点画）而不是预览那一族：它说的是
「你正沿着这条线」，不是「松手会变成什么」。命中与否由管线上报，呈现层不另判一次——各判一次的
症状是「画了射线但点没落在上面」。锁定与键入覆盖排在约束之后、能把点带离射线，因此画之前还要
验一次落点确实还在它上面。

角度约束是**会话级视图状态**，不写进文档、不进撤销历史：这是「怎么画」而不是「画了什么」，与
网格设置同一条判断。

### 2.9 连续绘制：画完一条接着画下一条（已确认）

**决策：两点命令提交后重启自己，由命令定义声明；`WIRE` 与 `ARROW` 声明，其余不声明。**

先分清两种「连续」——它们是两件事，只是名字撞了：

| 读法 | 结论 |
| --- | --- |
| (a) **一条**导线取多个点（折线导线） | ❌ 已否。价值几乎全部来自自动路由，而路由还没有；手画的拐点挪一下符号就得重画 |
| (b) 画完一条，**命令不结束**，接着画下一条 | ✅ 本节说的是这个 |

**调研：EDA 那一侧是一致的。**

| 工具 | 画完一条之后 |
| --- | --- |
| KiCad Eeschema | 工具**保持激活**，接着画下一条；`Esc` 退出 |
| Altium Designer | 同上，右键或 `Esc` 退出 |
| Visio 连接线 | 保持激活（另有显式的「保持工具」开关） |
| Fusion 360 / Onshape 草图 | 直线工具保持激活 |
| AutoCAD | 命令结束；`Enter`/空格重复上一条 |
| Figma | 工具回到「选择」 |

分野不在「谁抄谁」，而在**这个工具是干什么的**：接线是**成批**的活儿，一张图连二三十条；
AutoCAD 是通用绘图，画一个东西然后去调它。我们的场景是前者。

**判据用既有那条——用户画完之后想对它做什么**（当初判定 `RECTANGLE` 该产出矩形物料的同一条）：

- 导线画完，九成是接下一条 → **重启**
- 矩形画完，九成是填色、调圆角、往里塞东西 → **结束**

因此 `WIRE` 与 `ARROW` 声明重启，`RECTANGLE` / `CIRCLE` / `ARC` 不声明。这个不对称是设计。

**今天实际的样子里有一处缺口。** 提交即结束命令，而「空 Enter 重复上一条命令」**只在命令行
里生效**：图面上空闲时按 `Enter` 直接不接管。而画完最后一点时焦点正在图面上——**那条重复
机制在手所在的位置够不着**，每画一条得按一次 `W`。这一条先单独修掉，它与要不要重启无关。

**顺带的发现：画完不选中新建的对象。** 这削弱了「矩形画完要马上调它、所以命令该结束」这条
理由——反正还得再点一下它。它不推翻上面的不对称（意图仍然不同），但值得记下来：如果将来
改成「画完即选中」，重启对矩形就更没有位置了。

**重启之后 `Escape` 分两级**，与几何编辑里的两级同构：

- 当前这一条**已经取过点** → 放弃这一条，命令留着
- 当前这一条**一个点都没取** → 退出命令

不分级的话，`ARROW` 改成连续取点之后 `Enter` 变成「结束这一条并开始下一条」，唯一的退出只剩
`Escape`，而它此刻的含义（放弃整条命令）会把用户刚画一半的东西一起扔掉。

## 三、逐图形规格

### 3.1 汇总

「拖动」一列写的是**一次按下-拖-松手放几个点**；命令结不结束由「取点」一列的数量决定
（2.3），不由拖动决定。

| 命令 | 取点 | 拖动 | 动态输入 | 关键字 | 落地 |
| --- | --- | --- | --- | --- | --- |
| `LINE` | 连续 | 2 点，命令继续 | polar | `C` 闭合（新）、`U` 放弃上一段（新） | 逐段，每段一个 Entity |
| `PLINE` | 连续 | 2 点，命令继续 | polar | `C` 闭合（新）、`U` 放弃上一点 ✅ | 结束时提交一个 Entity |
| `RECTANGLE` | 2 | 2 点，取够即结束 | cartesian（宽、高） | — | 一次，闭合四顶点多段线 |
| `CIRCLE` | 2 | 2 点，取够即结束 | radius（**单字段**）；`D` 后 diameter | `D` 直径 / `R` 半径（新） | 一次，`sweep` 360 的弧 |
| `ARC` | 3 | ❌ 只支持点击 | polar，从**上一个点**起算 | — | 一次 |
| `ARROW` | 连续 | 2 点，命令继续 | polar | `U` 放弃上一点（新） | 结束时提交一个 Entity，带端点 marker |
| `WIRE` | 2 | 2 点，取够即结束 | polar | — | 一次，两端按取点来源绑定端口 |

### 3.2 各命令细则

**LINE（`L`）——已确认，作为其余六条的样板。** 单键 `L` 即启动，不要确认键；连续取点，
逐段落地，每段是独立 Entity，因此画一段场景树就多一行。一次拖动放两个点而**不结束命令**
（2.3）。全程按 2.5 的样子显示长度与角度，可键入、可锁定。

新增两个关键字：`C` 闭合（再画一段回到起点并结束）、`U` 放弃上一段。**`U` 与撤销的关系已
拍板：`LINE` 逐段落地，因此它的 `U` 就是一次文档撤销**，不是会话内回退——它与 `PLINE` 的 `U`
同名而机制不同，这一点要写进各自的注释，否则下一个人会试图合并它们。

**PLINE（`P`）——已确认。** 启动、连续取点、拖动放两点且命令继续、动态输入、结束与放弃键
**与 `LINE` 逐字相同**。只有三处不同：

1. **落地时机**：攒到结束才提交**一个** `Curve`（`kind: 'polyline'`）。这不是实现细节，是
   用户直接看得见的差别——画五段，`LINE` 给出五行场景树、点一下只选中一段、撤销一次退回四段；
   `PLINE` 给出一行、点一下整条选中、撤销一次整条没了。
2. **`U` 是会话内回退**，不是文档撤销（此刻文档上什么都还没有）。与 `LINE` 的 `U` 同名而机制
   不同，这是有意的：对用户来说两次 `U` 看起来做同一件事，差别只在撤销栈里。
3. **屏幕上多一条「已确定的折线」**。`LINE` 画到第三点时前两段已经是文档里的实线；`PLINE`
   画到第三点时前两段**还不存在**，必须由会话自己画出来（实线预览），否则用户只看到一条孤零零
   的橡皮筋，不知道自己画到哪了。当前段的长度/角度从**上一个顶点**起算，不是从起点。

关键字：`C` 闭合（置 `closed: true`，补上收尾那一段并结束——闭合本身就是结束信号，之后不再
等下一个点）、`U` 退回上一个点 ✅ 已有。`Escape` 仍然丢弃整条——它是唯一的放弃入口，而画错
一半想扔掉比画完更常见。

**丢掉 AutoCAD PLINE 的四个选项**（它的提示是 `[圆弧(A)/半宽(H)/长度(L)/放弃(U)/宽度(W)]`）：

| 丢掉的 | 理由 |
| --- | --- |
| 圆弧(A)——一条多段线里混弧段 | **协议缺口不是工作量**：顶点没有 bulge 字段，弧段在当前 `Curve` 协议里根本表达不出来，补它要动 Schema、归一化、命中、捕捉、渲染五条路径。AGENTS.md 已记录 |
| 宽度(W) / 半宽(H) | 线宽是 Renderer prop，属性面板改，不需要在画的过程中切 |
| 长度(L)——沿上一段方向续一个长度 | 动态输入的直接距离输入严格更强：方向锁住后打一个数就是它，而且不限于「沿上一段」 |

**`LINE` 与 `PLINE` 都留，但工具栏只放 `PLINE` 一个按钮**（用户 2026-08-29 拍板，方案 C）。
两条命令的交互几乎一模一样，唯一差别是落几个 Entity；把两个几乎一样的按钮并排摆出来会让不熟
CAD 的用户在按钮上做一次他还没有依据去做的选择。命令行两个词都认，`L` 对 CAD 用户的肌肉记忆
因此不失效。判据与「工具集只保留没有别的入口的动作」同源：入口的数量按**用户此刻分得清吗**
来定，不按命令的数量。

**RECTANGLE（`R`）——已确认。** 两个对角点，取够即结束。动态输入用 **宽 × 高** 而不是
长度 + 角度：矩形的自然量纲是两条边长，给用户一个对角线长度和一个 37°，他还得自己开根号才
知道这个框多宽。AutoCAD 全程只有一套「长度/角度」字段，我们的字段由命令声明，没有必要跟着
受这个限制。`Shift` 约束成正方形。**没有角度弧**——矩形轴对齐，角度恒为 0。

**产出的是矩形物料，不是 `Curve` 折线**（用户 2026-08-29 拍板，方案 B）。判据是**用户画完之后
想对它做什么**：画一个矩形外框，下一步九成是给它填色、调圆角、往里塞东西——这些 `Curve` 折线
全都做不到或做得很别扭。「矩形是四顶点的闭合多段线」那条判断管的是 `Curve` 协议内部要不要
另立 `rect` 类型，它**没有**说 `RECTANGLE` 命令必须产出 `Curve`。真需要一个纯几何四边形轮廓
时，`PLINE` 画四点按 `C` 就是，不缺入口。

视觉规格见 [`docs/mockups/drafting-rectangle-dynamic-input.html`](./mockups/drafting-rectangle-dynamic-input.html)。
与画线**同一条规则**（框落在自己那条标注的中点上、标注在框后断开），只是标注从一条变成两条
正交的。三处新增：

- **标注摆在靠近光标的那两条边外侧**，反向拖时换边。永远摆在上边和右边实现最简单，但从右上
  往左下拖时标注会跑到图形另一头，视线要来回跳。
- **活动字段里的数字整体选中**，打第一个字符即替换全部。这条画线那一节也适用，是当时漏写的。
- **`Tab` 在换焦点的同时锁住它离开的那个字段**（AutoCAD 的行为），因此「拖个大概的宽度 →
  `Tab` → 打一个精确的高度」是两步。

丢掉 AutoCAD 的 `[倒角(C)/标高(E)/圆角(F)/厚度(T)/宽度(W)]` 与 `[面积(A)/尺寸(D)/旋转(R)]`
全部八项：圆角/倒角是与 PLINE 弧段同一个 bulge 协议缺口；尺寸(D) 被动态输入严格覆盖；旋转(R)
画完再转（`rotation` 是独立且可打关键帧的属性）；面积(A) 罕见；标高/厚度是 3D 遗产；宽度(W)
是 Renderer prop。

**CIRCLE（`C`）——已确认。** 圆心 + 半径点，取够即结束。视觉规格见
[`docs/mockups/drafting-circle-arc.html`](./mockups/drafting-circle-arc.html) 第 01–04 格。

动态输入**只出一个框**（半径），不画角度弧，`Tab` 不接管，没有锁定这一档——理由见 2.4。
新增 `D` 关键字切成直径、`R` 切回（画元器件时端子直径是标注直接给出的量，少一次心算）。
切换一次改三样：提示文本、参数化、列出的关键字；少改任何一样，屏幕上都会出现两句互相矛盾
的话。**`D` 只作用于本次会话，不跨命令记忆**：AutoCAD 记住上一次的选择，代价是这条命令有了
一份看不见的状态——用户过两天回来，同一条命令问的问题变了，而屏幕上没有任何东西解释为什么。
改起来是一行，真需要时再改。

被量的那一段是**圆心 → 光标**；`D` 时换成**整条直径**（对径点 → 光标），框带 `⌀` 前缀。
同一个框换一个量，标注线跟着换，用户一眼看出自己在打哪个数。

AutoCAD 还有 `2P`/`3P`/`TTR`，暂不做——等有人真的需要再加一条会话分支。

**ARC（`A`）——已确认。** 三点定弧，保持现状。视觉规格见同一份交互稿第 05–08 格。
AutoCAD 有十一种起算方式，三点式覆盖鼠标绘制的绝大多数。三点共线时以 `rejected` 表达并收回
第三点，用户直接重取——这条已实现且是对的。

两个 `polar` 步从**上一个点**起算：第二点从起点，第三点从途经点，与 `LINE` 的「上一个点」
是同一条规则。**取两点时预览画的是一条直线而不是一段弧**：两个点定不出弧，画一段弧要替用户
猜一个半径，用户会以为形状已经定了，而第三个点会把它整个换掉。第三步声明被量的那一段
（途经点 → 光标），因为那时预览换成了弧，这一段不在弧上。

**不给第三步加一个只读的半径框**：半径对弧确实有意义，但那一步已经有两个数在跟着光标动了，
第三个没有输入语义的数只是噪音。真要读半径，画完在属性面板里看。

**ARROW（`X`）——已确认，改成连续取点。** 这是对既有实现的一处修正。

今天它取两点就结束，理由写的是「一支箭头只有一个头」。**那句话是对的，但它证明的是另一件事**
——它禁止的是像 `LINE` 那样**逐段落地**（画三段会得到三个各自带头的箭头），而不是禁止多段。
一条多段线只落**一个** Entity、marker 在最后一个顶点上，那句话照样成立。

它现在是两点，真实原因是**跟 `WIRE` 共用了会话工厂**；而 `WIRE` 两点的理由（折线导线的价值
几乎全部来自自动路由，路由还没有）**传不到 `ARROW` 身上**——引线的那个弯是用户手画的，不等
任何东西。接线图上的引线九成要拐一下才能绕开元器件，两点箭头等于逼用户画完再拖顶点。

因此 `ARROW` 走 `PLINE` 的取点模式（连续取点、攒成一个 Entity、回车结束），**但没有 `C`**：
闭合的箭头说不出是什么意思。它与 `LINE` 的差别是同一句老话——落几个 Entity。

**数据与渲染那一层已经通了，不需要任何改动。** `markerEnd` 加在几何元素上、不按 kind 分支，
而 SVG 的 marker 本来就作用于 `<polyline>`。缺的只有命令那一头。

推论：**`ARROW` 与 `WIRE` 不再共用会话工厂。** 那条共用规则的前提写得很明白——「两者的取点
逻辑**逐字相同**」；前提不成立，规则自己就化掉了。

**WIRE（`W`）——已确认，维持两点。**

`WIRE` 与 `ARROW` **根本不在一个维度上**：`ARROW` 改的是外观（`markerEnd` 一个 Renderer
prop），`WIRE` 改的是**数据关系**（一个 `Wire` Component，记「这一端绑到了哪个端口」）。
判据是既有那条——命中与捕捉路径读的字段必须是文档级契约，而端点位置要参与求解。

| | `ARROW` | `WIRE` |
| --- | --- | --- |
| 落地成什么 | `arrow` Preset（`markerEnd: 'arrow'`） | `curve` Preset（**与 `LINE` 同一个**）+ `Wire` Component |
| 端点坐标谁说了算 | 用户画的 | **端口**——布局 Runtime 每帧从端口位置解算，不存坐标 |
| 挪一下符号 | 原地不动 | 那一端**跟着走** |

**两端都没绑上时 `Wire` 根本不写**：那条「导线」与一条 `LINE` 是逐字相同的 Entity。反过来说，
`WIRE` 唯一多出来的东西就是那个绑定——这也是它为什么必须维持两点：一条导线只有两端。

**不做手画拐点的折线导线。** 折线导线的价值几乎全部来自自动路由（避开元器件、走线槽），而
路由还没有。手画的拐点在挪一下符号之后就得重画，比直线还糟——直线至少会自己跟过去。

**激活是三个等价入口 + 一个前提。** 入口：单键 `W`、工具栏按钮、命令行敲 `WIRE`/`WI`/`W`
（2.1）。前提是**目标 Entity 上得有 `Ports`**——它是可选 Entity Component，不是某类物料自带
的；组件实例从组件根 Frame 读，声明一次全部实例都有。

绑定**来自取点时记下的来源，不是事后按坐标反查**：反查会让一条恰好路过端口的普通线莫名其妙地
绑上，而那个绑定在屏幕上完全不可见——用户挪一下符号，一条他以为是装饰线的东西跟着跑了。因此
`WIRE` 绑、`LINE` 不绑，**键入的坐标永远不绑**（它没有来源）。

**端口捕捉排在端点之前**（`port > endpoint > midpoint > center > quadrant`）：端口几乎总是画
在符号线段的端点上，端点若在同等距离下胜出，用户会画出一条**像素级正确但没有绑定**的导线。

**顺带发现的一处缺陷（两条命令都中）**：它们今天用的是 `specifyNextPoint`，而那句文案写着
「指定下一点（**回车结束**）」——对取够点自己就提交的命令，这句话在说一件那里做不到的事。
规范里已经有这条（「取够点自己就提交的命令 MUST NOT 带这句提示」），实现漏了。`WIRE` 的第二
步应当是 `specifyEndPoint`；`ARROW` 改成连续取点之后反而**变得正确**——它那时确实要回车结束。

**动态输入**：两条都是第一点 `absolute`、其后 `polar`，与 `LINE` 逐字相同，无新增。

**视觉规格已确认**，交互稿：[`docs/mockups/drafting-wire.html`](./mockups/drafting-wire.html)。
箭头那一半与 `LINE` 共用，没有新东西；以下全部是导线独有的。

**端口靠近时整组显现。** 任何一个端口进入捕捉靶区，就把它所属符号的**全部**端口一起亮出来
（空心青圆）。

- **不常驻**：一张接线图上几十个与几何无关的点会把线和符号淹掉。它们回答的是**取点当下**的
  问题，因此在取点当下才出现；想确认「这个符号有哪些接线点」，Inspector 是那个入口。
- **不只亮最近的那一个**：继电器的端子只隔几个像素，只亮一个的话用户看不出旁边还有两个，
  也就无从选择——而他此刻正要在它们之间选。**端口是一个闭集**，这是它与端点、中点这类几何
  特征点最大的不同：那些是算出来的，端口是符号作者声明的，因此「有哪几个」本身就是信息。

**接线状态只在选中那条导线时显示**：已绑端画实心青点，自由端画空心青环（虚线）。两端一眼
对比，而平时图面上一个记号都不留。

- **自由端不常驻标出**：它**不是错误**——用户可能正画到一半。给每条未接完的线常驻一个记号，
  画到中途的图面会长满疹子。
- **失效绑定相反，常驻**（danger 色断口，该端保留作者几何）：那是缺陷，不该等到用户选中才
  显形。「还没接」「接错了」「接的东西没了」三者必须可区分，这是既有那条判断的又一次应用。
- 不显示的代价是明确的：不选中就看不出接没接上，而唯一的替代判据是「挪一下符号看它跟不跟」
  ——那是破坏性的验证。

**三个记号回答三个不同的问题，因此是三种颜色**：端口青（这里有一个接线点）、捕捉橙（吸上了
没有）、accent 蓝（这是选中的 / 将要产出的）。三者**可以同时有答案**（光标停在一个端口上、
吸住了、而这条线正被画着），所以不能共用一个颜色。这与「捕捉标记不借 `danger`、也不用
accent」是同一条判断的第二次应用。

**连续绘制见 2.9**：`WIRE` 提交后重启自己。

### 3.3 从盒物料下钻到自由几何（`EXPLODE`，待确认）

选 B 之后必然要回答的一个问题：画出来的是盒，想改成梯形怎么办。

**用户的设想是「双击矩形即进顶点编辑，像 Blender 的盒子双击进顶点编辑」。方向对，入口错。**

**Blender 的类比不成立，因为它只有一种几何表示。** Blender 的 cube 从一开始就是八顶点的
mesh，Object Mode 只是不显示顶点；Tab 进 Edit Mode **没有转换任何东西**，退出来还是同一个
mesh object，一点信息都没丢。我们选 B 恰恰是因为承认了**两种表示各有各的能力**——盒能填色、
圆角、进 Auto Layout；折线能自由改形。一旦第一个顶点被拖出矩形，HTML 盒就画不出来了
（`border-radius` 在梯形上无意义，背景渐变、内容盒同理）。因此在我们这里，「进入顶点编辑」
必然伴随一次**有损的类型转换**，而 Blender 那一步是无损的。

**挂在双击上有三个问题，第三个是决定性的：**

1. **双击今天是无副作用的。** 它进的是一个可随时 `Escape` 退出、什么都没变的会话（文字编辑、
   几何编辑）。让它在矩形上变成一次文档写入 + 类型变更，等于同一个手势在不同对象上做性质
   不同的事，而用户在按下去之前分不出来。
2. **会静默丢东西，而双击没有地方说这件事。** 圆角（bulge 协议缺口）与非 solid 背景（曲线
   只画 `solid`）都会丢。撤销能救回来，但用户要先发现丢了。
3. **不转换的话，四个顶点夹点和盒手柄做的事一模一样。** 矩形的四个顶点**恰好就是**它包围盒
   的四个角，因此在「还是矩形」的前提下拖顶点 ≡ 拖盒角手柄，逐像素相同。这条我们已经为曲线
   写下过（「曲线没有第二套端点选区 UI——两点直线的端点就在包围盒的对角」），矩形是它更强的
   版本。真正有价值的操作（拖成梯形、加第五个顶点、删成三角形）**结果都不再是矩形**，因此
   都必然要转换。

**也拒绝「延后转换」**：双击无副作用地进去，第一次真正改形状时才转换。转换点说不清（只拖一个
轴仍是矩形，转不转？），而且只是把「静默丢东西」从双击那一刻推迟到拖动那一刻，没有消除它。

**正确的形状是一条显式命令**——AutoCAD `EXPLODE`、Illustrator「转换为路径」、Figma「Flatten」
都是这么做的：有名字、可撤销、能在提示里说清会丢什么。而转换之后用户想要的手感**白拿**：出来
的是 `Curve` Entity，双击即进几何编辑，那条通道已经建好，一行不改。完整流程：

```
R 画矩形（物料，能填色圆角） → 想改形状 → EXPLODE → 双击 → 顶点编辑
```

比用户设想的多**一步**，换来的是「双击永远无副作用」这条不变量不被打破。

**丢什么是可以逐条点名的**（Rectangle Preset 没有 `Hierarchy`，因此没有子级要安置）：

| 字段 | 转换后 |
| --- | --- |
| `Appearance.backgroundPaint`（`solid`） | ✅ 无损——曲线填充复用的就是这个字段 |
| 边框颜色/宽度 | ✅ 映射成描边 Renderer props |
| `LayoutItem` | ✅ 原样保留，仍参与 Auto Layout |
| `borderRadius` | ❌ 丢——顶点没有 bulge |
| 非 `solid` 背景（渐变、图片） | ❌ 丢——曲线只画 `solid` |

**顺带补一个入口**：`VERTEX` 命令在选中矩形物料时，用它已有的 `rejected` 通道说明「这个对象
不是曲线，先 `EXPLODE`」。「三种拒绝必须互相可分」那条规则正好在这里用上——双击矩形什么都
不做（保持现状），但敲 `VERTEX` 会告诉你该怎么办。

**反方向（闭合四顶点折线 → 矩形物料）暂不做**，没有已知需求。

## 四、从 AutoCAD 拿什么、丢什么

### 4.1 留下（这些是任务需要的）

- 对象捕捉与优先级（`port > endpoint > midpoint > center > quadrant`）
- 键入坐标三种写法（`x,y` / `@dx,dy` / `距离<角度`）与「键入的坐标不被任何吸附改写」
- 命令的多步取点、关键字、`rejected` 不结束会话
- `Escape` 取消 / `Enter` 结束 / 右键等同 `Enter` / 空 `Enter` 重复上一条
- 逐段落地与整体落地两种提交语义（`LINE` vs `PLINE`）
- 命令行作为加速器与坐标入口
- 角度约束（正交与极轴，三态互斥，默认极轴）

### 4.2 丢掉（这些是 CAD 的历史包袱）

| 丢掉的 | 理由 |
| --- | --- |
| **空格/回车确认命令名** | 那个按键不携带任何信息。改单键快捷键 |
| **`acad.pgp` 别名文件** | 别名写在命令定义里，不给用户一个要维护的配置文件 |
| **F11/F12（对象捕捉追踪、动态输入）** | 追踪要先有「已捕获的点」这个概念；动态输入常驻，不需要开关 |
| **对象捕捉设置对话框（每种捕捉一个勾）** | 我们的捕捉优先级是固定的，一个总开关就够 |
| **极轴的附加角表** | 增量角是「一族」、附加角是「一条」，区别真实但眼下没有消费者。见 2.8 |
| **UCS 用户坐标系** | 场景（Frame）已经是坐标原点，够了 |
| **模型空间 / 布局空间** | 交付物是固定尺寸大屏，只有一个空间 |
| **图层** | 已由 DXF 导入决策否掉：图层在导入期求值掉，不进文档 |
| **`PEDIT` 式大杂烩命令** | 已明确拒绝。一个词做一件事 |
| **必须先选对象再执行** | 已支持两种次序，保持 |

## 五、协议改动清单

按包列出这套交互需要动的地方。**`@compose-ui/commands` 零运行时依赖、对效果类型泛型的性质
不变**。

1. **`@compose-ui/commands`** ✅ — `ComposeCommandPrompt` 新增可选 `fields`（五种参数化）与
   `measured`。**没有「各字段的标签与是否可编辑」**：标签是呈现层的事，而「是否可编辑」这个
   维度被单字段参数化取代了——不影响结果的字段根本不出框，而不是出一个只读框（2.4）。
2. **`@compose-ui/core`** ✅ — 五种参数化的正反算；角度约束（正交 / 极轴）与命中射线上报。
   **裸数字没有做进 `parseComposeCoordinate`**：它缺的是方向，而方向是活动字段之外那个分量
   此刻的值——那是呈现层的状态，不该进 `core` 的语法层。它落在 Stage 的提交路径上。
3. **`@compose-ui/stage`** ✅ — 动态输入覆盖层、追踪射线；字符转交（初稿一度判断不需要，
   见七的说明）。
4. **`@compose-ui/stage-engine`** ✅ — 各命令声明自己的字段；`LINE` 加 `C`/`U`，`PLINE`
   加 `C`，`CIRCLE` 加 `D`/`R`。
5. **`@compose-ui/interaction-kernel`** ⏳ — 仲裁器支持「暂缓认领」，让取点与拖动能共存
   （2.3 的已知障碍）。这是唯一动到内核的一项，**尚未做**。
6. **快捷键表** ✅ — `DEFAULT_STAGE_SHORTCUTS` 补七条绘图命令；命令定义补三个单字母别名。
7. **`@compose-ui/editor`** ✅ — 工具栏的正交与极轴按钮、增量角下拉；角度约束由 controller
   持有（工具栏要画按下态，事实来源只能有一份）。初稿漏了这一项，因为当时角度约束还没打算
   上工具栏。

## 六、待确认的决策

实现地图之前需要你拍板的，按影响面排序：

1. **单键快捷键占用哪些字母** —— 表在 2.1。`X` 给箭头是因为 `A` 被弧占了，如果你觉得箭头
   比弧常用，可以对调。
2. **矩形的动态输入用「宽 × 高」而不是「长度 + 角度」** —— 我认为这是对的，但它让不同命令
   的动态输入字段不一样，与 AutoCAD 全程「长度/角度」不同。
3. **制图几何的默认描边色（`#d8e2f1`，近白）** —— 它是按**编辑器画布的深底**选的，而
   **场景背景默认透明**（理由：「场景背景是会被发布出去的真实像素，由用户决定用什么底」）。
   两条判断不一致：线的颜色同样是会被发布出去的真实像素，却跟着编辑器的底走。落到浅底页面上
   它接近隐形。三条路：(a) 承认大屏九成是深底，维持；(b) 换一个深浅两种底都读得出来的中性色，
   代价是在深色画布上不如现在醒目；(c) 让 Preset 的初值跟随所属场景的背景——但背景透明时没有
   可跟随的东西。它影响的是**全部**制图几何（`DEFAULT_CURVE_PROPS` 是共用的），不只是导线。

   **「导线的颜色」这一半已经拍板：红（`#ff3b30`）+ 线宽 2，见 `DEFAULT_WIRE_PROPS`。** 一次
   接线图里红 = 合闸/带电，而储能、光伏这类图画的是**正常运行**的系统，整条一次回路本来就是
   带电的——实机上通篇是红。绿正好相反（分闸/停电），照抄 PCB 原理图会得到反的答案。剩下的仍是
   上面那条：**普通几何**的近白默认色该取什么，它与导线无关。
4. **`EXPLODE`：从盒物料下钻到自由几何** —— 选 B 之后需要一条「矩形物料 → `Curve` 折线」的
   显式转换命令，见 3.3。它是本 SDD 之外的一条新命令，要不要做、什么时候做。

已拍板、不再列为待确认的：**拖动不结束命令**（2.3）、**`LINE` 的 `U` 就是一次文档撤销**
（3.2）、**动态输入的全部视觉几何**（2.5）、**角度约束的三态与默认值**（2.8）。

**「字符转交」是必须做的，初稿判断错了。** 当时的理由是「输入端就是命令行那一个缓冲，键入的
字符本来就到得了活动字段」——错在**焦点**：用户点下第一个点之后焦点在图面上，命令行收不到
任何东西，`Tab` 与数字都掉在地上。这是 2.2 表格第三行，用户走一遍就撞上了。已随
`add-drafting-dynamic-input` 补上：数字与 `@ , . < -` 转交命令行并聚焦，字母不转交（那是
关键字与命令名，转交过去会把每一次误触都变成命令行里的垃圾）。

A、B、E 是低风险的即时收益，F 是唯一需要动内核的。C+D 合起来才是你截图里那个功能——分开做
的话，只有 C 用户会问「这个数字能改吗」，只有 D 没有东西可显示。

**剩下三刀，都不阻塞画图**：F（点击与拖动共存）要改仲裁器的认领时机；`Shift` 约束正方形要给
`ComposeCommandInput` 加修饰键；`EXPLODE` 还在待确认（3.3）。**极轴默认开着之后，F 的收益又
小了一截**——拖一下的价值本来就是「快速定一个大概的方向和长度」，而这两样现在一个由极轴给、
一个由动态输入给。

**默认开极轴对既有端到端用例零改动。** 提案里把这条标成了最大风险，实际 196 条全绿：绝大多数
用例的落点本来就是轴对齐的，极轴把它们吸到的正是它们已经在的位置。只有两条量夹点数学的组件
测试要显式关掉（`angleConstraint: 'off'`）——那是「依赖自由角度的用例必须显式关掉角度约束」这条
纪律的第一批实例。
