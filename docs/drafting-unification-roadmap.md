# 绘图统一路线图：CAD 融入页面世界

## 文档定位

本文是「把 CAD 能力融入页面编辑器」的**纲领性路线图**，用于串联多个 OpenSpec 变更，不代表
当前已经稳定的公共 API。每一步都是一个独立可发布、可回退的 OpenSpec 提案；**路线图是方向，
提案才是权威**——每刀的提案只在轮到它时写，吸收前面各刀实现时发现的事实；本文在每刀完成
后回填实测结果与被推翻的预判。

本文**接替** `cad-document-roadmap.md` 的后续方向：那条路线（独立 CAD 文档类型，步骤 1–9）
已经走完并交付了全部图元数学、捕捉、命令行与 DXF 解析——这些原样存活；被本路线替换的是
「独立文档类型 + 独立编辑外壳」这个壳。

**2026-08-23 大改**：用户校正了两条前提——「用户不熟 AutoCAD」与「绘图和设计只该差一套工具」
——路线因此重排。被推翻的判断集中记在下方同名小节，不要重提。

## 产品意图

实施工程师画一张主接线图：**刀闸是他自己画出来的普通对象**；给它刻角度关键帧，再由页面
脚本按遥信驱动。这是 SCADA/HMI 组态，不是绘图工具。

分工只有一条轴：

```
怎么画        取点 / 对象捕捉 / 正交 / 键入坐标 / 命令四态     ← 这一层借鉴 AutoCAD
画出来是什么   普通页面 Entity，和拖出来的完全同类              ← 这一层没有 CAD 的份
```

**用户不熟悉 AutoCAD**（2026-08-23 由用户指出）。因此判据是**这个任务需要什么**，不是
「AutoCAD 怎么做」：精确取点、捕捉、正交、键入坐标是任务需要的，留；累加选择集、方向敏感
框选、裸滚轮缩放是纯照搬，去。

命令行不是「CAD 的命令行」，是**命令面板顺便带了个输入框**——面板是主入口（搜得到、看得懂），
命令行是加速器（知道名字的人敲两个字母）。

## 已定的决策

| # | 决策 | 后果 |
| --- | --- | --- |
| 1 | **没有第二个世界**：删除 CadDocument / `.cad.json` / CAD 标签页 / `cad-canvas` | 曲线成为页面词汇；有消费者的数学下沉进 `core`、外壳与无消费者的部分一起消亡（12b 已交付） |
| 2 | **曲线保留盒**：`LayoutItem` + 盒局部几何 | 移动/动画/树/预览零改动可用；不需要 v8 |
| 3 | **命中判据按 Entity 而不是按画布** | 盒物料按矩形，曲线按点到几何距离；canvas-kit 边界不变 |
| 4 | **刀闸是画出来的普通对象**；成规模时做成组件、动画刻在组件里，差异走 `instanceOverrides` | 不引入片段/状态机 |
| 5 | **无限图纸消亡**：图画在场景（Frame）里 | 交付物本来就是固定尺寸大屏 |
| 6 | **不写迁移器**（无线上 `.cad.json` 资产） | 与删 Page Slot 同一条判断 |
| 7 | **没有绘图模式**（2026-08-23） | 模式只剩动画开关；见下 |
| 8 | **一套物料、一个概念**（2026-08-23） | 没有「绘图的矩形」和「设计的矩形」，只有矩形 |
| 9 | **同一个工具兼容两种下笔方式**（2026-08-23） | 拖着画（快）与取点/键入（精确）是同一个按钮的两种用法 |
| 10 | **模式只能是对象作用域**（2026-08-23） | 几何编辑 / 文字编辑 / 实例下钻是同一个模板；「整块画布换套规矩」的模式不再有 |
| 11 | **绘制与顶点编辑是同一个模式**（2026-08-23） | 都在取点，因此共用光标、点输入管线与吸附；见决策 11 |

### 决策 7：为什么没有绘图模式

绘图模式原本提供四样，逐条追问之后没有一样需要用模式来承载：

| 它提供的 | 收敛后 |
| --- | --- |
| 工具集 | 并进同一条工具栏——真正新增的绘制工具只有**弧**和**多段线**两个 |
| 十字光标 | **跟着工具走**（Stage 本来就是这么做的），另加两个偏好：始终十字、十字线长度 |
| 命令行 | 常驻/召唤，不属于任何模式 |
| 累加选择 + 方向敏感框选 | **去掉**（判据见产品意图） |

最有力的证据是**两套工具本来就重叠**：矩形、圆、线在两个模式里各有一个入口，差别只在产出
什么对象，而用户压根不该关心这个。为两个按钮维护一整个模式，账算不过来。

### 决策 8：一套物料

一个形状一个按钮、一个物料。区别不在「谁画的」，在**形状能不能由盒决定**：

| 形状 | 盒能决定它吗 | 存几何吗 |
| --- | --- | --- |
| 矩形 / 椭圆 / 正多边形 / 单段直线 | ✅ | 不用 |
| **弧 / 多段线 / 任意路径** | ❌ | 要 |

下面一行带 `Curve` Component。**这不是两个概念**——是同一个概念（带盒的 Entity）加一个可选
Component，正是 ECS 本来的样子。用户看不出区别：场景树、属性面板、动画、布局全都一样。

**所有形状都参与 Auto Layout。**这要求盒能独立于几何变化，与现行不变量「盒尺寸是几何的
派生」相反——机制是给 `Curve` 的 SVG 加 `viewBox`（`shape/` 物料现在就是按百分比画的，天然
参与布局，证明这条路走得通）。代价是**命中与捕捉必须应用同一个盒→几何变换**，漏掉就会再次
出现「画出来的和点得中的不在一处」，那是本仓库反复踩到的那一类缺陷。

### 决策 10：模式只能是对象作用域

刚删掉绘图模式又引入几何编辑，看起来矛盾，其实不是同一类：

| | 绘图模式（已删） | 几何编辑 / 文字编辑 / 实例下钻 |
| --- | --- | --- |
| 作用域 | 整个编辑器 | **一个对象** |
| 生命周期 | 切进去住在里面 | 双击进、Esc 出 |
| 改什么 | 工具栏、选择语义、框选、光标 | 只改「这一下点击是取点还是选中」 |

编辑器本来就有两个同形状的东西（双击进文字编辑、双击下钻进实例），没人觉得它们让人困惑，
因为进出边界清楚、作用域是一个对象。判据因此写成一句：**模式必须是对象作用域且有明确的
进出**，不能是「整块画布换套规矩」。

唯一的例外是动画开关——它改的是拖动结果落在哪里，是真正的全局模式，也只此一个。

### 决策 11：绘制与顶点编辑是同一个模式

一个「几何编辑」模式，三个入口：

```
入口 1   双击一个几何对象        → 编辑它的顶点
入口 2   选一个绘制工具          → 新建几何（画完停在模式里，可以接着调）
入口 3   命令行敲 LINE / ARC …   → 同上
入口 4   命令行敲 VERTEX         → 编辑既有对象的顶点（步骤 13 补齐）

模式内   光标 = 十字星
         取点走点输入管线（顶点这一半由步骤 13 接齐：按下夹点即开一条一点会话）
         盒手柄消失
退出     Esc / 点空白 / 切工具（点亮了夹点时，第一次 Esc 先熄灭它）
```

理由是**它们本来就是同一件事——都在取点**。分开做意味着两套光标规则、两套取点接线。合并
之后光标规则从「跟着工具走」收紧成更准的一句：**在取点就是十字星**。

Figma 是同一个模型：钢笔工具与矢量编辑是一回事。

两处随之确定：

- **进模式后隐藏盒手柄**。矩形的右下角手柄与右下角顶点几乎在同一像素上，两个含义（改盒 /
  改几何）叠在一起。Figma 在矢量编辑时同样隐藏包围盒。
- **矩形/椭圆没有顶点**（决策 8：它们由盒决定，不存几何）。双击它们仍**进入**几何编辑，拖动
  某个角时**升格成多段线**——与仓库既有的 `promoteComposeEntityToFrame`（「升格只做一件事」）
  是同一个手法。不进的话，双击在不同形状上行为不一致，用户学不会；而按决策 8 升格不丢任何
  能力（照样参与 Auto Layout）。

### 点输入管线：对齐吸附并轨

几何编辑要求特征点捕捉与 Figma 式对齐参考线**同时生效**。次序定死并**命中即短路**：

```
键入坐标  >  特征点捕捉(点)  >  对齐参考线(轴)  >  正交  >  网格
```

**点压过线**：在端点容差内就落到端点；不在，才考虑「与旁边对象的边对齐」。键入的坐标不被
任何一级改写，这条不变量不动。

`snapCandidates` 返回 `{ axis, value }` 的参考**线**，`findStageFeaturePoint` 返回二维**点**
——形状不同，是姐妹查询，因此并轨的做法是**串成两级**而不是合成一个函数。

## 被推翻的判断

记在这里以免重提。

| 曾经写下的 | 为什么错 |
| --- | --- |
| 「切换发生在模式层」「绘图模式换手势语义」 | 绘图模式提供的四样没有一样需要模式承载；见决策 7 |
| 「手感学 AutoCAD：命令行驱动、左窗口右交叉框选」 | 用户不熟 AutoCAD。任务需要的留，纯照搬的去 |
| 「绘图的矩形是描边多段线、设计的矩形是填充盒」 | 把「怎么画」和「画出来是什么」混在一起造出来的重复概念 |
| 「每实例状态无处安放」「覆盖表达不了轨道」 | `instanceOverrides` 是**七种**操作、四种改值；旧的暴露属性正是被迁移成 `set-field` |
| 「三个模式：设计 / 绘图 / 动画」 | 动画是另一根轴——它改的是**拖动的结果落在哪里**，可与任何工作区叠加。绘图不是轴，是几个按钮 |
| 「特征点捕捉与对齐吸附**不能同时生效**，两套会互相拉扯」 | 那描述的是**没有优先级**时的情形。并进同一条管线并定死次序 + 命中即短路之后不会拉扯——Figma 两套同时开，顶点赢。次序见下 |
| 「组件实例的动画绑定要写进组件文档的 `Animations.bindings`，因此撞上数组整份替换」 | 实例是宿主页面上的一个普通 Entity，而 Entity 早有逐实例的 `Bindings`。绑定放宿主侧，粒度问题不存在；已随步骤 5 交付 |
| 「命令面板与命令行是两类东西，一个是一次性动作、一个是多步会话」 | 动作是会话的退化情形，而这一档本来就在跑（`ERASE` 预选时 `prompt` 为 `null`）。两个形状是一个；已随步骤 7 交付 |
| 「不做热夹点（`GRIPHOT`）：夹点跟着预览几何走在光标底下，那个信息已经在屏幕上了」 | 那只对**拖动**成立。点亮之后夹点停在原位而光标在别处找目标点，屏幕上没有任何东西说得出「下一个点会挪哪个顶点」；多段线的若干个同形顶点尤其。拖动期仍然不做，两句话不冲突 |

**教训**：AGENTS.md 的断言是二手的，判断一条能力在不在，去看代数本身。

**作废的提案**：`add-drafting-chrome`（2026-08-23 写、同日路线重排后作废）。它假定绘图模式
会一直在，因此把「绘图工具栏」当成一块独立 chrome 来设计；决策 7 取消绘图模式之后，工具栏
不再有「绘图那一套」可换，去 `draw-line` 也并进了步骤 6。其中十字光标那部分的判断已救进
步骤 9，工具栏启动命令那条救进步骤 6，目录已删除。

## 模式与命令集

收敛后只剩一个开关：

```
动画   关 | 开     开时：拖动写关键帧、锁定原父级、底部时间线
```

命令集**不枚举模式组合**，由能力叠加：

```
基础能力   撤销、复制、删除、创建组件、对齐…      恒开
绘制能力   线 / 弧 / 圆 / 矩形 / 多段线 …          恒开
编辑命令   MOVE / COPY / ERASE                     恒开（只在命令行与面板，不占工具栏）
动画能力   打关键帧、删关键帧…                     动画=开 时
```

「当前能用什么」= 所有已开启能力的并集。一条规则同时管命令面板、命令行与工具栏——它们本来
就该是同一个集合的三种呈现。加第四种能力时不用回来重想一遍。

## 工具栏

```
[选择]  [缩放]  [旋转]                    指针与变换
────
[吸附]  [网格 ▾]                          辅助
────
[容器]  [文字]  [矩形]                    盒模型内容
[线 ▾]  [弧]   [圆]                       几何
```

**去掉**（都与既有手势重复）：框选工具（`select` 空白处拖拽即框选）、精确移动工具（`MOVE`
命令能键入精确位移，严格更强）、平移画布工具（空格/中键本来就是临时覆盖）、`draw-line`。

框选**判定模式**（窗口/交叉/方向敏感）保留为设置——模式不该偷偷改用户的设置。

| 原样存活（搬家） | 变形存活 | 消亡 |

原先写「`FLOW` → 曲线外观轨道」，实际只搬了属性，命令留在原地等 dash pattern 的单位修好。

### 步骤 1 · 曲线 Entity — `add-curve-entities` ✅

让「一条线」成为合法页面 Entity：core 可选 `Curve` Component（盒局部几何，`kind` union
留位）、几何写入漏斗（端点 → Curve + 紧包围盒同一事务）、stage-engine 距离窄相位命中、
`curve` 物料、工具栏点击添加。协议版本不变。

这一刀是整个论题的最小验证：线进场景树、能点选（点盒空角不选中）、能移动、能撤销、能预览、
能打位置与旋转关键帧——**旋转关键帧就是刀闸分/合的原语**。如果曲线在这条路上接不顺，损失
止于一刀。

刻意不做：弧/多段线/文字、绘图模式、CAD 框选语义、盒 resize 手势、端点几何关键帧。

**门槛**：五道 + 曲线纵向 e2e（添加 → 场景树 → 按距离命中 → 改端点 → 拖动 → 撤销 → 预览）
与关键帧 e2e。✅ 全绿，e2e 122 → 124。

**提案里最重要的一处判断被实测确认**：保留盒之后，场景树、属性面板、位置/旋转关键帧、
预览、撤销**没有写一行曲线专用代码**就可用——两条 e2e 正是为了钉住这一点。

**一处提案级修正（读代码才发现）**：以为 Stage 点选走 `StageSceneIndex.entityAtPoint`，
实际上 Stage 的点选是 **DOM 驱动**的（Entity 节点上挂 `onPointerDown`），`entityAtPoint`
只服务取色采样。因此「按距离而不是按盒」落在**两处**：DOM/CSS 那条（`.is-segment` +
物料的透明加宽 stroke，机制仓库里已有，line/arrow 就在用）与 `entityAtPoint` 那条。
线状判定改成按 `Curve` Component 而不是 Renderer 类型枚举。详见 change 的 design D4。

**创建入口定在 Palette 而不是 Stage 工具栏**：工具栏上的 line/arrow/circle 是拖拽绘制工具，
而本刀只做点击添加，Palette 的 `external.add` 恰好就是这条既有路径，零新代码。

**顺带修掉一处测试脆弱性**：`pointerDrop` 用 `boundingBox()` 作为按下点，而 Palette 可滚动
——新增一个 Preset 就把靠后的物料挤出视口，`boundingBox()` 仍返回坐标而按下位置已在面板之外
（ECharts 用例因此挂掉）。helper 补 `scrollIntoViewIfNeeded()`。

### 步骤 2 · 绘图模式 — `add-drafting-mode` ✅（模式外壳 + 画线）

Stage 的模式切换（会话状态，不进文档）：工具栏换成绘图工具、底部出命令行、十字线 + 捕捉
标记、CAD 选择语义（点中累加、Shift 移出、左窗口右交叉）。两点画线是第一个真手势——起点
终点各吸一次捕捉，非 100% 缩放验证。

捕捉候选从页面既有 `snapCandidates`（盒的六条参考线）扩展出**几何特征点**（端点、中点，
圆心/象限点随弧一起来）。命令行会话机、点输入解析从 `cad` 包搬运——它们不认识文档协议，
搬运成本低。

**门槛**：五道 + 绘图纵向 e2e（进模式 → `L↵` → 点两下 → 第二条起点捕捉到第一条端点 →
切回设计模式，线在场景树里、能撤销）与「命令进行中仍可平移」。✅ 全绿，e2e 124 → 126。

**命令引擎一行没搬**：`@compose-ui/commands` 本来就对 `TContext`/`TEffect` 泛型、连 `core`
都不依赖，Stage 只声明自己的两个类型。当初把它立成零依赖包的回报在这里兑现——若当时让它
认识 `CadDocument`，今天就要么改它的类型、要么写第二份。

**路线图这里写错了一处**：说「捕捉候选从既有 `snapCandidates` 扩展」。读代码后改口——
`snapCandidates` 返回 `{ axis, value }` 的参考**线**（Figma 式对齐），CAD 捕捉要的是一个二维
**点**。形状不同，是姐妹查询而不是扩展。v1 的候选因此只出曲线的端点与中点，**不出盒的角点**：
那正是对齐吸附覆盖的语义，两套同时生效会在同一次取点里互相拉扯。

**框选是白拿的**：`ComposeStageMarqueeMode` 已有 `directional`（左→右窗口、右→左交叉），
绘图模式切个默认值即可，零代码。

**一处对 CAD 优先级表的有意偏离**：CAD 里「命令取点」最高，Stage 把它排在 `pan` **之下**
——`pan` 是按住空格/中键的临时覆盖，命令进行中仍要能平移画布去看远处那个点。有一条 e2e 钉住它。

**顺带下沉两块共享物**：点输入管线与坐标语法从 `cad` 移进 `core`（两个消费者、无文档知识），
命令行组件从 `cad-canvas` 上移到 `components`（正好满足 AGENTS 的「两个第一方消费者」门槛）。
`ComposeGridSettings` 借此改成两轴独立——页面网格本就允许 X≠Y，单一步长会把一个轴吸错。
CAD 的 87 项既有用例不改一行即全绿，是这两次搬运没有改变行为的证据。

### 步骤 2b · 编辑命令与选择语义 — `add-drafting-editing-commands` ✅

`MOVE`/`COPY`/`ERASE` 与 CAD 选择语义一刀落地。两者是同一个用户故事的两半：选择语义单独
落地没有消费者，而 `MOVE` 的第一步就是「选择对象」——替换语义下点第二个对象会丢掉第一个，
三条命令全部退化成单选。

**门槛**：五道 + 选择语义 e2e（点中累加 → Shift 移出 → Esc 清空 → 切回设计模式恢复替换）
与编辑纵向 e2e（命令中选两条 → 基点 → `@60,0` → 一起走 → 一步撤销 → `E↵` 当场删 → `CO`
连续放两份）。✅ 全绿，e2e 126 → 128。

**选择语义是 Context 上的一个标记，不是第二套插件**：`StageInteractionContext.selectionMode`
（`'replace'` 默认 / `'accumulate'` 绘图），点选与框选读**同一张表**（`selection-mode.ts`）。
写成两套插件会把「命中一个 Entity 之后该做什么」复制两份，而那条路径里还有双击进文字编辑、
锁定判定、拖动接管、幽灵 ID 过滤四件与选择语义无关的事。分开写还会让「点着累加、框着替换」
这种没人设计过的组合悄悄出现。

**这一刀刻意不下沉**：`cad` 有形状一样的 `applyCadSelection`，但插件这边要的是四行分支，
而那个函数的契约里还有「内容不变时原样返回入参」——那是 `ComposeCadCanvas` 为了按引用判断
重绘加的。步骤 2 搬点输入管线是因为搬的是一整条求解；这里搬的是一个 `if`，够不着门槛。
共享的门槛是**行为会不会漂移**，不是「两处都有」。

**选择集归宿主，会话只是镜像**：CAD 的命令会话自己攒 `picked`（`selection` 输入是并入）。
Stage 不能照抄——选择集在这里已经存在（选中框、属性面板、场景树联动、Esc 清空）。会话攒第二
份，Shift 移出就只改宿主那份，用户看着两个对象被移出而命令仍作用在三个上。因此 Stage 的
`selection` 输入语义是**替换**，宿主在选择集变化时喂进当前完整选择集。这是对 CAD 会话的
有意偏离，理由是两边的选择集所有权不同。

**`MOVE` 与拖动共用的是提交漏斗，不是拖动预览**：`planMovePreview` 里的三样都是拖动特有的
——激活阈值区分「点一下」与「拖一下」（命令没有这个歧义，沿用会让小位移静默失败）、平移吸附
在命令路径上**违规**（基点与位移点已经各自过了点输入管线，再吸一次会改写键入的坐标）、落点
解析会把纯平移变成跨父级重挂载。共用点因此定在 `planTransformCommit`，产出**一条**
`entity.transform.set`，多选移动是一步撤销。

**一处实现中才发现的缺口**：累加语义下点空白**不清空**选择集（那是一次没框住东西的框选），
于是「怎么清空」在绘图模式里没有入口。补成 AutoCAD 的答案——没有命令在跑时 Esc 清空选择集。
提案里没写这一条，是把两套语义的差异只想到了「怎么加」而没想到「怎么减」。

**`createDuplicateCommand` 的 `+10` 让出成可选参数**：那个常量的语义是「复制一份别正好盖住
原件」，而 `COPY` 有真实位移，叠加固定偏移会让每个副本都偏出一个常量——在图上看着像手抖。

### 步骤 3 · 旋转基点 — `add-rotation-pivot` ✅（闭环完成）

**本节于 2026-08-23 由用户校正，原方案作废（原编号步骤 5）。** 原文写的是「命名片段住组件定义、状态住实例、
脚本用 `qs1.setState('open')`」。用户给出的实际流程是：

1. 刀闸由用户**画出来**；
2. 在**动画模式**下于动画面板给它刻角度关键帧；
3. 再由**脚本控制播放**。

也就是说这条路走的是**既有的动画能力**，不需要任何新抽象。读代码确认三段里有两段今天就通：
角度轨道是 `['Transform', 'rotation']`，动画模式的自动记录已经在写它
（`editor/animation-mode/auto-record.ts`）；播放由动画清单的 `playing` 布尔绑定驱动，脚本
导出一个布尔即可（`preview/playback/use-animation-playback.ts`）。曲线在步骤 1 就已经验证过
能打位置与旋转关键帧。

**因此本刀只剩一件事：旋转基点。** `stage-geometry.ts` 的实体矩阵是
`rotate ∘ translate(−盒中心)`——绕**盒中心**转。刀片绕**铰点**转，而铰点是刀闸的一端。
基点不解决，用户刻出来的每一帧角度都对，画面上刀片却在原地打转而不是绕轴摆动。

候选（提案阶段定夺，路线图不预先拍板）：

- **`Transform` 加基点**（归一化盒坐标或局部坐标）。改动面是矩阵求解、Stage 渲染、Preview
  渲染、rotate 手势与属性面板，采样器不受影响——它只写 `rotation` 这个标量。
- **不加字段，靠盒**：把盒撑大让铰点落在中心。零协议改动，但盒与画出来的几何不再吻合，
  命中、包围盒与场景树里读到的尺寸全部跟着失真。这是一条要在提案里显式否掉的路，不是备选。

**取消的东西一并记下，以免重提**：命名片段、实例状态、`setState` 脚本 API，以及老路线图
挂起的「变体切换表达成 step 轨道」——那个问题的前提（片段）已经不存在了。

**门槛**：五道 + 闭环纵向 e2e（绘图模式画线 → 设计模式设基点「左中」→ 动画模式 0 ms 刻 0°、
200 ms 刻 90° → 铰点不动、另一端扫过）。✅ 全绿，e2e 128 → 129。

**落地方案与提案一致**：`Transform.pivot` 可选、归一化盒坐标、缺席即中心。改动面比预估还小
——`matrixFromTransform` 里 `width / 2` 变成 `width * pivot.x`，渲染是
`composeEntitySceneStyle` 的一行 `transform-origin`。

**一处漏斗的回报兑现**：Stage Scene、Preview 与组件实例三条渲染路径共用同一个
`composeEntitySceneStyle`，因此变换原点只改了一处。若当初三处各写各的 style，这一刀要改三处
且永远无法确认第四处不存在。

**`decomposeMatrix` 的基点参数刻意做成必填**：给默认值会让漏传的调用点静默按中心分解，而合成
那一侧按真实基点——两者不再互逆，症状是手势提交后对象跳一下、位移量恰好等于基点偏移，且**只在
非中心基点的对象上出现**。必填让编译器逐个点出九处调用点。新建容器与新建组件实例这两处显式
传中心，是可复查的决定而不是默认值兜的底。

**顺带补了一处不变量的漏网**：`rotate-plugin` 内联了自己那份 Shift 切换，是「点选与框选读同一
张表」漏掉的**第三条**点选路径，改读 `resolveStageClickSelection`。

**判别性验证**：把 `transform-origin` 改回 `center`，闭环用例的偏差恰好是**半个线长**
（100.9px / 200px 的线）。这条数值对得上，说明用例测的正是它该测的东西。

**顺带更新 13 张黄金图**：Inspector 几何分组多了一个字段，凡是拍到属性面板的截图都变了。

### 步骤 4 · 词汇扩展 — 拆成两刀

**拆分依据（2026-08-23，读代码后）：文字与弧/多段线没有一行共享实现。** 弧与多段线扩的是
`Curve` Component 的 `kind` union，共用归一化、紧包围盒、距离、特征点、渲染、命中六条路径；
文字压根不碰 `Curve`——它是既有的 Text 物料，另一个 Component。放一个提案里就是两个不相干
的半边。

#### 4a · 弧与多段线 — `add-curve-vocabulary` ✅

`kind` union 扩到 arc / polyline。**整圆仍是 ±360 扫掠弧、矩形仍是闭合多段线**——两条判断
原样平移，理由与 `cad` 里一字不差。数学从 `cad/geometry` 搬运（`cad-arc-geometry.ts` 约 220 行、
`cad-polyline-geometry.ts` 约 44 行，都不认识文档，是纯形状运算）。

一处比 `cad` 更好的地方：多段线在页面里渲染成**一个** `<polyline>` 而不是 N 个 `<line>`，
`pointer-events: stroke` 天然承担命中；`cad` 里那句「一条多段线在 DOM 里是 N 个 `<line>`」
的代价在这边不存在。

**门槛**：五道 + 三条纵向 e2e（画圆/矩形/弧各成一个 Entity 且渲染分支正确、`PLINE` 攒成一个
Entity 且可放弃上一点、圆心捕捉）。✅ 全绿，e2e 129 → 132。

**搬运的证据**：`cad` 的 284 项用例**一个测试文件都没改**就全绿，两个几何文件净减 235 行。
改了一行就说明搬运顺手改了语义。

**整个模块一起搬，不按消费者拆**：`flattenComposeArc` 目前只有 CAD 侧的交叉框选与块展开用得到，
按「两个消费者」的counting 规则该留在 `cad`。但把它单独留下会让弧的数学横跨两个包，而那正是
「一半改了另一半没改」的温床。判据是**模块的内聚性**，不是逐个函数的消费者计数——这与上一刀
否掉「把四行选择集分支下沉」是同一条判断的两面。

**实现中发现的一处陷阱**：`composeCurvePoints` 原本的 TSDoc 写着「弧与多段线加入后在此扩展，
包围盒与平移因此不必各自认识 kind」。前半句对、后半句错——它对弧返回的是**决定紧包围盒的
那组点**（含象限点），拿它当端点集合会让象限点以端点优先级参与捕捉，还会凭空造出一批相邻点
的中点。特征点因此必须自己按 kind 分派。

**捕捉次序与 CAD 对齐**：`endpoint > midpoint > center > quadrant`，与 `CAD_SNAP_MODES` 同一
次序。两块画布的捕捉手感必须相同。

**`PLINE` 的 `U` 关键字不是文档撤销**：取点期间文档上什么都还没有，放弃的是会话里的顶点。
有一条 e2e 钉住这一点（放弃后画布上仍是 0 条曲线）。

**顺带修一个 `-0`**：归一化的平移量是 `-bounds.x`，原点处正好产出 `-0`。JSON 序列化会写成
`0`，因此它是一个只在 `Object.is` 与断言里现形的幽灵差异；在归一化的取整处 `+ 0` 掉。

#### 4b · 绘图模式的文字 — **作废**

结论曾是「完全复用页面 Text，`TEXT` 命令几乎不用写」。取消绘图模式之后它自动成立——文字就是
既有的 `draw-text` 工具，没有第二条路径要建。

其中一条结论仍然有效并**移交步骤 12**：DXF 的 TEXT 带基线锚点，而导入器是无 DOM 的纯函数，
需要一个 ascent 比例做换算。这次的承诺弱得多——它只是**导入那一刻的落点估计**，不是命中框
契约，因此不复活「字体栈与比例是一对不变量」那条警告。

### 步骤 5 · 组件内动画在实例里播放 — `add-instance-animation` ✅（播放侧）

`component-instance` Renderer 多了两条可绑定 Prop（`animation` 与 `animationTime`），
实例在「解析覆盖之后、喂给嵌套 Yoga 之前」按它们采样一次。

**提案推翻了这一步原本的问题设定。**路线图当时写着「要在提案里定的是**粒度**」，并给了两个
候选：接受 `Animations.items` 整份替换，或者把删掉的「暴露属性」声明请回来。两个都不用——
那段推理默认了「实例要改的是组件文档里的绑定」，于是撞上「数组只作为字段整体写入」。但实例
是宿主页面上的一个普通 Entity，而 Entity 早就有一套逐实例的绑定机制（`Bindings.rendererProps`）。
**把绑定放在宿主侧，粒度问题不是被解决的，是根本不存在**：八个刀闸就是八个 Entity。

顺带确认了一个既有事实：实例渲染器不向嵌套文档传 `scriptScope`，因此组件文档里那份
`Animations.bindings` 在实例内**永远解析不出东西**。以前它看起来像个待补的洞，现在它是对的。

**v1 只有 seek，没有时钟**，规范也从「play、pause、seek 与播放模式」收窄到只有 seek。刀闸
本来就是状态不是动作；而做 play/pause 就得在物料里养一个每实例的 rAF 加播放模式状态机，
那正是「导航会话没有 `dispose`」那条坑的形状。没有时钟的物料是纯函数，没有生命周期就没有
生命周期缺陷。

其余几条判断：播放头是**毫秒**不是归一化 0–1（钳制已经吃掉了 0–1 的主要好处，而多一种时间
单位要所有读代码的人先分辨手上是哪一种）；`animation` 缺席不采样且**不回退到清单第一条**
（与「不得回退到 `rootIds[0]`」同一条判断）；失效 id 保留原值并在 Inspector 标为失效
（抄 `Interaction.navigate.target` 的可判别性）。

`materials` 因此新增对 `animation` 的依赖，形状与既有的 `layout-engine` 依赖一样——同为第 1 层
headless 领域包，同样只为组件实例的嵌套 Runtime 服务。

**这一刀没有闭掉刀闸故事**，见下面的步骤 5b。

### 步骤 5b · 让动画进得了组件文档 — `add-component-document-animation` ✅

补上步骤 5 实现时才暴露的两处**各自独立**的缺口。一条用例覆盖不了另一条，因此端到端也是两条。

**组件文档进不了动画模式。**设计/动画切换器只渲染在页面文档面板上，注释写的理由是「动画
绑定是页面级概念」——而步骤 5 之后绑定住在宿主页面上那个实例 Entity 的 `Bindings` 上，
根本不在组件文档里，组件文档里只剩清单与轨道。**那条理由自己失效了。**开关一开即可：
动画作用域解析的是 controller 的当前文档（组件文档单根且根必须是 Frame），动画命令注册在
controller 自己的 runtime 上，因此撤销天然只回退组件文档——这两处一行没改。

**创建组件不搬运动画清单。**轨道住 Entity 上，被子树复制带过来了；清单住 Frame 上，留在
源页面。结果是一份**有轨道、没清单**的文档，而清单才是「有哪些动画」的事实来源。

三条判断：

- **动画 id 逐字保留。**轨道按动画 id 分组，换个新 id 会让刚提取出来的轨道全部变成悬空分组
  ——时间线上什么都不动，而文档校验不会拒绝它。这是最容易写错也最难看出来的一处，判别性
  断言因此写成「`items[0].id` 等于子级 `clips` 的键」而不是「组件有一条动画」。
- **复制不是搬运。**选区可能只是这条动画的一部分：同一条动画给 A 和 B 都打了点，用户只把 A
  存成组件时删掉源条目，会让 B 的轨道全部悬空——**而用户根本没有选中 B**。
- **组件的动画内嵌在资产里，没有 `.animation.json`。**实例读的是 `resolvedSnapshot.document`，
  整份组件文档就嵌在实例 Entity 里，清单在其中；再配一份文件就是两份清单，而文件那份谁也
  读不到。顺带白拿两件事：组件保持是一份可移植的文件；保存不需要「把镜像聚合回文件」那段
  页面侧最复杂的回写逻辑。

一处包边界处理：轨道 Component（`Animation`）属于 `@compose-ui/animation` 的词汇，而
`stage-engine` 的依赖清单被边界用例钉死（只有 `core` / `commands` / `interaction-kernel`），
因此「一个 Entity 参与了哪几条动画」由调用方注入一个读取函数。硬编码 `'Animation'` 这个
字符串是另一条路，但那样两处知道同一个键而没有编译期联系，改名时会静默失效。

步骤 5 那份手写的「刀闸」组件资源随之删除——它存在的唯一理由就是这条缺口。`?switch-demo`
保留，现在只控制两个供绑定的数值导出。

### 步骤 6 · 取消绘图模式 — `remove-drafting-mode` ✅

模式切换器三选一 → 两段（设计 / 动画）。绘图能力**恒开**：命令行常驻、绘图与编辑命令随时可
启动、光标按「当前是否在取点」切换。

**判别性用例只有一条，也确实先红了**：动画开关打开时仍能画线。`setDrafting(mode ===
'drafting')` 是三选一切换器的直接后果，切到动画就把绘图强制关掉——这条断言在既有实现上
必然失败，它同时是「动画是另一根轴」这句判断的实证。

顺带删掉四个工具值，各自都与既有手势完全重复：`marquee`（`select` 空白拖拽即框选）、
`move`（`MOVE` 命令能键入精确位移）、`pan`（空格与中键是随时可用的临时覆盖，不占工具状态）、
`draw-line`（`LINE` 命令产出 `Curve`）。判定模式菜单改挂 `select`——它在空白处拖拽本来就是
框选，判定正是这个动作的参数。

**选择语义只剩 Figma 那一套**（替换 + Shift 累加）。原先规范里写的理由是「用户的肌肉记忆
来自 AutoCAD」，而那条前提已被推翻。推论：`MOVE` / `ERASE` 的多选走 Shift。

实现时冒出来的两处，都不在提案里：

- **Esc 的归属。**绘图恒开之后，它原来那条「没有命令在跑时也吃 Esc」会**抢在文字编辑的退出
  分支之前**——用户在画布上改完字按 Esc 会变成清空选择集而不是提交。那条本来就是累加语义的
  配套（点空白不清空，Esc 是唯一入口），语义统一之后自动失效。现在只有命令在跑时才吃。
- **命令行常驻改变了画布几何。**底部恒定少 30px，于是所有写死画布偏移量的用例与十二张黄金图
  一起变。黄金图按预期更新；有一条用例改成从「实例 ∩ 图面」取交集中心而不是写死偏移，
  另一条把画布拖拽换成 Inspector 编辑（它的主题是「实例能不能参与动画」，不是拖拽自动记录）。

**推迟两项**（提案里已写明理由）：绘制工具「拖与取点二合一」——`drafting-point`(1650) 高于
`draw`(1000)，两者同时武装时拖动永远起不来，而 `pointerdown` 那一刻分不出点还是拖，真做要改
仲裁器的认领时机；十字光标的两条偏好——组件本身要在步骤 9 下沉到 `canvas-kit` 并补齐三形态与
`CURSORSIZE`，现在加等于做两遍。

### 步骤 7 · 命令词汇表合并 — `merge-command-vocabulary`（2026-08-23 交付）

「能敲什么」曾经定义了两遍：`ComposeCommandDefinition`（`commands`，会话，命令行读，八条）
与 `ComposeCommandAction`（`command-panel`，一次性，面板读，三十一条）。后果是撤销、编组、
创建场景在面板里有、命令行敲不出来；`LINE`/`MOVE`/`ERASE` 反过来。步骤 6 刚把命令行变成常驻
——它常驻了，却只认得八个词。

**两个形状本来就是一个，而且退化的那一支已经在跑了**：`ERASE` 预选时 `prompt` 就是 `null`。
因此 `Action` 的呈现半边上升成不带泛型的 `ComposeCommandDescriptor`，`run()` 由
`createComposeImmediateCommand` 包成 `prompt` 为 `null` 的会话，`runComposeCommandImmediately`
是跑退化会话的唯一实现。编辑器目录一次算出描述符与可用性，面板与命令行各自派生。

判别性用例先验红：命令行键入 `UNDO` 撤销上一步（今天只会回「未知命令」）。

**合并必须同时带来可用性**：八条内建命令恒可用，因此命令行至今只有一种拒绝。宿主动作不是——
敲 `GROUP` 而没选够对象会**什么都不发生**，这在屏幕上与敲错字无法区分。现在三种拒绝互相可分：
词不在表里 / 词在表里但此刻不可用（给缺什么）/ 会话进行中的非法输入。可用性跟着选择集走，
选够两个之后同一个词就执行了。

**别名表暴露了两处重复，按「不造第二个词」处理**（九条动作不给别名）：八个工具切换让给绘图
命令——绘制工具与绘图命令是同一能力的两个入口，`RECTANGLE` 这个词已经属于命令；`edit.delete`
让给 `ERASE`/`E`——后者**严格更强**，没选中时会提示选择对象。剪贴板借 AutoCAD 的
`COPYCLIP`/`CUTCLIP`/`PASTECLIP` 避开几何 `COPY`。缺席不等于敲不出来：`id` 仍可键入。

**命令历史分两处**：组件记文本行（上下箭头召回），宿主记上一条成功启动的命令（空 Enter 重复）。
`LINE↵ 10,10↵ 40,40↵` 之后上箭头依次召回三行，而空 Enter 重的是 `LINE`——做成一个的话，空
Enter 会把 `40,40` 当命令名去解析。

实现时冒出来的一处：**`ComposeEditorController` 是宿主可以手写的接口**，既有测试与插槽宿主
用 `as unknown as` 只实现关心的那几项。新增的 `actionContext` 因此必须按可选消费，与
`controller?.renderStage` 同一口径；缺席时命令行退回只认内建命令，而不是让整个编辑器挂掉。

**Non-Goal（提案里已写明理由）：面板不启动画布会话。**`LINE` 要在画布上取点，而「哪块画布」
随标签页而变——CAD 标签页的 `LINE` 是另一条命令。没有画布→宿主的描述符上报通道就把 `LINE`
塞进面板，切到 CAD 标签页后面板照旧列着 Stage 的那条，点下去要么没反应要么启动另一块画布的
命令，**比现在的「搜不到」更难诊断**。推迟不制造债：本刀建的描述符、可用性与合并注册表正是
那条通道要用的，补的时候是加不是改。

#### 步骤 8b · 物料统一 — `unify-shape-materials` ✅ 已交付

`shape/` 删除，`arrow` 与 `circle` 两个 Preset 原地换成 `Curve` 实现（Preset id 与公共导出名

**两条预判被推翻，都是 8a 交付带来的：**

- **椭圆不用做。**非正方盒里的整圆经 `viewBox` 画出来就是椭圆，命中侧的投影也已经跟着走。

- **端点选区 UI 是删除而不是搬运。**原本写的「搬到 `Curve` 是净删代码」不再成立：两点直线的
  端点就在紧包围盒的对角，8a 之后拖盒角手柄与拖那个端点落点**逐像素相同**。那套 UI 当初存在
  只因为 Shape 的线没有可用的盒语义。留下的差额是轴对齐的线掰不成斜的——那正是步骤 10 要回答
  的问题，现在搬进去等于在它必须拆掉的位置先盖一栋房子，还顺手替它做了决定。
  **代价是明的**：8b 到 10 之间轴对齐的线要改方向须重画一次，或用 `LINE` 命令键入坐标。

**一条实现时才浮现的判断：填充必须住在 `Appearance.backgroundPaint`，不能是 Renderer prop。**
填过色的面积是用户看见的墨，因此要参与命中；而 8a 立下的边界是「命中路径读的字段必须是文档级
契约」。复用还让外观 Inspector、数据绑定与外观动画轨道一样都不用做。连带：宿主盒与共享 Paint
层不再为曲线画背景（盒是矩形而形状不是），`isCircleShapeEntity` 那个 50% 圆角补丁一并删除。
v1 只画 `solid`。

marker 走 props，且**参与 `viewBox` 变换**——它是几何，不是描边。

删掉的还有整条端点手势链：`segment-resize` 插件、`segment.commit` 效果、`segment-endpoint`

#### 步骤 9 · 十字光标下沉 — `extract-crosshair` ✅ 已交付

十字光标进 `canvas-kit`：一个受控 `<g>` 加一个纯解析函数。CAD 与 Stage 共用同一份，
`data-testid` 前缀由调用方给出。

**查证翻出两处，第二处比第一处严重：**

- **Stage 画了十字线却没收走系统光标。**绘图命令不改工具，而游标推导只看
  `isDrawingTool(tool)`，于是屏幕上是一支箭头压着一副十字线。它还缺拾取框形态（等待选择
  对象时图面上什么都不画）、缺 `CURSORSIZE` 百分比、触摸屏上照画不误。
- **CAD 违反它自己的规范。**`cad-document` 写着「十字光标 MUST 钉在与橡皮筋终点、坐标读数
  相同的**解算后落点**上」，`use-indicated-point.ts` 也写着四个消费者必须读同一个值——而实现
  取的是 `indicated.screen`（裸指针），另外三个取 `indicated.world`。默认栅格步长 10 且吸附
  默认开着，**十字线一直停在用户不会落笔的地方**。本刀修正了它。

**设计上只有一处需要想：**`resolveComposeCanvasCrosshair` 是「是否在画」的唯一判据，调用方拿
同一个返回值决定绘制与隐藏系统光标。两处各判一次必然漂移，而漂移的样子就是 Stage 曾经的样子。
触摸豁免因此也进解析函数——「不画」与「不隐藏系统光标」必须同时成立。

**两条刻意的不对称写进了规范：**CAD 空闲时线与框都画，Stage 空闲什么都不画（页面编辑器的
静息光标是箭头）；CAD 的拾取框半边长等于点选命中容差，Stage 的**只表达靶区、不参与命中判定**
——它的点选是 DOM 驱动的，没有全局容差那个数。

**「既有用例不改一行」这条证据标准按实际调整了**：落点修正是行为变化，因此证据换成「那是唯一
的 diff」。实测 CAD 既有 87 条一条没改即全绿，新增的一条钉住修正后的落点。

#### 步骤 10 · 几何编辑模式 — `add-geometry-editing` ✅ 已交付

双击曲线进入几何编辑：夹点显形、盒手柄让位、画十字光标、拖动经与绘图命令**同一条**落点解算
之后派发 `entity.curve.set`。`Escape`、点空白、换工具、选中别的对象都退出。8b 记下的那笔债
（轴对齐的线掰不成斜的）由判别性用例钉住还上。

**这一刀有一大半是「别造第二套」。**顶点编辑的整套机制早就在仓库里，只是被动画独占着：
`StageEditablePath`、`path` 插件（优先级 1400，显式高于点选的 700）、三阶段效果链、并发中止与
目标切换的守卫。它的 TSDoc 自己写着「命名不含动画语义：这一层可被将来的矢量路径编辑复用」。
复用之后路线图里「顶点必须是热的且优先级显式排在点选之上」这条**不需要写任何代码**。

**写入方向相反是设计**：宿主传入的运动路径只上报（它的事实是关键帧，Stage 不认识那套协议），
而曲线几何**就是文档本身**，Stage 为它派发命令，与 resize、move、绘制一致。规范里那句「路径
几何的事实来源始终在宿主」因此收窄到**宿主传入的那条**——留着原话，下一个人会以为几何编辑
违反了规范。

**三条预判被推翻：**

- **不是「把已有 UI 泛化」，而是「换一条已有通道」。**原文说老的 `shape/` 有端点 UI 而曲线拿到
  更差的选中 UI——但那套 UI 在 8b 就删掉了，剩下的是运动路径那条**更完整**的通道。
- **矩形升格挪出这一刀。**它不是几何编辑，是一次**物料转换**：Rectangle 是盒物料，升格要把
  `Renderer.type` 从 `rectangle` 换成 `curve` 并加 `Curve`，与「拖顶点」不共用一行代码。
  顺带纠正决策 8 的表：**椭圆已经不在「盒能决定它」这一档**，8b 之后它是 `sweep` 为 360 的弧。
- **对齐参考线并轨挪出这一刀。**顶点拖动接不进既有的参考线通道：那条通道由**自己解算吸附的
  插件**发布，而 `path` 插件刻意什么都不解算（落点由宿主定）。接它要新拉一条 overlay 接线。
  AGENTS.md 里那段「两套不能同时生效」因此**不用改**——它说的是特征点候选不出盒的角点，那条
  仍然成立。

**两处实现时才浮现的判断：**

- **双击落在盒手柄上也要进。**一条水平线的包围盒高度接近零，上下两条边缘命中区把整条线盖住，
  双击**永远**打不到实体本身——而轴对齐的线正是这一刀要救的那一类。用一条对角线验证会全绿，
  水平线才拦得住；这与「弧的紧包围盒要算象限点」是同一类缺陷：对称/斜的样例看不出来。
- **正在编辑的对象必须从捕捉里排除。**它自己的端点就在指针底下，不排除的话夹点被吸回原处，
  用户要把指针拖出容差半径才动得了。悬停标记与落点解算读同一份排除表，否则会出现「标记在
  这里、点落在那里」。为此场景索引改由 Stage 注入并两处共用——排除表与落点解算互为前提，
  两个 Hook 不能各自建索引。

弧的四个夹点各只改一个自由度，**另一端一动不动**：圆心平移、起点改起始角并同步扫掠角、终点
只改扫掠角、中点只改半径。整圆只出圆心与中点（起点与终点落在同一个像素上）。

**一处行为变化**：曲线绘制手势结束后直接进入几何编辑，因此那一刻盒手柄让位于夹点（与「画完
文字直接进文字编辑」同一条规则）。既有的箭头绘制用例因此改了三行断言，那是全部 diff。

#### 步骤 11a · Entity 端口 — `add-component-ports` ✅ 已交付

`Ports` 是可选 Entity Component（任意 Entity 都能有，与 `Interaction` 同一条判断），端口进特征点
捕捉且**排在端点之前**，与 `CAD_SNAP_MODES` 一字不差。

**步骤 11 拆成两刀**，缝在「端口」与「导线」之间：端口是一个可选 Component、没有求解、没有删除
语义，落地即可用（画线能吸到接线柱上）；导线要动求解管线与删除语义，是另一份账。**捕捉次序必须
在这一刀定对**——等 11b 再改就晚了，用户会先学会「吸到的是那段短线的端点」，而那正是 11b 要防的
错误。

**一条预判被推翻：镜像改成读取。**提案写的是「把组件根的端口复制到实例 Entity 上」，理由是 8a
那条「命中与捕捉路径读的字段必须是文档级契约」。实现时发现刷新快照走的是 `setRendererProps`，
镜像要在创建与每一处刷新各写一遍，**漏一处的症状是「端口停在符号搬走之前的位置」**——看起来像
捕捉坏了而不是同步坏了。改成 `getComposeEntityPorts` 一个读取入口并让它住在 `core`：那条边界
要的是「捕捉一侧不必认识组件协议」，而**入口的归属**就能满足，不必靠复制。

**一处白拿**：Component Asset 的 `document` 就是一份 ComposeDocument，因此「端口搬到 Component
Asset」不需要动资产 schema——端口是组件根 Frame 上的一个 Component，变体覆盖它走既有的
`set-field`，继承与覆盖一行代码都不用写。

#### 步骤 11b · 符号导线 — `add-symbol-wires` ✅ 已交付

`Wire` 只记「这一端绑到了哪个端口」，缺席即自由端且不存坐标。`WIRE` 命令按**取点时记下的来源**
绑定，拖动端点即改接线。几何求解不存储。

**那个开放问题的答案：读快照，而且求解住在布局 Runtime。**求解要读绑定实例的盒（算旋转基点要
真实尺寸，实例的 `LayoutItem` 是 Hug、`value` 只是兜底），并且**会改导线自己的盒**——文档与快照
因此必须成对产出。仓库里已经有这条经验，写在动画那条路径上：「画布必须拿到『同一次求解』的
文档 + 快照一致对……直接配对会让 stage 的几何索引抛错并卸载整个画布」。Runtime 是唯一同时握着
两者的地方，于是三条渲染路径各自零改动。

**一处实现时才浮现的坑：身份判定与渲染对象是两件事。**预览与编辑器都用 `state.document ===
入参` 判断「这份状态是不是我传进来的那份文档产出的」，而解算之后 `document` 已经不是入参了——
预览会永远停在 loading。因此 `ready` 状态拆成两个字段：`document` 是**已解算**的那份（与快照
配对），`sourceDocument` 是输入（只用于身份判定）。**这个坑没有任何用例会自己暴露**，它只在
文档里真有一条导线时才发生。

**不做「删除时冻结端点」这条从 CAD 收窄掉了。**它的存在理由是 CAD 的校验器拒绝悬空引用、会让
整批删除被打回；而本仓库对同类情形已有另一条判断（实例动画：指向不存在的 id 时保留原值并标为
失效）。照它办之后删除路径一行不用改，也不需要在核心的删除命令里去拿一份它没有的布局快照。

**`entity.curve.set` 多了一个可选的 `wire` 载荷**：拖端点同时改几何与绑定，而运行时一次只跑
一条命令——分成两条会产生可观察的不一致中间态（几何动了、绑定还指着旧端口），撤销也变两步。
缺席即不动 `Wire`，Inspector 那条写入路径一行不改。

**风险没有兑现**：把交给 Stage 的文档换成 Runtime 那份已解算的文档之后，146 条既有端到端用例
一条没改即全绿，退路（两个渲染入口各自 memo）没有用上。

五条决策全部落地，其中两条推翻了本文原先的记载：

- **「全部几何数学原样存活」不成立**。`segmentIntersection` / `segmentCrossesBounds` /

移植**：能力全在页面这边（组件库、端口 Inspector、描边 Inspector、`draw-text`），缺的只是
能敲的那个词，补一批与既有入口重复的命令违反「一个动作一个入口」。

`canvas-kit`、`interaction-kernel` 与 `components` 的命令行 Pattern 在 CAD 走后**各只剩一个

#### 步骤 13 · 顶点取点走命令那一套 — `add-vertex-command-session` ✅ 已交付

按下夹点即开一条**一点命令会话**（提示「指定新位置」），松手时按指针有没有离开过按下点分流：
动过就提交、一步没动则会话留着且夹点**点亮**，此后再点一下画布或**键入一个坐标**提交同一条
`entity.curve.set`。加 `VERTEX`（别名 `VE`）作为几何编辑的键盘入口。

**这一刀的立项理由是一条实测的不一致**：顶点是 Stage 里唯一一处「人在取点、键盘却进不来」的
地方——`LINE`、`ARC`、`MOVE` 都能键入精确坐标，唯独「把这个顶点放到 `100,50`」答的是
「未知命令」。决策 11 写的「模式内 取点走点输入管线」只兑现了指针那一半。

三条实测（探针跑完即删）：几何编辑期间命令行显示的是上一条命令留下的「已取消」；键入坐标得到
「未知命令」；夹点的**单击槽位是空的**（原地按下松开位移 0、不产生撤销记录——0 是网格把落点
吸回了原格点，换细网格或关掉网格吸附时它会变成一次无意的微移，同一件事的两面）。AutoCAD 在
这个槽位上放的正是缺的那件事。

**实现时才浮现的两条：**

- **「动过没有」不能用「来过 move 阶段没有」判**。路径手势在 `pointerup` 上会先发一次 `move`
  （终点与松手修饰键都由那一次带回来），因此原地单击同样收得到一个 move 阶段，照这个判会
  永远走进「提交」分支、点亮永远不出现。判据必须是**落点与按下点逐个比较**。也不能用位移
  阈值——那是本仓库别处都不需要的魔法数。
- **拖动、点亮后取点、点亮后键入坐标必须汇到同一处几何求解**。做法是把提交那一步整个搬进
  `planStageDraftingEdits`：会话只带回落点，盒局部换算与 `applyStageCurveGrip` 都在规划里。
  `nextWireFor`（改接线）因此也从 Stage 搬进引擎，三条路径的撤销粒度与接线语义就都一样了。
  拖动期的本地预览仍然自己解算一次——它画的是「松手之后会是什么样」，不写文档。

**推翻了一条记载**：`GRIPHOT` 从「不做」改成「拖动期不做、点亮期要做」，理由见上方表格。
它需要真的 React 状态（一个夹点 id），与「不为悬停反馈引入每帧 `pointermove` 的 React 状态」
不冲突——那条的对象是悬停，点亮每次手势只写一次。

**`VERTEX` 不叫 `PEDIT`**：AutoCAD 的 `PEDIT` 还管闭合、合并、拟合与样条化，拿一个已有确切
含义的词做一件小得多的事比另起一个词更糟。它复用 `ERASE` 那条两次序共用的状态机，候选不是
恰好一个时以 `rejected` 说明——「敲了没反应」与敲错字在屏幕上无法区分。

#### 步骤 13b · 点亮之后的目标位置预览 — `add-armed-grip-preview` ✅ 已交付

步骤 13 留下的一处遗留：原地松手时 `setPreview(null)`，此后没有任何东西再按光标重算预览。
实测点亮 `end` 夹点再挪光标——轮廓与夹点**一动不动**，画面上只有一条橡皮筋，而拖动那一半是
跟手的。同一个会话的两条路径给出了不同的呈现。

那条橡皮筋还有欺骗性：它从**旧位置**指向光标。在直线端点上勉强像结果，在弧的半径夹点、
多段线顶点与直线的**平移**夹点上说的完全是另一回事。

AutoCAD 的说法是明确的：选中一个端点夹点、移动光标时线段就跟着拉伸，这个拉伸是临时的，
直到取到一个点为止。

**一处自我更正。**步骤 13 给热夹点写的理由是「点亮后夹点停在原位而光标在别处找目标点」——
加上实时预览之后这句话不成立了，夹点跟着预览走到光标底下，与拖动期一样。理由重述而不是撤销：
红色说的是**「有一次编辑正在进行」**，不是「是哪一个」；后者由预览本身表达了，前者在光标还没动
的那一刻、以及视线离开又回来时仍然只有它和命令行提示在说。

**两条实现上的约束：**

- **「正在拖动」不能再由「有没有预览」派生。**点亮期同样有预览，派生的话点亮会被当成拖动，
  热夹点与拾取框一起错。它改成一次指针手势在不在进行中这件事本身。
- **绘图 Hook 必须排在几何编辑之前。**预览要读它解算后的落点，读得晚一拍就等于让预览慢光标
  一帧。反方向的两处依赖（进入几何编辑、判断能不能几何编辑）改走 ref，它们只在事件回调里
  调用，那时 ref 早已就位。

**用例夹具上的一个坑**：文档几何必须在**点亮之前**读。按下那一刻就解一次落点，而开着网格
吸附时它已经把顶点挪了半格——与「拖动按下即预览」是同一条既有行为，不是缺陷。照着点亮之后
读，会拿一份已经带预览的几何去当基准。

#### 步骤 14 · 框选的两个方向 — `add-marquee-direction-feedback` ✅ 已交付

实测：画一个矩形，两个方向各拖一次、都只框住它一半——**两次逐字相同**。

```
左→右   mode=intersect  fill=rgba(54,135,255,0.1)  stroke=rgb(54,135,255)  dash=4,3  选中 1
右→左   mode=intersect  fill=rgba(54,135,255,0.1)  stroke=rgb(54,135,255)  dash=4,3  选中 1
```

两半各有一个原因，都不是「没做」：

- **判定**：`directional` 那套代数一直都在（起点在左等价 `contain`，在右等价 `intersect`），
  但引擎默认值与编辑器初值都是 `'intersect'`。不去工具栏菜单里手动选一次，方向就什么都不做
  ——**功能在，可达不到**，与「不进模式就看不见命令行」是同一类毛病。
- **呈现**：样式表里只有一条差异（`intersect` 加虚线），填充与描边共用同一个蓝。虚实是唯一
  区分，而它在拖动中的细边框上分辨率很低。

修法是两个默认值一起改成 `directional`，并给两种判定各自的颜色（窗口蓝 / 窗交绿，取自
AutoCAD 的 `WINDOWAREACOLOR` / `CROSSINGAREACOLOR`），虚实保留。

**分色依据是生效判定而不是方向。**钉死相交时两个方向都是窗交色——那正是此刻生效的判定。
样式表拿到的 `data-marquee-mode` 已经在引擎里归约过，因此它不需要认识 `directional`。

**这是一处行为变化，代价落在既有用例上。**改后从左往右只选完全框住的对象，因此凡是「随手
拖个框选中部分重叠对象」的写法都会红。补法是**给那些用例钉死判定模式**，而不是把默认值改
回去掩盖过去——判据是「这条用例讲的是判定吗」：讲布尔组合、讲排除 hidden/locked、讲「空白
拖拽起的是框而不是移动」的，都与判定无关，钉死一种即可。实际红了 6 条单元用例、0 条 e2e
（既有 e2e 的框大多完全罩住目标，两种判定给出同一个答案）。

## 踩过的坑

- **曲线的「接缝」「尖角被削平」「水平线点不中」是同一个根因**（2026-08-23 实测定位）。
  不是 SVG 的 `overflow`——`composeEntityOverflowStyle` 对叶子恒发**内联** `overflow: hidden`，
  内联压过样式表，`.compose-stage__node.is-segment { overflow: visible }` 那一条**从来没有
  生效过**。而曲线的盒是几何的紧包围盒，描边以几何为中心画、必然超出半个线宽，于是被盒切掉：
  尖角削平、端点圆头被切、水平线（盒高被钳到 1px）连命中都只剩几何那一条线，实测触达 0px。
  判据必须是 `Curve` Component 而不是 Renderer 类型——按物料类型枚举，每加一种线状物料都会
  漏掉这一处。**量具**：把线宽临时调到 24px 截图，裁剪与否一眼可见；命中则沿法向扫
  `elementFromPoint`。我最初把它错记成 SVG 的 `overflow`，那条记录已更正。

- **`vector-effect: non-scaling-stroke` 中和不了 HTML 祖先上的 CSS 变换**（2026-08-23）。
  它只作用于 SVG 文档片段**内部**的变换，而 Stage 的缩放来自 `.compose-stage__scene` 那个
  HTML 节点。症状最阴险的地方是 computed 值老老实实报 `non-scaling-stroke`，只断言属性
  生效的用例因此全绿，而屏幕上描边照样跟着涨——实测放大 4.22 倍后触达从 6px 变 29px。
  正确做法是反向除掉画布缩放：Stage 把 zoom 发成 `--compose-canvas-zoom`，物料写
  `calc(<宽度>px / var(--compose-canvas-zoom, 1))`；变量缺席即 1，预览与其它宿主自动回到
  页面单位。**量具是沿法向扫 `elementFromPoint` 量实际触达**——`getBoundingClientRect` 在
  SVG 几何元素上不含描边，量不出来。

- **只断言「机制被声明」而不是「机制起作用」的用例会全绿**。上面那条 `non-scaling-stroke`
  是活例：组件测试断言属性在、e2e 断言 computed 值对，两条都绿，而屏幕上是错的。量具找不到
  时该继续找，不该退而求其次换一个更弱的断言。

- **默认线宽 2 明显偏粗**（2026-08-23）。同一个仓库里 `CAD_DEFAULT_STROKE_WIDTH = 1`，两条
  「画出来的线」宽度差一倍。AutoCAD 出厂同样是一个像素的发丝线（默认 lineweight 0.25mm，而
  模型空间默认不显示 lineweight）。接线图靠**线的走向**传达信息，加粗只会让密集区糊成一片。

- **紧接在「双击进入几何编辑」之后的那一下，落在刚刚显形的中点夹点上**（2026-08-25 由步骤 13
  发现并修复）。夹点是被那次双击变出来的，而直线的中点夹点**正好压在光标底下**；用户先单击
  选中、再双击进入时，那一下的连击计数是 3，路径插件因此为它开了一次拖拽。旧行为是原地松手
  写一条几何等于原样的命令，看起来无害；顶点会话落地之后同一下会把那个夹点**点亮**，接着
  偷走用户的下一次点击——症状是「进了顶点模式，第一次拖端点整条线跳走了」。
  **第一版修法是错的**：把连击中的按下一律 `consumed`，结果连「双击进入之后马上拖中点」也
  一起挡掉了——那是常用手法，而中点夹点恰好与前几下同一个像素，计数一路涨到 4。正确的修法是
  **手势照开，只是把连击计数交给宿主**：原地松手时，计数大于 1 的那一下取消而不是点亮。
  **量具是命令行提示**：进入之后它应当是空闲的，是它先说了「指定新位置」，才把注意力引到
  那次多余的按下上。

## 待修的缺陷

- **虚线图案由线宽推出，而两者已经不是同一个单位**（2026-08-23 发现）。
  `strokeDasharray` 的 `'8 4'` 实际写成 `线宽*4  线宽*2`，这在线宽也是世界单位时说得通；
  线宽改成屏幕像素之后，用一个屏幕量去推一个世界量就成了单位错配——线宽 1 时图案是 4/2
  世界单位，缩到 0.3 倍就看不见了。正确的形状是一个**独立于线宽**的世界量 dash pattern。
  改动会影响既有虚线曲线的外观，因此单独立项。**12b 之后它多背了一条**：`FLOW` 的页面对应物
  停在「给属性不给命令」，正是因为命令要从 dash pattern 求出一个完整周期，而这里的周期还不
  可信。修好这条之后，「一条命令让线流动起来」才值得重新考虑。

- **Stage 把指针存成世界坐标，而它应当存屏幕坐标**（2026-08-24 由步骤 9 发现，未修）。
  理由是：「凡是不以光标为锚点的视口变化，世界坐标不变而屏幕位置变了，指示就会
  飘离真实光标」。Stage 的 `use-stage-drafting` 存的是世界点，因此**命令进行中按空格平移**
  （这是明确支持的：取点插件优先级排在 `pan` 之下）会让十字光标跟着世界点走而不是跟着光标走。
  没有在步骤 9 里修：`pointer` 有六个消费者，改存储单位是那条点输入管线的重构，而步骤 9 的
  三条行为变化已经够多了。

- **旋转过的曲线拖顶点，盒会重新归一化**（2026-08-24 由步骤 10 发现，未修）。
  `entity.curve.set` 按新几何的紧包围盒重算盒与 offset，而旋转基点缺席时是盒中心——因此盒原点
  一移动，图形会绕新中心重新摆一次。这是盒模型固有的，与 resize 一样；真要解需要「旋转时以
  哪个点为不动点」有答案，不是几何编辑一刀能定的。

## 未定的决策

- **数据源协议**：整条刀闸流程上最后一个空白，且尚未进过任何路线图。页面脚本要订阅什么、
  怎么订阅、断线怎么办，全部未定。
- **实例级动画绑定的粒度**：见步骤 5。接受整份数组替换，还是给绑定换一个对实例友好的形状。
- **动画开着时编辑命令的语义**：`MOVE` 一个已有对象是写关键帧还是改 `offset`？v1 的安全解是
  动画开启时禁用 `MOVE`/`COPY`/`ERASE`，只留绘制命令——按「能力并集」的规则，这就是一条可用性
  声明，不需要新机制。
- **顶点增删**：步骤 10 答了一半——**要做**（一根四折的线既然是一个对象，插顶点就是刚需），
  但它要的不是新机制，是一种新手柄（`StagePathHandleKind` 加一个值）加上删点的入口。未立项。
  **多段线的段中点这个位置已被显式保留给它**：直线拿到中点平移夹点时，多段线刻意没有跟着拿
  ——段中点是插顶点的天然位置，先用它表示平移会把那条路堵死。
- **几何编辑里对齐参考线的参照系**：只对齐同父级兄弟，还是对齐视野内所有对象？前者可预期，
  后者在密集图纸上更有用但候选会爆。步骤 10 没有并轨（理由见该节），因此这条仍然未答。
- **矩形升格成多段线**：决策 11 要求双击矩形也进几何编辑、拖角时升格。步骤 10 把它挪出去了
  ——它是物料转换而不是几何编辑。未立项。
- **AutoCAD GROUP（命名选择集）**：一个对象可同时属于多个组，树表达不了。等实际使用暴露需求
  再立项。
- **几何关键帧下的编辑语义**：「渲染用采样、命中用原件」在几何会动时产生可感分歧。步骤 3 校正
  后**不再触发它**——刀闸摆动走 `Transform.rotation`，几何一动不动。真要动几何（端点轨道）
  时再答。
