# 绘图统一路线图：CAD 融入页面世界

## 文档定位

本文是「把 CAD 能力融入页面编辑器」的**纲领性路线图**，用于串联多个 OpenSpec 变更，不代表
当前已经稳定的公共 API。每一步都是一个独立可发布、可回退的 OpenSpec 提案；**路线图是方向，
提案才是权威**——每刀的提案只在轮到它时写，吸收前面各刀实现时发现的事实；本文在每刀完成
后回填实测结果与被推翻的预判。

本文**接替** `cad-document-roadmap.md` 的后续方向：那条路线（独立 CAD 文档类型，步骤 1–9）
已经走完并交付了全部图元数学、捕捉、命令行与 DXF 解析——这些原样存活；被本路线替换的是
「独立文档类型 + 独立编辑外壳」这个壳。

**2026-08-23 大改**：用户校正了两条前提——「用户不熟 AutoCAD」与「绘图和设计只该差一套工具」
——路线因此重排。被推翻的判断集中记在下方同名小节，不要重提。

## 产品意图

实施工程师画一张主接线图：**刀闸是他自己画出来的普通对象**；给它刻角度关键帧，再由页面
脚本按遥信驱动。这是 SCADA/HMI 组态，不是绘图工具。

分工只有一条轴：

```
怎么画        取点 / 对象捕捉 / 正交 / 键入坐标 / 命令四态     ← 这一层借鉴 AutoCAD
画出来是什么   普通页面 Entity，和拖出来的完全同类              ← 这一层没有 CAD 的份
```

**用户不熟悉 AutoCAD**（2026-08-23 由用户指出）。因此判据是**这个任务需要什么**，不是
「AutoCAD 怎么做」：精确取点、捕捉、正交、键入坐标是任务需要的，留；累加选择集、方向敏感
框选、裸滚轮缩放是纯照搬，去。

命令行不是「CAD 的命令行」，是**命令面板顺便带了个输入框**——面板是主入口（搜得到、看得懂），
命令行是加速器（知道名字的人敲两个字母）。

## 已定的决策

| # | 决策 | 后果 |
| --- | --- | --- |
| 1 | **没有第二个世界**：删除 CadDocument / `.cad.json` / CAD 标签页 / `cad-canvas` | 曲线成为页面词汇；cad 数学存活、外壳消亡 |
| 2 | **曲线保留盒**：`LayoutItem` + 盒局部几何 | 移动/动画/树/预览零改动可用；不需要 v8 |
| 3 | **命中判据按 Entity 而不是按画布** | 盒物料按矩形，曲线按点到几何距离；canvas-kit 边界不变 |
| 4 | **刀闸是画出来的普通对象**；成规模时做成组件、动画刻在组件里，差异走 `instanceOverrides` | 不引入片段/状态机 |
| 5 | **无限图纸消亡**：图画在场景（Frame）里 | 交付物本来就是固定尺寸大屏 |
| 6 | **不写迁移器**（无线上 `.cad.json` 资产） | 与删 Page Slot 同一条判断 |
| 7 | **没有绘图模式**（2026-08-23） | 模式只剩动画开关；见下 |
| 8 | **一套物料、一个概念**（2026-08-23） | 没有「绘图的矩形」和「设计的矩形」，只有矩形 |
| 9 | **同一个工具兼容两种下笔方式**（2026-08-23） | 拖着画（快）与取点/键入（精确）是同一个按钮的两种用法 |
| 10 | **模式只能是对象作用域**（2026-08-23） | 几何编辑 / 文字编辑 / 实例下钻是同一个模板；「整块画布换套规矩」的模式不再有 |
| 11 | **绘制与顶点编辑是同一个模式**（2026-08-23） | 都在取点，因此共用光标、点输入管线与吸附；见决策 11 |

### 决策 7：为什么没有绘图模式

绘图模式原本提供四样，逐条追问之后没有一样需要用模式来承载：

| 它提供的 | 收敛后 |
| --- | --- |
| 工具集 | 并进同一条工具栏——真正新增的绘制工具只有**弧**和**多段线**两个 |
| 十字光标 | **跟着工具走**（Stage 本来就是这么做的），另加两个偏好：始终十字、十字线长度 |
| 命令行 | 常驻/召唤，不属于任何模式 |
| 累加选择 + 方向敏感框选 | **去掉**（判据见产品意图） |

最有力的证据是**两套工具本来就重叠**：矩形、圆、线在两个模式里各有一个入口，差别只在产出
什么对象，而用户压根不该关心这个。为两个按钮维护一整个模式，账算不过来。

### 决策 8：一套物料

一个形状一个按钮、一个物料。区别不在「谁画的」，在**形状能不能由盒决定**：

| 形状 | 盒能决定它吗 | 存几何吗 |
| --- | --- | --- |
| 矩形 / 椭圆 / 正多边形 / 单段直线 | ✅ | 不用 |
| **弧 / 多段线 / 任意路径** | ❌ | 要 |

下面一行带 `Curve` Component。**这不是两个概念**——是同一个概念（带盒的 Entity）加一个可选
Component，正是 ECS 本来的样子。用户看不出区别：场景树、属性面板、动画、布局全都一样。

**所有形状都参与 Auto Layout。**这要求盒能独立于几何变化，与现行不变量「盒尺寸是几何的
派生」相反——机制是给 `Curve` 的 SVG 加 `viewBox`（`shape/` 物料现在就是按百分比画的，天然
参与布局，证明这条路走得通）。代价是**命中与捕捉必须应用同一个盒→几何变换**，漏掉就会再次
出现「画出来的和点得中的不在一处」，那是本仓库反复踩到的那一类缺陷。

### 决策 10：模式只能是对象作用域

刚删掉绘图模式又引入几何编辑，看起来矛盾，其实不是同一类：

| | 绘图模式（已删） | 几何编辑 / 文字编辑 / 实例下钻 |
| --- | --- | --- |
| 作用域 | 整个编辑器 | **一个对象** |
| 生命周期 | 切进去住在里面 | 双击进、Esc 出 |
| 改什么 | 工具栏、选择语义、框选、光标 | 只改「这一下点击是取点还是选中」 |

编辑器本来就有两个同形状的东西（双击进文字编辑、双击下钻进实例），没人觉得它们让人困惑，
因为进出边界清楚、作用域是一个对象。判据因此写成一句：**模式必须是对象作用域且有明确的
进出**，不能是「整块画布换套规矩」。

唯一的例外是动画开关——它改的是拖动结果落在哪里，是真正的全局模式，也只此一个。

### 决策 11：绘制与顶点编辑是同一个模式

一个「几何编辑」模式，三个入口：

```
入口 1   双击一个几何对象        → 编辑它的顶点
入口 2   选一个绘制工具          → 新建几何（画完停在模式里，可以接着调）
入口 3   命令行敲 LINE / ARC …   → 同上

模式内   光标 = 十字星
         取点走点输入管线
         盒手柄消失
退出     Esc / 点空白 / 切工具
```

理由是**它们本来就是同一件事——都在取点**。分开做意味着两套光标规则、两套取点接线。合并
之后光标规则从「跟着工具走」收紧成更准的一句：**在取点就是十字星**。

Figma 是同一个模型：钢笔工具与矢量编辑是一回事。

两处随之确定：

- **进模式后隐藏盒手柄**。矩形的右下角手柄与右下角顶点几乎在同一像素上，两个含义（改盒 /
  改几何）叠在一起。Figma 在矢量编辑时同样隐藏包围盒。
- **矩形/椭圆没有顶点**（决策 8：它们由盒决定，不存几何）。双击它们仍**进入**几何编辑，拖动
  某个角时**升格成多段线**——与仓库既有的 `promoteComposeEntityToFrame`（「升格只做一件事」）
  是同一个手法。不进的话，双击在不同形状上行为不一致，用户学不会；而按决策 8 升格不丢任何
  能力（照样参与 Auto Layout）。

### 点输入管线：对齐吸附并轨

几何编辑要求特征点捕捉与 Figma 式对齐参考线**同时生效**。次序定死并**命中即短路**：

```
键入坐标  >  特征点捕捉(点)  >  对齐参考线(轴)  >  正交  >  网格
```

**点压过线**：在端点容差内就落到端点；不在，才考虑「与旁边对象的边对齐」。键入的坐标不被
任何一级改写，这条不变量不动。

`snapCandidates` 返回 `{ axis, value }` 的参考**线**，`findStageFeaturePoint` 返回二维**点**
——形状不同，是姐妹查询，因此并轨的做法是**串成两级**而不是合成一个函数。

## 被推翻的判断

记在这里以免重提。

| 曾经写下的 | 为什么错 |
| --- | --- |
| 「切换发生在模式层」「绘图模式换手势语义」 | 绘图模式提供的四样没有一样需要模式承载；见决策 7 |
| 「手感学 AutoCAD：命令行驱动、左窗口右交叉框选」 | 用户不熟 AutoCAD。任务需要的留，纯照搬的去 |
| 「绘图的矩形是描边多段线、设计的矩形是填充盒」 | 把「怎么画」和「画出来是什么」混在一起造出来的重复概念 |
| 「每实例状态无处安放」「覆盖表达不了轨道」 | `instanceOverrides` 是**七种**操作、四种改值；旧的暴露属性正是被迁移成 `set-field` |
| 「三个模式：设计 / 绘图 / 动画」 | 动画是另一根轴——它改的是**拖动的结果落在哪里**，可与任何工作区叠加。绘图不是轴，是几个按钮 |
| 「特征点捕捉与对齐吸附**不能同时生效**，两套会互相拉扯」 | 那描述的是**没有优先级**时的情形。并进同一条管线并定死次序 + 命中即短路之后不会拉扯——Figma 两套同时开，顶点赢。次序见下 |

**教训**：AGENTS.md 的断言是二手的，判断一条能力在不在，去看代数本身。

## 模式与命令集

收敛后只剩一个开关：

```
动画   关 | 开     开时：拖动写关键帧、锁定原父级、底部时间线
```

命令集**不枚举模式组合**，由能力叠加：

```
基础能力   撤销、复制、删除、创建组件、对齐…      恒开
绘制能力   线 / 弧 / 圆 / 矩形 / 多段线 …          恒开
编辑命令   MOVE / COPY / ERASE                     恒开（只在命令行与面板，不占工具栏）
动画能力   打关键帧、删关键帧…                     动画=开 时
```

「当前能用什么」= 所有已开启能力的并集。一条规则同时管命令面板、命令行与工具栏——它们本来
就该是同一个集合的三种呈现。加第四种能力时不用回来重想一遍。

## 工具栏

```
[选择]  [缩放]  [旋转]                    指针与变换
────
[吸附]  [网格 ▾]                          辅助
────
[容器]  [文字]  [矩形]                    盒模型内容
[线 ▾]  [弧]   [圆]                       几何
```

**去掉**（都与既有手势重复）：框选工具（`select` 空白处拖拽即框选）、精确移动工具（`MOVE`
命令能键入精确位移，严格更强）、平移画布工具（空格/中键本来就是临时覆盖）、`draw-line`。

框选**判定模式**（窗口/交叉/方向敏感）保留为设置——模式不该偷偷改用户的设置。

### 步骤 1 · 曲线 Entity — `add-curve-entities` ✅

让「一条线」成为合法页面 Entity：core 可选 `Curve` Component（盒局部几何，`kind` union
留位）、几何写入漏斗（端点 → Curve + 紧包围盒同一事务）、stage-engine 距离窄相位命中、
`curve` 物料、工具栏点击添加。协议版本不变。

这一刀是整个论题的最小验证：线进场景树、能点选（点盒空角不选中）、能移动、能撤销、能预览、
能打位置与旋转关键帧——**旋转关键帧就是刀闸分/合的原语**。如果曲线在这条路上接不顺，损失
止于一刀。

刻意不做：弧/多段线/文字、绘图模式、CAD 框选语义、盒 resize 手势、端点几何关键帧。

**门槛**：五道 + 曲线纵向 e2e（添加 → 场景树 → 按距离命中 → 改端点 → 拖动 → 撤销 → 预览）
与关键帧 e2e。✅ 全绿，e2e 122 → 124。

**提案里最重要的一处判断被实测确认**：保留盒之后，场景树、属性面板、位置/旋转关键帧、
预览、撤销**没有写一行曲线专用代码**就可用——两条 e2e 正是为了钉住这一点。

**一处提案级修正（读代码才发现）**：以为 Stage 点选走 `StageSceneIndex.entityAtPoint`，
实际上 Stage 的点选是 **DOM 驱动**的（Entity 节点上挂 `onPointerDown`），`entityAtPoint`
只服务取色采样。因此「按距离而不是按盒」落在**两处**：DOM/CSS 那条（`.is-segment` +
物料的透明加宽 stroke，机制仓库里已有，line/arrow 就在用）与 `entityAtPoint` 那条。
线状判定改成按 `Curve` Component 而不是 Renderer 类型枚举。详见 change 的 design D4。

**创建入口定在 Palette 而不是 Stage 工具栏**：工具栏上的 line/arrow/circle 是拖拽绘制工具，
而本刀只做点击添加，Palette 的 `external.add` 恰好就是这条既有路径，零新代码。

**顺带修掉一处测试脆弱性**：`pointerDrop` 用 `boundingBox()` 作为按下点，而 Palette 可滚动
——新增一个 Preset 就把靠后的物料挤出视口，`boundingBox()` 仍返回坐标而按下位置已在面板之外
（ECharts 用例因此挂掉）。helper 补 `scrollIntoViewIfNeeded()`。

### 步骤 2 · 绘图模式 — `add-drafting-mode` ✅（模式外壳 + 画线）

Stage 的模式切换（会话状态，不进文档）：工具栏换成绘图工具、底部出命令行、十字线 + 捕捉
标记、CAD 选择语义（点中累加、Shift 移出、左窗口右交叉）。两点画线是第一个真手势——起点
终点各吸一次捕捉，非 100% 缩放验证。

捕捉候选从页面既有 `snapCandidates`（盒的六条参考线）扩展出**几何特征点**（端点、中点，
圆心/象限点随弧一起来）。命令行会话机、点输入解析从 `cad` 包搬运——它们不认识文档协议，
搬运成本低。

**门槛**：五道 + 绘图纵向 e2e（进模式 → `L↵` → 点两下 → 第二条起点捕捉到第一条端点 →
切回设计模式，线在场景树里、能撤销）与「命令进行中仍可平移」。✅ 全绿，e2e 124 → 126。

**命令引擎一行没搬**：`@compose-ui/commands` 本来就对 `TContext`/`TEffect` 泛型、连 `core`
都不依赖，Stage 只声明自己的两个类型。当初把它立成零依赖包的回报在这里兑现——若当时让它
认识 `CadDocument`，今天就要么改它的类型、要么写第二份。

**路线图这里写错了一处**：说「捕捉候选从既有 `snapCandidates` 扩展」。读代码后改口——
`snapCandidates` 返回 `{ axis, value }` 的参考**线**（Figma 式对齐），CAD 捕捉要的是一个二维
**点**。形状不同，是姐妹查询而不是扩展。v1 的候选因此只出曲线的端点与中点，**不出盒的角点**：
那正是对齐吸附覆盖的语义，两套同时生效会在同一次取点里互相拉扯。

**框选是白拿的**：`ComposeStageMarqueeMode` 已有 `directional`（左→右窗口、右→左交叉），
绘图模式切个默认值即可，零代码。

**一处对 CAD 优先级表的有意偏离**：CAD 里「命令取点」最高，Stage 把它排在 `pan` **之下**
——`pan` 是按住空格/中键的临时覆盖，命令进行中仍要能平移画布去看远处那个点。有一条 e2e 钉住它。

**顺带下沉两块共享物**：点输入管线与坐标语法从 `cad` 移进 `core`（两个消费者、无文档知识），
命令行组件从 `cad-canvas` 上移到 `components`（正好满足 AGENTS 的「两个第一方消费者」门槛）。
`ComposeGridSettings` 借此改成两轴独立——页面网格本就允许 X≠Y，单一步长会把一个轴吸错。
CAD 的 87 项既有用例不改一行即全绿，是这两次搬运没有改变行为的证据。

### 步骤 2b · 编辑命令与选择语义 — `add-drafting-editing-commands` ✅

`MOVE`/`COPY`/`ERASE` 与 CAD 选择语义一刀落地。两者是同一个用户故事的两半：选择语义单独
落地没有消费者，而 `MOVE` 的第一步就是「选择对象」——替换语义下点第二个对象会丢掉第一个，
三条命令全部退化成单选。

**门槛**：五道 + 选择语义 e2e（点中累加 → Shift 移出 → Esc 清空 → 切回设计模式恢复替换）
与编辑纵向 e2e（命令中选两条 → 基点 → `@60,0` → 一起走 → 一步撤销 → `E↵` 当场删 → `CO`
连续放两份）。✅ 全绿，e2e 126 → 128。

**选择语义是 Context 上的一个标记，不是第二套插件**：`StageInteractionContext.selectionMode`
（`'replace'` 默认 / `'accumulate'` 绘图），点选与框选读**同一张表**（`selection-mode.ts`）。
写成两套插件会把「命中一个 Entity 之后该做什么」复制两份，而那条路径里还有双击进文字编辑、
锁定判定、拖动接管、幽灵 ID 过滤四件与选择语义无关的事。分开写还会让「点着累加、框着替换」
这种没人设计过的组合悄悄出现。

**这一刀刻意不下沉**：`cad` 有形状一样的 `applyCadSelection`，但插件这边要的是四行分支，
而那个函数的契约里还有「内容不变时原样返回入参」——那是 `ComposeCadCanvas` 为了按引用判断
重绘加的。步骤 2 搬点输入管线是因为搬的是一整条求解；这里搬的是一个 `if`，够不着门槛。
共享的门槛是**行为会不会漂移**，不是「两处都有」。

**选择集归宿主，会话只是镜像**：CAD 的命令会话自己攒 `picked`（`selection` 输入是并入）。
Stage 不能照抄——选择集在这里已经存在（选中框、属性面板、场景树联动、Esc 清空）。会话攒第二
份，Shift 移出就只改宿主那份，用户看着两个对象被移出而命令仍作用在三个上。因此 Stage 的
`selection` 输入语义是**替换**，宿主在选择集变化时喂进当前完整选择集。这是对 CAD 会话的
有意偏离，理由是两边的选择集所有权不同。

**`MOVE` 与拖动共用的是提交漏斗，不是拖动预览**：`planMovePreview` 里的三样都是拖动特有的
——激活阈值区分「点一下」与「拖一下」（命令没有这个歧义，沿用会让小位移静默失败）、平移吸附
在命令路径上**违规**（基点与位移点已经各自过了点输入管线，再吸一次会改写键入的坐标）、落点
解析会把纯平移变成跨父级重挂载。共用点因此定在 `planTransformCommit`，产出**一条**
`entity.transform.set`，多选移动是一步撤销。

**一处实现中才发现的缺口**：累加语义下点空白**不清空**选择集（那是一次没框住东西的框选），
于是「怎么清空」在绘图模式里没有入口。补成 AutoCAD 的答案——没有命令在跑时 Esc 清空选择集。
提案里没写这一条，是把两套语义的差异只想到了「怎么加」而没想到「怎么减」。

**`createDuplicateCommand` 的 `+10` 让出成可选参数**：那个常量的语义是「复制一份别正好盖住
原件」，而 `COPY` 有真实位移，叠加固定偏移会让每个副本都偏出一个常量——在图上看着像手抖。

### 步骤 3 · 旋转基点 — `add-rotation-pivot` ✅（闭环完成）

**本节于 2026-08-23 由用户校正，原方案作废（原编号步骤 5）。** 原文写的是「命名片段住组件定义、状态住实例、
脚本用 `qs1.setState('open')`」。用户给出的实际流程是：

1. 刀闸由用户**画出来**；
2. 在**动画模式**下于动画面板给它刻角度关键帧；
3. 再由**脚本控制播放**。

也就是说这条路走的是**既有的动画能力**，不需要任何新抽象。读代码确认三段里有两段今天就通：
角度轨道是 `['Transform', 'rotation']`，动画模式的自动记录已经在写它
（`editor/animation-mode/auto-record.ts`）；播放由动画清单的 `playing` 布尔绑定驱动，脚本
导出一个布尔即可（`preview/playback/use-animation-playback.ts`）。曲线在步骤 1 就已经验证过
能打位置与旋转关键帧。

**因此本刀只剩一件事：旋转基点。** `stage-geometry.ts` 的实体矩阵是
`rotate ∘ translate(−盒中心)`——绕**盒中心**转。刀片绕**铰点**转，而铰点是刀闸的一端。
基点不解决，用户刻出来的每一帧角度都对，画面上刀片却在原地打转而不是绕轴摆动。

候选（提案阶段定夺，路线图不预先拍板）：

- **`Transform` 加基点**（归一化盒坐标或局部坐标）。改动面是矩阵求解、Stage 渲染、Preview
  渲染、rotate 手势与属性面板，采样器不受影响——它只写 `rotation` 这个标量。
- **不加字段，靠盒**：把盒撑大让铰点落在中心。零协议改动，但盒与画出来的几何不再吻合，
  命中、包围盒与场景树里读到的尺寸全部跟着失真。这是一条要在提案里显式否掉的路，不是备选。

**取消的东西一并记下，以免重提**：命名片段、实例状态、`setState` 脚本 API，以及老路线图
挂起的「变体切换表达成 step 轨道」——那个问题的前提（片段）已经不存在了。

**门槛**：五道 + 闭环纵向 e2e（绘图模式画线 → 设计模式设基点「左中」→ 动画模式 0 ms 刻 0°、
200 ms 刻 90° → 铰点不动、另一端扫过）。✅ 全绿，e2e 128 → 129。

**落地方案与提案一致**：`Transform.pivot` 可选、归一化盒坐标、缺席即中心。改动面比预估还小
——`matrixFromTransform` 里 `width / 2` 变成 `width * pivot.x`，渲染是
`composeEntitySceneStyle` 的一行 `transform-origin`。

**一处漏斗的回报兑现**：Stage Scene、Preview 与组件实例三条渲染路径共用同一个
`composeEntitySceneStyle`，因此变换原点只改了一处。若当初三处各写各的 style，这一刀要改三处
且永远无法确认第四处不存在。

**`decomposeMatrix` 的基点参数刻意做成必填**：给默认值会让漏传的调用点静默按中心分解，而合成
那一侧按真实基点——两者不再互逆，症状是手势提交后对象跳一下、位移量恰好等于基点偏移，且**只在
非中心基点的对象上出现**。必填让编译器逐个点出九处调用点。新建容器与新建组件实例这两处显式
传中心，是可复查的决定而不是默认值兜的底。

**顺带补了一处不变量的漏网**：`rotate-plugin` 内联了自己那份 Shift 切换，是「点选与框选读同一
张表」漏掉的**第三条**点选路径，改读 `resolveStageClickSelection`。

**判别性验证**：把 `transform-origin` 改回 `center`，闭环用例的偏差恰好是**半个线长**
（100.9px / 200px 的线）。这条数值对得上，说明用例测的正是它该测的东西。

**顺带更新 13 张黄金图**：Inspector 几何分组多了一个字段，凡是拍到属性面板的截图都变了。

### 步骤 4 · 词汇扩展 — 拆成两刀

**拆分依据（2026-08-23，读代码后）：文字与弧/多段线没有一行共享实现。** 弧与多段线扩的是
`Curve` Component 的 `kind` union，共用归一化、紧包围盒、距离、特征点、渲染、命中六条路径；
文字压根不碰 `Curve`——它是既有的 Text 物料，另一个 Component。放一个提案里就是两个不相干
的半边。

#### 4a · 弧与多段线 — `add-curve-vocabulary` ✅

`kind` union 扩到 arc / polyline。**整圆仍是 ±360 扫掠弧、矩形仍是闭合多段线**——两条判断
原样平移，理由与 `cad` 里一字不差。数学从 `cad/geometry` 搬运（`cad-arc-geometry.ts` 约 220 行、
`cad-polyline-geometry.ts` 约 44 行，都不认识文档，是纯形状运算）。

一处比 `cad` 更好的地方：多段线在页面里渲染成**一个** `<polyline>` 而不是 N 个 `<line>`，
`pointer-events: stroke` 天然承担命中；`cad` 里那句「一条多段线在 DOM 里是 N 个 `<line>`」
的代价在这边不存在。

**门槛**：五道 + 三条纵向 e2e（画圆/矩形/弧各成一个 Entity 且渲染分支正确、`PLINE` 攒成一个
Entity 且可放弃上一点、圆心捕捉）。✅ 全绿，e2e 129 → 132。

**搬运的证据**：`cad` 的 284 项用例**一个测试文件都没改**就全绿，两个几何文件净减 235 行。
改了一行就说明搬运顺手改了语义。

**整个模块一起搬，不按消费者拆**：`flattenComposeArc` 目前只有 CAD 侧的交叉框选与块展开用得到，
按「两个消费者」的counting 规则该留在 `cad`。但把它单独留下会让弧的数学横跨两个包，而那正是
「一半改了另一半没改」的温床。判据是**模块的内聚性**，不是逐个函数的消费者计数——这与上一刀
否掉「把四行选择集分支下沉」是同一条判断的两面。

**实现中发现的一处陷阱**：`composeCurvePoints` 原本的 TSDoc 写着「弧与多段线加入后在此扩展，
包围盒与平移因此不必各自认识 kind」。前半句对、后半句错——它对弧返回的是**决定紧包围盒的
那组点**（含象限点），拿它当端点集合会让象限点以端点优先级参与捕捉，还会凭空造出一批相邻点
的中点。特征点因此必须自己按 kind 分派。

**捕捉次序与 CAD 对齐**：`endpoint > midpoint > center > quadrant`，与 `CAD_SNAP_MODES` 同一
次序。两块画布的捕捉手感必须相同。

**`PLINE` 的 `U` 关键字不是文档撤销**：取点期间文档上什么都还没有，放弃的是会话里的顶点。
有一条 e2e 钉住这一点（放弃后画布上仍是 0 条曲线）。

**顺带修一个 `-0`**：归一化的平移量是 `-bounds.x`，原点处正好产出 `-0`。JSON 序列化会写成
`0`，因此它是一个只在 `Object.is` 与断言里现形的幽灵差异；在归一化的取整处 `+ 0` 掉。

#### 4b · 绘图模式的文字 — **作废**

结论曾是「完全复用页面 Text，`TEXT` 命令几乎不用写」。取消绘图模式之后它自动成立——文字就是
既有的 `draw-text` 工具，没有第二条路径要建。

其中一条结论仍然有效并**移交步骤 12**：DXF 的 TEXT 带基线锚点，而导入器是无 DOM 的纯函数，
需要一个 ascent 比例做换算。这次的承诺弱得多——它只是**导入那一刻的落点估计**，不是命中框
契约，因此不复活「字体栈与比例是一对不变量」那条警告。

### 步骤 5 · 组件内动画在实例里播放 — `add-instance-animation` ✅（播放侧）

`component-instance` Renderer 多了两条可绑定 Prop（`animation` 与 `animationTime`），
实例在「解析覆盖之后、喂给嵌套 Yoga 之前」按它们采样一次。

**提案推翻了这一步原本的问题设定。**路线图当时写着「要在提案里定的是**粒度**」，并给了两个
候选：接受 `Animations.items` 整份替换，或者把删掉的「暴露属性」声明请回来。两个都不用——
那段推理默认了「实例要改的是组件文档里的绑定」，于是撞上「数组只作为字段整体写入」。但实例
是宿主页面上的一个普通 Entity，而 Entity 早就有一套逐实例的绑定机制（`Bindings.rendererProps`）。
**把绑定放在宿主侧，粒度问题不是被解决的，是根本不存在**：八个刀闸就是八个 Entity。

顺带确认了一个既有事实：实例渲染器不向嵌套文档传 `scriptScope`，因此组件文档里那份
`Animations.bindings` 在实例内**永远解析不出东西**。以前它看起来像个待补的洞，现在它是对的。

**v1 只有 seek，没有时钟**，规范也从「play、pause、seek 与播放模式」收窄到只有 seek。刀闸
本来就是状态不是动作；而做 play/pause 就得在物料里养一个每实例的 rAF 加播放模式状态机，
那正是「导航会话没有 `dispose`」那条坑的形状。没有时钟的物料是纯函数，没有生命周期就没有
生命周期缺陷。

其余几条判断：播放头是**毫秒**不是归一化 0–1（钳制已经吃掉了 0–1 的主要好处，而多一种时间
单位要所有读代码的人先分辨手上是哪一种）；`animation` 缺席不采样且**不回退到清单第一条**
（与「不得回退到 `rootIds[0]`」同一条判断）；失效 id 保留原值并在 Inspector 标为失效
（抄 `Interaction.navigate.target` 的可判别性）。

`materials` 因此新增对 `animation` 的依赖，形状与既有的 `layout-engine` 依赖一样——同为第 1 层
headless 领域包，同样只为组件实例的嵌套 Runtime 服务。

**这一刀没有闭掉刀闸故事**，见下面的步骤 5b。

### 轨道 B · 闭环：让刀闸故事跑通

#### 步骤 5b · 让动画进得了组件文档 — `add-component-document-animation`

步骤 5 交付了**播放**，但没人能**做出**要播的东西——实现时才发现有两处各自独立的缺口：

### 轨道 A · 收敛：把两个世界合成一个

#### 步骤 7 · 命令词汇表合并 — `merge-command-vocabulary`

`ComposeCommandAction`（面板，`id/title/run()`）是 `ComposeCommandDefinition`（会话，
`id/aliases/title/start()`）的**退化情形**——一个立刻提交、没有 prompt 的会话。这个形态已经
在跑了（`ERASE` 预选时 `prompt` 就是 `null`）。

- `Action` 收进 `Definition`，一个注册表
- **可用性标记**（属于哪个能力、当前能不能执行）——没有它，面板会列出点了没反应的条目
- **命令历史**：上箭头召回、空 Enter 重复上一条。与 `operation-log` 的事务日志分清楚——一个
  记「我敲了什么」，一个记「文档变了什么」，一条命令可能产生零条或多条事务
- 上下文**不硬合并**：保持窄（选择集 + 文案 + dispatch），其余依赖在注册时闭包捕获
- 会话仍住 Stage，宿主**注入**自己的动作定义。合并的是「能敲什么」，不是「谁在跑」

#### 步骤 8 · 物料统一 — `unify-shape-materials`

- `Curve` 补三样：**填充**（闭合几何；要绕开 `composeEntityAppearanceStyle` 把纯色写到宿主
  盒的那条，否则画出的是矩形色块而不是形状内部）、**椭圆**（两个半径）、**端点 marker**
- 弧与多段线加 `viewBox` 参与 Auto Layout；**命中与捕捉应用同一个盒→几何变换**
- **删掉 `shape/` 物料**（它比 `curve/` 只多 marker 与椭圆两样）
- 工具栏的「圆」换成 Curve 椭圆；`draw-circle` / `draw-arrow` 一并删

**不新建 `materials/src/cad/`**：那个名字会把刚拆掉的界线挪进目录树，而且是按**来源**分组
而非按能力（AGENTS.md 禁止的那类桶）。基础图形已经有家——`curve/`；要做的是让 `shape/`
消失，而不是多一个分组。

**提案前必须确认**：现场页面文件里有没有 Shape 的 line/arrow/circle。没有就按「为零份文档
写迁移是纯粹的负债」直接删；有就要写迁移器，那是完全不同的工作量。

#### 步骤 9 · 十字光标下沉 — `extract-crosshair`

提到 `canvas-kit` 并补齐三形态（按等待的输入类型：取点画线、选对象画框、等键盘不画）、拾取框、
线在框处断开、触摸豁免。CAD 画布改用同一个组件，既有用例不改一行即全绿是搬运没有改变行为的
证据。

输入是**两个形态布尔**而不是 `prompt`：`accepts` 属于命令协议，而 canvas-kit 不能依赖它。

一处**诚实的不对等**要写进规范：CAD 的「拾取框边缘压住即命中」在 Stage 不成立——Stage 点选是
DOM 驱动的，容差散在各物料的 stroke 里，没有全局的那个数。

独立，可随时插队。已有一份写好的提案 `add-drafting-chrome` 可裁剪复用（其中的绘图工具栏部分
并入步骤 6/7，去 `draw-line` 部分并入步骤 6）。

#### 步骤 10 · 几何编辑模式 — `add-geometry-editing`

**原名「夹点编辑」，2026-08-23 按决策 11 改形状**：绘制与顶点编辑合并成一个模式，因此这一刀
同时交付两者的共用接线，而不只是给已有对象加夹点。

现状：选中一条斜线，出来的是**填充的蓝色矩形 + 四角手柄**。而老的 `shape/` 反而有端点 UI
（`lineSegmentForEntity`），判据写死在 `renderer.type === 'shape'` 上，曲线被挡在外面——新几何
拿到了更差的选中 UI。这一刀有一半是**把已有 UI 泛化**。

- 单击 → 选中：盒 + 四角手柄（拖手柄按决策 8 等比缩放几何）
- **双击 → 几何编辑**：顶点显形、**盒手柄隐藏**、光标变十字星、取点走点输入管线
- 选中绘制工具 → **同一个模式**，目标是一个还没落地的新对象；画完停在模式里可继续调
- 顶点必须是「热」的：点顶点开始拉伸，优先级显式排在点选之上，不靠插件注册顺序
- 逐 kind 的顶点集：line 两端点；polyline 全部顶点；arc 圆心 + 两端点 + 中点
- 矩形/椭圆双击也进模式，拖角时**升格成多段线**（决策 11）
- **对齐吸附并轨**：按「点输入管线」一节的次序接进来，并同步改掉 AGENTS.md 里「两套不能同时
  生效」那段

依赖步骤 8（盒与几何的关系要先定，否则「拖盒手柄」与「拖顶点」各干什么说不清）。

#### 步骤 11 · 符号组件：端口与导线 — `add-symbol-components`

端口从块定义搬到 Component Asset（组件局部坐标，一次声明全部实例都有）；导线是曲线 Entity，
端点是 `free | port` 引用，几何**求解不存储**。端口捕捉排在端点之前——像素级正确但没有绑定的
导线在屏幕上不可见。删除被绑定实体时端点冻结成自由端点。

开放问题：导线求解读布局快照还是读文档几何——实例在场景里是绝对定位，但求解时机要与布局求解
的帧序对齐。

依赖步骤 8。

#### 步骤 12 · DXF 入页面、拆除旧世界 — `add-dxf-to-scene`

DXF 导入产出场景 + 组件（BLOCK → Component Asset），按内容包围盒开场景。解析器与诊断聚合原样
复用，映射层重写目标。然后**删除** `CadDocument`、CAD 标签页、`cad-canvas`；`cad` 包中仍被
引用的纯数学下沉或随消费者搬家；AGENTS.md 与 README 的 CAD 段落重写。

依赖步骤 8 与 11——词汇齐了、端口导线有了页面对应物，才删得干净。

## 关于步骤顺序

**排序原则（2026-08-23 由用户定）：先最快闭环，再丰富细节，然后组件。**

- **轨道 B（步骤 5 ✅ → 5b）**只依赖已交付的步骤 3。5 交付了播放，5b 才让刀闸从画到动到
  脚本驱动**整条流程真正跑通**——之后轨道 A 的每一刀都能拿真实流程验证，而不是等到最后
  才知道通不通。
- **轨道 A（6→7→8→10→11→12）**是概念收敛：6 是概念重置（后面全部假定没有模式），7 依赖 6

## 踩过的坑

- **曲线的「接缝」「尖角被削平」「水平线点不中」是同一个根因**（2026-08-23 实测定位）。
  不是 SVG 的 `overflow`——`composeEntityOverflowStyle` 对叶子恒发**内联** `overflow: hidden`，
  内联压过样式表，`.compose-stage__node.is-segment { overflow: visible }` 那一条**从来没有
  生效过**。而曲线的盒是几何的紧包围盒，描边以几何为中心画、必然超出半个线宽，于是被盒切掉：
  尖角削平、端点圆头被切、水平线（盒高被钳到 1px）连命中都只剩几何那一条线，实测触达 0px。
  判据必须是 `Curve` Component 而不是 Renderer 类型——按物料类型枚举，每加一种线状物料都会
  漏掉这一处。**量具**：把线宽临时调到 24px 截图，裁剪与否一眼可见；命中则沿法向扫
  `elementFromPoint`。我最初把它错记成 SVG 的 `overflow`，那条记录已更正。

- **`vector-effect: non-scaling-stroke` 中和不了 HTML 祖先上的 CSS 变换**（2026-08-23）。
  它只作用于 SVG 文档片段**内部**的变换，而 Stage 的缩放来自 `.compose-stage__scene` 那个
  HTML 节点。症状最阴险的地方是 computed 值老老实实报 `non-scaling-stroke`，只断言属性
  生效的用例因此全绿，而屏幕上描边照样跟着涨——实测放大 4.22 倍后触达从 6px 变 29px。
  正确做法是反向除掉画布缩放：Stage 把 zoom 发成 `--compose-canvas-zoom`，物料写
  `calc(<宽度>px / var(--compose-canvas-zoom, 1))`；变量缺席即 1，预览与其它宿主自动回到
  页面单位。**量具是沿法向扫 `elementFromPoint` 量实际触达**——`getBoundingClientRect` 在
  SVG 几何元素上不含描边，量不出来。

- **只断言「机制被声明」而不是「机制起作用」的用例会全绿**。上面那条 `non-scaling-stroke`
  是活例：组件测试断言属性在、e2e 断言 computed 值对，两条都绿，而屏幕上是错的。量具找不到
  时该继续找，不该退而求其次换一个更弱的断言。

- **默认线宽 2 明显偏粗**（2026-08-23）。同一个仓库里 `CAD_DEFAULT_STROKE_WIDTH = 1`，两条
  「画出来的线」宽度差一倍。AutoCAD 出厂同样是一个像素的发丝线（默认 lineweight 0.25mm，而
  模型空间默认不显示 lineweight）。接线图靠**线的走向**传达信息，加粗只会让密集区糊成一片。

## 待修的缺陷

- **虚线图案由线宽推出，而两者已经不是同一个单位**（2026-08-23 发现）。
  `strokeDasharray` 的 `'8 4'` 实际写成 `线宽*4  线宽*2`，这在线宽也是世界单位时说得通；
  线宽改成屏幕像素之后，用一个屏幕量去推一个世界量就成了单位错配——线宽 1 时图案是 4/2
  世界单位，缩到 0.3 倍就看不见了。CAD 侧的 `dashPattern` 本来就是**独立于线宽**的世界量，
  页面这边迟早要跟上。改动会影响既有虚线曲线的外观，因此单独立项。


- **`shape/` 物料的 line / arrow 大概率有与曲线相同的裁剪问题**（推断，未实测）。它们同样是
  叶子、同样把描边画在盒边上，而曲线那条例外按 `Curve` Component 判定，覆盖不到它们。
  **不单独修**——步骤 8 删掉 `shape/` 时它一并消失。

  怎么订阅、断线怎么办，全部未定。
- **实例级动画绑定的粒度**：见步骤 5。接受整份数组替换，还是给绑定换一个对实例友好的形状。
- **动画开着时编辑命令的语义**：`MOVE` 一个已有对象是写关键帧还是改 `offset`？v1 的安全解是

  声明，不需要新机制。
- **图层的归属**：CAD 图层的 visible/locked 与场景树既有的显隐/锁定重叠，但 DXF 的 byLayer

- **AutoCAD GROUP（命名选择集）**：一个对象可同时属于多个组，树表达不了。等实际使用暴露需求
  再立项。
- **几何关键帧下的编辑语义**：「渲染用采样、命中用原件」在几何会动时产生可感分歧。步骤 3 校正

  时再答。
