# 绘图统一路线图：CAD 融入页面世界

## 文档定位

本文是「把 CAD 能力融入页面编辑器」的**纲领性路线图**，用于串联多个 OpenSpec 变更，不代表
当前已经稳定的公共 API。每一步都是一个独立可发布、可回退的 OpenSpec 提案；**路线图是方向，
提案才是权威**——每刀的提案只在轮到它时写，吸收前面各刀实现时发现的事实；本文在每刀完成
后回填实测结果与被推翻的预判。

本文**接替** `cad-document-roadmap.md` 的后续方向：那条路线（独立 CAD 文档类型，步骤 1–9）
已经走完并交付了全部图元数学、捕捉、命令行与 DXF 解析——这些原样存活；被本路线替换的是
「独立文档类型 + 独立编辑外壳」这个壳。

## 产品意图（2026-08-22 修订）

用户场景把方向定死了（2026-08-23 由用户当面校正，见步骤 3 与 5）：实施工程师画一张主接线图，
**刀闸是他自己画出来的普通对象**；进动画模式给它刻角度关键帧，再由页面脚本按遥信驱动播放。
这是 SCADA/HMI 组态，不是绘图。

因此分工是：**CAD 借的是画法，对象世界归页面。**

- **身份模型学 Figma**：画出来的东西是普通页面 Entity——进场景树、有属性面板、能打关键帧、
  能做成组件、被页面脚本控制。画的方式特殊，画出来的东西不特殊。
- **手感学 AutoCAD**：命令行驱动、对象捕捉、正交、十字线、左窗口右交叉框选。用户拿到的
  原图是 DXF，肌肉记忆是 CAD 的。
- **切换发生在模式层，不发生在文档层**：绘图模式是 Stage 的会话状态（参照 Figma 的
  Design/Draw 切换），换工具栏、换手势语义、加命令行；文档、场景树、属性面板、动画面板
  在两个模式下是同一套。

## 路线

每刀门槛一致：五道（`lint` / `typecheck` / `test` / `build` / `test:e2e`）+ 该刀自己的
端到端纵向用例；判别性断言先验红再实现。

### 步骤 1 · 曲线 Entity — `add-curve-entities` ✅

让「一条线」成为合法页面 Entity：core 可选 `Curve` Component（盒局部几何，`kind` union
留位）、几何写入漏斗（端点 → Curve + 紧包围盒同一事务）、stage-engine 距离窄相位命中、
`curve` 物料、工具栏点击添加。协议版本不变。

这一刀是整个论题的最小验证：线进场景树、能点选（点盒空角不选中）、能移动、能撤销、能预览、
能打位置与旋转关键帧——**旋转关键帧就是刀闸分/合的原语**。如果曲线在这条路上接不顺，损失
止于一刀。

刻意不做：弧/多段线/文字、绘图模式、CAD 框选语义、盒 resize 手势、端点几何关键帧。

**门槛**：五道 + 曲线纵向 e2e（添加 → 场景树 → 按距离命中 → 改端点 → 拖动 → 撤销 → 预览）
与关键帧 e2e。✅ 全绿，e2e 122 → 124。

**提案里最重要的一处判断被实测确认**：保留盒之后，场景树、属性面板、位置/旋转关键帧、
预览、撤销**没有写一行曲线专用代码**就可用——两条 e2e 正是为了钉住这一点。

**一处提案级修正（读代码才发现）**：以为 Stage 点选走 `StageSceneIndex.entityAtPoint`，
实际上 Stage 的点选是 **DOM 驱动**的（Entity 节点上挂 `onPointerDown`），`entityAtPoint`
只服务取色采样。因此「按距离而不是按盒」落在**两处**：DOM/CSS 那条（`.is-segment` +
物料的透明加宽 stroke，机制仓库里已有，line/arrow 就在用）与 `entityAtPoint` 那条。
线状判定改成按 `Curve` Component 而不是 Renderer 类型枚举。详见 change 的 design D4。

**创建入口定在 Palette 而不是 Stage 工具栏**：工具栏上的 line/arrow/circle 是拖拽绘制工具，
而本刀只做点击添加，Palette 的 `external.add` 恰好就是这条既有路径，零新代码。

**顺带修掉一处测试脆弱性**：`pointerDrop` 用 `boundingBox()` 作为按下点，而 Palette 可滚动
——新增一个 Preset 就把靠后的物料挤出视口，`boundingBox()` 仍返回坐标而按下位置已在面板之外
（ECharts 用例因此挂掉）。helper 补 `scrollIntoViewIfNeeded()`。

### 步骤 2 · 绘图模式 — `add-drafting-mode` ✅（模式外壳 + 画线）

Stage 的模式切换（会话状态，不进文档）：工具栏换成绘图工具、底部出命令行、十字线 + 捕捉
标记、CAD 选择语义（点中累加、Shift 移出、左窗口右交叉）。两点画线是第一个真手势——起点
终点各吸一次捕捉，非 100% 缩放验证。

捕捉候选从页面既有 `snapCandidates`（盒的六条参考线）扩展出**几何特征点**（端点、中点，
圆心/象限点随弧一起来）。命令行会话机、点输入解析从 `cad` 包搬运——它们不认识文档协议，
搬运成本低。

**门槛**：五道 + 绘图纵向 e2e（进模式 → `L↵` → 点两下 → 第二条起点捕捉到第一条端点 →
切回设计模式，线在场景树里、能撤销）与「命令进行中仍可平移」。✅ 全绿，e2e 124 → 126。

**命令引擎一行没搬**：`@compose-ui/commands` 本来就对 `TContext`/`TEffect` 泛型、连 `core`
都不依赖，Stage 只声明自己的两个类型。当初把它立成零依赖包的回报在这里兑现——若当时让它
认识 `CadDocument`，今天就要么改它的类型、要么写第二份。

**路线图这里写错了一处**：说「捕捉候选从既有 `snapCandidates` 扩展」。读代码后改口——
`snapCandidates` 返回 `{ axis, value }` 的参考**线**（Figma 式对齐），CAD 捕捉要的是一个二维
**点**。形状不同，是姐妹查询而不是扩展。v1 的候选因此只出曲线的端点与中点，**不出盒的角点**：
那正是对齐吸附覆盖的语义，两套同时生效会在同一次取点里互相拉扯。

**框选是白拿的**：`ComposeStageMarqueeMode` 已有 `directional`（左→右窗口、右→左交叉），
绘图模式切个默认值即可，零代码。

**一处对 CAD 优先级表的有意偏离**：CAD 里「命令取点」最高，Stage 把它排在 `pan` **之下**
——`pan` 是按住空格/中键的临时覆盖，命令进行中仍要能平移画布去看远处那个点。有一条 e2e 钉住它。

**顺带下沉两块共享物**：点输入管线与坐标语法从 `cad` 移进 `core`（两个消费者、无文档知识），
命令行组件从 `cad-canvas` 上移到 `components`（正好满足 AGENTS 的「两个第一方消费者」门槛）。
`ComposeGridSettings` 借此改成两轴独立——页面网格本就允许 X≠Y，单一步长会把一个轴吸错。
CAD 的 87 项既有用例不改一行即全绿，是这两次搬运没有改变行为的证据。

### 步骤 2b · 编辑命令与选择语义 — `add-drafting-editing-commands` ✅

`MOVE`/`COPY`/`ERASE` 与 CAD 选择语义一刀落地。两者是同一个用户故事的两半：选择语义单独
落地没有消费者，而 `MOVE` 的第一步就是「选择对象」——替换语义下点第二个对象会丢掉第一个，
三条命令全部退化成单选。

**门槛**：五道 + 选择语义 e2e（点中累加 → Shift 移出 → Esc 清空 → 切回设计模式恢复替换）
与编辑纵向 e2e（命令中选两条 → 基点 → `@60,0` → 一起走 → 一步撤销 → `E↵` 当场删 → `CO`
连续放两份）。✅ 全绿，e2e 126 → 128。

**选择语义是 Context 上的一个标记，不是第二套插件**：`StageInteractionContext.selectionMode`
（`'replace'` 默认 / `'accumulate'` 绘图），点选与框选读**同一张表**（`selection-mode.ts`）。
写成两套插件会把「命中一个 Entity 之后该做什么」复制两份，而那条路径里还有双击进文字编辑、
锁定判定、拖动接管、幽灵 ID 过滤四件与选择语义无关的事。分开写还会让「点着累加、框着替换」
这种没人设计过的组合悄悄出现。

**这一刀刻意不下沉**：`cad` 有形状一样的 `applyCadSelection`，但插件这边要的是四行分支，
而那个函数的契约里还有「内容不变时原样返回入参」——那是 `ComposeCadCanvas` 为了按引用判断
重绘加的。步骤 2 搬点输入管线是因为搬的是一整条求解；这里搬的是一个 `if`，够不着门槛。
共享的门槛是**行为会不会漂移**，不是「两处都有」。

**选择集归宿主，会话只是镜像**：CAD 的命令会话自己攒 `picked`（`selection` 输入是并入）。
Stage 不能照抄——选择集在这里已经存在（选中框、属性面板、场景树联动、Esc 清空）。会话攒第二
份，Shift 移出就只改宿主那份，用户看着两个对象被移出而命令仍作用在三个上。因此 Stage 的
`selection` 输入语义是**替换**，宿主在选择集变化时喂进当前完整选择集。这是对 CAD 会话的
有意偏离，理由是两边的选择集所有权不同。

**`MOVE` 与拖动共用的是提交漏斗，不是拖动预览**：`planMovePreview` 里的三样都是拖动特有的
——激活阈值区分「点一下」与「拖一下」（命令没有这个歧义，沿用会让小位移静默失败）、平移吸附
在命令路径上**违规**（基点与位移点已经各自过了点输入管线，再吸一次会改写键入的坐标）、落点
解析会把纯平移变成跨父级重挂载。共用点因此定在 `planTransformCommit`，产出**一条**
`entity.transform.set`，多选移动是一步撤销。

**一处实现中才发现的缺口**：累加语义下点空白**不清空**选择集（那是一次没框住东西的框选），
于是「怎么清空」在绘图模式里没有入口。补成 AutoCAD 的答案——没有命令在跑时 Esc 清空选择集。
提案里没写这一条，是把两套语义的差异只想到了「怎么加」而没想到「怎么减」。

**`createDuplicateCommand` 的 `+10` 让出成可选参数**：那个常量的语义是「复制一份别正好盖住
原件」，而 `COPY` 有真实位移，叠加固定偏移会让每个副本都偏出一个常量——在图上看着像手抖。

### 步骤 3 · 旋转基点 — `add-rotation-pivot` ✅（闭环完成）

**本节于 2026-08-23 由用户校正，原方案作废（原编号步骤 5）。** 原文写的是「命名片段住组件定义、状态住实例、
脚本用 `qs1.setState('open')`」。用户给出的实际流程是：

1. 刀闸由用户**画出来**；
2. 在**动画模式**下于动画面板给它刻角度关键帧；
3. 再由**脚本控制播放**。

也就是说这条路走的是**既有的动画能力**，不需要任何新抽象。读代码确认三段里有两段今天就通：
角度轨道是 `['Transform', 'rotation']`，动画模式的自动记录已经在写它
（`editor/animation-mode/auto-record.ts`）；播放由动画清单的 `playing` 布尔绑定驱动，脚本
导出一个布尔即可（`preview/playback/use-animation-playback.ts`）。曲线在步骤 1 就已经验证过
能打位置与旋转关键帧。

**因此本刀只剩一件事：旋转基点。** `stage-geometry.ts` 的实体矩阵是
`rotate ∘ translate(−盒中心)`——绕**盒中心**转。刀片绕**铰点**转，而铰点是刀闸的一端。
基点不解决，用户刻出来的每一帧角度都对，画面上刀片却在原地打转而不是绕轴摆动。

候选（提案阶段定夺，路线图不预先拍板）：

- **`Transform` 加基点**（归一化盒坐标或局部坐标）。改动面是矩阵求解、Stage 渲染、Preview
  渲染、rotate 手势与属性面板，采样器不受影响——它只写 `rotation` 这个标量。
- **不加字段，靠盒**：把盒撑大让铰点落在中心。零协议改动，但盒与画出来的几何不再吻合，
  命中、包围盒与场景树里读到的尺寸全部跟着失真。这是一条要在提案里显式否掉的路，不是备选。

**取消的东西一并记下，以免重提**：命名片段、实例状态、`setState` 脚本 API，以及老路线图
挂起的「变体切换表达成 step 轨道」——那个问题的前提（片段）已经不存在了。

**门槛**：五道 + 闭环纵向 e2e（绘图模式画线 → 设计模式设基点「左中」→ 动画模式 0 ms 刻 0°、
200 ms 刻 90° → 铰点不动、另一端扫过）。✅ 全绿，e2e 128 → 129。

**落地方案与提案一致**：`Transform.pivot` 可选、归一化盒坐标、缺席即中心。改动面比预估还小
——`matrixFromTransform` 里 `width / 2` 变成 `width * pivot.x`，渲染是
`composeEntitySceneStyle` 的一行 `transform-origin`。

**一处漏斗的回报兑现**：Stage Scene、Preview 与组件实例三条渲染路径共用同一个
`composeEntitySceneStyle`，因此变换原点只改了一处。若当初三处各写各的 style，这一刀要改三处
且永远无法确认第四处不存在。

**`decomposeMatrix` 的基点参数刻意做成必填**：给默认值会让漏传的调用点静默按中心分解，而合成
那一侧按真实基点——两者不再互逆，症状是手势提交后对象跳一下、位移量恰好等于基点偏移，且**只在
非中心基点的对象上出现**。必填让编译器逐个点出九处调用点。新建容器与新建组件实例这两处显式
传中心，是可复查的决定而不是默认值兜的底。

**顺带补了一处不变量的漏网**：`rotate-plugin` 内联了自己那份 Shift 切换，是「点选与框选读同一
张表」漏掉的**第三条**点选路径，改读 `resolveStageClickSelection`。

**判别性验证**：把 `transform-origin` 改回 `center`，闭环用例的偏差恰好是**半个线长**
（100.9px / 200px 的线）。这条数值对得上，说明用例测的正是它该测的东西。

**顺带更新 13 张黄金图**：Inspector 几何分组多了一个字段，凡是拍到属性面板的截图都变了。

### 步骤 4 · 词汇扩展 — 拆成两刀

**拆分依据（2026-08-23，读代码后）：文字与弧/多段线没有一行共享实现。** 弧与多段线扩的是
`Curve` Component 的 `kind` union，共用归一化、紧包围盒、距离、特征点、渲染、命中六条路径；
文字压根不碰 `Curve`——它是既有的 Text 物料，另一个 Component。放一个提案里就是两个不相干
的半边。

#### 4a · 弧与多段线 — `add-curve-vocabulary` ✅

`kind` union 扩到 arc / polyline。**整圆仍是 ±360 扫掠弧、矩形仍是闭合多段线**——两条判断
原样平移，理由与 `cad` 里一字不差。数学从 `cad/geometry` 搬运（`cad-arc-geometry.ts` 约 220 行、
`cad-polyline-geometry.ts` 约 44 行，都不认识文档，是纯形状运算）。

一处比 `cad` 更好的地方：多段线在页面里渲染成**一个** `<polyline>` 而不是 N 个 `<line>`，
`pointer-events: stroke` 天然承担命中；`cad` 里那句「一条多段线在 DOM 里是 N 个 `<line>`」
的代价在这边不存在。

**门槛**：五道 + 三条纵向 e2e（画圆/矩形/弧各成一个 Entity 且渲染分支正确、`PLINE` 攒成一个
Entity 且可放弃上一点、圆心捕捉）。✅ 全绿，e2e 129 → 132。

**搬运的证据**：`cad` 的 284 项用例**一个测试文件都没改**就全绿，两个几何文件净减 235 行。
改了一行就说明搬运顺手改了语义。

**整个模块一起搬，不按消费者拆**：`flattenComposeArc` 目前只有 CAD 侧的交叉框选与块展开用得到，
按「两个消费者」的counting 规则该留在 `cad`。但把它单独留下会让弧的数学横跨两个包，而那正是
「一半改了另一半没改」的温床。判据是**模块的内聚性**，不是逐个函数的消费者计数——这与上一刀
否掉「把四行选择集分支下沉」是同一条判断的两面。

**实现中发现的一处陷阱**：`composeCurvePoints` 原本的 TSDoc 写着「弧与多段线加入后在此扩展，
包围盒与平移因此不必各自认识 kind」。前半句对、后半句错——它对弧返回的是**决定紧包围盒的
那组点**（含象限点），拿它当端点集合会让象限点以端点优先级参与捕捉，还会凭空造出一批相邻点
的中点。特征点因此必须自己按 kind 分派。

**捕捉次序与 CAD 对齐**：`endpoint > midpoint > center > quadrant`，与 `CAD_SNAP_MODES` 同一
次序。两块画布的捕捉手感必须相同。

**`PLINE` 的 `U` 关键字不是文档撤销**：取点期间文档上什么都还没有，放弃的是会话里的顶点。
有一条 e2e 钉住这一点（放弃后画布上仍是 0 条曲线）。

**顺带修一个 `-0`**：归一化的平移量是 `-bounds.x`，原点处正好产出 `-0`。JSON 序列化会写成
`0`，因此它是一个只在 `Object.is` 与断言里现形的幽灵差异；在归一化的取整处 `+ 0` 掉。

#### 4b · 绘图模式的文字 — `add-drafting-text`

**结论：完全复用页面 Text，而且比路线图原本设想的更彻底。** 字段一一对上——`height`(字号 em)
就是 `fontSize`（场景单位本来就是 px，**不用换算**）、`content` 就是 `text`（而且能绑定脚本
导出）、`rotation` 走 `Transform.rotation` + 步骤 3 的基点、`align` 就是 `textAlign`、
Hug 宽度天然单行。

白拿三样：

1. **`CAD_TEXT_ADVANCE_RATIO` 等三个比例与等宽字体约束整个消失。** 它们存在的唯一理由是
   `cad` 无 DOM 拿不到字体度量。AGENTS 里「字体栈与这三个比例是一对不变量，换字体不换比例
   命中框会从字形上漂开」那条警告随之作废。
2. **「文字按包围盒命中不算破例」那段解释不需要存在**：页面 Text 是 DOM 节点，点选本来就按盒。
3. **`TEXT` 命令几乎不用写**：页面已有 `draw-text`（按一点、Hug 宽度、双击原地编辑），正是
   AutoCAD 的 TEXT 流程，且原地编辑比命令行输入好用。绘图模式派发同一条路径即可。

**一处真的对不上**：`CadText.position` 是**基线锚点**，页面 Text 的 `offset` 是**盒左上角**。
创建时可以换算，但之后改字号 CAD 里基线不动、页面里盒顶不动，两者分岔。判断是 **v1 用盒
左上角**，与绘图模式创建的其它 Entity 一致；混着来更糟，而单行标签放下就不怎么改字号。

**连带影响记在这里，别让步骤 7 的人以为比例活过来了**：DXF 的 TEXT 带基线锚点，而导入器是
无 DOM 的纯函数，换算 ascent 又要用到刚删掉的比例。但这次的承诺弱得多——它只是**导入那一刻
的落点估计**，不是命中框契约；落点差一两像素，页面随后按真度量渲染与命中，「渲染与命中必须
一致」那条不变量不受影响。今天 `cad` 里那个比例是渲染与命中**共同**依赖的，那才是危险的。

### 步骤 5 · 组件内动画在实例里播放 — `add-instance-animation`

**规模答案由用户于 2026-08-23 给出**：几十个刀闸时把刀闸做成组件，**动画在组件里刻一次**，
实例各自赋值。读代码确认这条路数据模型上是通的，而且大半已经具备：

| 需要什么 | 现状 |
| --- | --- |
| 组件文档得是个动画作用域 | ✅ 组件根**必须是 Frame**（`component-file.ts`），而清单正挂在 Frame 的 `Animations` 上 |
| 采样器能作用于组件的嵌套文档 | ✅ 已泛型到「任何带 `entities` 的文档」，一个字符不用改（当初为 CAD 做的泛化第二次兑现） |
| 实例得渲染一份完整嵌套文档 | ✅ 实例渲染器本来就跑嵌套文档 + 独立 Yoga runtime |
| 每个实例能有自己的值 | ✅ `instanceOverrides` 的 `set-field` 就是它——见下方「一处被文档误导的判断」 |
| **实例内部会被采样** | ❌ **唯一的缺口**：`applyComposeAnimationAtTime` 的消费者只有顶层文档，实例内部是静态的 |

**一处被文档误导的判断（记下来以免重演）**：评估时曾断言「每实例状态无处安放」与「覆盖表达
不了轨道」，两条都是错的，来源是 AGENTS.md 当时写着「`instanceOverrides` 只含结构操作；暴露
属性已删除」。代码里覆盖代数是**七种**，`set-field` / `remove-field` / `add-component` /
`remove-component` 四种改值；旧的暴露属性正是被**迁移成 `set-field`**
（`migrateLegacyComposeInstanceOverrides`）——删掉的是那层声明，能力被一个更强的东西接管了。
AGENTS.md 已同步改正。**教训**：AGENTS 的断言是二手的，判断一条能力在不在，去看代数本身。

剩下要在提案里定的是**粒度**而不是可行性：清单 `Animations.items` 是数组，而覆盖「数组只作为
字段整体写入，绝不生成数组下标路径」，因此按实例改 `bindings.playing.exportName` 等于替换整份
`items`，之后定义端对该数组的改动会被实例遮住。这是覆盖遮蔽的老问题，仓库已有 Apply/Revert
chrome 兜底；候选是接受整份替换、或给绑定换一个对实例友好的形状。

**依赖步骤 3**：组件里那把刀闸同样要绕铰点转。

### 步骤 6 · 符号组件：端口与导线 — `add-symbol-components`

端口从块定义搬到 Component Asset（组件局部坐标，一次声明全部实例都有）；导线是曲线 Entity，
端点是 `free | port` 引用，几何**求解不存储**（移动、复制、撤销、导入自动正确的那条论证
原样成立）。端口捕捉排在端点之前——像素级正确但没有绑定的导线在屏幕上不可见。
删除被绑定实体时端点冻结成自由端点。

开放问题（轮到时答）：导线求解读布局快照还是读文档几何——实例在场景里是绝对定位，但求解
时机要与布局求解的帧序对齐。

### 步骤 7 · DXF 入页面、拆除旧世界 — `add-dxf-to-scene`

DXF 导入产出场景 + 组件（BLOCK → Component Asset），按内容包围盒开场景。解析器与诊断
聚合原样复用，映射层重写目标。然后**删除** CadDocument、CAD 标签页、`cad-canvas`；`cad`
包中仍被引用的纯数学下沉或随消费者搬家；AGENTS.md 与 README 的 CAD 段落重写。

## 踩过的坑

- **`vector-effect: non-scaling-stroke` 中和不了 HTML 祖先上的 CSS 变换**（2026-08-23）。
  它只作用于 SVG 文档片段**内部**的变换，而 Stage 的缩放来自 `.compose-stage__scene` 那个
  HTML 节点。症状最阴险的地方是 computed 值老老实实报 `non-scaling-stroke`，只断言属性
  生效的用例因此全绿，而屏幕上描边照样跟着涨——实测放大 4.22 倍后触达从 6px 变 29px。
  正确做法是反向除掉画布缩放：Stage 把 zoom 发成 `--compose-canvas-zoom`，物料写
  `calc(<宽度>px / var(--compose-canvas-zoom, 1))`；变量缺席即 1，预览与其它宿主自动回到
  页面单位。**量具是沿法向扫 `elementFromPoint` 量实际触达**——`getBoundingClientRect` 在
  SVG 几何元素上不含描边，量不出来。

## 待修的缺陷

- **水平线与垂直线几乎点不中**（2026-08-23 手工测试发现，已实测确认）。曲线的命中靠物料
  内部那条透明加宽 stroke，而 SVG 的 `overflow: visible` **只让描边画出去，不让它接命中**——
  命中被 SVG viewport 裁掉，而水平线的 viewport 高度正是被钳到 `COMPOSE_CURVE_MIN_EXTENT`
  的那 1px。实测：斜线（盒 296×104）在离线 0–6px 内都命中，正是 12px stroke 的半宽；水平线
  （盒 296×1）只有 0px 命中，偏 2px 就落空。接线图里水平与垂直恰恰是最常见的两种线。
  Shape 物料的 line/arrow 是同一个形状的问题，因此这是**既有缺陷**而不是曲线引入的。
  修法要答一个问题：外扩量必须是**屏幕像素**（命中容差本来就是屏幕量），而物料不知道 zoom；
  候选是 Stage 把 zoom 作为 CSS 变量传下去用 `calc()` 外扩，或者慷慨地外扩一个大的世界量——
  后者不会造成误命中，因为实际命中区仍由非缩放的 stroke 决定，外扩只是给它让出地方。

## 未定的决策

- **图层的归属**：CAD 图层的 visible/locked 与场景树既有的显隐/锁定重叠，但 DXF 的图层
  语义（byLayer 颜色继承）页面世界没有对应物。候选：图层退化成 Group、或成为标签式的
  命名选择集。定夺推到步骤 7（DXF 映射时必须答）。
- **AutoCAD GROUP（命名选择集）**：一个对象可同时属于多个组，树表达不了。等场景树里的
  实际使用暴露需求再立项。
- **端点夹点编辑与盒 resize 的关系**：盒缩放该不该等比缩放几何点，与夹点手势一起答
  （步骤 2 或 4）。
- **几何关键帧下的编辑语义**：「渲染用采样、命中用原件」在几何会动时产生可感分歧，
  老路线的这条警告仍然成立。步骤 3 校正后**不再触发它**——刀闸摆动走的是
  `Transform.rotation`，几何一动不动，看得见的线与点得中的线仍在同一个地方。真要动几何
  （端点轨道）时再答。

## 关于步骤顺序

**排序原则（2026-08-23 由用户定）：先最快闭环，再丰富细节，然后组件。** 3–7 因此按现在的
编号重排过一次，判据不是依赖关系而是**什么时候能拿到一条走得通的完整流程**。

1（曲线）是地基且风险最集中，必须最先；2（绘图模式）与 2b（编辑命令）交付了「怎么画、怎么
改」。到这里对象已经画得出来，但**还不会动**。

**3（旋转基点）因此提到最前**：它是「画出来的刀闸真的会摆动」唯一还缺的一环，做完就有一条
从画到动到脚本驱动的完整纵向流程。它只改旋转基点，与词汇、端口、导线全都无关，因此不欠任何
前置。**先闭环的价值不是省事，是让后面每一刀都能拿真实流程验证**——弧画出来之后立刻可以打
关键帧看它转，而不是等到第 7 步才第一次知道整条路通不通。

4 拆成 4a（弧与多段线）与 4b（文字）：两者没有一行共享实现，风险都低，靠 2 已有的绘制
入口就能验证。
5（组件内动画）依赖 3——组件里那把刀闸同样要绕铰点转。
6（端口与导线）依赖 4a（导线是多段线级词汇）。
7（DXF 与拆除）收尾，依赖 4a 与 4b（词汇齐了才有映射目标），与 5、6 可并行。
