用真实浏览器（有头 Chromium）驱动 `apps/example/` 示例编辑器，把一张 1920×1080 的储能监控大屏效果图

## 一、已确认的缺陷

### T-1　中文 Hug 文本必定折行，并被裁成最后一个字　【严重】　**已修**

**复现**：文字工具点画布 → 输入「电站总数」→ `Escape`。不改任何属性。

**看到**：画布上只剩一个「数」。

**证据**：

| 内容 | 节点宽(Hug) | 节点高(Hug) | span 实际高 | 行数 |
|---|---|---|---|---|
| 电站总数 | 47.6875px | 15px | 29.8px | 2 |
| 运行 | 23.8438px | 15px | 29.8px | 2 |
| 华东储能电站 | 71.5156px | 15px | 29.8px | 2 |
| ABCDEFG | 56.2656px | 15px | 13.2px | 1 |
| Hello World Foo | 89.8125px | 15px | 13.2px | 1 |

节点 `overflow: hidden` 且 Hug 高度只留一行，第二行被裁掉，屏幕上只剩最后一个字。
与画布缩放无关（100%、88%、69% 都复现）。

**根因**：`-webkit-locale`。中日韩字形回退**由 locale 决定而不由 `font-family` 决定**：
同一条 `Inter, ui-sans-serif, system-ui, sans-serif` 把「运行监控大屏」在 `en` 下排成
159.95px、`ja` 下 165.33px、`zh-CN` 下 168px——三套字体、三种字宽，样式表一个字节没变。

而 locale 来自环境：渲染节点继承 Stage 根上的 `lang`（`compose-stage.tsx` 的
`lang={resolvedLocale}`，编辑器 UI 语言，默认 `zh-CN`），测量宿主挂在 `document.body` 上、
继承的是**宿主页面**的 `<html lang="en">`。两者恒不相等，于是量出来比渲染窄，配上
`overflow-wrap: anywhere`（每个汉字都是合法断点）必折。拉丁文字不中招，因为两种 locale
选中的是同一个字体——这也是「换一台机器才冒出来」的原因。

**曾经写在这里的那条根因是错的**：此前归因为渲染端 `display:flex` 套 `width:100%` 的
亚像素取整。逐段二分推翻了它——渲染那一侧的可用宽度实测比测量值还**多**出不到一个布局
单位（1/64px）。按那条错根因加的 `Math.ceil` 能治 12px 却治不了 28px（差 1.34px/字）。

**修法**：渲染与测量**都不读环境**，共用 `COMPOSE_TEXT_LAYOUT_LOCALE`
（`packages/materials/src/text/defaults.ts`）。这样同一份文档在 Stage、预览与导出页里
逐像素相同，而 adapter 也不必去读 Scene DOM（架构边界明令禁止）。取 `zh-CN` 而不是
`""`(auto)：Stage 今天就跑在 `zh-CN` 上，钉住它渲染一个像素不变、只有测量跟上。
同时删掉了那两处 `Math.ceil`——它与「量化不作用于布局求解结果，Hug 的文字测量宽度本就是
真实小数」相抵触。

实测（28px 十个汉字）：盒 267→280、盒高/内容高 33/80→40/40、行盒数 2→1。

### T-2　排版分组的「行高」显示一个渲染并不使用的数　**已修**

新建 12px 文字，属性面板「行高」显示 `14.4`；28px 时显示 `33.6`。而 DOM 上的
`line-height` 计算值是 `normal`，28px 的真实行盒高 40。面板在字段缺席时顶替
`字号 × 1.2`，那个数渲染与测量都不读。用户照它微调（比如从 33.6 调到 34）文字反而**变矮**
6px；而一旦写下一个数就再也回不到 Auto——面板没有「清空」的入口。

**修法**：行高改为**可缺席**（`v.optional`），缺席即 CSS `normal`，面板照产品既有的
「未设置 + 存在性开关」呈现，不再顶替一个数；关掉存在性是**删掉字段**而不是写一个值。
勾上时的起始值按当前字号推（`字号 × 1.2`）——面板自己造的初值是 `0`，而 `line-height: 0`
会把每一行压进同一个像素。

**曾经写在这里的一条判断是错的**：此前说「Hug 高度按 15px 给，文字底部被裁掉约 2px」。
15px 就是那一行的正确盒高；34px 的 span 是**折行**的结果，也就是 T-1，不是行高的问题。

### C-1　颜色 HEX 输入：Enter 不提交，缺 `#` 静默丢弃　【严重】　**已修**

**复现**：选中容器 → 背景填充 → HEX 框输入 `#0D1B3A` → 回车。

**看到**：输入框显示 `#0D1B3A`，画布上颜色**没变**。色板 chip 与色盘拖动都正常。
输入后 blur（Tab / 点别处）才生效。不带 `#` 的 `0D1B3A` 即使 blur 也被丢弃，无任何提示。

**证据**：`packages/components/src/color-picker/compose-color-picker.tsx:318` 与 `:334`，
两个 HEX 输入都是 `defaultValue` + **只有 `onBlur`**，没有处理 Enter；
`normalizeComposeColor()` 拒绝不带 `#` 的值时直接返回，不回显错误。

**期望**：Enter 提交；非法输入给出可见反馈，或容忍省略 `#`。

**影响**：照着设计稿填色是主路径，而设计稿给的就是 HEX。

**修法**：抽出 `packages/components/src/color-picker/hex-input.ts`，四个 HEX 框共用——
Enter 与 blur 都提交、省略 `#` 也收（纯十六进制串自动补上）、非法值当场退回当前值，
因此「打了什么都没发生」这一档不复存在。

### C-2　同一个属性面板里两套颜色弹框，HEX 一个露一个藏　**已修**

「背景填充」走 `ComposePaintPicker`（纯色/渐变/图片三个 tab，HEX + RGBA 直接可见）；
「边框颜色」「文字颜色」走 `ComposeColorPicker` 弹框形态，HEX 被折进默认收起的
`<details>「精确」`。同一件事（挑一个颜色）两种形态、两个位置。

**这不是疏漏，是一条要推翻的既有决定**：规范明写「默认（带 Trigger 的）形态的可见 UI
MUST 不显示 HEX、RGB、HSL 或 CSS 文本输入」。推翻它的理由是这个产品的主路径——实施工程师
照着设计稿搭大屏，而设计稿给的就是 HEX；代价不对称，多一行读数是看得见的一点拥挤，藏起来
是用户找不到。

**修法**（OpenSpec `update-color-picker-hex-parity`）：删掉折叠块，两种形态共用同一块值行
（HEX + 只读 RGBA + 不透明度 + 吸管 + 透明），差别只保留**面板内色块**——默认形态的
Trigger 上已经有一个。顺带收掉一处源码重复：这块值行此前写了两份，露哪一份由样式表决定
（内嵌形态把折叠块整个 `display: none`），改其中一份的人很容易漏掉另一份。

### L-1　加上 Auto Layout / Grid 之后，属性面板的布局分组是空的　【严重】　**已修**

**复现**：选中容器 → 布局「＋」→ 选 Auto Layout。

**看到**：布局分组里只有标题「Auto Layout」和一个 `⋯`，**方向/换行/项间距/主轴/交叉轴/内边距
全部缺席**。等 6 秒不出现；点面板、点画布上这个容器本身，都不出现。
必须**把选择切到别的对象再切回来**才出现。Grid 同样（列数/行高/项间距/内边距/空洞自动填上）。

**判别性验证**：空容器加完布局立刻读 → 无字段；不加任何子项、只把选择切走再切回 → 字段全在。
因此与「有没有子项」无关，是纯粹的面板不刷新。**重选同一个对象不够**——必须是一次真正的选择变化。

**影响**：绝大多数人加完看到一个什么都调不了的空分组，会认为这个功能坏了。
自动化里为此每个布局容器多走两次选择切换，96 个容器就是 192 次。

**给场景加布局时这条更难绕过**：常用的绕法是「先点场景再点回来」，而目标本身就是场景时，
场景不能当那个「别的对象」——必须在树里另找一个节点。第一次给画布加网格就栽在这里，
四个网格字段一个都没写进去，而屏幕上看起来只是「网格加上了」。

**根因与修法**：`entity-inspector.tsx` 里「Component 缺失」与「Component 存在」两个分支
用的是**同一个** `key`，而分组在折叠时会卸载子级——于是缺失态那份折叠状态泄漏到了存在态，
看起来就是「加完什么都没有」。两个分支各带自己的 key 后，加完布局字段当场展开。
实测 flex 7 个字段、grid「列数」、场景 grid「列数」全部一次到位，无需任何选择切换。

### L-2　往 Auto Layout 容器里拖第二个子项，会落进第一个子项内部　【严重】　**已修**

**复现**：建容器 → 设成纵向 Auto Layout（gap 8、padding 12）→ 从物料面板往容器中心连拖三个容器。

**看到**（已在「默认高度不再拉伸」之后复测，仍然复现）：

```
流容器 400×300
└ 子0 320×240
  └ 子1 320×240      ← 落进了子0 里面
    └ 子2 320×240    ← 又落进了子1 里面
```

根因不是拉伸，而是**落点取指针下最深的容器**：默认 320×240 的第一个子项本来就盖住了父容器中心，
此后每一次拖放都落进上一个子项。改掉默认拉伸只是让子项不再被撑满，挡不住这条。

**期望**：往一个布局容器里拖东西应追加为同级子项，并在画布上给出插入位置指示线（Figma 的做法）。

**绕过**：用场景树的「新增节点」按钮，结果正确（两个同级子项按列排下来）；
或者先按绝对坐标建好全部子项、最后再给父容器加布局（本次还原采用的顺序）。

**修法**（OpenSpec `update-flow-container-drop`）：**Flex 容器的 Flow 子级不接管落点**——
那个盒是父级排出来的，不是作者写的；在排队容器里「放进它」与「放到它旁边」在屏幕上是同一块
面积，而用户做的绝大多数是排队。要钻进去按 `Alt`（那正是它的既有语义）。

顺带补齐两处：Flex 容器跨容器落进来时**解算插入位**（网格早就有这一支，flex 却直接退成一句
`reparent`），既有的插入指示线因此直接生效；最内层容器不满足「深入内部」判定时**上浮到最近
一个满足的祖先**，而不是交回「没有落点」——后者的症状是贴着子项边缘拖过去松手，什么都没发生。

**这一条最容易漏的是**：L-2 报的复现走的是物料面板拖放（`externalDrop` 直接取
`containerAtPoint`），**根本不经过**画布拖动那个解算器。规则因此抽成一处给两条路共用，
而第一版 e2e 落点没打在第一个子级身上，是一条永远绿的假用例。

### G-2　启用 Grid 只能用默认参数，之后没有任何入口能按新几何重新落位　【严重】　**已修**

**背景**：整张大屏可以建在一个 12 列画布网格上——列宽 147、行高 36、间距 12、内边距 12，
`12*147 + 11*12 + 2*12 = 1920`；12 个顶层块正好铺满 12 列 × 22 行，互不重叠。
场景（Frame）本身接受布局，因此「画布是网格布局」这条路是通的
（证据图 [dashboard-canvas-grid.png](dashboard-canvas-grid.png)）。

**复现**：按上面的几何建好 12 个块（每块矩形都精确落在格线上）→ 给场景加 Grid →
把列数/行高/项间距/内边距设成 12/36/12/12。

**看到**：12 块里 11 块的落位与它们的像素位置不符，行号还一路被推大（写 row 16 读回 27），
整张图纵向膨胀到 37 行、溢出场景。

**根因**（逐块复算确认，12/12 吻合）：`planEnableComposeGridLayout` 在**启用那一刻**
按当时的网格参数从像素推落位，而菜单项只提供**默认网格**（12 列 / 行高 48 / 行间距 6 /
内边距 16）。我的几何按 36/12/12 设计、参数是启用之后才改的——于是 180px 在默认的
「行高 48 + 间距 6」下算出 3 行（`round((180+6)/54)`），在我的几何下本该是 4 行；
列同理，内边距 16 与我的 12 差 4px，`floor((489-16)/157.83) = 2` 而不是 3。

**推断本身没有错**：`nearestCell()` 的 `round((box + gap) / step)` 对它当时看到的那个网格
是正确的。真正的缺口有两个，都在工作流上：

1. **启用时无法指定网格参数**。菜单上只有「网格 12 列」一项，行高/间距/内边距一律取默认值。
2. **改完参数之后落位不重推，也没有重推的入口**。「更多网格操作」里只有
   「切换为自动布局」和「移除网格」；实测把行高改成 36、间距改成 12 之后，
   已有子项的 `网格位置/网格尺寸` 一个字节不动。用户只能逐个手填 12 个块的四个数。

**期望**：网格参数改变后提供一条「按当前几何重新落位」——解算逻辑已经现成
（`nearestCell` + 求解器），缺的只是入口。

**修法**：「更多网格操作」里新增「按当前几何重新落位」（`planReflowComposeGridLayout`）。
关键是它读**作者写下的** `LayoutItem`（offset 与 width/height 的 `value`）而不是求解后的
快照盒——网格一旦接管，快照就是网格自己的输出，照它重推是个恒等变换（第一版就是这么写的，
一个字节都不动）。实测 11/12 错 → 点一下 0/12 错。

**附带**：「空洞自动填上」默认开着，因此写进去的行号会被上浮压缩（写 row 1 读回 row 0）。
这是 GridStack 式的设计行为、关掉开关即守住，不是缺陷——但它与上面那条叠在一起时，
用户很难判断自己看到的错位到底来自哪一个。

**范围说明**：带完整内容（321 实体 + 96 卡内布局）的画布网格版本没有跑完——
在这台机器上那一趟耗时异常（同样工作量前一次 838s、这次 18229s，期间有并发任务），
中途有 4 个卡内布局和画布落位超时。因此本条证据取自 12 块的隔离用例，
它与完整版读到的落位数值**逐字相同**，结论不受影响。

### L-3　Grid 子项的尺寸输入被禁用，但没有任何说明　**已修**

容器进了 Grid 之后 `尺寸宽度`/`尺寸高度` 变成 disabled，改由 `网格尺寸 宽/高`（跨几列几行）决定。
这个设计是对的，但面板上没有一个字解释为什么这两个框按不动了。

**修法**：两个框下面写一行「尺寸由网格决定，改下面的「网格尺寸」」。写在框**外面**而不是挂
`aria-describedby`——框已经 `disabled`、聚焦不到它，挂上去等于没写；也只写一次而不是每个轴
写一遍，两个轴的理由恒相同。

只读还有第二个来源（`resize: 'none'`，Group 与接线点），**那一档不写**：同一个面板里的
「几何约束 › Resize 模式：禁止」已经说了，再写一句是把同一件事说两遍。因此内部记的是
**原因**而不是一个布尔——两种只读对代码是同一句话，对用户不是。

## 三、能力缺口

### M-1　物料只有一种图表，大屏最基本的三类图都做不出来　**部分已修（折线 / 柱 / 饼）**

**我原先的记法有个更糟的前提错误**：产品**一个图表都没有**。唯一那个 `echarts-bar` 住在
`apps/example/src/StageDemo.tsx` 里，而 AGENTS 明写示例应用「不是正式编辑器产品」。

效果图里的**折线图**（功率曲线、SOC 变化）、**环形图**（电量构成）、**地图**（区域分布）
都没有对应物料。只能用柱状图顶替两处折线、用圆角容器套圆角容器拼一个假环形、用空容器加
占位文字当地图。

**修法**（OpenSpec `add-chart-materials`）：新增第一方包 `@compose-ui/chart-materials`，
折线 / 柱 / 饼开箱可用。三条判断写在明处：

- **独立成包**而不是塞进 `materials`——图表自带一个第三方图表运行时，放进基础物料包会让
  只画方块与文字的宿主也装上它；这与 `dxf`、`svg-import` 各自独立成包是同一条判断。
- **一个 Renderer + `kind` 三元联合**，不是三个 Renderer（`Curve` 那条判断的第二次应用）；
  但**物料面板出三格**，因为用户找的是「饼图」。
- 数据模型三种共用，**改类型不丢数据**——让饼图另立一套数据形状会让「把柱图改成饼图」
  丢掉数据，而那正是用户最常做的一次尝试。

**地图没做**：它还要一份 GeoJSON 资源管线，是另一件事。

### M-2　图表数据只能一个一个加　**已修**

`数据` 是数组，面板上一项一格，加第 5 个点要先点一次「添加 数据」再填。
7 天的收益要点 3 次 + 填 7 次。没有批量粘贴一列数的入口。

**这不是图表的问题**：任何 `array(number)` / `array(string)` 字段都一样，因此入口做在
`property-panel` 的数组分组上（OpenSpec `add-array-bulk-edit`），图表只是第一个消费者。

**修法**：基本类型数组多一个「批量编辑」，打开一块文本区，一行一项，确认后整体替换、
**一次**受控变更（逐项提交会让撤销按 N 下）。分隔符收换行/制表符/逗号——从表格复制一列得到
换行、复制一行得到制表符、CSV 得到逗号。非法项**整体拒绝并指出是第几项**，不静默丢弃：
贴进 20 个数只看到 18 个，而屏幕上没有任何东西说明少掉的是哪两个。非基本类型不出这个入口。

### A-1　没有样式复用，重复劳动全靠手工　**已修（文字样式）**

建一个卡片 = 拖一次 + 名称 + 位置XY + 宽高 + 背景色（4 步）+ 边框色（4 步）+ 边框宽度。
一条文字 = 点工具 + 点画布 + 打字 + Escape + 位置XY + 字号 + 字重 + 宽高 + 颜色（4 步）。
320 个实体 + 96 个布局跑下来约 2600 次交互、14 分钟。

没有共享样式 / 文本样式，12 行表格里 48 条文字的颜色字号是一条条填的。
**这正是这个产品要解决的问题本身。**

**已落地**（OpenSpec `add-text-styles`）：文档可选 `styles` 表 + Entity 可选 `Style`
Component + 纯函数 `resolveComposeStyles`，并接进布局 Runtime。三条判断写在明处：

- **解析住在布局 Runtime，与导线、填充并排**：排版值被 Stage 渲染、Preview、文字测量与
  Inspector 四条路径读，解析一次下游全部自动正确；各路径自己解析一遍正是仓库为导线几何
  明令禁止的那一类。
- **排在求解之前而不是之中**：样式不依赖几何（导线与填充依赖），而文字测量要用到排版值，
  排在之中会造出一个循环。
- **样式垫底、作者值覆盖**，因此跟随样式的字段在文档里**缺席**——推论是「应用样式」必须在
  同一个事务里删掉被管辖的 props，不删的话样式加上去什么都不会变。

**编辑器接线**：Inspector 多一个「文字样式」分组——下拉挑已有样式、从当前这一条**提取**、
**把这一条写回样式**、**脱离**。不做独立面板：样式的三件事都以「当前选中的这一条」为对象，
放进 Inspector 才与它作用的东西在同一处。

「改一条」与「改所有跟随者」是**两个意图，两个入口**：直接改字号是局部覆盖（只影响这一条），
「写回样式」才让全部跟随者一起变——只给一个入口的话，用户改错一次就得撤销再走另一条路。

端到端验过一整个往返：提取 → 应用到第二条 → 改一条只有它变（26/12）→ 写回样式两条一起变
（26/26）→ 脱离后呈现逐像素不变。

**样式表本身的两件事也已落地**：重命名走的是同一条 **upsert**（同 id、新 name、原样 props），
不造第二条命令词——「新建」与「改写」的载荷逐字相同，差别只是这个 id 在不在。删除**不追着去
解除跟随者的引用**（那会把一次删除变成一次波及全文档的写入，撤销还得一条条放回去），因此确认
框必须把跟随者数量说出来：被管辖的字段在「应用」那一步就已经从它们身上删掉了，样式没了它们会
回到默认排版，这是一次看得见的外观改动。

**作用对象改成了选区，单选是它恰好一个成员的退化情形**（与时间线的关键帧选区同一条判断）：
多选面板此前只有一句「只选中一个才能编辑属性」的空态，现在多出样式一段——「把这一批统一成同一
个样式」本来就是以整组为对象的操作，规划器也一直按 `entityIds` 收数组。**混合与「不跟随」分别
呈现**：后者是一条能派发的命令（脱离），把混合也画成那个空选项会让用户读成「这一批已经都不
跟随了」。提取与写回**只在单选下出现并说明理由**——两者都要从「这一条」取值，而多选没有这一条。

跑出来才发现的一处：`ComposeConfirmDialog` 的 `onConfirm` **不关自己**，开合仍归调用方那份
状态。少清一次的症状是删除确实发生了、模态框却留在屏幕上，此后整个编辑器都点不动——看起来像
是「删除把编辑器卡死了」。组件测试与端到端各钉一条。

文档协议缺席即今天的行为，因此这一整段落地不改变任何既有文档的呈现。
