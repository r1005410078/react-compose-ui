仪表盘网格

这一稿只回答一件事：「GridStack 式网格」在这个产品里具体是什么交互。 不是 CSS Grid 的模板声明（grid-template-areas 那一套），而是一块 12 列的板子—— 卡片被拖到格子上，挡住谁就把谁推下去，让出来的空洞被下面的卡片自动填上。 协议、成本与落地顺序不在本稿，等这一稿对齐之后进 OpenSpec 提案。

01先说清楚它用在哪

如果这一节说的场景不对，后面全都不用看了。

接线图 用不上

端子的位置是客观事实——继电器的第 3 号脚就在那儿，不能因为旁边多了一个符号就被推走。 这一侧靠的是绝对坐标、对象捕捉与正交约束，已经做完了。

网格在这里不但没用，还是有害的：任何"自动让位"都会把一张画对的图变成画错的图。

大屏的仪表盘区域 就是它

一块区域里摆 6 张卡片：实时功率、告警列表、趋势曲线、环境温湿度…… 实施工程师在客户现场被要求"把告警挪到左上角、趋势拉宽一点"， 他要的是拖一下就重排，不是一个一个算坐标。

卡片之间没有客观的相对位置，只有"谁在上面、谁更宽"。 这正是 GridStack 存在的理由，也是 CSS 绝对定位不好使的地方。

02一块板子的解剖

容器上挂一个 Layout，type 是 grid（flex 的兄弟）。子级各自带一个 GridItem，记 {x, y, w, h}，单位是格。

画布 · 静息态ZOOM 100%
1列宽是算出来的，行高是给定的。容器变宽，格子跟着变宽、卡片跟着变宽；行高恒定 48px。这是 GridStack 的行为，对大屏也是对的——大屏的宽度会因为投屏设备变，而"一行有多高"是作者的设计决定。
2静息态什么都不多画。没有格线、没有格点、没有任何与当前操作无关的装饰。这抄的是仓库里端口的那条判断——端口不常驻，用户还没在找接线点的时候，那几十个记号只是噪音。
3列数默认 12，可改。12 能被 2/3/4/6 整除，所以"两栏""三栏""四栏"都能整齐排开，这是 Bootstrap 以来的默认答案。不做响应式列数收缩——大屏的分辨率是作者用 Frame.size 定死的，没有"手机上变一栏"这回事。

03拖动的四个状态

这是整份稿子的核心。把「环境」那张卡从右上角拖到左下角。

01还没碰它

见上一节。格线不画——这块板子此刻和一个普通容器在屏幕上没有区别，因为用户还没有提出与格子有关的问题。

02按下卡片的那一刻，格线显形
画布 · 按下格线显形

列带 + 行线，都很淡。判据是指针按下而不是"选中"——选中一张卡片是为了改它的颜色时，格线同样是噪音。 选中容器本身时也画，那时用户正在调列数与行高，格线就是他的问题的答案。

03拖动中 —— 三样东西同时在
画布 · 拖动中落点 0,2 · 4×2
1跟手的那张卡不吸附。它就在光标下面，抬起一档、带阴影。吸附的是影子不是卡——卡一旦吸格，拖动就会一顿一顿，而这块画布上别的手势（resize、夹点）也都是"几何吸、光标不吸"。
2占位影子回答「松手会变成什么」。虚线 + 淡蓝底，吸在格子上，角上印着落点与格数。这和取点命令的预览几何是同一条规则的又一个实例。
3被挡住的卡片真的移动，不是画个虚线框。「发电趋势」占着 0,2 那一片，影子压上来，它就整块下移一行——动画式地、实时地。原位留一个淡虚线残影，这样"它从哪来"是看得见的。
4没被挡住的一动不动。「设备列表」在 7..12 列，影子只占 0..4，它就不动。推挤是碰撞驱动的，不是整块重排——否则拖一张卡会让满屏卡片一起抖。
5容器自己长高了。它是 Hug，行数变多就跟着长。要固定高度就把它设成 Fixed，超出部分由既有的 Overflow: scroll 承担。
04松手
画布 · 已提交1 条事务 · 撤销一步全回去

影子变实体，卡片吸进去，八个手柄回来。 整次手势是一条事务——"环境移到 0,2" 和 "发电趋势下移一行" 写在同一条 batch 里， 撤销一步两个一起回去。拆成两条的话用户要按两次撤销，而他只做了一个动作。

04重力：空洞会被自动填上

GridStack 的 float: false（默认）。删掉中间那张卡，下面的自动上浮。这是网格与"带吸附的绝对定位"最本质的区别。

删掉「发电趋势」之前

之后 —— 下面两张自己上来了

1重力是开关，默认开。关掉（GridStack 的 float: true）时卡片停在作者放的行上，中间允许留空。做成开关而不是写死，是因为"故意留一行空白当分隔"是真实用法。
2只往上浮，不往左靠。列是作者的构图意图（这张在左、那张在右），行不是。GridStack 的重力也只有一个方向，这不是简化。

05Resize：手柄照旧，读数换成格

八个手柄一个不少，但边缘吸到格线上，而且同样会推挤。

画布 · 缩放中东手柄
1读数的单位是格，不是像素。"8 × 2 格"。像素值在这里是派生的、会随容器宽度变的，印出来只会误导。
2缩放同样推挤。拉宽到 8 格挡住了「设备列表」，它下移一行。这与拖动共用同一个求解器，不是两套规则。
3最小/最大是格数，写在 GridItem 上。一张趋势图可以声明"最少 4 格宽"，拖不下去。

06边界：它和 Auto Layout 不一样的地方

同一个手势在两种容器里含义不同。这不是不一致，是两种布局各自的自然语义——但必须说出来。

同一件事Auto Layout（flex）网格（grid）
拖一个子级只能改顺序；坐标由排布算出来，拖动不写 offset改它的坐标 x, y。这是主要操作
子级的尺寸每轴 fixed / fill / hug 三选一没有自由度，盒 = 格矩形。几何分组的「尺寸」降为只读，见第 07 节
兄弟实时让位只有 resize 时move 和 resize 都要。这是 GridStack 的灵魂，见第 10 节
拖出容器两边一样：GridItem 删掉、转 absolute、几何烘焙成世界落点——沿用既有的"移出 Layout 时烘焙 Absolute 几何"
拖进容器插到某个顺序位落在光标所在的那一格；被占了就把原住户推下去
容器自己的高两边一样：Hug 跟着内容长，Fixed + Overflow: scroll 固定住

08否掉的四个做法

写在这里是为了让"为什么不那样"可复查。

  • CSS Grid 的模板声明（grid-template-columns / areas）。你已经说了太复杂，我同意，而且还有一条独立的理由：那是声明式模板，用户在画布上拖出来的结果要能反向表达成一份模板，这是个反向约束——它会让"随便拖到哪儿"变成"只能拖到模板允许的地方"。
  • 拖动时兄弟只画虚线框、松手才真动。这样便宜很多（不需要 move 期的实时求解），但它会让网格退化成"带吸附的绝对定位"——而那个能力画布上已经有了（网格吸附 + COMPOSE_SNAP_RADIUS）。用户看不见推挤的结果就没法判断这一下该不该松手。
  • 用既有的画布网格吸附冒充。那条管线是"落点吸到格点"，没有列数、没有碰撞、没有重力，而且它是会话级视图状态（怎么看），网格布局是文档（画了什么）。两者连住的地方都不一样。
  • 响应式列数收缩（GridStack 的 column(n) 重排）。大屏的分辨率由 Frame.size 定死，没有消费者。做它还要回答"从 12 列压到 6 列时怎么重排"，而那个答案会渗进求解器。

09要你拍板的三件事

其余的我都按既有判据取了值。这三件我有倾向，但它们各自会改变落地的量级或手感。

01

拖动时，兄弟要不要真的实时让位 影响成本最大

这是本稿唯一要动既有架构的地方。现在 Stage 的实时布局求解只接了 resize——代码里明写着 "resize 是唯一需要真实布局求解的手势"。要让拖动时兄弟也动，得把 move 也接进那条预览通道。

不做的话，第 03 节状态 3 那张图里，「发电趋势」就只是一个虚线框停在原地，松手才跳下去。

我的意见：做。不做就等于本稿第 08 节否掉的第二条——它会让整件事退化成一个已经有了的能力。通道本身已经写好（rAF 合并、配对清理都在），主要是要重新论证一条既有约束在网格下还成不成立。估 2–3 天，是三件里最贵的一件。

02

行高固定 px，还是按列宽的比例

GridStack 两种都支持。固定 px：容器变宽时格子变宽、行高不变，卡片会变"扁"。 按比例（如 1:1 方格）：容器变宽时卡片等比长高，整块板子跟着长。

我的意见：v1 只做固定 px。大屏的宽度在一个项目里通常是定死的，比例模式的价值要等到同一份页面投多种分辨率时才出现；而它是纯粹的加法，以后补不破坏任何东西。

03

推挤的方向：只向下，还是允许交换

GridStack 默认只向下推。另有一种"两张同尺寸的卡片对调"的交换语义（swap）， 手感更聪明，但它有一个说不清的边界：尺寸不同的时候换不了，于是同一个动作有时交换、有时推挤。

我的意见：只向下推。理由就是上一句——用户无法预测的规则比笨一点的规则更糟，而"拖上去、它下去"任何时候都成立。
