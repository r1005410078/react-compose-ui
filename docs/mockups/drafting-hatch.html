填充：点一下，填满围出来的那块面

今天的填充属于对象——一个矩形的底色是它自己 Appearance.backgroundPaint 上的一个字段。 但用户指着的常常是一块面：矩形的三条边加上圆弧的一段围出来的那块。两者都要有，而且必须是两件东西。 本稿提的是第二件：一条 HATCH 命令，点一下把光标底下那块面落成一个新的 Entity。 边界是图上所有可见曲线，交点即拐角——与已落地的 TRIM 是同一份边界、同一种输入、同一套求交数学。 画布片段按 Stage 的真实 token 1:1 绘制；琥珀虚线圈 = 本稿提议、尚未落地。

填的是什么
光标底下围出来的那块面
不是某个对象的属性。对象的填充照旧——矩形还可以有自己的底色，那条路径一个字节不动。 这一件回答的是另一个问题：「这几条线围出来的这块」。两者不能合并，见右下第一段。
面的边界在哪
所有可见曲线，交点即拐角
与 TRIM 同一份边界：图上每条曲线自动是边界，不用先选。 从落点向外走，碰到第一条线就沿着它拐，每到一个交点取最靠右的转向，绕回起点即闭合。
填出来的是什么
一个普通 Entity——除非那块面本来就是某个对象
不是渲染规则、不是组、不是蒙版，是带 Curve 的普通曲线 Entity，因此选中、改色、绑定、 动画轨道与撤销全部白拿。而边界恰好是一个对象的完整几何时改它的填充、不新建， 否则拿桶点一个矩形会凭空多出一个与它重合的东西。见 02。
为什么不能让矩形的红色自己避开圆

这是最容易想到的解法——「让对象的填充按周围的线裁切」。它错在两处。 其一，一条导线穿过设备外框时，外框的底色会被切成两块，而接线图上导线天天穿过外框； 同一条规则在「圆压住矩形」上看着聪明，在「线穿过矩形」上就是一个缺陷。 其二，它让 backgroundPaint 的含义取决于图上别的对象—— 「这个矩形是什么颜色」这个问题的答案要先看它周围有什么，而这个字段还要参与命中、数据绑定与动画采样。 因此红与黄是两个对象，不是一个做错了：红色属于矩形，黄色属于那块面。

别人怎么做

做这件事的产品分两类：从落点反推边界（本稿要的），与在作者画好的轮廓里减出填充（KiCad 的敷铜、Altium 的覆铜）。后者不是同一个交互，但它回答关联性的方式恰恰最值得抄。

产品 · 工具怎么定边界产出什么关联间隙取不取
AutoCAD · HATCH（拾取内部点） 射线 + 逆时针绕行——-HATCH 的帮助原文就是「从指定点沿 +X 射出一条线到遇到的第一个对象，然后按逆时针方向沿边界绕行」。候选集是当前视口里看得见的那些 一个新的 HATCH 实体，同时存三份：烘死的环几何、边界对象的句柄、以及那个落点（DXF 组码 98/10/20） 默认开（HPASSOC=1）。边界改完仍闭合就跟随；变成开的就静默失联并停在原地 HPGAPTOL，0–5000 图纸单位，默认 0 取：算法、自动切割边、HPDRAWORDER 默认「送到边界之后」。不取那个落点的关联用法，见下
Illustrator · Live Paint 把组里所有路径拍平到一个平面上——「没有哪一部分在另一部分的前面或后面」。交点之间的一段叫 edge，围出来的叫 face 不产出对象：颜色是 face 的一个属性 有，但 face 的身份不稳定：删掉一条边时两个 face 合并，按面积大的那个的颜色留下，另一个静默丢掉 Small / Medium / Large / 自定义（数值未公开） 不取。代价见下面那段
Illustrator · Shape Builder 同上的平面图，但作用于当前选区 一个新路径，并替换掉原对象 没有。Adobe 自己的社区专家答「想保持可编辑就别用它，用 Live Paint」 3 / 6 / 12 pt，而且是近似匹配不是上限——设大了反而测不到小缝 不取。边界对象一个都不能动，这是我们与它的根本分歧
Figma · Paint（Shift B） 在一个 VectorNode 的图上找环。VectorRegion.loops 存的是段下标，不是坐标 节点上的一个 region，不产出对象 有，而且很稳——因为引用的是下标，拖顶点时填充自然跟着 没有，必须真闭合 跨不了对象：要跨两个图层得先 Flatten，而那是破坏性的。这正是我们不能照抄它的地方
Inkscape · 油漆桶 按渲染出来的像素漫填——官方原文「这个工具是感知的，不是几何的」，分辨率取决于当前缩放 一条与任何东西都无关的新 <path> 没有 无 / 2 / 4 / 6 屏幕像素，因此也随缩放变 不取。同一块区域在两个缩放下得到不同的顶点数，这块画布上每条几何都必须是真几何
Affinity Designer · Vector Flood Fill 几何的（不是像素的），检测边缘后填满完全封闭的区域 一个新形状 没有（官方未明说，社区一致认为是一次性的） 一点都没有：「必须由曲线或形状的边完全自封闭」 取它这一条：看过前面所有方案之后仍然选择不做容差，这是本稿最直接的先例
KiCad · 敷铜区 轮廓是作者画的，填充按间距减出来 区域自己的填充 默认手动重填（B），而且「在生成输出或跑 DRC 之前会警告你区域还没重填」 — 取那条警告：过期状态必须看得见，见下
Altium · 内电层分割 与本稿逐字相同：随便摆几条线把内电层隔开，「一旦隔离出一块，就产生一个新的分割面」，双击那块面给它指定网络 什么表示都不存 — — 它的代价写在自己的文档里：CAM 导出不支持这种分割面，「因为它无法定出描述每块区域的那条多段线」

两处直接印证了本稿已经写下的决定。AutoCAD 的 Normal 岛屿检测在 DXF 里的组码 75 就叫「odd parity」—— 「一层层交替挖空」与 fillRule: 'evenodd' 不是相似，是同一件事，因此那一段说的「协议一个字节不改」有出处。 而 Illustrator 把颜色挂在 face 上的账单是公开的：Live Paint 的 face 不能单独有透明度、效果、外观堆栈， 也用不了 Pathfinder、轮廓化描边、剪切蒙版、混合与符号——因为那个颜色没有对象可以挂。 本稿产出一个真的 Entity，这张账单一分钱都不用付。

调研里最该改变设计的一条：AutoCAD 最常见的失联，就是那个落点

文档只写了「边界改成开的就失联」，而实际被抱怨最多的不是它——是边界挪了之后，存着的那个落点落到了边界外面， 填充于是留在原地。老手的对策是干脆别用「拾取内部点」，改用「选择边界对象」，因为后者存的是对象句柄而不是一个点。 本稿的 Hatch.seed 正是那个点。这不否定 v1，反而正好说明 v1 为什么必须是手动的： AutoCAD 那个错之所以糟，是因为它静默——没有记号、没有报错，通常是图印出来之后才发现。 真正要抄的是 KiCad 与 Altium 的做法——前者在跑 DRC 与生成输出前警告区域没重填，后者把重填做成带「保持原样」按钮的提示。 结论落成一句：关联可以晚点做，过期状态不能晚点做。

协议：一个可选 Component，一个字段

几何的事实来源仍然是 Curve——填充落地之后就是一条普通的闭合多段线或 path。Hatch 只记一件事：这块面是从哪一点找出来的。

// packages/core/src/hatch.ts —— 可选 Entity Component
Hatch: {
  seed: { x: number, y: number }   // Entity 局部坐标，与 Curve 几何、Ports.position 同一个空间
}

缺席即不是填充，与 Wire 缺席即不是导线同一条。 seed 用 Entity 局部坐标而不是父级局部：它跟着这个 Entity 走，与 Ports.position 的理由逐字相同。 它不存边界对象的 id——存了就要回答「这条边是与哪个对象的第几个交点」， 而一条直线穿过一个圆有两个交点，选哪一个是个启发式，那正是 AutoCAD 关联图案填充最常断的地方。 重算就是拿 seed 把当初那次求解原样再跑一遍：同一个算法、同一个输入、没有第二套规则。

岛（洞）不需要任何协议改动。既有的 path.subpaths 加 fillRule: 'evenodd' 正好表达它——AutoCAD 的 Normal 岛屿检测就是奇偶规则， 「一层一层交替挖空」是同一句话的两种说法。isPointInsideComposeCurve 已经按 fillRule 分派， 因此看得见的洞与点不中的洞自动是同一个洞。

每一种情况

三格一组：之前 · 悬停（预览）· 落地。光标是拾取框加一个油漆桶徽标——填充不取点，因此没有十字线；徽标由提示自己声明（badge: 'bucket'），与 TRIM 的剪刀走同一条通道。

01圆压在矩形上：填矩形内、圆外的那块面

边界由两个对象各出一段：矩形出三条边加两截顶边，圆出下面那段弧——而没有任何一个 Entity 的几何是这块面。 落地取能表达它的最窄 kind：含弧边所以是 path（弧段规范化成三次贝塞尔）； 全是直边时落成闭合 polyline，见 04。矩形与圆一个字节不动——它们是边界，不是被作用的对象，与 TRIM 的切割边逐字相同。

弧边转成三次贝塞尔是一次近似，不是等价变换——path 的段只有三次一种，这是协议已经做过的取舍 （多一种段类型就是让归一化、平移、距离、包围盒、渲染与校验六条路径各多一支）。每 90° 切一段时最大径向误差约为半径的 2.7e-4，半径 500px 上是 0.14px，屏幕上读不出来。写在这里是因为它是全稿唯一一处几何不精确的地方， 而「这条弧和那个圆到底是不是一条线」是以后一定会有人问的问题。 svg-import 已经在做同一件事（svgpath().unarc()），但它靠一个第三方库，而 core 零运行时依赖、不能引它——这处重复是包边界造成的，不是疏忽，与 property-panel 自带一份数值格式化同源。

02边界恰好是一个对象时，改它，不新建

「用桶填色」与「给图形填色」在数据上是同一件事，在动作上不是。 两者最后写的都是 Appearance.backgroundPaint——填出来的那块面，和一个你手画的矩形，在文档里是同一类东西。 但给图形填色是改一个已有对象的一个字段，用桶是先求出一块面、把它变成一个对象、再给这个新对象上色： 前者是编辑，后者是创建。

分清这一层之后，一条规则就跑不掉了：这块面的边界恰好是某一个 Entity 的完整几何时，改它的填充，不新建。 否则按 01 的样子新建。没有这条的话，拿桶点一个没有任何东西穿过的矩形，会得到一个与那个矩形几何 逐像素重合的新对象压在它下面——屏幕上看着对了，场景树里多出一个一模一样的东西，而用户想要的显然是把这个矩形填上色。 判据是「完整几何」而不是「都来自同一个 Entity」：自交的折线（8 字形）两个环都出自它自己， 而写它的 backgroundPaint 会把两个环一起填上，不是用户点的那一个。 它自己被任何交点切开过，就不算完整。

这不是「同一个手势有两种含义」那类模式歧义。决定走哪一支的是图上看得见的东西—— 这块面是一个对象围出来的，还是几段边拼出来的——而不是一份藏在别处的状态； TRIM 早就有同样的形态（同一下点击按边界在哪儿，可能是缩短、可能是断成两条、也可能整条删掉）。 规矩也照抄那一条：悬停预览与落地读同一份解算，并且命令行把这一下会发生什么写出来—— 将改变「矩形」的填充: 与 将新建一个填充对象: 是两句不同的话。 锁定的那个 Entity 改不了，此时拒绝并说明，而不是退回去新建一个—— 「你锁了它」和「我给你造了个新的」是两件事，后者会让锁形同虚设。

03里面还有东西：岛就是 evenodd

外环走完之后，落在它内部而又走不到的每一个连通分量各是一条子路径。 这在协议上一个字节都不用改：path.subpaths 与 fillRule: 'evenodd' 已经在那儿， isPointInsideComposeCurve 也已经按 fillRule 分派——因此看得见的洞与点不中的洞自动是同一个洞。 再往里一层（岛中之岛）由奇偶规则自己交替填回来，不需要第二条规则。

04四条各自不闭合的线，围出一块闭合的面

四条线一条都不闭合，而它们围出的那块面是闭合的——这正是「填充不是某个对象的属性」最干净的形态： 没有任何一个 Entity 可以被赋予这个颜色。落地取最窄 kind，全直边所以是闭合 polyline， 于是它双击进得了几何编辑、拖得动顶点、也能有 cornerRadius。四条线各自伸出去的那一截照旧在图上—— 填充不修剪任何东西，要去掉伸出的那一截是 TRIM 的事。

05不封闭：拒绝，并且指出断口在哪

v1 没有间隙容差：走出去了就拒绝。这个仓库里每一个容差都有来源——拾取框抄 PICKBOX、 捕捉半径是「多近算在这条线上」的唯一事实——而「差多少还算封闭」没有这样的来源，它取决于图纸比例。 代价写在明处：一个 0.5px 的缝也会被拒。补偿是把缝画出来——走到哪个节点走不下去了，就在那儿画一对琥珀记号。 AutoCAD 在这一档只说「找不到有效的图案填充边界」，用户得自己在整张图上找那条缝。 琥珀是复用失效端点那个 token 而不是第七种颜色：缺口就是图上的一处失效，与悬空的绑定是同一族的问题。

06边界动了：v1 不自动跟随，但重算只要一下

v1 的关联是手动的，入口在 Inspector 上而不是画布上——画布上「按当前边界重算」这个手势 与「新建一块填充」逐字相同，做成两个手势等于给同一件事造第二个入口。这与导线的「解除绑定」按钮是同一条例外理由。 重算失败（seed 处已经没有封闭的面了）时保留原几何并标为失效，与悬空的导线绑定一模一样： 「还没配」「配错了」「配的东西没了」三者必须可区分。 自动关联的钩子就在旁边——layout-runtime.ts:877 每帧调 resolveComposeWires(document, snapshot)， 接一个 resolveComposeHatches 上去是一行；贵的不是接线，是求解本身，见「待定」第一条。

07层序：压在最靠后的那条边界之下

这与「矩形默认空心」是同一条理由的第二次应用：外框套在符号外面，填色会把里面的符号整片盖住。 区别在于那一条的答案是「默认不填」，而填充这条命令的全部意图就是填——所以答案只能落在层序上。 规则一句话：插在最靠后的那条边界之下（AutoCAD 的 HPDRAWORDER 默认档也是「送到边界之后」）。 落地不需要第二条命令——entity.create 的载荷本来就收一个可选的 index（builtin-commands.ts:405）， 因此层序与创建在同一个事务里，撤销一步全回去。

08工具栏上的那一格：一个油漆桶

可以，而且应该。它排在 TRIM 之后——两者都是「对着已经画好的图做一下」， 而它产出新对象这一点又让它属于绘图那一段，不该被推到别处去。 图标与光标徽标是同一个油漆桶：用户在工具栏上按下的那个形状， 下一秒就跟着光标出现在图面上，两处画成两样是这块画布最不该有的一类不一致。

只上绘图货架，不上页面货架。页面那条只留 RECTANGLE 与 ARROW， 理由是「大屏页面真会画的几何只有分区框与指示」——而大屏的分区底色本来就是一个矩形的 backgroundPaint， 用不着求面。代价要说在明处：绘图货架已经是 16 格，加到 17 格之后尾部那一格 （文字）会被收进「更多」。自定义对话框可以再把它拖回来，但默认值不该假装这件事没发生。

给别名 H，不给单键。别名是 AutoCAD 里同一条命令的同一个字母，用户只记一套词； 而七个绘图单键已经占满了与命令名有认读关系的裸字母，那是快捷键表里最容易被宿主重绑撞上的一类。 判据与 TRIM 逐字相同——它不是每分钟都按的那一类。 如果落地之后发现填充用得比想象中频繁，补一个 H 单键是一行改动，反过来收回一个已经给出去的键才难。 目录里的 entrance 写 { kind: 'command' }，自定义对话框的来源列因此印出「填充 · H」—— 那句「拿掉一格不会拿掉那项能力」的承诺是可核对的。

09怎么给桶换颜色

图标就是色板，不另给一个色块。「按这个按钮会发生什么」与「这次会填成什么颜色」是同一个问题， 用两个东西回答只会让它们有机会说得不一样。 本格与 08 画的是选过颜色之后的样子（琥珀）， 01–07 画的是还没选过时的中性默认（石板）—— 这两个状态在屏幕上必须一眼可分，否则「桶里那块是什么」这句话就没有兑现。

这枚图标画错过一版，错的地方值得记下来

第一版是 24 画幅、描边取画布的近白，还画成了倾倒的桶。三处都错： 工具栏图标的画幅是 20×20 且按 20px 渲染，一个单位就是一个设备像素，24 画幅每一笔都要乘 5/6、 一根都不落在像素格上；描边必须是 currentColor，取画布的近白等于假设工具栏永远是深色， 浅色主题下轮廓直接消失，只剩一个深色块加一滴；而倾倒的桶在 20px 上读作一个歪方块， 根本认不出是桶——这正是它被打回来的样子。

重画之后还试过第二种上色：单色桶 + 底部一条色带。它的桶在任何漆色下都清清楚楚，但被两条规则否掉—— 色带是一个只出现在这一枚图标上的新记号，而这套图标的记号词汇表只有五个且写着「accent 只标点」； 而且色带落在 y=16–18，那一圈版式规则写明只有夹点方块可以进。

最终取的是正面直桶、只有漆面填当前色：桶口留一截空，剪影因此在近白漆与近黑漆下都还成立 （整桶填色时这两档会和轮廓糊成一块）。漆面不是新记号——它就是这个桶里装着的东西。 图面上的光标徽标是同一个剪影，只有描边换成十字光标那一色：它归画布词汇，图标归 chrome 词汇。

它凭什么可以被记住。这个仓库拒绝过一次同类记忆：CIRCLE 的 D/R 不跨命令记，理由是那份状态看不见——用户过两天回来，同一条命令问的问题变了，而屏幕上没有东西解释为什么。 而 POLYGON 的边数可以记，因为它印在提示的 <6> 里。 桶身就是这里的 <6>。所以记忆的合法性不在「方不方便」，在值有没有被印出来。 只记在本次编辑会话（宿主的一个 ref，不写文档、不写偏好），与边数逐字相同。

色板里是「这一页已经用过的颜色」，不是一份内置色表。内置一份等于替宿主做了一个多半要改的决定—— 与「不内置电压等级色表」是同一条。而第二块区域十有八九和第一块同色，这份列表因此正好是最常用的那几个。 它不引入任何文档字段：扫一遍文档里带 Hatch 的 Entity 就有。 代价说在明处：重开编辑器之后桶回到中性色。这很便宜——色板是从这一页算出来的，你上次用的颜色就在弹出层第一行。

不把它挂到光标旁的动态输入框上。那一档是给每取一个点都在变的量准备的 （长度、角度、边数），把眼睛正在看的那个位置让给一个每填几次才动一次的值，是拿最贵的位置放最不常变的东西。 而改已经填好的那块是另一件事，走既有的属性面板：填充复用 Appearance.backgroundPaint， 所以外观 Inspector、数据绑定与外观动画轨道一行都不用写——这正是当初复用那个字段换来的东西。

边界规则的一句话

与 TRIM 的「向两边走到第一个交点」是同一份数学的另一种用法：那条在一维上排序取邻居，这条在二维上绕一圈。

// 候选：同父级、可见、带 Curve，且不是接线点、不是别的填充
1. 每条候选投影进自己的盒（projectComposeCurveToBox），再乘世界矩阵  ← 与命中、框选、捕捉同一条链
2. 两两求交（intersectComposeSegments / SegmentArc / Arcs），交点即节点，
   节点之间的弧段即边
3. 从 seed 向 +x 射出一条射线，取最近的边 → 进入这个面的第一条边
4. 沿边走；每到一个节点，取最靠右的那条转向
5. 回到起点即闭合 → 这就是包含 seed 的那个面
6. 落在外环内部而走不到的每个连通分量 → 一条子路径（岛）
7. 这块面的边界恰好是某一个 Entity 的完整几何？
   是 → 改它的 backgroundPaint，到此为止      ← 见 02
   否 → 继续
8. 收成最窄 kind：全直边 → 闭合 polyline；含弧边 → path，落成新 Entity

第 1 步与第 2 步一行新代码都不用写：curve-trim.ts 里的 boxCurve 与 worldShapes 已经把「盒局部几何 → 世界空间的线段与弧」这一段做完了（弧的半径按 sqrt(|det|) 缩放、镜像矩阵翻转 sweep）， 三个求交函数也已经在 core/curve-geometry.ts 里。真正新增的只有第 3 到第 6 步，住在 core/curve-region.ts—— 与弧的数学同一个包，因为它是平面形状运算；不放进 curve-geometry.ts 是因为那是一个 1142 行的模块， 而不是因为消费者不同。worldShapes 要从 curve-trim.ts 提到一个共享模块：两条命令都要它，各写一份必然漂移。

一处 HATCH 必须与 TRIM 给出不同答案的地方：圆角

TRIM 的 worldShapes 走 composePolylineSegments——尖角顶点，不管圆角， 并把代价写在明处：剪口会与画出来的弧差一个圆角的距离。填充不能取同样的近似： 差一个圆角的面积是屏幕上看得见的一块色，四个角就是四块，而剪口差一点只是缺口的位置偏了。 因此填充的边界必须走 composePolylineOutline（缩短的直段与角弧交替的那一列）， 与渲染、命中、内部判定读的是同一列。这不是给填充开特例——「看得见的形状与点得中的形状必须是同一个」本来就是那一列存在的理由。

刻意不做的

每一条都是被认真考虑过又放下的，理由写在明处。

不做图案填充（斜线、网格、砖纹）

getComposeCurveFill v1 只认 solid，图案要么是一个新的 Paint kind、要么是 SVG <pattern>， 两者都动到共享 Paint 层。而这个产品里的填充是分区底色与设备块，不是机械制图的剖面线—— 用户要的是「这一片是 10kV 段」，不是「这是钢」。

不做「把对象自己的填充按周围的线裁切」

见开头那段。它在「圆压住矩形」上看着聪明，在「导线穿过外框」上就是缺陷，而后者是这张图上每天发生的事。

不做间隙容差

见 04。补偿是把断口画出来——把一次挫败变成一次诊断，这比猜一个数更有用，也更容易在将来换成别的答案。

不做拖过多块，也不做一次多点落成一个 Entity

一块面，一个 Entity。AutoCAD 的一次多点落成一个图案填充对剖面线成立，对分区着色不成立： 这个产品里每块区域各自绑定——一条母线段带不带电是它自己的事，塞进一个 Entity 就只剩一个绑定点。 TRIM 的拖动批量在这里也没有对应物：拖过去的每一块面都要各自求解、各自配色，一次拖出六块色是用户读不懂的结果。

不做布尔运算（Illustrator Shape Builder / Affinity）

那是对已有对象做交并差，产出替换掉原对象。这里的边界对象一个都不能动：矩形还是那个矩形，圆还是那个圆。 它们是边界，不是原料——与 TRIM 的切割边是同一条。

不做像素漫填（Inkscape 油漆桶）

按渲染结果漫填再描摹，产出的是一圈近似顶点：与缩放有关、顶点拖不动、也不可能重算。 这块画布上每一条几何都是真实几何，这条是唯一会产出假几何的做法。

填充与接线点不参与边界

填充自己没有描边，拿一个用户看不见边的东西当边界，是最难自己发现的一类缺陷—— 第二块填充会莫名其妙地被第一块围住。接线点沿用 TRIM 已有的 isJunction 谓词： 它是一个坐在导线端点上的记号，当边界会在每条支路末端啃出一个记号大小的缺口。

待定

本稿没有回答、而实现之前要有答案的。

自动关联不能是「把手动重算改成每帧跑一遍」

调研之后这一条从「性能问题」变成了「设计问题」。性能那一半仍在：接线只要查一个端口的位置， 求面要把同父级下所有曲线两两求交，每帧一遍是 O(N²)。但更要紧的是第二半—— 边界动了之后 seed 可能落进另一个面（圆挪过来把它罩住了），于是形状在用户没碰这块填充的情况下整个换掉。 AutoCAD 在这里踩的坑有名有姓：它存了落点，边界挪出去之后填充静默地留在原地， 而老手的对策是干脆不用「拾取内部点」。所以 v2 不是「打开开关」，它得先回答「seed 换了面时听谁的」。

过期状态怎么被看见——这一条不能拖到 v2

所有做了关联的产品里，用户抱怨的都不是「它会断」，而是「断了我不知道」。 KiCad 的答案是在跑 DRC 与生成输出之前警告区域还没重填，Altium 的答案是把重填做成一个带「保持原样」的提示。 本稿 v1 的 Inspector 上写着「边界已改变」——但没说这句话是怎么算出来的，而不重算就不知道边界变没变。 一个便宜的答案是只在这块填充被选中时重算一次：那正是用户在问这个问题的时刻，一次 O(N²) 不是每帧 O(N²)。 要不要这么做、以及选中一块填充因此变慢多少，是实现之前要量的。

共线重叠的两条边界

intersectComposeSegments 对平行与共线重叠返回空——「没有哪一个点能被称作交点」。 两条画在一起的边界线因此不产生节点，绕行会从其中一条上直接走过去。多半无害，但要有用例钉住它到底走成什么样。

path（贝塞尔）边界

TRIM v1 也拒绝 path，同一条欠账：三次贝塞尔两两求交要么细分要么解高次方程。 v1 一并拒绝并说明，不要把它悄悄拍扁成折线——那会让填出来的面与画出来的曲线差一圈。

文字与符号算不算岛

AutoCAD 的岛屿检测会把文字挖空，好让标注压在填充上仍读得出来。这里的文字 Entity 没有 Curve， 天然不是候选——所以 v1 的答案是「不算」。这在深色底上填浅色时会出问题，但那是配色的事，先看有没有人真的撞上。

首次默认色取什么

「记住上次用的」已经在 08 里定了，剩下的只有第一次那一下。 中间一度把理由写成「区域没有最常见的那一档，所以只能给个中性的占位」——那是一句推辞，不是一条理由。 真正的理由是正面的：区域填充的角色是垫在符号底下的一层底，它必须让上面的墨读得出来。 这与导线红取「最常见的那一档」是同一条判据的两个答案——导线问的是「它通常是什么」，底色问的是「它得让什么东西看得清」。 低饱和、压得住的深色因此不是将就，是这个角色要求的。待定的只是取值： 场景背景默认透明，填充是会被发布出去的真实像素，所以它要在深色画布与白底页面上都成立。 导线红当初按这条量过对比度（编辑画布 ≈5.1:1、白底页面 ≈3.6:1），这一块也得量，本稿画的 #3f5068 还没量过。

宿主要不要能注入一份色板

08 的色板是从这一页算出来的，这对「第二块跟第一块同色」足够好，但对「这个项目的 10kV 一律用这个色」不够。 本稿不内置色表（那是替宿主做一个多半要改的决定），而让宿主注入一份是另一回事， 它与既有的 Registry / Preset 注入是同一类。没做是因为眼下没有消费者——按仓库的规矩， 没有消费者的东西不进协议。

场景树里它叫什么

「填充 1」读不出是哪一块。可能按边界对象命名，也可能就按区域大小排序编号。暂无答案。

本稿画的是提案，一行代码都还没有。命令骨架照抄已落地的 TRIM（同一种 pick 输入、同一条手势插件、 同一套世界坐标求交），求面的绕行算法是 core/curve-region.ts 里要新增的一组纯函数。 落地前按仓库规则先走 OpenSpec 变更提案。
