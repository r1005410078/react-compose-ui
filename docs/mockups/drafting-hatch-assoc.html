填充跟着边界走

上一份落地的填充是手动关联的：边界动了，填充停在原处， Inspector 上标一句「已过期」，按一下「重新生成」才跟上。那一份把「自动关联怎么做」整条留在了「待定」第一条， 理由不是工作量——是它有一个没有答案的问题：边界动了之后落点可能落进另一块面，于是形状会在用户 没碰这块填充的情况下整个换掉。本稿回答它。 画布片段按 Stage 的真实 token 1:1 绘制；琥珀虚线圈 = 本稿提议、尚未落地。

什么时候算
这次事务碰了我的边界，才算
存一份边界清单，与事务的 targetIds 求交；交集为空就一次都不跑。 这个清单不用新算——落地那一刻已经算出来了，现在拿它决定插在哪一层，之后就扔了。
跟随到什么程度
清单相同即跟随，不同即过期
几何变了而边界还是那几个（拖顶点、拉边、圆胀大）→ 静默跟上。 拓扑变了（圆整个挪出去了，边界从「三边一弧」变成「四条边」）→ 不替用户换形状，标过期问他一下。
落点是什么

跟随之后把它重取到最大内切圆的圆心——离边界最远，下一次变形才扛得住。 v1 里两者恰好相同（那块面刚从那一点求出来），而身份要跟着面走。
先回答一个提过的方案：填充落地时顺手建一个 Group 把边界包起来

它想修的痛点是真的，但它修的不是坏掉的那一档。组能让整组一起挪的时候填充跟着走—— 可那一档本来就不坏：框选一片东西一起拖，填充和边界都在选区里，本来就一起走。 真正坏掉的是相对运动（把圆从矩形里拖出来、拉长某条边、拖一个顶点），而这些在组里照样做得到， 做完填充照样过期。

代价那一侧还有两条是硬拦路。一个对象可以同时是好几块面的边界，而一个 Entity 只有一个父级—— 第二次填充时那个矩形已经在上一个组里了，抢过来还是不分组，两个答案都是坏的。 更糟的是它会踩坏导线绑定：wire.parent-mismatch 是文档非法， 填一块面顺手把某个符号卷进新组、而接在它端口上的导线没进去，一次填色就让文档校验不过、保存被阻断， 而用户完全无法把这两件事联系起来。层序也保不住——见 06。

这个仓库已经拒绝过一次拿 Group 当别的用：DXF 导入的图层没有退化成 Group，理由逐字相同—— Group 是空间容器，拖一下会搬走全部成员，而图层是分类。 结论：分组是「自动关联」的一个有损代理，要的是跟随就直接做跟随。

别人怎么让填充跟着走

问的是同一个问题：这块面的身份存在哪儿。三种答案——一个点、一组对象引用、一份拓扑下标——各有各的账单。

产品存什么什么时候重算断了怎么办取不取
AutoCAD · 关联图案填充 三份：烘死的环几何、边界对象的句柄、以及那个落点（DXF 组码 98） 边界对象一变就跟（HPASSOC=1 默认） 静默失联并停在原地——没有记号、没有报错，通常是图印出来才发现 取那三份里的前两份，不取「静默」。老手的对策是干脆别用「拾取内部点」，正说明那个落点是它最弱的一环
Figma · VectorRegion loops 存的是段下标，不是坐标 拖顶点时自然跟着——引用的是拓扑，几何怎么变都不影响 拓扑变了（加段、删段）下标就错位 取它的判断方向（身份该由拓扑表达），但抄不了：它限定在一个 VectorNode 里，跨对象要先 Flatten，而我们的面天生跨多个 Entity
Illustrator · Live Paint 颜色挂在 face 上，face 由平面图实时算 实时 删掉一条边时两个 face 合并，按面积大的那个的颜色留下，另一个静默丢掉 不取。这是「身份怎么延续」最直接的先例，而它的答案是有损的，且丢的那一半没有任何提示
KiCad · 敷铜区 轮廓是作者画的，填充按间距减出来 默认不自动，手动重填 B 在跑 DRC 与生成输出之前警告你区域还没重填 取那条警告——上一份已经取了（Inspector 的过期标记）。本稿把它从「唯一的答案」降成「跟不上时的答案」
Altium · 内电层分割 什么都不存，分割面由线实时围出 实时 不存在「断」——但也拿不到那块面 不取。它的代价写在自己的文档里：CAM 导出不支持这种分割面，「因为它无法定出描述每块区域的那条多段线」

盘完账，三种存法我们已经存了一种（落点），而第二种是白拿的——边界对象的清单在落地那一刻就算出来了， 现在拿它决定插在最靠后那条边界之下，用完就扔。第三种（拓扑下标）抄不了：Figma 那份的前提是单个节点， 而我们这块面的边界来自好几个 Entity，各自还会被加段删段。 因此本稿的形态是：清单当过滤器与判据，落点当身份。

协议：加一个可选字段

没有新 Component、没有新 Entity 类型、版本号不变。

// packages/core/src/hatch.ts
Hatch: {
  seed: { x: number, y: number }
  boundaryIds?: string[]   // 新增。围出这块面的那几个 Entity；缺席即不跟随
}

缺席即不跟随，与 Hatch 自己「缺席即不是填充」、Clip「缺席即不裁剪」同一条。 这条回退让迁移不需要做：上一份已经落地的每一块填充都没有这个字段，因此行为逐字不变—— 仍然只标过期、仍然要按一下「重新生成」，而那一下会把清单补上。

存 id 而不存「哪几段」：段下标在顶点被增删之后就错位了（Figma 那份的已知边界）， 而我们要它回答的两个问题都只需要 id——「这次事务碰没碰到我」与「边界还是不是那几个」。 更细的粒度现在没有消费者，按仓库的规矩不进协议。

不存烘死的环几何（AutoCAD 存了）：Curve 就是那份几何。存第二份等于给同一个形状造两个事实来源， 与导线「自由端 MUST NOT 存坐标」是同一条判断。

每一种情况

基准场景沿用上一份 01 那一格：一个圆压在矩形上边，填充是「矩形内、圆外」那块，边界是三条直边加一段圆弧。

01一次边界改动，三种结果

跟随的判据只有一条：重求一遍，边界清单与存着的那份相同即跟随。 几何怎么变都不影响它——拖顶点、拉边、圆胀大、整块图一起挪，围出这块面的仍然是那个矩形和那个圆。

拓扑变了就停手，这是刻意保守的一档。圆整个挪出去之后，边界从「三边一弧」变成「四条边」， 此刻「跟上」意味着把填充换成整个矩形——那是一次用户没有要求过的形状改变。上一份留下的那个问题 （边界动了之后形状会在用户没碰它的情况下整个换掉）正是在这里被挡住的。 代价说在明处：这一档要按一下「重新生成」。它比 AutoCAD 多了一步，而 AutoCAD 那一步省下来的代价是静默。

失效那一档一个像素都不动，并且画出断口——与上一份「不封闭时在走不下去的那个节点画一对琥珀记号」 是同一套呈现，复用失效端点那个 token。三档在 Inspector 上是三句不同的话：「与边界一致」「边界已改，填充已过期」 「边界已断开」。「还跟着」「跟不上了」「边界没了」必须可区分，与导线绑定的 「还没配 / 配错了 / 配的东西没了」是同一条判断，这个仓库已经用过三次。

02清单是过滤器：没碰到就一次都不跑

这是「不能每帧 O(N²)」那条的正面答案。上一份把自动关联的性能问题写成了「求面要把同父级下所有曲线 两两求交」，而那句话漏了一个前提——绝大多数事务与任何一块填充都不相干。挪一个符号、改一段文字、 调一个颜色，交集为空，一次都不跑。

过滤器与判据是同一个字段，这不是巧合。「这次改动与我有没有关系」和「边界还是不是那几个」问的是 同一件事的两面，因此一份清单答完。这也是为什么它值得进协议：一个字段解决两个问题，而它连算都不用算—— 落地那一刻已经有了（现在的名字叫 belowIds，用来把填充插在最靠后那条边界之下），用完就扔掉了。

跟随成功之后清单跟着更新。圆真的被挪出去、用户按了「重新生成」之后，清单里就不再有那个圆—— 它以后再怎么动都不该再惊动这块填充。不更新的话，一块分区底色会被一个早就搬到别处去的符号永久拖着， 每次挪它都白跑一次求解。

03落点是这块面的身份，不是你点的那一下

这是上一份那个没有答案的问题被真正解决掉的地方。那一份写的是「边界动了之后 seed 可能落进另一块面」， 而只要落点停在用户当初点的位置上，它就一定会在某次变形之后掉进别的面里——角落是最容易被吞掉的地方， 而用户点填充时恰恰爱点在空的地方，也就是角落。

重取到最大内切圆的圆心（地图标注放置用的那个 pole of inaccessibility）之后，落点离每一条边界都尽可能远。 边界要把它吞掉，就得先把整块面压扁到比现在这个内切圆还窄——而那时候求解本来就会失败，于是结果是 「标失效」这个看得见的答案，而不是「悄悄换成另一块面」这个看不见的答案。 把一个静默的错变成一个可见的错，是这一条全部的价值。

代价是 seed 不再是「当初那一下点在哪儿」，因此上一份 Inspector 上那行只读的「取点」要改口—— 它现在读作这块面的锚点。这值得换：那个字段唯一的消费者就是求解，没有别人读它， 而让它更扛得住变形正是它的本职。它仍然只读——要换位置就再填一次。

只在跟随成功之后重取，不在落地那一刻重取。刚填出来的那块面，用户点的地方就是他心里那块面， 此时把点挪到别处只会让「重新生成」在他眼里变得不可预测。算内切圆要把弧边采样成折线—— 它只用来选一个点，不产出任何几何，因此这处近似不违反「这块画布上每条几何都是真几何」。

04只在提交那一刻算，手势期不动

判据是「文档变没变」而不是「手在不在动」。这块画布上的手势期走的是预览变换， 一个字节都还没写进文档；跟随挂在事务提交上，因此它天然是每次手势一遍，而不是每帧一遍。 撤销也白拿——跟随写进的是同一个事务，撤一步边界与填充一起回去。

代价写在明处：拖动过程中填充不跟着变形，松手才跳一下。 这与导线不同——导线求解确实住在布局 Runtime 里每帧跑，但它只需要查一个端口的位置，而求面是两两求交。 要不要为手势期付这笔账，是本稿刻意不回答的（见「待定」）：它要先量， 而且量的时候筛选已经把候选压到了这块面周围的三五个对象，可能比想象中便宜。

05不想让它跟了：断开关联

不给「跟不跟随」开关，给「断开关联」。一个布尔字段会造出一块看不见的状态—— 两块长得一样的填充，一块跟一块不跟，屏幕上没有任何东西解释为什么。而断开关联做的是一件说得清的事： 删掉 Hatch，缺席即不是填充，它变回一条普通的闭合多段线，从此选中、拖顶点、改颜色全都和别的曲线一样。

它本来就是一条闭合多段线——上一份那条「产出一个真的 Entity」的决定在这里第二次付清了红利： 不需要为「脱离关联的填充」发明任何新东西。入口在 Inspector 而不在画布上， 与导线的「解除绑定」是同一条例外理由：画布上没有能只断开关联而不动几何的手势。

06为什么不是「顺手建一个 Group 包起来」

左边那条是硬拦路。wire.parent-mismatch 在这个仓库里是文档非法而不是警告， 理由是「跨层级要合成整条祖先链的变换，限制在同一父级把『嵌套时静默错位』变成一条读得出来的问题」。 填一块面顺手把某个带端口的符号卷进新组、而接在它上面的导线没进去，结果是一次填色让文档校验不过， 而这两件事在用户眼里毫无关系。

右边那条毁的是上一份 07 那一格整格在讲的事。现在填充插在最靠后那条边界之下的那一格上， 因此区域里的符号仍然在填充之上；而组只占一个 z 位置，夹在中间的符号要么被扫进组里（它根本不是边界）， 要么被挤到组外——两种都会让它被整片盖住，也就是 07 判定为错的那个样子。

还有两条在画面上说不出来、但同样致命：一个对象可以同时是好几块面的边界，而一个 Entity 只有一个父级； 以及它改动了边界对象，而这条设计的脊梁是「边界对象一个都不能动」（与 TRIM 的切割边同一条）—— 改父级比「在它们下面多一个对象」是大得多的改动。 这个仓库已经拒绝过一次拿 Group 当别的用：DXF 的图层没有退化成 Group，理由逐字相同。

跟随不是一条新命令，也不是一个新模式。它是既有的那一次求解挂在事务上跑一遍， 因此命令行、光标、徽标、预览一个像素都不变；用户学不到任何新东西，这正是想要的。

刻意不做的

每一条都被认真考虑过又放下，理由写在明处。

不做自动分组

见 06。它修的不是坏掉的那一档，而代价里有两条是硬拦路（导线跨父级即文档非法、层序被压平）。

不做「跟不跟随」的布尔开关

那会造出一块看不见的状态——两块长得一样的填充，一块跟一块不跟，屏幕上没有任何东西解释为什么。 见 05：要它不跟就断开关联，它变回一条普通闭合多段线，而它本来就是。

不存烘死的环几何，也不存边界的段下标

前者是给同一个形状造两个事实来源（Curve 就是那份几何），与导线「自由端 MUST NOT 存坐标」同一条； 后者在顶点被增删之后就错位，而 Figma 能用它的前提是整块面在一个节点里，我们的面天生跨多个 Entity。

不在拓扑变了的时候替用户换形状

这是本稿最保守的一处，也是上一份留下那个问题的答案。「跟上」在那一档意味着一次用户没有要求过的形状改变， 而 AutoCAD 正是在这里静默出错、Illustrator 正是在这里静默丢掉一个 face 的颜色。 代价是多按一下「重新生成」，它买到的是这次改动被看见。

不做「跟随失败时自动断开关联」

AutoCAD 在边界变成开的时候就是这么做的——静默失联。失效必须是一个可见且可恢复的状态： 几何原样保留、图上画断口、Inspector 说出来，把缝补上之后它自己就回来了。自动断开会把一次可修的故障 变成一次不可逆的降级。

待定

本稿没有回答、而实现之前要有答案的。

手势期要不要跟着变形

本稿只在提交那一刻算（见 04），因此拖动过程中填充不动、松手跳一下。要不要为手势期付这笔账要先量： 候选经包围盒筛选之后通常只剩这块面周围的三五个对象，可能比「两两求交」这个说法听起来便宜得多。 真做也只该为受影响的那几块跑，而不是所有填充。

落点被边界横扫而过

一条线从落点上扫过去时，边界清单没有变（还是那个矩形和那条线），因此按本稿的规则会跟随—— 而跟随的结果是填充跳到线的另一半。重取到最大内切圆圆心让落点一路后退、把这一档压到很窄， 但压不到零：线走得够远时仍然会翻面。还需不需要第三条规则，以及那条规则能不能不引入魔法数，暂无答案。

一次事务改了很多边界

框选一百个对象一起挪时，交集可能命中几十块填充，于是一次事务里跑几十次求解。 需要一个上限、还是需要在超过某个数量时退回「全部标过期」，要量过才知道。 退回那一档是安全的——它就是上一份已经落地的行为。

撤销之后清单对不对得上

跟随写进同一个事务，因此撤销一步几何与清单一起回去。但跨多步撤销时， 中间某一步更新过清单，回退到更早的状态时清单是否仍然自洽，要有用例钉住。

组件实例里的填充

实例是离线快照，内部 Entity 的 id 在快照里稳定，但跨实例是同一批 id。 清单存的是 id，因此实例内部的填充跟随时会不会互相串，要先看一眼快照的寻址规则。 v1 的填充只落在页面文档里，这一档眼下没有消费者。

本稿画的是提案，一行代码都还没有；它接着《填充：点一下，填满围出来的那块面》往下写， 回答那一份「待定」的第一条与第二条。求解复用已落地的 resolveComposeCurveRegion， 落地前按仓库规则先走 OpenSpec 变更提案。
一处调研留的尾巴：AutoCAD 的 HPASSOC 只说明「边界变成开的就失联」， 而「落点落到边界外之后填充静默留在原地」这条在官方文档里查不到，它来自 Autodesk 自己的 FAQ 与社区的一致描述；本稿把它当作现象引用，不当作规格引用。
