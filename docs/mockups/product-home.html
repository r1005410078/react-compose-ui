首页与二次编辑

编辑器不再是应用的入口，页面库才是。它回答的是「这东西该怎么画」——左栏是两段： 上段是项目 / 模板 / 回收站三个去处，下段是场景类型（PCS、BMS、一次接线、总览）， 跟着上面选中的那一个走。同一类里并排摆着已经画过的几十种画法。而它真正的用法是当着客户翻：客户指中哪一张， 就以那一张为底开始改；演示那一屏不出现任何内部信息——屏幕正对着客户。 后端只出现在一个位置：资源管理服务，连同分类标签一起由它交回来。

00三个名词

先把词对齐，后面每一条都压在它们上面。三者各自已经在代码里有确切含义，这次不新造任何一个。

页面= 一份 .page.json = 一张卡
库里的每一张卡就是一个页面，打开它就是编辑它。这是仓库既有的单位，不新造—— 页面文件是 { document, setupScript, activeFrameId } 的聚合， 缩略图取它的激活场景渲染，因此缩略图有唯一来源、不会与内容不符。
三个大分类项目 / 模板 / 回收站
这是左栏的上段，分的是性质：真交付出去的图、拿来给客户挑的底、已删除的。 场景类型（PCS、一次接线、总览……）在这三者内部都成立，因此它不与三者并排， 而是作为下段跟着选中的那一个走——切到模板，那八项的计数跟着换成模板的。
场景类型= 资源服务上的标签
PCS / BMS / 一次接线 / 总览 / 报表……它回答「这张图画的是什么」， 不进文档，见第 04 节。

01页面库

默认落点。左栏分两段，各回答一个问题：上段是「在哪儿找」——项目（真交付出去的图）、 模板（拿来给客户挑的底）、回收站，互斥；下段是「找哪一类」——场景类型， 跟着上段选中的那一个走。最近打开不是第四个去处，它横跨三者，所以隔一段留白摆在最上面。 主区按类型分段，一段里并排的是同一类东西的各种画法——这一屏回答的是「这东西该怎么画」。

判据
项目与模板是两种性质，不是两个标签。一个是真交付给客户的图（改它要担责）， 一个是拿来给客户挑的底（改它是在改公司的家底）。并排摆成两段时， 「用过 340 次」与「上周刚交付」会出现在同一列里，读者得自己分辨哪些是真图。 回收站是第三种性质（已删除）。场景类型在这三者内部都成立，所以它不与三者并排—— 并排摆会让「PCS」这一段同时混着真图与模板。
判据
左栏不是一棵树。此前是：三个大分类各带一个折叠三角，展开是同样的八个场景类型—— 那棵树逼着这八项被抄两遍（项目底下一遍、模板底下一遍），还让一层半的结构付了整套树的 代价：三角列、缩进列、每行一个不表达任何东西的色块，以及「项目 418」与子项「全部 418」 把同一个数写了两遍。拆成两段之后这五样一起消失。两段的选中因此画法不同—— 位置是实底、筛选是左边一条竖条：同一种画法会让它们读成并列的两个选项，而它们回答的是 两个问题。代价写在明处：项目 / PCS 不再是一条可读的路径，要做深链接得把两段 的值分别写进去。
代价
看一类场景的全部画法（真图加模板一起看）要点两处。补偿是主区卡片上那个 官方角标——在「项目」这一支里看到的都是真图，而模板那一支里的每一张都带角标， 两边都不需要再去分辨。
判据
不要卡片，图自己就是那个对象。卡片是一个容器，而这一屏里唯一有决定性的东西是图—— 再给它套一个盒、在盒下面留一块文字区，等于用两层 chrome 去托一张图。 现在名称与「用过多少次」压在图的底边上（一层渐变压住线条），省下的高度全给了图。
判据
只放有区分度的东西。之前每张卡下面都写着 1920 × 1080 · 2 小时前—— 同一类里尺寸几乎总是一样，四行一字不差，等于没写。换成用过多少次： 它正好回答用户此刻的问题——哪个画法是大家在用的。没被用过的就不写， 那一行的空缺本身也是信息。尺寸退到 hover 上，它只在你真要用时才要紧。
代价
「用过多少次」要资源服务记一笔：每次「就用这个」给来源加一次计数。 这是本稿唯一要求后端写业务数据的地方——别处它只管存取文件。
推论
卡头右端分两组：排序与视图开关是「怎么看」，新建是「做什么」，两组之间只用间距 分开、不画竖线——沿用顶栏那条规矩。「新建页面」是 split button，因为新建必然有两条路： 空白页面，或从模板——而后者才是这个产品的主路径，它不该藏在一个菜单的第二项里。
推论
卡片的单位是页面，仓库里既有的那个单位（.page.json）。 缩略图取它的激活场景渲染，因此缩略图有唯一来源，不是一张随手截的图。
代价
按画的是什么分，就没法按「哪一批活儿」连着看——同一批做出来的几张图在墙上是散开的。 眼下靠最近打开与搜索兜底；要不要再给一条「按批次看」的入口，留到有人真被这件事挡住时再说。

02给客户看

这面墙真正的用法是当着客户翻：「PCS 我们有这几种画法，您看哪个顺眼」。 所以要有一屏没有任何编辑器 chrome的全屏演示，左右翻页，选中了当场开始改。 屏幕此刻正对着客户，这一条决定了下面每个细节。

PCS 详情方案 3 / 64 就用这个
全屏演示整屏只有图与一条控制条；不出现分类、文件名与修改时间
←→翻同一类的下一张 Enter就用这个 Esc退回页面库 F真全屏（投影仪）
判据
这一屏上不出现任何内部信息。不画分类、不画修改时间、不画文件名—— 它们都是我们自己的记账，而屏幕此刻正对着客户。翻页时只写「方案 3 / 64」， 因为客户此刻唯一要回答的问题是哪一张顺眼。
推论
因此分类不是内部检索的方便，它是给客户的菜单。「PCS 有 64 种画法」这句话 必须当着客户成立，所以分类要按客户认得的设备分（PCS、BMS、消防）， 而不是按我们的内部结构分（组件、图层、模板版本）。
代价
演示的是真实渲染而不是缩略图——客户要凑近看数值与线宽。 因此这一屏要当场加载那份文档，第一张会有一个可见的加载过程； 补偿是翻页时预取相邻两张，客户按着方向键连翻时不再等。

演示屏上按下「就用这个」落到这里，墙上 hover 的那颗按钮也落到这里。它做的是复制一份： 客户指中的这张图成为你自己那一份的底，此后两边再无关系。客户就在旁边等着，所以这一步 只问一个必须问的问题——它叫什么。

04场景类型从哪来

这一节是整套分类法的地基：「这块场景属于 PCS」这句话存在哪儿。三个候选，只有一个站得住。

靠名字猜Frame.name 含「PCS」
零改动，也零可靠。改个名字就掉出分类，而「PCS-1」「pcs详情」「储能变流器」指的是同一类。
写进文档给 Frame 加一个字段
要动 ComposeDocument 协议、校验与迁移。而分类是「怎么看」不是「画了什么」—— 与网格设置不写进文档、工作区按偏好记忆是同一条判断。否决。
资源服务上的标签目录服务的一张表
取这条。标签挂在「哪个资源根的哪个 Frame id」上，住在后端目录里。协议不动、编辑器不动， 分类体系随时能改而不需要迁移任何一份文档；一块场景还能同时属于多类。
代价
把一份页面导出到别处、或离线打开时，标签不跟着走——那边只剩文件名。 这是对的取舍：标签是这套协作产品的索引，不是那张图的一部分。
推论
必须有一类叫「未分类」并且默认显示（图里是 30 块）。新建、导入、DXF 转进来的场景一律先落在 这里；藏起来的话，用户会以为库里没有那块图，转头再画一遍。打标签的入口在场景的右键菜单上。

首页的每一格数据都来自网络，所以这四种状态不是边角料，它们和正常态一样常见。

06与编辑器的关系

先说一个被推翻的做法：把编辑器的 chrome 逐条照抄过来（面板卡、6px 沟槽、30px 卡头、 280/288 栏宽）。它在纸上讲得通——切换时不动的东西最多——做出来很丑， 而且它正是上一轮「条条框框太多」的根因。

为什么丑密度是给谁用的
编辑器那套密度是为同屏七八个面板抢空间设计的：每块都要能停靠、折叠、拖走， 所以每块必须是一张带边框的卡，行 22px、沟槽 6px。而首页只有两块内容、都不可停靠—— 照搬的结果是两块内容画了四条边框，每一条还在宣称一个首页根本没有的能力。
保留顶栏与 token
顶栏一个像素不动：30px、标志在最左、后面是打开的文件。颜色与字体也仍是 ui-context 的同一套。切换时眼睛的锚点是顶栏，不是栏宽—— 那一行不动，两屏就是同一个应用。
放弃面板 chrome
不分卡、不留沟槽、不设面板头。左栏与主区之间只有一条竖线；整屏带边框的东西 只剩图自己。行高从 22 放到 26、字号从 12 放到 13——浏览页不是工具， 它一屏只做一件事，可以呼吸。
代价左边界会横移
左栏 236 而场景树是 280，切进编辑器时左边界横移 44px。 这是放弃照抄换来的账，写在明处。要抹平就把两边调成同一个数， 但那等于让浏览页去迁就工具的密度——而那正是这一节推翻掉的做法。
判据
平滑不等于一样。此前那条写的是「切换时不动的东西比动的多」，于是一路推到 逐条照抄——那是把可度量的指标当成了目标。真正要的是「这仍然是同一个应用」， 而承担这句话的是顶栏与配色，不是左栏宽度。
推论
既然首页不照抄，它的布局就不受编辑器改动的牵连：编辑器哪天把栏宽、卡头或沟槽调了， 首页一行不用改。反过来也一样。两边只在顶栏与 token 上有约定，而那两样都很稳。

07四条边界

这三条决定了架构设计那一步能不能顺，先在设计稿里钉住。

首页不是一个工作区route ≠ workspace
工作区是 Dockview 的一份布局加一组画布会话开关，而首页没有画布。 做成工作区会让 fromJSON 去恢复一个没有 Stage 的布局。首页与编辑器是两条路由， 编辑器整体挂载 / 卸载。
模板不是新协议= 一份只读的页面
模板与项目里的页面逐字节同构，差的只是能不能写——那是资源服务上的一个权限位， 不新增文件类型、不加 kind。推论：任何一张画得好的图都能一键「发布为模板」， 这件事因此不需要任何新功能；左栏那三个分类也就只是三个池子，不是三种数据。
演示不是第三种渲染复用 ComposePreview
全屏演示就是已有的只读 Preview 加一条控制条，不新写渲染器。 客户看到的每一个像素因此与交付出去的那一页逐像素相同—— 另写一份的话，「演示时好好的、上了大屏不一样」这类问题永远查不清是谁的。
后端只在 Provider 后面editor 一行不改
编辑器已经只认 compose-ui/assets 的 Provider 协议。后端要做的是 这个协议的一个远程实现加项目/模板/成员这一层目录服务。 首页自己不读文档——它只要卡片元数据与缩略图，不该把 5000 个 Entity 拉下来算一张图。

08留给架构设计的问题

这些我没有在设计稿里替你决定，它们会实质改变后端形状。

Q1
墙上那几百张缩略图谁来渲染？ 演示屏已经定了用真实 Preview，但墙上一屏就有二十来张。服务端跑一次无头渲染存成图片（首屏快、后端要跑一份 Compose 运行时），还是前端按文档现画（后端轻、一屏二十份文档拉不动）。这条决定后端形状。
Q2
场景的标签谁来打？ 几百张页面，靠人一张张标不现实。是导入时按名字与符号构成自动建议、人确认，还是先只让「未分类」堆着、用到谁标谁？自动建议要跑一次识别，那是另一条技术路线。
Q3
复制带着组件走，会攒出 73 份同样的 PCS 组件吗？ 每复制一次就带一份过去，同一个 PCS 主体会攒出几十份。共享组件库能去重，代价是引入页面之外的第二种资源归属，以及「库更新了，已交付的那张图要不要跟」——而按本稿的判断，已交付的图不该自己变样。
Q4
到客户那儿演示时网络是什么状况？ 客户现场常常没有外网。要不要支持把一批页面带下来离线翻？这会反过来决定资源粒度是文件级还是整根打包——而那正是协作与多端同步的同一个问题。
Q5
保存是显式还是自动？ 今天编辑器是显式保存，而列表上写着「最近修改」，用户会期待它准。自动保存要回答冲突、版本历史与离线。
Q6
交付物是什么？ 本稿只解决「在哪儿编辑」，没有回答「客户现场跑的是什么」——导出一份静态站点、发布到某个地址，还是由宿主应用直接读资源？发布流程会反过来影响页面的组织方式。
