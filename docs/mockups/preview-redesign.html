@compose-ui/preview · 设计稿

预览的两种形态

今天只有一条预览入口——那个模态弹框，而它同时在做两件互相冲突的事：既想当随手一看， 又想当交付长什么样。更根上的一处是：它那个缩放下拉把「这块屏多大」和 「我把它看多大」混成了一个控件——UE4 的 UMG Designer 把这两件事分给了两个控件， 分开之后「适应 68%」这个说法自己就不成立了。下面先看调研，再把两个问题拆开， 然后是九条各有出处的保真度缺陷与两个形态的设计稿。

01调研：UE4 的 UMG Designer 怎么做

它是「在编辑器里预览一块固定分辨率的界面」这个问题被磨得最久的一份答案，先照着盘一遍。

照抄 四条

  1. 右上角一个 Screen Size 下拉，每一项是描述 + 宽 + 高 + 宽高比四样，不是一串裸数字。
  2. 直接拖画布边角就能改预览分辨率，拖动中吸附到清单里的分辨率——不必先去开菜单。
  3. Custom 手输任意宽高；清单是快捷入口，不是取值约束。
  4. 当前分辨率与缩放常驻显示在 Designer 上，不用点开任何东西才知道自己在看多大。

有意偏离 五条，各自有理由

  • 不按设备类别分组。UE4 要覆盖手机／平板／主机／电视，分组是必需的；我们的用户全在工控与大屏上，分完只剩一组，那就是噪音。清单是一条扁平列表。
  • 吸附目标是整份分辨率，不是两条独立的轴。仓库已经就这件事判过一次：「宽命中而高不命中不算匹配——预设是一整个分辨率」。因此它是尺寸空间里的一个二维点（特征点捕捉），不是两条对齐参考线。
  • 场景自身的尺寸是最高优先级的吸附目标。UE4 的 widget 分辨率无关，没有「自己的尺寸」这回事；我们的场景有，而「拖回 1:1」正是最常要落的那一次。优先级严格先于距离，与既有捕捉次序同一条规矩。
  • 吸附容差取屏幕距离，不取分辨率差。与极轴那条逐字相同的理由：同样 40px 的分辨率差，在 25% 与 100% 视图下是完全不同的手感。复用既有的 snapRadius。
  • 不做 ini 扩展。UE4 的清单要追每年的新机型，我们这六档十年没动；真要扩就改 core 那个常量，不为它造一层配置。

02一个控件里混着两个问题

这是「适应 68%」读起来别扭的根因。两个问题的答案互不相干，却共用了一个下拉。

这块屏多大？被预览的那块屏幕的分辨率
头部 · 屏幕尺寸下拉拖画布边角（吸附）自定义宽高
改变被预览的东西：屏幕变成 1366 × 768 之后，1920 × 1080 的场景就要按 fit 映射进去、四周留黑边——这正是它在现场那台显示器上的样子。
我把它看多大？我在对话框里的取景
台面左下角 · 缩放滚轮Ctrl + 0 回 100%
只改变我的取景，不改变任何被预览的东西。台面因此复用 core 的视口代数——与两块画布同一个底座，滚轮、缩放、平移一行新概念都不引入。
「适应」既不是前者也不是后者，它是一个动作——按一下，把当前这块屏取景到窗口里，与画布上的「适配选择／适配容器」同一类。 做成一个常驻档位，就等于让用户永远停在一个非 1:1 的状态里还不知道。所以它从下拉里移出去，变成缩放控件旁的一个按钮，以及双击尺寸胶囊的那一下。

03为什么现在不符

红条是保真度缺陷（用户看到的不是真的），琥珀条是功能缺陷（会看到错的），灰条是打磨。

F1
画板与 Preview 根都被强制刷成白底 场景默认背景是 transparent（core 的显式决定：「编辑器不替用户填一个他迟早要改的颜色」）。于是同一块场景在画布上是深色、在预览里是白色，而用户无从判断哪个是真的。这就是「背景默认色不对」。
preview-dialog/styles.css
__artboard { background: #fff }
F2
zoom: 0.75 会在该比例下重新布局 文字度量、亚像素取整与换行位置都跟 100% 不是同一份结果——缩小的预览与真实输出在像素上确实不同。要看起来一样只能先按真实尺寸布局、再整体 transform: scale()。
compose-preview-dialog.tsx
--compose-preview-dialog-scale
F3
默认缩放是 75%，而且屏幕上没有任何地方写着这件事 用户以为自己在看 1:1。缩放可以不是 1:1，但必须印出来。
useState<PreviewDialogScale>('0.75')
F4
画板 12px 圆角 + overflow: hidden + 白色 1px 外圈 真实页面四个角是直的。圆角把角上的真实内容切掉了，白外圈还在深色场景边缘加了一道不存在的亮边。
__artboard { border-radius: 12px }
F5
对话框硬上限 1280×820，台面还有 clamp(20px,4vw,56px) 内边距 一块 1920×1080 的场景在 100% 下根本放不进去，只能滚动着看。而它的交付形态是整屏。
.compose-preview-dialog { height: min(820px, 100%) }
F6
场景选择器的名字读错了文档 列表来自当前页（activeDocument），名字却从正在编辑的那份文档取。跳到别的页面后整列退化成裸 id。
composeDocument?.entities[id]?.name
F7
跳转后闪一帧「Preview 目标 X 不存在或不是 Frame」 对话框把 frameId 显式传给 PageHost，而显式 id 按约定不回退；hostPage 要等 effect 才更新，于是新页面 ready 的那一帧拿到的是上一页的 frameId。
resolvePreviewFrameId(document, frameId, …)
F10
打开组件再按预览，看到的是上一个页面 页面模式一旦成立就静默压过传入的 document（activeDocument = hostPage.page?.document）。而宿主手上是两份互不相干的会话事实——activePage 与 activeComponent 各自独立，打开组件不会清掉页面会话，于是画布上是组件、预览里是页面。缺的是「画布上现在是哪一份文档」这**一个**答案。

const pageMode = navigation !== undefined && …
F8
场景选择器那套 CSS 是死的 样式写的是 button[aria-pressed]，markup 早就是 <select>。同一行里左边是浏览器原生控件、右边是定制控件。
.compose-preview-dialog__target button
F9
协议里的 fit / alignment 从没被用上；页脚恒占一行讲「按 Esc 关闭」 对话框绕过 fit 自己用 zoom；那句提示只在第一次有用，却永久占着高度。

整屏必须是同标签页路由，不能是新开一个标签页：既有硬规则是「页面预览必须包含未保存的改动」， 而新标签页读不到编辑器手上的 live 文档，它只能拿到上次保存的那一份。 「在新标签页打开」仍然给，但它是次级动作，并且要先落盘——这一点在按钮上说清楚，而不是静默地给出旧内容。

1面包屑就是目标：页面 › 场景，两级都可点开切换。页面那级只在宿主给了导航端口时出现。顺手修掉 F6——名字从当前页的文档取。

6时间轴只在目标场景有动画时出现。今天只有一个播放按钮，看不出播到哪儿、也没法回到某一刻。动画按场景独立，因此它跟着面包屑的场景走。

屏幕与场景不一致时，场景按 fit 映射进屏幕——协议里那个从没被用上的 fit 终于被用上了（修 F9）。 默认 contain：等比放进去、居中、剩下的部分画页面底色。这就是它在现场那台 16:10 显示器上真实的样子，而不是一个百分比读数。

吸附目标
场景自身尺寸 > 清单里的六档。优先级严格先于距离：场景尺寸更远也赢——「回到 1:1」不该被一档碰巧更近的分辨率抢走。与既有捕捉次序同一条规矩。
判据
屏幕距离，复用既有的 snapRadius（按视图缩放折算），不是分辨率差。同样 40px 的分辨率差，在 25% 与 100% 视图下手感天差地别——与极轴用屏幕距离而不是角度差是逐字相同的理由。
粒度
整份分辨率，是尺寸空间里的一个二维点，不是两条独立的轴参考线。沿用 findComposeSceneSizePreset 已经判过的那条：「宽命中而高不命中不算匹配」。
记号
命中时手柄与读数转琥珀并套一个方框，同时写出通名；没命中就是普通读数。与画布上的捕捉标记同形同色，形状先分开、颜色再分开。
锚定
对角锚定：拖右下角时左上角不动，与画布上 resize 手柄逐字相同的语义——用户已经会了。松手不重新居中，那会让屏幕在松手瞬间跳一下。Shift 锁宽高比，Alt 从中心缩放，两条都是通用手势，不为它们造新词。
回到原尺寸
双击尺寸胶囊 = 回到场景尺寸并重新居中，与菜单最上面那一组是同一个动作。
不写文档
预览里拖的是屏幕，不是场景。ComposePreviewDialog 不得改动传入的 ComposeDocument，这是既有约束。要改场景尺寸请去画布上的尺寸胶囊——那一条走 entity.frame.size.set，进撤销历史。两个长得像的矩形做不同的事，必须在屏幕上分得开：预览的画板没有八个手柄，只有一个角，读数也一直写着「屏幕」。

两个待定 需要你拍板

  • 要不要往清单里加拼接屏？现有六档全是单屏（1280×720 … 3840×2160）。储能／光伏现场的大屏经常是 3840 × 1080 双拼、5760 × 1080 三拼，而这两档在任何通用清单里都没有。加它们要改 core 那个已被用例逐项断言的常量——判据是你们的客户现场到底有没有拼接屏，这个我答不了。
  • 画布上的场景 resize 要不要也吸附到同一份清单？同一套吸附数学、同一份清单、同一个读数，但那一条是文档编辑（entity.frame.size.set，可撤销）。它与本节正交，可以单独排期。

两条推论 都是「不要为组件开特例」

  • 「自定义」是查表查不到的结果，不是组件的特例。把场景设成 1000 × 800 时，场景预览的第一项同样读作自定义——findComposeSceneSizePreset 返回 null、formatComposeSceneSizePresetLabel 不留空括号，这两条既有规则已经把答案定好了，一行新逻辑都不用写。组件只是几乎恒落在这一档。
  • 底部那个动作因此改叫「输入尺寸…」。一个词描述状态（这个尺寸不在清单上）、一个词描述动作（打开两个输入框），两者共用「自定义」会让菜单里出现两个同名而含义不同的东西——这块画布上正在反复躲的就是这一类。

但这些都要先修 F10 否则组件预览根本打不开

  • 今天打开组件再按预览，看到的是上一个页面：页面模式一旦成立就静默压过传入的 document，而宿主手上的 activePage 与 activeComponent 是两份互不相干的会话，打开组件不会清掉页面会话。
  • 修法不是在对话框里加一个开关，是让宿主交出一个答案：画布上现在是哪一份文档。目标种类（场景／组件）从那一个答案读出来，上面整张表都挂在它上面。

8没有时间轴：动画按它自己的 autoplay 与脚本绑定跑。要刮擦时间轴就回弹框——那是编辑动作。

09底色：默认不该是白

交付页面的底是宿主的，预览无从知道。今天的做法是默默替它答了「白」—— 而这个产品的大屏九成挂在深色底上。正确的做法是把这个不确定显示出来，并给一个就地试的开关。

1# 储能单元
透明 · 默认棋盘 = 这里没有墨
1# 储能单元
深底一键试宿主深色底
1# 储能单元
白底今天唯一的、且沉默的取值

三条边界 照搬 fit / alignment 那条既有判断

  • 帧内一律按文档画，预览不为任何 Entity 补一个文档里没有的底色。
  • 透明处画棋盘，不画白——白是一个看起来像内容的谎，而棋盘是一句实话。
  • 「页面底色」是会话状态，与 fit / alignment 同一条边界：属于播放侧，MUST NOT 写进文档、不进撤销历史。宿主真的知道交付底色时，用一个 prop 直接给出来，那时预览就画它——答案已知就不必再问。

10重构：抽一层 Surface，两个形态都只是它的 chrome

今天 ComposePreviewDialog 一个文件里同时握着：目标解析、页面宿主、播放会话、缩放、全屏、chrome。 照原样再加一个整屏形态，前五样会被抄第二遍——而抄漏的那一份，症状就是「两个预览不一样」。

ComposePreviewSurface新增 · 无 chrome

  • 解析目标：页面模式走 ComposePageHost，文档模式走 ComposePreview；对外只暴露「当前页 + 当前场景 + 可选场景列表」
  • 屏幕：屏幕尺寸（默认 = 场景尺寸）+ fit / alignment，把场景映射进这块屏；尺寸来自 core 的 COMPOSE_SCENE_SIZE_PRESETS，拖边角改它并吸附
  • 视图：复用 core 的视口代数（滚轮 / 平移 / Ctrl+0）+ transform: scale()（不是 zoom，修 F2）；屏幕与视图是两份互不影响的状态，并各自上报读数
  • 底色：棋盘 / 纯色 / 宿主指定，画在帧外与透明处，帧内一个像素都不碰
  • 播放会话：播放头、播放模式、rAF 生命周期
  • 目标回退：页面变化时同一帧内重解目标，不经 effect——修 F7

ComposePreviewDialog保留 · 改造

  • Surface + 模态 chrome（面包屑、时间轴、Esc、遮罩）
  • 默认屏幕 = 场景尺寸（因此默认 1:1），视图取「适应窗口」一次
  • 删掉页脚、zoom、画板圆角与白外圈、那套死 CSS

ComposePreviewPage新增

  • Surface 铺满视口 + 自动隐藏控制条
  • 默认屏幕 = 实际视口，视图 1:1；挑了别的屏幕尺寸就在真屏幕里套出那块屏
  • 宿主负责路由；不卸载编辑器，因此 live 文档照旧在手上

11落地顺序

前三步不动结构，当天就能让弹框「符」；结构改动排在后面，因为它要先有一条能跑的纵向流程。

1修保真度四条：白底、zoom、圆角与白外圈、缩放读数F1–F4。纯 CSS 与一个 state 默认值，不动任何协议。改
2修两条缺陷：场景名读错文档、跳转后闪错误态F6–F7。后者把目标解析挪进渲染期的 prev-adjust，与 PageHost 里已有的那处同一种写法。修
3把缩放下拉换成「屏幕尺寸 + 视图缩放」两个控件清单复用 core 既有常量；fit 终于被用上（F9）。这一步就让「适应」这个档位消失。改
4宿主交出「画布上是哪一份文档」这一个答案，修 F10目标种类（场景／组件）从它读出来，第 07 节整张表都挂在它上面。修
5拖边角改屏幕尺寸，带吸附吸附数学是纯函数，Vitest 直接钉；优先级、容差与记号按上一节那七条。新能力
6抽 ComposePreviewSurface，把弹框改成它的 chrome行为逐条不变，既有用例全绿即为通过。重构
7新增 ComposePreviewPage 与宿主路由OpenSpec 变更：新增公共 API + 新能力，按流程先提案。新能力
