## ADDED Requirements

### Requirement: `.dwg` 不静默

资源浏览器 MUST 在 `.dwg` 文件上给出可读的说明，MUST NOT 什么都不出现。

一片空白让用户读到的是「这个工具不支持我的图」，而真实原因是「先转成 DXF 就能用」。说明
MUST 给出可执行的下一步，而不只是声明不支持——这与「导入能导的，报告导不了的」是同一条
判断，只是发生在导入开始之前。

这一项 MUST NOT 依赖任何 DWG 解码实现：它在解码器缺席时**始终**是正确行为，因此不受许可证
或体积的任何决定阻塞。

#### Scenario: 右键一个 `.dwg`

- **WHEN** 用户在一个 `.dwg` 文件上打开上下文菜单
- **THEN** 出现一项说明该格式需要先转成 DXF，并指出可用的转换途径

#### Scenario: 其他文件上不出现

- **WHEN** 用户在一个非 `.dwg` 文件上打开上下文菜单
- **THEN** 该项不出现——它对别的文件毫无意义，常驻只会让菜单更长

### Requirement: DWG 解码器由宿主注入

系统 MUST 提供无 React、无 DOM 的 `@compose-ui/dwg`，只依赖 `core` 与 `dxf`。本包 MUST NOT
在 `dependencies` 中包含任何 DWG 解码实现，解码器 MUST 由调用方注入。

三条独立成立的理由：**许可证**（现有的开源解码器是 GPL-3.0，注入把「要不要引入它」留给做
决定的那个人）、**体积**（wasm 本体约 6.6 MB，而它一个项目只用一次，注入让不导 DWG 的宿主
零成本）、**可替换**（买了商业 SDK 或自建转换服务的宿主注入同一个端口即可复用整条链路）。

解码器端口的类型 MUST 结构化声明，MUST NOT 从任何解码库引入——与 `DxfEntitySeed` 不从
`@compose-ui/component-registry` 引入是同一个手法。

#### Scenario: 注入一份自定义解码器

- **WHEN** 调用方注入一份结构上满足端口的解码器
- **THEN** 导入按它的输出进行，本包不引用任何解码库

#### Scenario: 未注入解码器

- **WHEN** 宿主没有注入解码器
- **THEN** `.dwg` 上仍然是那条说明，既不报错也不静默

### Requirement: DWG 复用 DXF 的映射层

DWG 导入 MUST 把解码结果适配成 `DxfRecord[]`，随后交给 `@compose-ui/dxf` 的记录层入口。
坐标翻转、角度取反、图层求值、`BLOCK` → Component Asset、`INSERT` → 组件实例、块基点 →
`Transform.pivot`、诊断聚合 MUST NOT 另写一份。

DWG 与 DXF 是**同一份数据的两种编码**：产出什么文档没有变，变的只是编码，因此被换掉的只有
分词层与记录层。`@compose-ui/dxf` MUST 导出记录层入口，使映射层可以被两种编码共用。

适配层把结构化实体重新写回组码对，这是明知的一次绕行：取它而不是另立中立 IR，因为后者要
连同测试重写既有映射层，而产出的文档完全一样。

#### Scenario: 同一张图的两种编码

- **WHEN** 同一张图的 `.dwg` 与 `.dxf` 两份分别导入
- **THEN** 两份导入计划逐字段相同

#### Scenario: 块与插入

- **WHEN** DWG 含一个块定义与引用它的两个插入
- **THEN** 结果与 DXF 那一路一致：一份组件资产与两个引用它的实例

### Requirement: 解码失败必须可判别

解码失败 MUST 产出可判别的诊断，MUST NOT 退化成一份空场景。

损坏的文件、过新的版本与解码器自身的崩溃在屏幕上都可能呈现为「导进来一张白图」——一个看
起来正常的错误结果比一条读得出来的失败糟得多。这与「悬空引用只是解算失败、不让文档非法」
同源：失败要说出来。

解码器读不了的实体 MUST 走既有的诊断聚合规则，按类型计数。

#### Scenario: 损坏的文件

- **WHEN** 解码器对一份 `.dwg` 返回失败
- **THEN** 导入不产出场景，用户看到一条说明解码失败的诊断

#### Scenario: 读不了的实体

- **WHEN** 文件含解码器跳过的高级实体
- **THEN** 其余内容照常导入，诊断中该类型聚合成一项并带计数
