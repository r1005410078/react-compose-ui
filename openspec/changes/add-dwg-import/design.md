# 设计

## 上下文

问题不是「怎么解析 DWG」，而是「**要不要**在这个仓库里解析 DWG，以及谁来承担它的代价」。
技术路径只有三条，其中两条的成本不写在代码里——一条写在许可证里，一条写在账单上。

因此本文档先把四条路摆出来并给出推荐，再写落地的技术决策。

## 目标 / 非目标

- 目标：让手上只有 `.dwg` 的用户走得下去——要么导进来，要么当场知道该怎么办。
- 目标：无论走哪条路，**产品侧的映射逻辑一行不重写**。
- 非目标：自研 DWG 解码器；DWG 导出；服务端转换服务。
- 非目标：借这一刀扩充实体覆盖。

## 决策 1 · 四条路的对照，推荐 B（有条件）

| | 做法 | 一次性成本 | 持续成本 | 阻碍 |
|---|---|---|---|---|
| **A** | 不解析，让用户先转成 DXF | 一条说明文案 | 每次导入多一步手工转换 | 无 |
| **B** | LibreDWG 编译的 WASM，**由宿主注入** | 适配层 + 懒加载 | 跟随上游 | **GPL-3.0**；6.6 MB wasm |
| **C** | ODA Drawings SDK | 会员申请 + 集成 | 年费，$0（教育）～ $25,000+（企业） | 无浏览器发行，实际要后端 |
| **D** | 自研解码器 | 以人年计 | 每个 DWG 大版本一次 | 闭源二进制、版本各异 |

**D 直接否掉**。DWG 没有公开规范，LibreDWG 逆向了二十多年才做到「读基本完成」。把它排进
路线图是在骗自己。

**C 与产品定位冲突**。ODA 的 Drawings SDK 是 C++ 原生库，没有官方的浏览器/WASM 发行，落地
形态必然是「宿主部署一个转换服务」。而本仓是一组**可嵌入宿主 React 项目**的客户端包——为
一个导入功能要求每个宿主运维一个服务，是把成本从我们这里挪到每一个用户那里。年费是次要
理由，架构冲突才是主要理由。

**B 是唯一在客户端成立的路**，但它带两个真实代价，见决策 2 与决策 3。

**A 无论如何都要做**。它不是 B 的替代品，是 B 的下位兼容：许可证的答案是「不行」时 A 就是
终局，答案是「可以」时 A 仍然是解码器没注入那一档的行为。因此提案把它排成第一步，不挂在
任何条件下。

## 决策 2 · 许可证是这件事的主要阻碍，而它不是技术决定

LibreDWG 是 **GPL-3.0 or later**（上游自述）。npm 上每一份 WASM 发行都是它的衍生作品——
`@mlightcad/libredwg-web` 的仓库许可证同样写着 GPL-3.0。

这意味着：把它写进 `@compose-ui/dwg` 的 `dependencies` 并发布，那个包就得是 GPL-3.0；而任何
链接它的宿主应用也落进同一件事的射程。**本仓今天既没有 LICENSE 文件，也没有 `package.json`
的 `license` 字段**，而各包的 `publishConfig.access` 都是 `public`——也就是说，这个问题今天
根本还没有答案，却已经在发布了。

因此本提案**不替任何人做这个判断**，也不在代码里假装它不存在。需要先回答的是：

1. 这些包打算以什么许可证发布？
2. 目标用户交付的大屏是内部系统，还是对外分发的产品？（GPL 的传染在分发那一刻才发生，
   实施工程师给甲方做的内部系统与一个卖出去的 SDK，答案可能完全不同。）

我不是律师，上面是对公开许可证条款的读法，不是法律意见。

## 决策 3 · 解码器由宿主注入，本包不 bundle

即使许可证的答案是「可以」，解码器也不进 `@compose-ui/dwg` 的依赖。三条独立成立的理由：

- **许可证**：注入把「要不要引入 GPL 代码」这个决定留在**做决定的那个人**手上。库不替宿主
  选，这与本仓一贯的「Preset seed / Paint 编辑端口 / 导航端口由宿主注入」是同一条边界。
- **体积**：wasm 本体 6.6 MB、打包后的 JS 约 9 MB（`@mlightcad/libredwg-web@0.7.10`）。这是
  本仓最大的产物，高出一个数量级，而它**一个项目只用一次**。注入让不导 DWG 的宿主一个字节
  都不付。
- **可替换**：宿主如果买了 ODA 或自建了转换服务，注入同一个端口即可复用整条映射链路。把
  实现钉死在包里会让这条路走不通。

端口的类型**结构化声明**，不从 `@mlightcad/*` 引入——与 `DxfEntitySeed` 不从
`@compose-ui/component-registry` 引入是同一个手法：类型上兼容即可传进来，本包因此连
`devDependencies` 都不需要它。

## 决策 4 · 换掉分词与记录层，映射层一行不改

`@compose-ui/dxf` 的包注释已经把这条写下来了：「分词层与记录层认识的是 DXF 的**组码结构**，
与产出什么文档无关；被重写的只有映射层。」DWG 是这句话的**镜像用法**——产出什么文档没变，
变的正是编码，因此被换掉的只有分词与记录层。

落地的缝就在 `dxf-plan.ts:672` 那一行：

```ts
export function planDxfImport(text: string, options: PlanDxfImportOptions): DxfImportPlan {
  const records = groupDxfRecords(tokenizeDxf(text))
  // ……以下 150 行映射，只读 records
}
```

把内层拆出来导出成 `planDxfImportFromRecords(records, options)`，DWG 这一路就是
「解码 → `DxfRecord[]` → 同一个函数」。Y 轴翻转、角度取反、ACI 色表、图层求值、块基点补偿、
诊断聚合——823 行一个字符不改，它们的测试也继续钉着同一份行为。

**这条缝的代价说在明处**：适配层要把解码器给出的**结构化实体**重新写回组码对，看起来像绕了
一圈。取它而不是另立一层中立 IR，理由是后者要把那 823 行连同它们的测试一起重写，而重写的
**收益是零**——产出的文档完全一样。何况组码本来就是 DWG 实体模型自己的词汇：LibreDWG 的
结构体逐字段对应 DXF 组码，那是它被写出来时的目标。

判别性用例因此是：**同一张图的 `.dwg` 与 `.dxf` 两份，导入结果必须逐字段相同**。这条用例
同时钉住「映射层没被 fork」这件事——fork 了它就会红。

## 勘察 1 · 字段齐全：映射层读的每一个组码都有对应

对着 `@mlightcad/libredwg-web@0.7.10` 的类型声明逐条核对映射层**实际读到**的组码
（`dxf-plan.ts` 里每一处 `numberValue` / `firstValue` / `allValues`）：`LINE` 的
`startPoint`/`endPoint`、`CIRCLE` 的 `center`/`radius`、`ARC` 的 `startAngle`/`endAngle`、
`LWPOLYLINE` 的 `vertices[].x/.y/.bulge` 与 `flag`、`TEXT` 的
`startPoint`/`textHeight`/`text`/`halign`/`rotation`、`INSERT` 的
`name`/`insertionPoint`/`xScale`/`yScale`/`rotation`、实体的 `layer`、`LAYER` 表的
`name`/`colorIndex`、`BLOCK_RECORD` 的 `name`/`basePoint`/`entities`——一项不缺，`halign`
的枚举值逐值等于组码 72。

顺带一条：`DwgDatabase.entities` **只含模型空间**，块内容挂在 `tables.BLOCK_RECORD` 上
（真实文件里确认为 `*Model_Space` / `*Paper_Space` / `*Paper_Space0` 加真实块名），因此适配层
天然不会把布局块内容漏到顶层。

## 勘察 2 · 角度是弧度，已在真实文件上逐位确证

拿 LibreDWG 自己的测试图纸（成对的 `.dwg` / `.dxf`，同一张图两种编码）跑：`Arc.dwg` 解出
`startAngle = 2.002420826591628`，而同一张图的 DXF 写着 `50 = 114.7302621727979`——
`2.002420826591628 × 180 / π` 正是这个数，**逐位相同**。

解码器原样透出 LibreDWG 的内部表示，不做单位换算；DXF 的组码 50/51 是度，`dwg2dxf` 在写出
那一刻才换算。漏掉换算的症状是**每一段弧与每一个符号都被转了 57.3 倍**，而它在对称图形上
完全看不出来——与「块基点写成盒中心」是同一类错误。

## 勘察 3 · `dwg_write_dxf` 可用，决策 4 的适配层因此可能整个不需要

上游文档写着 DXF 写出默认关闭，**但这个 npm 构建里是开的**：`LibreDwg.dwg_write_dxf(bytes)`
吃 DWG 字节、吐 DXF 文本。八份夹具**八份都成功**，耗时 9–108 ms。产出与原始 DXF 对照：

- `example_2018` 的 **30 种实体类型，计数逐项相同**（含 `VERTEX` 13、`SEQEND` 4 这些老式
  `POLYLINE` 的附属记录——而 typed DB 那条路把它们收成了一个 `POLYLINE3D`，两条路的
  **诊断计数因此会不一样**）；
- `ARC` 的角度 `264.9225334366025` vs `264.9225334366026`，只差末位浮点。

这条路是 `DWG 字节 → DXF 文本 → 现有的 planDxfImport(text)`，**一行适配层都不用写**：
弧度换算、图层布尔反向编码、`VERTEX` 归并全部由 LibreDWG 自己的写出器承担，而它显然比我们
新写的适配层更懂这些。推论：记录层的那条缝（`planDxfImportFromRecords`）与 `dxf-import`
那条 MODIFIED 需求**也不需要了**。

代价有两条，都要写在明处：**它依赖第三方包的一个构建开关**（上游若按文档改回
`disable-dxf` 就整条失效）；以及走了一趟文本（75 KB 的 DWG 出来 332 KB 的 DXF）。前者可在
运行期检出——`dwg_write_dxf` 失败时返回 `null`，那一档退回第 1 步那条「先转成 DXF」的说明，
因此失效是**可见的降级**而不是静默。

## 勘察 4 · 图层状态两条路都是错的，而且它们互相矛盾

这是这次 spike 最重要的发现，也是只有跑真实文件才抓得到的那一类。

- **`dwg_write_dxf` 这条路**：产出的每一个图层色号都是**负数**（DXF 里负色号 = 图层关闭）。
  17 个图层，**17 个负数**；而参考 DXF 里本来关着的是 **0 个**。
- **typed DB 这条路**：每一个图层都报 `locked: true`，与参考 DXF 的 `70 = 0` 不符——
  17 个里 **16 个不符**。

两条路出自**同一个库、同一份文件**，却对同一个字段给出互相矛盾的答案（typed 说 `off: false`，
它自己的写出器写 `-7`）。至少有一个是错的，而参考 DXF 站在 typed 那一边。结论是**两条都不
可信**。

按现有映射层的规则，这会让导进来的每一张图**整张不可见**（负色号 → `Visibility` 关）或
**整张锁定**——图确实导进来了，用户却什么都看不见、什么都动不了，而屏幕上没有任何东西解释
为什么。

因此 DWG 这条路 MUST **不采信解码器给的图层开关与锁定**：一律按可见、未锁定导入，并出一条
诊断说明图层状态没有带过来。判据是既有那条**代价不对称**——丢掉图层状态，用户两下点击就能
自己关掉某一层；而整张图不可见是一个看起来像「导入失败」的成功导入。色号取**绝对值**。

## 勘察 5 · 解码错误码被高层 API 吞掉了

喂八个字节的垃圾进去：`dwg_read_data` **照样返回一个指针**，`convert` 给出
`entities: 0` 而 `tables` 有 7 张——一份**结构上看起来正常的空库**。决策 5 担心的那个失败
模式是真的。

错误码本身是有的：底层 `wasmInstance.dwg_read_file()` 返回 `{ error, data }`，垃圾输入那次
`error = 2048`（LibreDWG 的 `INVALIDDWG`），而两份 `example_*` 是 64/68
（`VALUEOUTOFBOUNDS` / 加 `UNHANDLEDCLASS`，非致命）。但**包装层只把它 `console.warn` 出去
就丢掉了**，只返回 `data`。

推论：**解码器端口的契约必须带上错误码**，不能是 `(bytes) => database`。宿主要么走底层
API，要么在注入时把错误码一起交出来——否则「解码失败必须可判别」这条需求根本无从满足。

## 决策 4 需要重判（勘察 3 的直接后果）

原决策是「适配 typed DB → `DxfRecord[]` → 复用映射层」。勘察 3 之后有了更短的一条：
**`dwg_write_dxf` → DXF 文本 → `planDxfImport`**，它删掉整个适配层、删掉记录层的缝、
删掉 `dxf-import` 那条 MODIFIED 需求，还顺带把勘察 2 与勘察 4 的一半交给上游去做。

推荐走这一条，理由是**新写的适配层不可能比 LibreDWG 自己的写出器更懂 DXF**，而勘察 2 已经
证明我们确实会在单位上栽跟头。原方案作为退路留着：上游哪天真的关掉 DXF 写出，那条缝仍然是
可行的第二条路，而届时勘察 1 已经把字段核对做完了。

两条路都躲不开勘察 4 与勘察 5——图层状态不可信、错误码必须带出来，与走哪条编码无关。

## 决策 5 · 版本覆盖够用，但失败必须响

LibreDWG 上游自述：「解码器基本完成，只有少数很高级的 R2010+ 实体读不了、会被跳过」。我们
只读 `LINE`/`CIRCLE`/`ARC`/`LWPOLYLINE`/`TEXT`/`INSERT` 加图层表与块表——恰好是覆盖最好的
那一批。因此版本覆盖**不是**这条路的风险点。

真正的风险是**读出来是空的**：损坏的文件、过新的版本、解码器自己崩掉，在屏幕上都可能呈现
为「导进来一张白图」。因此解码失败 MUST 是一条可判别的诊断，MUST NOT 退化成一份空场景——
这与「悬空引用只是解算失败、不让文档非法」同源：失败要**说出来**，而不是变成一个看起来正常
的错误结果。

## 决策 6 · 懒加载，且只在真的要导的时候

6.6 MB 不能进主包。解码器由宿主注入这一条已经让它落在宿主侧，示例应用里再示范一次
`await import()`：用户右键点下「导入为页面」的那一刻才去取 wasm。

推论：导入变成一个**有可感知延迟**的操作，界面要有进行中的反馈。这不是 DXF 那一路的行为
（那一路是同步纯函数），因此不能假设两条路的 UI 可以逐字共用。

## 风险 / 权衡

- **GPL 传染** → 由宿主注入；仓库许可证先有答案再做第二步。
- **6.6 MB** → 不进主包、懒加载、不导 DWG 的宿主零成本。
- **上游停更** → 端口是结构化声明的，换实现不动映射层；最坏情况回落到路 A。
- **适配层重写组码看起来绕** → 换来 823 行映射层与它的测试原样不动；由「同图双格式结果相同」
  的用例钉住。
- **导入有延迟** → 明确的进行中反馈；失败有可读诊断。

## 迁移计划

无。这是纯新增：DXF 那一路的行为、协议与文档一个字段都不改，`planDxfImport` 的签名保持不变
（它变成一行封装）。第一步与第二步之间也没有中间态——第一步的说明在解码器缺席时**始终**是
正确行为。

## 待解决问题

1. **仓库以什么许可证发布？** 第二步的前提，且这个问题今天本来就欠着（无 LICENSE 文件、
   无 `license` 字段，而各包已在公开发布）。
2. **目标用户的交付形态是内部系统还是对外分发？** 决定 GPL 的传染是否真的落地。
3. **要不要先拿真实图纸做一次 spike？** 建议要：拿三份真实的 `.dwg`（设计院一次接线、厂家
   符号库、机房平面）跑通「解码 → 记录 → 现有映射」，在写任何产品代码之前验证决策 4 的缝
   是否真的不需要改映射层。这一步不发布任何东西，因此**不受许可证问题阻塞**。
