# DWG 导入

## Why

实施工程师手上的图**不一定是 DXF**。DXF 是交换格式，DWG 才是 AutoCAD 的原生存档格式——
设计院发出来的一次接线、厂家给的符号库，原始文件几乎全是 `.dwg`，DXF 是有人为了交换**另
存**出来的那一份。

今天在资源浏览器里右键一个 `.dwg`，什么都不会发生：没有「导入为页面」，也没有任何一句话
说明为什么。用户能读到的唯一解释是「这个工具不支持我的图」，而真实原因是「先转成 DXF 就
能用」——一句话的事，我们没说。这与「静默丢弃不可接受」是同一条判断，只是发生在导入开始
之前。

前一刀（DXF 导入）已经把**产品侧**的难题全部解完了：Y 轴翻转与角度取反、图层在导入期求值、
`BLOCK` → Component Asset、`INSERT` → 组件实例、块基点 → `Transform.pivot`、诊断按类型聚合。
DWG 与 DXF 是**同一份数据的两种编码**，因此这一刀不该重做其中任何一项——它只该换掉最下面
那一层。

## What Changes

### 第一步：`.dwg` 不再静默（无条件做）

资源浏览器在 `.dwg` 上给出一条**说明**而不是一片空白：这个格式需要先转成 DXF，以及去哪里转
（ODA File Converter 免费、跨平台、可批量）。这一步不引入任何依赖，也不等许可证的答案。

判据与既有那条一致：**一次看不见的失败等于没有失败**。用户此刻需要的不是导入，是知道下一步
往哪走。

### 第二步：解码器由宿主注入（许可证有答案之后才做）

新增 `@compose-ui/dwg`，无 React、无 DOM，只依赖 `core` 与 `dxf`。它**不 bundle 任何 DWG 解码
实现**——解码器由调用方注入，本包只做「解码结果 → DXF 记录」的适配，随后交给既有映射层。

这与 `DxfCreateSeed` 是同一个手法：Preset seed 由调用方注入，因此 `@compose-ui/dxf` 不认识
Registry；解码器由调用方注入，因此 `@compose-ui/dwg` 不认识 LibreDWG。理由不同（那里是分层，
这里是**许可证与体积**），动作相同。

为此 `@compose-ui/dxf` 要把已有的记录层入口露出来：`planDxfImport(text)` 今天就是
`planDxfImportFromRecords(groupDxfRecords(tokenizeDxf(text)))` 的一行封装（`dxf-plan.ts:672`），
把内层导出即可。**映射层一个字符不改**，而那是 823 行已经被测试钉住的代码。

### 本步刻意不做

- **自己写 DWG 解码器**：DWG 是闭源二进制格式，每个大版本的结构都变。LibreDWG 做了二十多年
  才做到「读基本完成」。这不是一刀的工作量，是一个项目。
- **服务端转换**：本仓是一组**可嵌入宿主 React 项目**的客户端包，没有后端，也不该因为一个
  导入功能就要求宿主部署一个服务。
- **DWG 导出**：与 DXF 导出同一条理由——导入与导出是两个方向，各有各的取舍。而且 LibreDWG
  的**写**只到 R2000，比读弱得多。
- **扩充实体覆盖**：DWG 能表达而我们表达不了的东西（`SPLINE`、`HATCH`、`DIMENSION`、三维）
  仍然走既有诊断，不因为换了编码就多支持一种。

## Impact

- **`@compose-ui/dxf`**：导出记录层入口 `planDxfImportFromRecords`。行为不变，映射层不改。
- **`@compose-ui/dwg`**（新）：结构化声明的解码器端口、解码结果 → `DxfRecord[]` 适配、诊断。
  依赖 `core` 与 `dxf`，无第三方运行时依赖。
- **`@compose-ui/editor`**：`.dwg` 的上下文菜单项（第一步是说明，第二步是导入）。
- **`app/`**：注入解码器的集成示例与一份演示用 `.dwg`。
- **仓库许可证**：第二步的前提。见 `design.md` 的待解决问题——**这不是技术决定**。
