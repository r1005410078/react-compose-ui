# 设计说明

## 按钮启动的必须是**同一条**会话

按钮不得自己走一条「构造上下文、推进状态机」的路径。命令行敲名字那条路已经处理了三种拒绝
（词不在表里、词在表里但此刻不可用、会话进行中的非法输入），另写一份必然只实现其中一两种。

这与仓库已经做过的判断同形：`runComposeCommandImmediately` 是跑退化会话的**唯一**实现，各
消费者内联「`prompt` 为 null 就 accept」会让同一条命令在不同入口给出不同结果。

因此句柄的实现是**把命令 id 喂给命令行已经在用的那个启动函数**，一行不多。

## 为什么是命令式句柄，不是受控 prop

受控写法（`pendingCommandId` + `onConsumed`）把一个**事件**建模成状态，代价有三：需要一次
消费握手；同一个按钮连点两次要靠 nonce 才能再次触发；而「当前挂着一个待启动的命令」这个中间
态在任何时刻都不描述真实世界的任何东西。

`useImperativeHandle` 在本仓库有先例（`ComposeCanvasRulersHandle`）。句柄只暴露动作，不暴露
状态——状态仍由 `onActiveCommandChange` 单向上报，两个方向各自单一。

## 为什么按钮要有按下态

命令进行中时命令行会显示「指定第一个角点」，但那行字在图面下方，不在用户刚刚点击的位置。
AutoCAD 的 ribbon 按钮在命令进行期间保持高亮，正是因为这个距离。

按下态由 Stage 上报的**当前会话命令 id** 驱动，MUST NOT 由工具栏自己记「我刚点了哪个」——
命令可能被 `Escape`、被并发文档变化、被另一条命令取代而结束，工具栏记的那一份会停在过去。

## 为什么删掉形状工具而不是留着

三条各自独立：

1. **同一件事两套机制。**矩形在一边是拖一下、在另一边是取两个点，而路线图已经把这种拆分
   列为绘图模式的代价之一。
2. **它让一处已知的仲裁器冲突变得用鼠标就能触发。**取点插件（1650）高于绘制（1000），两者
   同时武装时 `pointerdown` 被前者吃掉，拖动永远起不来。今天要先点工具再敲命令才凑得出来，
   加了按钮之后两下鼠标就到。
3. **命令那一套严格更强**：能键入精确坐标、能捕捉、能正交、能中途放弃上一点。拖拽只快在
   「大概画一个」，而这个产品的用户画的是接线图。

`draw-container` 与 `draw-text` 不在此列：它们不是制图几何，没有命令等价物，也不与取点插件
争抢——它们本来就是拖一个盒出来。

## `ARROW` 是补一个缺口，不是造第二个词

「已经有等价画布命令的动作不再造第二个词」挡的是重复。箭头今天**没有任何命令表达得了**——
`LINE` 产出的曲线不带 `markerEnd`。先补上这个词，再删工具，能力不缺一块。

它与 `LINE` 的差别只有一个 Renderer prop 的初值，因此实现上共用同一个会话工厂，只多传一个
seed；不复制一份取点逻辑。

## 判别性

| 用例 | 钉住的东西 | 改前 |
| --- | --- | --- |
| 点 `RECTANGLE` 按钮后命令行提示「指定第一个角点」 | 按钮真的启动了会话 | 必红 |
| 点按钮后取两个点，画布上多出一个矩形曲线 | 启动的是**那条**命令 | 必红 |
| 会话进行中该按钮是按下态，`Escape` 之后不是 | 按下态来自 Stage 而不是工具栏自己 | 必红 |
| 工具栏上不再有形状 split button | 删除真的发生了 | 必红 |
| `ARROW` 画出的曲线带 `markerEnd` | 能力没有随工具一起消失 | 必红 |

第三条的判别性容易被做假：如果按下态由工具栏自己的 `useState` 记，前半句照样通过，只有
`Escape` 那半句会红。因此**两半必须写在同一条用例里**。
