# 设计

## 为什么是「按下即开会话」而不是「点击与拖动二选一」

一个自然的写法是先判别这次手势是点击还是拖动（超过阈值算拖），再分派。它有两个问题：

- **阈值是新引入的魔法数**，而仓库里没有第二处需要它。
- **提示会迟到。**用户按住夹点的那一刻就该看到「指定新位置」，而阈值判别要等他动或不动才
  知道自己在干什么。

因此会话在 `pointerdown` 就开，两条路径共用同一个会话：

```
pointerdown 夹点   →  会话开始，提示「指定新位置」，夹点点亮
  移动后 pointerup →  用这个落点推进会话 → 提交 → 会话结束，熄灭
  原地 pointerup   →  会话留着，夹点保持点亮
    再点一下画布   →  用那个落点推进会话 → 提交 → 结束
    键入坐标 ↵     →  同上，但落点不经捕捉/正交/网格
    Escape         →  会话取消，熄灭，几何编辑会话仍在
```

拖动那一支与今天逐字相同：`start` / `move` 更新本地预览、`end` 派发一条 `entity.curve.set`。
本刀**没有**改写它，只是让它顺带带上提示与热夹点。

## 会话必须是 `ComposeCommandSession`

`stage-engine` 的既有规范写着「MUST NOT 另实现一套命令会话」，`commands` 的写着「能敲什么
只有一种形状」。顶点取点是一条一步会话——与 `LINE` 的第二点同形——因此它 MUST 由
`@compose-ui/commands` 的四态推进承载，而不是在几何编辑 Hook 里现搓一个「等一个点」的状态。

代价是这条会话**没有名字**：它由手势启动，不由词启动。这不与「命令行只认一份词汇表」冲突
——那条挡的是「面板里有、命令行敲不出来」的**动作**，而本会话不是一个动作，是一个手势的
中间态。`useStageDrafting` 因此要开放一个按**会话对象**启动的入口，与既有的按名启动并列。

## 排除点的来源要跟着搬

今天 `snapExcludedPoint` 由 `use-stage-geometry-editing` 的 `dragVertexId` 反查文档几何得出。
点亮期同样要排除——指针移回夹点附近时不排除的话会被吸回原处。事实来源因此从
「正在拖的夹点」放宽成「**正在被这条会话作用的**夹点」，两条路径读同一个值。

读的仍然是**文档**几何而不是预览：要挡的是它出发的地方。

## 热夹点为什么这次要做

`AGENTS.md` 记着「不做热夹点（`GRIPHOT`，拖动中变红）：它要表达『正在拖的是哪一个』，而夹点
本来就跟着预览几何走在光标底下，那个信息已经在屏幕上了」。这句话在**拖动**上是对的，本刀不
翻它。点亮是另一种情形：

| | 拖动中 | 点亮后松手 |
| --- | --- | --- |
| 夹点在哪 | 光标底下 | 停在原位 |
| 光标在哪 | 同一处 | 在别处找目标点 |
| 「下一个点会挪哪个顶点」 | 已经在屏幕上 | **没有任何东西说得出来** |

多段线尤其：五个顶点一模一样，点亮了哪一个只能靠记。

它需要**真的 React 状态**（一个夹点 id），这不违反「不为一个视觉反馈引入每帧 `pointermove`
都要写的 React 状态」——那条约束的对象是悬停，而悬停仍然是纯 CSS。点亮每次手势只写一次。

## 拾取框的第三态

既有规范写「未拖动时画框、拖动时只画线」，理由是「框表达可抓的靶区；一旦抓住，那件事已经
发生」。点亮期同样是**已经抓住了**，因此框也不该画。规则不是多一条分支，而是把条件写准：

```
画框  ⟺  会话在跑  ∧  没点亮  ∧  没拖动
```
