# 设计决策

## D1 · 绘图是**模式**而不是 `StageInteractionTool` 的新成员

工具回答「现在这一下要干什么」（select / draw-rectangle / pan），模式回答「整块画布按哪套
规矩工作」。绘图模式要同时换四样东西：工具集、光标、框选默认判定、底部 chrome。塞进
`StageInteractionTool` 意味着每一处消费 tool 的代码（光标派生、绘制接管、工具栏高亮、
键盘绑定）都要再判断一次「是不是绘图模式的工具」，而这些判断没有一处是它们自己的职责。

编辑器已有 `ComposeEditorMode = 'design' | 'animation'` 与一个 radiogroup 切换器，绘图是
第三段。切换器的方向键逻辑当前写死「另一个就是对面那个」，泛化成按索引循环。

模式是**会话状态**，不进文档——与视口、网格、播放头同一条既有规矩。

## D2 · 命令引擎零搬运：`commands` 本来就是泛型的

`ComposeCommandDefinition<TContext, TEffect>` / `ComposeCommandSession<TEffect>` 对上下文与
效果两个类型参数泛型，包本身连 `core` 都不依赖。因此 Stage 侧只需要：

```
StageDraftingContext  // 当前文档、活动场景、选择集、上一点
StageDraftingEffect   // { kind: 'entities.add', entities } 之类，由宿主翻成 EditorCommand
```

`cad` 当初为命令行付出的设计成本（四态推进、`rejected` 不结束会话、`prompt` 携带 `commit`
连续放置）在这里直接兑现。**这也是当初把 `commands` 立成零依赖包的回报**——如果当时让它
认识 `CadDocument`，今天就要么改它的类型、要么写第二份。

`stage-engine` 因此新增对 `commands` 的依赖：`commands` 是零运行时依赖的 Layer 1 包，
`stage-engine` 也在 Layer 1，方向合法且不引入 React/DOM。

## D3 · 会话状态住在 Stage，命令行由 Stage 渲染

命令会话产出三样东西：提示文本、预览几何、捕捉标记。它们是同一份状态的三种呈现。把命令行
交给编辑器渲染意味着要把提示、预览与标记逐帧回传给宿主，凭空造出一个跨包协议；而
`ComposeCadCanvas` 已经证明「画布自己持有会话」是可行的形状。

编辑器只做两件事：切模式、把工具栏换成绘图工具。

## D4 · 点输入管线下沉 `core`，不进 `commands`

AGENTS.md 当初判定坐标语法「是 CAD 专有，不进 `commands`」——**前半句现在不成立了**（两个
消费者），后半句仍然成立（它不是命令概念，是输入解析）。`core` 是正确落点：它已经承载视口
代数、轴点阵、几何精度这一类无文档的纯计算，而 `cad` 与 `stage-engine` 都依赖它。

管线的优先级不变，并且这条不变量本身要跟着搬：**键入的坐标不被任何吸附改写**。用户打了
`100,50` 却落在 `96,48`，看起来像浮点误差、实际是流程错误，是这类工具里最难排查的一类缺陷。

## D5 · 特征点捕捉是姐妹查询，不是扩展 `snapCandidates`

`snapCandidates` 返回 `StageGuide`——`{ axis: 'x' | 'y', value }`，是**一条参考线**，服务
Figma 式对齐（「与那个盒的左边对齐」）。CAD 捕捉要的是**一个二维点**（「正好落在那条线的
端点上」）。两者输入相同、输出形状不同、消费方式也不同，硬并成一个查询只会得到一个返回
联合类型的函数。

v1 的候选只有**端点与中点**，且只来自带 `Curve` 的 Entity。不出盒的角点/中心，理由是语义
撞车：盒角点正是既有 guide 吸附覆盖的「对齐」语义，两套同时生效会在同一次取点里给出两个
互相拉扯的答案，而用户看不出是哪一套在起作用。

优先级沿用 CAD 的既有次序（端点 > 中点），弧的圆心/象限点随步骤 3 一起加入。

## D6 · 取点插件排在 `pan` 之下

CAD 的既有优先级是「命令取点」最高。Stage 不能照抄：`pan`（按住空格 / 中键）是**临时覆盖**
而不是一个工具，命令进行中仍然要能平移画布去看远处那个端点——AutoCAD 同样如此。因此顺序是

```
text-edit-guard(1800) > pan(1700) > drafting-point(1650) > 其余不变
```

`text-edit-guard` 在绘图模式下不会触发（不进入文字编辑），排在上面只是保持表的单调性。

插件在**任何 hit kind 上都接管**：命令进行中点到一个已有 Entity，用户的意图是「在那里取一个
点」而不是「选中它」。这与设计模式恰好相反，是模式的意义所在。

## D7 · 命令行组件上移 `components`

它只消费 `ComposeCommandPrompt` 与一组文案，不认识文档、选择集或任何命令语义；现在有两个
第一方消费者。AGENTS.md 的上移门槛（「已经被至少两个第一方包复用」）正好满足，`components`
也已经依赖 `commands`（键位类型就是它的别名）。文案由调用方注入，不在包内硬编码。

## D8 · 框选与选择语义的取舍

**框选是白拿的**：`ComposeStageMarqueeMode` 已有 `directional`（左→右窗口、右→左交叉），
绘图模式把默认值切过去即可。

**点选累加不在本刀**。AutoCAD 的「点中即加入选择集、Shift 移出」只有配合 `MOVE`/`ERASE`
才有意义——本刀没有任何命令消费选择集，单独改掉点选语义只会让用户在绘图模式里发现「点两下
选中了两个东西，然后没有任何操作可做」。它与编辑命令是同一个用户故事的两半，一起做。
