# 设计：DXF 入页面

## 1. 只重写映射层

导入器本来就是三层纯函数：**分词**（组码/值成对）→ **记录**（按 `0` 分组，`pairs` 保留数组）
→ **映射**。前两层认识的是 DXF 的文件结构，与产出什么文档毫无关系，因此一个字符不改。

被重写的只有第三层。它今天产出 `CadLine` / `CadArc` / `CadText` / `CadInsert` 四种 Component，
之后产出 `Curve` / Text 物料 / 组件实例——而 `Curve` 的 `line | arc | polyline` 三元联合与
CAD 侧**一字不差**（同一条「整圆是扫掠 ±360 的弧、矩形是四顶点闭合多段线」的判断），所以
几何映射基本是改个 Component 名。

## 2. 产出「计划」而不是文档，Preset 由调用方注入

页面 Entity 需要 Preset 与 Renderer，而那些住在 `materials` / `component-registry`——一个
无 React 的格式包不该认识它们。`createStageDraftingCurveCommand` 已经解决过同一个问题：
**seed 注入**。本包因此只依赖 `core`。

产出是计划而不是直接写盘，因为一次导入要落**两类资源**：一份 `.page.json` 与若干
`.component.json`，而它们分别属于 Page Store 与 Component Store。纯函数产出计划、宿主负责
写入，测试就不需要假造两个 Store。

## 3. 块基点就是 `Transform.pivot`

DXF 的 INSERT 绕**块基点**旋转，而块基点不一定在块几何的包围盒里（接线端子的基点常在图形
外侧的接线点上）。

步骤 3 定 `pivot` 时留了两条正好对上的口子：它是**归一化盒坐标**，且**不钳制到 `[0,1]`**
——理由当时写的是「基点落在盒外表达绕外部支点摆动，是正当用法」。DXF 的块基点是这条口子的
第二个真实消费者。

于是换算只有一步：`pivot = (base − blockBounds.origin) / blockBounds.size`。实例位置则是
`insertPoint + (blockBounds.origin − base)`——把盒的左上角摆到该在的地方，转轴自然落回插入点。

**判据是一段不对称的图形加一个非 90 度的旋转**：基点写成盒中心（也就是缺席）时，对称图形
转出来的结果与正确实现逐像素相同，这个错误要等到有人导入一张真实图纸才暴露。

## 4. 图层被求值掉，不进文档

DXF 图层携带四样：名字、`visible`、`locked`、byLayer 颜色。前三样在页面世界各有**更细**的
对应物（每个 Entity 自己的 `Visibility` / `Lock` / 名字），颜色是**继承**，而页面世界没有
继承——因此导入时求值一次即可，这正是「导入能导的」。

**不退化成 Group。**Group 是空间容器：有盒、参与 Auto Layout、拖动它会搬走全部成员。图层
不是空间关系，是分类。把分类做成空间容器，用户拖一下就搬走半张图，而他并没有要求这件事。

**也不新造 Component。**沿用端口那条判断——「只有 id 与位置：面向用户的名称与方向眼下没有
任何消费者」。图层名眼下的消费者只有场景树里显示的那个名字，那正是 `entity.name` 的职责。
真要「按图层批量选中」时，那是命名选择集（已推迟立项），图层名会是它的第一个消费者。

## 5. 文字：盒 Hug，落点估算

DXF 的 TEXT 锚在**基线**上，页面 Text 锚在盒左上角，因此需要一个 ascent 比例做换算。导入器
无 DOM，量不到真实字体度量。

分两半处理，各自用它该用的东西：

- **盒用 Hug**，由 Yoga 在渲染时量真实文字——盒是会被看见的东西，不该是估算值。
- **落点用比例估算**（ascent 换算基线、advance 换算居中/右对齐的偏移）。它只是**导入那一刻
  的初值**，不是任何契约；用户拖一下就改掉了。

这与 CAD 侧「字体栈与比例是一对不变量」**不同**：那条的理由是命中框必须与字形对齐、两处
必须同时正确，而这里估算只影响初始位置。

## 6. 场景按内容紧包围盒开

DXF 的坐标动辄几千几十万，而场景是绝对坐标的**原点**。因此几何整体平移到包围盒左上角，
场景尺寸取包围盒（钳到最小 1）。

CAD 侧对应的做法是「打开时按内容取景」——那是会话状态，因为图纸无限。页面这边场景本身就有
尺寸，归一化之后既有的自动适配会把它取好景，不需要第二套机制。

**顺带避开一个 `-0`**：平移量是 `-bounds.x`，原点处正好产出 `-0`。它在 JSON 里写成 `0`，是
只在 `Object.is` 与断言里现形的幽灵差异，在取整处 `+ 0` 掉。

## 7. 非 1 缩放的 INSERT 只报告

实例尺寸的唯一事实来源是组件根（既有不变量），`Transform` 里也没有 scale——缩放在页面世界
**无处可放**。三个选择：静默按 1 导入、整份拒绝、按 1 导入并报告。前两个分别是这个功能已经
拒绝过的两种做法（「静默丢弃让用户认为工具不可靠」「一个 DIMENSION 不该毁掉 95% 可用的图」），
因此只剩第三个。

候选解法是「每个不同的缩放值生成一份独立组件」，它可表达且不需要新机制，但会让一个符号在
组件面板里变成三行。等真实图纸暴露需求再说。
