# 变更：接上页面库不等于让它抢走入口

## 原因

今天「宿主给了 `pages.library`」与「编辑器从页面库那一屏起手」是**同一件事**——
`useState(pages?.library !== undefined)` 就是全部的判据。于是想要页面库（以及它带来的全屏
演示、「就用这个」、最近打开）就必须接受它成为应用入口，反过来也一样。

这个绑定在示例应用上看得最清楚：页面库被压在 `?library` 后面，理由写在代码注释里——默认
开着会让**每一条**以「打开就在画布上」起手的端到端用例先经过一屏页面库。量过：280 次
`page.goto`，其中 268 次落在 `/` 或 `/?no-auto-fit` 上。也就是说，为了不动那 268 处，整块
页面库能力在默认形态下一次都不出现，包括它唯一的演示入口。

判据是**这两句话回答的是不同的问题**：「这个宿主有没有页面库」是能力，「打开编辑器先看到
什么」是形态。把形态从能力里拆出来，宿主才能说出「库可达，但我这一屏从画布起手」。

## 变更内容

- `ComposeEditorLibraryConfig` 增加可选 `openOnStart?: boolean`，**缺席即 `true`**：
  页面库一旦接上就是应用入口，这是它的产品定位，既有宿主一个字节不改、行为逐字不变。
  显式给 `false` 表示「库可达但不抢入口」——标志菜单、应用菜单里那条「返回页面库」与它的
  全屏演示照旧都在，只是编辑器从画布起手。
- **缺席即 `true` 而不是 `false`**：反过来会让每一个已经接上库的宿主在升级后静默地换掉入口，
  而那个变化在屏幕上看起来像「页面库没了」。可选字段的缺席值必须保住既有行为。
- 它 MUST NOT 变成第二份「当前在不在库里」的事实：`openOnStart` 只喂 `libraryOpen` 的**初值**，
  此后这份状态仍然只有一个持有者，回库与离开库仍走既有那两条路径。
- 示例应用因此默认接上页面库，`?library` 从「接不接上库」降级为「起手在不在库里」。

## 影响

- 受影响的规范：`library-browser`（宿主如何声明这一屏是不是入口）
- 受影响的代码：
  - `packages/editor/src/pages/page-workspace-types.ts`：`openOnStart`
  - `packages/editor/src/compose-editor/compose-editor.tsx`：`libraryOpen` 初值
  - `apps/example/src/StageDemo.tsx`：默认接上库，`?library` 改为控制起手位置
