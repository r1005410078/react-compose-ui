# 设计说明

## 为什么选择"删覆盖"而不是"级联勾选 Fill"

最初提出的方案是"父级设为拉伸时，自动把子节点的 Fill 复选框勾上"。这个方案能达到目的，但代价是把
一次父级属性修改变成一次隐式的多子节点文档写入，随之而来的问题都不好回答：

- 父级从拉伸改回其他对齐方式时，被级联勾选过的子节点要不要跟着改回 Hug？如果不改，用户会看到一堆
  "看起来是 Fill、其实是被动带上的"子节点，无法分辨这是有意选择还是级联结果。
- 如果用户级联后又手动把某个子节点关掉 Fill，下一次父级属性变化时这个意图要不要保留？这需要在文档里
  记一个"用户是否手动覆盖过"的标记，而现有的 `ComposeLayoutItem` 里没有这个概念。
- 嵌套容器要不要递归级联？多选或批量创建时呢？每多问一个场景就多一条需要专门设计的分支。

根因其实不需要这些：Hug 交叉轴在 Yoga 里本来就是真正的 `undefined`（auto），`applyAxis` 已经这么做
了。只要删掉那段无条件覆盖，`alignSelf: auto` 继承父级 `alignItems` 就是 Yoga 内置的标准行为，跟
浏览器 CSS Flexbox 完全一致——不需要新增字段，不需要级联写入。子节点想跳出父级拉伸时，用它自己的
`alignSelf` 显式设成 `flex-start` / `center` / `stretch` 等即可，Inspector 里已经有这个下拉框，这条
路径本来就存在，只是此前被无条件覆盖抢先短路了。

## 为什么"勾 Fill"的直觉是合理的

值得记录一下：这个项目的数据模型里，"Fill"在主轴和交叉轴其实已经是两种含义——`applyAxis` 里主轴
Fill 对应 `flexGrow`，交叉轴 Fill 对应 `alignSelf: stretch`。用户提出"勾上 Fill"的直觉正是从这个已有
的双重含义类推出来的，不是无中生有。

但这次要解决的问题发生在"没有手动碰过任何子节点属性"的默认路径上：删覆盖让默认路径本身就正确，
"级联勾选"要解决的问题也就不存在了。

## 为什么补一条显式需求

被删掉的这段覆盖逻辑没有任何 OpenSpec 需求或测试保护它——正因如此它才能长期存在而没人发现。修复时
顺手把正确语义写成显式需求（含"子级显式 alignSelf 优先"和"父级非拉伸时 Hug 保持内容尺寸"两个反向
约束），是为了让下一个改到这块的人有明确的契约可依，而不是再次凭直觉加一段特判。
