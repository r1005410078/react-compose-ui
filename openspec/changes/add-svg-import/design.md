# 设计：SVG 导入为可二次编辑的组件

## 判据

这个仓库反复用的那条判据在这里同样适用——**用户导进来之后想对它做什么**。答案是：改一个
部件的颜色、给一个部件打关键帧、把导线接到它的端子上。三件事都要求那个部件**是一个 Entity**，
因此「保留 SVG、只做具名子元素绑定」（WinCC Unified 的 `hmi:bind:fill`、DynSVG、Ignition
Perspective 按元素 id 匹配 tag 那一套工业界通行做法）不够：它做得到改色与动画，做不到拖顶点、
挂端口、在场景树里看见部件，而那正是「二次绘制」这个词的全部内容。它还会造出第二套改色入口，
与 Inspector 的 Appearance / Renderer props 打架。

## 决策 1：贝塞尔进协议，做成 `Curve` 的第四种 kind

`ComposeCurve` 今天只有 `line | arc | polyline`。设计稿型 SVG（Illustrator、Figma、Iconify）
几乎全是带 `C`/`Q` 的 `<path>`，而工程符号型 SVG（EPLAN、AutoCAD、Visio 导出）以直线、圆、
弧为主。两类都要导，因此贝塞尔必须在第一步就有，否则设计稿那一类进来大半不可编辑。

**它比看起来便宜。** `composeCurveSegments` 已经有「弧拍平成线段」的通道，贝塞尔按同一条通道
自适应细分即可，于是点选、框选、内部判定、特征点捕捉这些下游**一行不改**。渲染直接吐 `d`。
最舒服的一点是投影：`projectComposeCurveToBox` 对弧要按等比/非等比分流（非等比把弧拍扁成
多段线），而贝塞尔的控制点在仿射变换下**精确**，因此 `path` 根本没有这条分流。

### 段类型只有三次贝塞尔

直线段规范化成控制点落在段上的三次段，**不另立段类型**。这是「整圆是扫掠 ±360 的弧」与
「矩形是四顶点的闭合多段线」同一条判断的第三次应用：多一种段类型就是让归一化、平移、距离、
包围盒、渲染与校验六条路径各多一支。代价（直的那一段多存两个点）由下一条抵消掉。

### 导入器取**最窄**的 kind

只含 `M`/`L`/`H`/`V`/`Z` 的路径落成 `polyline`，单段圆弧落成 `arc`，`<circle>` 落成扫掠 360
的弧，`<rect>` 落成四顶点闭合多段线（`rx` 落成既有的 `cornerRadius`）。`path` 只在真的有
曲率、或有多条子路径时才出现。因此一份工程符号图导进来一个 `path` 都没有，全是能拖顶点的
既有 kind——而那正是这类图纸的用户接下来要做的事。

### 子路径与 `fillRule` 进协议，不落成多个 Entity

一个带洞的图形（字母 O、有孔的垫片）是**一条**路径的两条子路径加 `evenodd`。拆成两个 Entity
会把洞画成一块实心的覆盖物，而用户看见的是「导进来多了一块色块」。因此 `path` 携带子路径
数组；`fillRule` **缺席即 `nonzero`**，`nonzero` MUST NOT 写成显式值——缺席与显式是同一件事，
留两种表示会让「填充规则是什么」在两处读出不同答案，这与 `cornerRadius` 归零时删字段是同一条
判断，也让本字段不需要迁移。

### 紧包围盒要解贝塞尔的极值，不能用控制点凸包

控制点凸包是紧包围盒的**超集**，S 形段上肉眼可见地大一圈，盒会宣称对象并不占据的面积。极值
由一元二次求根得到（每轴至多两个 t）。这是「弧的紧包围盒必须把落在扫掠内的象限点算进去」
同一条规则的第三个实例，症状也一样：只在特定形状上出现，很容易被当成渲染问题。

### `path` 的夹点是顶点方块加控制手柄

贝塞尔的自由度是控制手柄，因此不给手柄等于导进来的曲线改不了形状——而「导完之后改形状」正是
做这次导入的理由。它复用既有的几何编辑会话（`StageEditablePath` 与 `path` 插件），不另起
一套。

**手柄是小圆加一根连到顶点的杆。** 圆角手柄已经是圆，但它是**孤立**的圆、只在矩形上出现；
控制手柄从来不孤立——那根杆本身就是它最强的辨识特征，也是唯一能表达「它属于哪个顶点」的画法。
这符合本画布「形状先分开、颜色再分开」的既有规矩。顶点仍是方块，与既有 `vertex` 角色一致。

**会话里顶点与手柄全画。** 这一条在实现中被推翻过一次：原本只画「正在被会话作用着的那个顶点」
的，理由是密度——一条导入来的路径有几十个顶点，手柄全画就是几十根杆糊在图形上。**那样行不通**：
点亮的语义是「下一次按下就是取点」，于是按向手柄的那一下会先被点亮的会话吃掉、提交成一次顶点
移动，手柄永远按不到。悬停显形有同一个毛病（指针从顶点移向手柄的路上就已经离开了顶点），两条
是同一个**可达性**问题的两种说法。密度是真的代价，但一个按不到的手柄等于没有这项能力。

它落在既有可编辑路径的切线通道上（顶点上的 `inTangent` / `outTangent`），因此覆盖层一行不改：
那条通道本来就画「一个小圆加一根连到顶点的杆」。

**默认拖动保持另一侧共线等长，`Alt` 断开对称。** 这是 Illustrator 与 Figma 的通行解法，
用户手上已经有这套肌肉记忆。

**平滑与尖角 MUST NOT 存成标志位**：两个手柄共不共线从控制点本身读得出来，存一位就是给同一
份事实造第二个来源，而它会在用户拖出共线之后立刻失真。这与「`closed` 是布尔而不是首尾顶点
重复」「`fillRule` 缺席即 `nonzero`」是同一条判断。

**加点与删点不在本变更内**：它对既有 `polyline` 同样不存在（本仓库今天没有任何入口），是一条
独立能力，单开 `add-vertex-insert-delete`。`path` 因此与 `polyline` 站在同一条起跑线上，
MUST NOT 只给 `path` 开这个口子——那会让同一个动作在两种 kind 上一个有一个没有，而用户看不出
为什么。

## 决策 2：transform 在导入期烘进几何

`Transform` 只有 `rotation` 与 `pivot`，没有 scale、skew 或 matrix，SVG 的 `transform` 因此
无处可放，只能在导入期烘进几何点。对直线、折线与贝塞尔这是**精确**的（仿射不变）；对弧
在非等比缩放下要拍扁成多段线——**这条规则仓库里已经有了**（`projectComposeCurveToBox` 的等比
判定），照抄它而不是新写一条。

`stroke-width` 不参与仿射：非等比缩放下它没有单一正确答案，取两轴比例的几何平均并诊断。

**旋转是唯一的例外**：纯旋转矩阵 MAY 分解进 `Transform.rotation`。刀闸的刀之所以能摆动，
靠的正是 `rotation` 轨道加一个落在铰点上的 `pivot`，如果导入期把旋转烘死进几何，用户拿到的
就是一条方向对但转不起来的线。判据是**这个部件接下来要不要转**，而导入器不知道——因此保留
旋转、不保留缩放，让能转的那一半保持可转。

## 决策 3：样式在导入期求值掉

样式有四处来源：`<style>` 里的 class、内联 `style=`、呈现属性、`<g>` 继承。它们 MUST 在导入期
求值成每个 Entity 自己的 props，与 DXF「byLayer 颜色在导入期求值进描边」是同一条判断——
文档里留下的必须是这个 Entity 自己的颜色，否则改一个部件的色要先问它继承自谁。

`<style>` 只支持 `tag`、`.class`、`#id` 与它们的逗号组：Illustrator 与 Figma 导出的就是
`.st0{fill:#231815}` 这一档。其余选择器跳过并诊断，MUST NOT 猜。

**渐变降级成纯色并诊断**：曲线的填充复用 `Appearance.backgroundPaint`，而读取入口
`getComposeCurveFill` v1 只画 `solid`。降级取中位色标，因为它比首尾任一个都更接近整体观感。

## 决策 4：不可表达的**属性**降级，元素**永不丢弃**

`filter`、`mask`、`clip-path`、`pattern` 忽略但**保留几何**：它们是外观修饰，忽略之后用户看到
的是一个少了阴影的正确图形——**可见的降级**；而丢掉整个元素是不可见的，用户拿结果和原图一对
只会认为工具不可靠。只有 `<script>`、`<foreignObject>`、`<animate>` 这类**不是几何**的东西
整个丢弃。可执行内容 MUST 丢弃，与既有 SVG 净化是同一条判断。

诊断机制照抄 DXF：同类聚合成 `{ subject, count }`，宿主压成一行提示。

## 决策 5：落成 Component Asset v2

与 DXF 的块一致：一份 SVG → 一份组件资产（根是 Frame，尺寸取 `viewBox`），场景里落一个引用
它的实例。刀闸这类符号要在一张图上摆很多份，只有这条路成立；合闸/分闸两个状态是 Variant，
组件的动画**内嵌在资产里**（组件资产不落 `.animation.json`），每个实例的播放头是
`animation` / `animationTime` 两条 Renderer prop 绑页面脚本导出，于是八个刀闸有八个独立状态。

写入次序与不回滚的理由照抄 `importDxfAsPage`：组件文件先写，因为实例需要它的引用与 revision，
那正是纯函数计划里**不含实例 Entity** 的理由。

## 决策 6：`<image>` 的资源由计划带出、宿主写盘

内嵌 data URI 的 `<image>` MUST 由导入计划带出成一份「待写资源」，由宿主写成资源文件之后
回填引用——纯函数包不写盘，这与「计划里不含组件实例 Entity，因为它需要写完文件才存在的引用与
revision」是同一条次序。外链 `href` 已经被安全规则丢弃，因此 data URI 是唯一进得来的形式。

## 决策 7：解析层引第三方库

- `fast-xml-parser`：XML 分词。零运行时依赖、MIT，处理实体转义与命名空间——自己写这一层
  是在重新发明一个已经被大量输入验证过的东西，而 SVG 的输入完全不受我们控制。
- `svgpath`（fontello，MIT、零依赖）：`abs()` / `unshort()` / `unarc()` / `transform()` 一步
  把路径数据规范成绝对的 `M`/`L`/`C`/`Z` 并把矩阵烘进去。路径数学（尤其是弧到贝塞尔的转换）
  是最容易写错、且错了只在特定角度组合下现形的一段。

两个库都只在 `@compose-ui/svg-import` 内部使用，MUST NOT 出现在公共 API 的类型里——与
`layout-engine` 不让 Yoga 类型进公共 API 是同一条边界。拍平、极值与内部判定住在 `core`
（命中路径要读），MUST NOT 依赖这两个库。

CSS 命名色表是**数据不是逻辑**，包内自带一份。文字度量的两个估算比例与 DXF 各存一份：那两个
包互不依赖，这处重复是包边界造成的，与 `property-panel` 自带一份数值格式化同理。

## 未做与理由

- **顶点加删**：见决策 1 末段，单开 `add-vertex-insert-delete`。
- **容器缩放时子树跟随**：单开 `add-subtree-scaling`。导入产物全是绝对定位的子级，父级拉大
  时它们原地不动，于是符号整体改不了大小——而今天的 `svg` 物料靠 `fit` 做得到这件事。这条
  必须补，但它对手工画的图形同样成立，不是导入的附属物。
- **镜像与对齐分布**：单开 `add-mirror-and-align`。
- **布尔运算 / 复合路径合并**：SVG 的 `mask` 与重叠子路径在设计工具里对应布尔运算，本仓库
  没有这个概念，补它是另一件事。
- **`<text>` 的 `tspan` 定位与多行**：只取纯文本内容并诊断。文字的盒走 Hug，由布局求解量真实
  字体，导入期的落点估算只是初值——与 DXF 的 TEXT 是同一条判断。
- **动画元素（`<animate>` / SMIL）转成关键帧**：源文件里的动画与本产品的动画清单是两套时间
  模型，猜一次映射比不映射更糟。
