# 点亮之后要有目标位置预览

## Why

实测（探针跑完即删）。点亮 `end` 夹点，再把光标挪到别处：

```
刚进入        轮廓 242.96,373.20 360.63,432.03   end 夹点 x=356.63   橡皮筋 0
点亮之后      轮廓 242.96,373.20 360.63,432.03   end 夹点 x=356.63   橡皮筋 1
光标挪走之后  轮廓 242.96,373.20 360.63,432.03   end 夹点 x=356.63   橡皮筋 1   ← 一动不动
拖动中        轮廓 428.88,352.02 360.63,432.03   end 夹点 x=356.63   橡皮筋 1   ← 跟手
```

**点亮之后画面上只有一条橡皮筋，几何本身不动。**用户看不到「点下去会变成什么样」，只能看到
一条从旧位置指向光标的直线——那条线在直线端点上勉强像结果，在弧的半径夹点、多段线顶点或
直线的中点（平移）夹点上说的完全是另一回事。

AutoCAD 的说法是明确的：选中一个端点夹点、**移动光标时线段就跟着拉伸**，这个拉伸是临时的，
直到取到一个点为止（[Just Grip It!](https://help.autodesk.com/view/ACD/2025/ENU/?guid=GUID-BBEA1F71-EB16-4D49-80D9-970A6909F508)、
[To Edit Objects Using Grips](https://help.autodesk.com/view/ACD/2024/ENU/?guid=GUID-484774B4-8F67-4E19-8647-83A7D314782B)）。
拖动那一半我们已经这样了，点亮这一半没跟上——同一个会话的两条路径给出了不同的呈现。

根因是上一刀的一处遗留：原地松手时 `setPreview(null)`，此后没有任何东西再按光标重算预览。

## What Changes

- **点亮期按光标实时重算几何预览**，与拖动期共用同一条求解。读的是**解算后**的落点，与十字
  光标、橡皮筋终点和捕捉标记同一个值——各读各的会让预览停在用户不会落笔的地方。
- **`dragging` 不再由「有没有预览」派生**，改成它自己的事实：一次指针手势在不在进行中。
  不改的话点亮会被当成拖动，热夹点与拾取框跟着一起错。
- **橡皮筋补一条规范。**它是上一刀的副产品（会话把 `reference` 设成夹点原位置），今天已经在
  画，却没有任何一条规范说它该在——先把既有行为钉住，再谈改不改。

## Impact

- 规范：`stage` 的「顶点取点是一条命令会话」一条 MODIFIED。
- 代码：`packages/stage`（`use-stage-drafting` 交出解算后的落点、`use-stage-geometry-editing`
  在点亮期重算预览并自持 `dragging`）。
- 破坏性：无。

## Non-Goals

- **不做动态输入的尺寸标注**（AutoCAD 的 `DYNMODE`：光标旁的长度/角度输入框）。提示与坐标
  键入由常驻命令行承担，那是两套并行的输入界面，不是这一刀的事。
- **不做夹点模式轮换**（空格在 `STRETCH` / `MOVE` / `ROTATE` / `SCALE` / `MIRROR` 之间切）
  与 `Base point` / `Copy` 关键字。上一刀已声明为非目标，这一刀不动它。
- **不改橡皮筋的画法。**本刀只把既有行为写进规范。它在直线端点上与预览重叠成一个三角形，
  是否该在点亮期改画法（例如只在平移类夹点上画）需要先有使用反馈，现在改是凭空猜。

## 一处要更正的记载

上一刀给热夹点（`GRIPHOT`）写的理由是「点亮后夹点停在原位而光标在别处找目标点」。
**加上实时预览之后这句话不再成立**——夹点跟着预览走到光标底下，与拖动期一样。

理由要重述而不是撤销：红色说的是**「有一次编辑正在进行」**，而不是「是哪一个」。后者由预览
本身表达了；前者在光标还没动的那一刻、以及用户视线离开又回来时，仍然只有它和命令行提示在说。
