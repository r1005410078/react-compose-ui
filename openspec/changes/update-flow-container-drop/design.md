## 上下文

画布拖拽的落点由 `resolveStageDropTarget` 解算，产出 `StageDropTarget` 的三种 kind。网格容器
已经有完整的一支：算出格坐标、发布落点、画出松手之后那张卡的位置。Flex 容器只有**同容器内**
重排走完整解算（`resolveSameContainerReorder`），跨容器落进来时直接退成 `reparent`。

排队插入所需的几何算法**已经写好且与容器身份无关**：`resolveInsertIndex` 接受
`childIds` 与 `draggedIds`，跨容器时 `draggedIds` 不在 `childIds` 里，函数照样给出一个合法
插入位。提交侧同样已经就位：`createReparentCommand` 的第五个参数就是插入下标，今天恒传
`childIds.length`。

## 目标/非目标

- 目标：往 Flex 容器里拖东西能落成**同级子项**，并在画布上看见落在哪两个之间。
- 目标：跨容器与同容器走同一条解算，不产生第二套插入位规则。
- 非目标：不做 Figma 那种悬停高亮下钻树，不引入新的 chrome，不改 `LayoutItem.positioning`
  的既有规则（拖拽 MUST NOT 隐式脱流）。
- 非目标：不碰网格那一支。

## 决策

**决策一：`reorder` 的语义放宽成「落进 `containerId` 的第 `index` 位」，不新增 kind。**
这句话与 `grid-cell` 已经写下的那句逐字相同——「它同时表达重排与 reparent，父级变没变由提交方
比较 `containerId` 与当前父级得出，不需要第二个 kind」。新增一个 `flow-insert` kind 会让
覆盖层、提交侧与预览文档三处各多一支，而它们对「落进谁的第几位」的处理完全相同。

替代方案：新增 `flow-insert`。否掉的理由是上一段——三处各多一支逐字相同的代码，且
`grid-cell` 已经给出了先例。

**决策二：Flex 容器的 Flow 子级不接管落点，`Alt` 下钻。**
判据是**这个盒是谁写下的**：Flow 子级的盒是父级排出来的，不是作者写的；在排队容器里，把
东西放到某个子项「里面」与放到它「旁边」在屏幕上是同一块面积，而用户在排队容器里做的绝大
多数是排队。代价不对称——今天「拖第二个同级子项」根本做不到且屏幕上没有解释，而下钻还有
`Alt` 与场景树两条路。

`alt` 不需要新语义：它已经写着「强制以指针命中的最内层合法容器为 reparent 落点」。

替代方案：按悬停时长或悬停高亮下钻（Figma）。否掉的理由是它要一整套新 chrome 与一份计时器
状态，而这条规则一句话说得清。

**决策三：最内层不满足深入判定时上浮到最近的成立祖先。**
今天 `isDeepInside` 失败即返回 `null`——指针贴着子项边缘时**一个落点都没有**，而用户看到的是
「拖过去松手，什么都没发生」。上浮之后贴边那一档落在父级上，正是边缘留白想表达的意思：
「你不是要放进这个，是要放进它外面那个」。

## 风险/权衡

- 风险：往一个 Flow 子容器里拖东西从「直接可以」变成「要按 Alt」→ 缓解：场景树的新增节点与
  拖放照旧可用；而这一档此前把「拖同级」整个吃掉了，两害相权。
- 风险：`reorder` 语义放宽后，既有读取方若假设「同容器」会出错 → 缓解：读取方只有覆盖层
  （只用 `containerId` + `index` 画线）与提交侧（本变更一并改），用例逐个钉住。

## 迁移计划

无文档迁移：`StageDropTarget` 是运行期会话类型，不进文档。类型形状不变，只有语义放宽，
因此宿主编译不受影响。

## 待解决问题

- 多选跨容器插入沿用「按文档顺序提交」的既有规则，与网格那一支的 v1 限制（只写第一个）
  不同；本变更不统一它们。
