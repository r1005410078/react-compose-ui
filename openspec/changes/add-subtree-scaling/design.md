# 设计：组件实例的内容缩放

## 为什么是 Renderer prop 而不是新的 Component

「内容怎么填满这个盒」只有渲染与 Inspector 读它，不参与命中判定、不参与布局求解、不被
`stage-engine` 或 `core` 读取。按本仓库既有的那条边界——**命中与捕捉路径读的字段才必须是文档级
契约**——它属于 Renderer props。落在那里还白拿三样：Inspector、数据绑定与外观关键帧轨道。

## 为什么不是替换既有行为

`'layout'` 与 `'scale'` 都有真实用途，而且**互斥**：一张卡片组件拉宽时要的是内部重排（按钮
留在右边、文字换行），一个电气符号拉大时要的是整体放大（线宽、间距、字号一起变）。默认取
`'layout'` 是因为它是今天的行为，既有文档因此逐像素不变；导入器产出的实例显式取 `'scale'`，
因为符号属于后一类。

**两支 MUST NOT 同时改一份数据**：`'layout'` 把盒尺寸写进嵌套根 Frame（既有机制），`'scale'`
保持嵌套文档尺寸不变、只在外层加一个比值。同时做会让「这个实例多大」在两处读出不同答案，
而症状是拖一次角手柄图形跳两次。

## 非等比拖动按两轴各自的比值

不强行等比后留白。判据是仓库里已经有的那条——曲线按 `viewBox` 与盒的比例跟随，两轴各算各的；
符号被拉扁时它的每一条线也该跟着扁。想要等比的用户按住 `Shift`，那是既有的 resize 约束，
不需要在这里再造一个。

## 下钻选中为什么是透明的

实例内部的选中框由 DOM 测量得到（`getBoundingClientRect`），而 CSS transform 的缩放会被
它如实反映。因此内容缩放对下钻选中、命中与实例内部编辑**一行不改**——这一条是选 CSS transform
而不是「把比值乘进每个子级的几何」的主要理由，后者还会污染组件文档本身。
