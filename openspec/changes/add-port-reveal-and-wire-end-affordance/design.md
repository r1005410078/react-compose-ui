# 设计：端口显现与导线端点的接线状态

## 为什么「端口不画标记」那句话要改，而它当初又是对的

原话：**端口不画标记，靠捕捉标记在光标靠近时显出来**；理由是「常驻标记会让一张接线图上多出
几十个与几何无关的点」。

那个理由**只否定了常驻**。「取点时按符号整组显现」不落在它的射程里：没有命令在取点时依然一个
都不画，图还是干净的；而用户按下 `W` 的那一刻，他要找的正是接线点——此时把它们画出来不是噪音，
是他刚刚提的问题的答案。

至于「靠捕捉标记显出来」这后半句，它是**不够**而不是错：捕捉标记按定义只标一个点，回答的是
「吸上了没有」。接线图上端子密集（继电器的端子只隔几个像素），只亮一个的话用户看不出旁边还有
两个，会以为自己够到的就是唯一的那个。两者因此不是同一件事，也不该合并：

| | 回答的问题 | 数量 |
| --- | --- | --- |
| 捕捉标记 | 落点吸上了什么 | 恰好一个 |
| 端口显现 | 这个符号上有哪些接线点 | 一个符号的全部 |

**整组而不是最近的一个**，判据就是上一段：只亮一个时用户读到的是「这里只有一个端子」，而那是
错的。

## 为什么两种记号必须长得不一样

端口记号与端点状态记号会同时出现在屏幕上（画第二条线时，第一条的端点就在旁边），而它们说的是
两件事：一个是「这里可以接」，另一个是「这里接上了/没接上」。形状必须分开，MUST NOT 只靠颜色
——本产品的画布上颜色已经被捕捉、选中、框选与运行状态占了好几层。

## 为什么失效常驻而已绑定/自由不常驻

这不是不一致，是**同一条判据的两个答案**：

- 「这一端接到哪儿」是用户**问的时候**才想知道的信息 → 选中时画。常驻的话，一张有两百条线的
  图上就多出四百个记号，而其中三百九十九个此刻没人在看。
- 「这个绑定坏了」是**用户没问也必须知道**的信息 → 常驻。它是一个缺陷，等用户主动选中那条线
  才显形等于把发现缺陷的责任推给用户，而他恰恰不知道该去选哪一条。

这与实例动画把失效的清单引用标出来是同一条判断，也与「还没配 / 配错了 / 配的东西没了 三者必须
可区分」同源。

## 为什么不改协议

`Ports` 与 `Wire` 一个字段都不加。三样东西全部可以从既有文档算出来：端口位置是
`getComposeEntityPorts` 的返回值，绑定状态是「引用解析得开吗」，而那个解析
（`resolveComposeWireEnd` 那条路）已经在 Inspector 里跑着。呈现层新增字段是这一类需求里最常见
的错误答案——它会让同一份事实有两处来源，而漏更新的那处的症状是「屏幕上说接着，实际没接」。

## 不做什么

- **不做端口的悬停高亮与点选**。端口不是 Entity，给它做选中态要一整套命中与选择语义，而它此刻
  唯一的消费者是取点。
- **不给端口画名称**。`Ports` 眼下只有 id 与位置，没有面向用户的名称字段——补那个字段要先有
  消费者，而这条判断（没有消费者的字段不进协议）正是端口协议当初定成这样的原因。
- **不在预览里提前显示「会绑到哪个端口」**。落点解算已经把端口捕捉排在端点之前，捕捉标记停在
  哪儿就是会绑到哪儿；再加一层说明是同一句话说两遍。
