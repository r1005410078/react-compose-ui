# 设计：带拐点的导线

## 横平竖直是约束，不是辅助

初稿写的是「横平竖直由既有的角度约束给（极轴默认开、增量角 45°），用户点到哪儿就是哪儿」。
**那句话有个洞**：极轴的增量角是 45°，而 45° 本身就是斜的；而且极轴只在容差内投影，够不着就
放行。于是「能画出直角」并不等于「画不出斜线」——给出的是辅助，而导线要的是规范。

**约束与辅助是两回事。** 会话级的角度约束是用户的**偏好**（关 / 正交 / 极轴）；而导线在一次
接线图与 PCB 上一律横平竖直，斜着走的导线不是「用户的选择」，是一张画错的图。因此从第二个点
起把角度约束**钉死成正交**，会话级设置管不到这一步。

它由**提示**声明（`ComposeCommandPrompt.constrain`）而不由宿主按命令 id 判断：哪一步该被钉死
只有命令知道——第一个点没有上一点、量不出方向，因此不钉。

**钉死的只是角度约束那一档**，管线次序原样成立（`键入 > 捕捉 > 网格 > 角度约束`）。两条推论
都是想要的：

- **捕捉命中即短路**，最后一段够得着端口，不会被正交挡在门外——这正是「连不上端子」这类
  显而易见的死路本来会出现的地方。
- **键入的坐标不被改写**，用户打出来的精确值仍然是精确值。

## 为什么不做自动路由

PCB 工具画线时还会**替用户补拐角**：鼠标一动，它按当前走线模式自动在中间插一到两个拐点。这件
事要回答一个我们此刻答不了的问题——**拐点该拐在哪儿**。真正的答案要考虑障碍物（别的符号、别的
导线），而那就是自动路由，是一整个子系统。

正交只把落点拽回轴向，**不替用户决定拐几次**。这是本变更能这么小的全部原因。

## 只有首尾绑定

中间的拐点是纯几何，不参与 `Wire`。理由是 `Wire` 回答的问题就是「这一端接到了哪个端口」，而
拐点不接任何东西——它是走线的形状，不是连接关系。

推论：求解时**只有首顶点与末顶点会被写**，其余顶点一个字不动。

## 符号挪走之后拐点会变丑，这是明写的代价

绑定端跟着端口走，而相邻那个拐点不动，因此原本水平的第一段会变成斜的。

**不做「保持正交」的补偿**，尽管它看起来只是把相邻顶点也挪一下。两个理由：

1. 一条导线**两端都可能绑定**，两端各自要求「保持我这一段正交」时，中间那些顶点该听谁的没有
   答案；而两端同时被拖动（拖框选中一片符号一起挪）恰恰是最常见的操作。
2. 任何「保持正交」的规则都是**路由的一半**。半条规则会产出用户预测不了的形状，而那比一条明显
   变斜的线更难修——他至少看得出斜线错在哪儿。

因此 v1 的规则是一句话：**绑定端落到端口上，其余顶点原样保留**。要更聪明的行为，那是自动路由
那一刀的事。

## 为什么与 `PLINE` 同一条路径而不是像 `LINE` 那样逐段落地

一条导线是**一个**连接，它必须是一个 Entity——逐段落地会得到 N 个 Entity，中间的接头又变回今天
那种「两个自由端刚好重合」的假接头，而这正是本变更要消灭的东西。

推论（既有那条判断的第二次应用）：攒到结束才提交的命令**需要「放弃上一点」关键字**，因为此刻
文档上什么都还没有，撤销够不着它。因此 `WIRE` 获得 `U`，与 `PLINE` 一致。

## `ARROW` 就此与 `WIRE` 分家

两者原本共用两点会话工厂，理由是「取点逻辑逐字相同」。现在不同了：`ARROW` 仍是两点（**一支
箭头只有一个头**，连着画会得到一串各自带头的箭头），`WIRE` 是连续取点。共用的前提消失，工厂
拆开。

## 收尾的两处小事

- **`Enter` 在取够两个点之前 MUST 拒绝而不是提交**：一个点的导线画不出来，也没有第二端可言。
- **`collectStageWireEnds` 要认 `polyline`**：端点记号画在首尾两个顶点上。它今天写死了
  `kind !== 'line'` 就返回空，症状会是「折线导线选中之后两端什么都不显示」。

## 不做什么

- **不做自动路由**（见上）。
- **不做「拐点圆角」**。它是纯呈现，且 `Curve` 的多段线没有 bulge 字段——那条协议缺口在弧段那里
  已经记过一次。
- **不给拐点做端口捕捉之外的特殊语义**（比如 T 接、节点）。多条导线接到同一个点在文档上仍然是
  各自绑到同一个端口，节点是符号的事，不是导线的事。
