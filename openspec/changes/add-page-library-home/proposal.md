# 变更：页面库成为应用入口

配套设计稿（自包含 HTML，浏览器直接打开）：
[产品形态](../../../docs/mockups/product-home.html) —— 首页那一屏长什么样、每条判断的理由。
后端那一半在 [`add-service-ports`](../add-service-ports/proposal.md)，本变更**依赖**它的
`ComposeLibraryPort`。

## 原因

**编辑器不再是应用的入口，页面库才是。**今天打开产品看到的是一块空画布；而实施工程师打开它
时手里的问题不是「我要画点什么」，是**「这东西该怎么画」**——而答案是公司里已经画过的那几十张。

这面墙真正的用法是**当着客户翻**：「PCS 我们有这几种画法，您看哪个顺眼」。客户指中哪一张，
就以那一张为底开始改。这一句话推出本变更的全部内容。

`add-service-ports` 定了数据从哪儿来，但它把**首页宿主本身**明确列进了不做。这一份补上那一半。

## 变更内容

### 一、新增 `@compose-ui/library-browser`

受控 React Widget，消费 `ComposeLibraryPort`，与 `@compose-ui/asset-browser` 之于 `assets`
同构。三块内容：

- **左栏两段，不是一棵树**。上段回答「在哪儿找」（最近打开 / 项目 / 模板 / 回收站，互斥），
  下段回答「找哪一类」（场景类型，跟着上段走）。做成树要把八个场景类型在项目与模板底下**各抄
  一遍**，还要为一层半的结构付整套树的代价——三角列、缩进列、每行一个不表达任何东西的色块，
  以及「项目 418」与子项「全部 418」**把同一个数写两遍**。两段的选中因此**画法不同**：位置是
  实底、筛选是左边一条竖条——同一种画法会让它们读成并列的两个选项，而它们回答的是两个问题。
- **主区是图墙，不是卡片**。卡片是一个容器，而这一屏里唯一有决定性的东西是**图**；再给它套一个
  盒、在盒下留一块文字区，等于用两层 chrome 去托一张图。名称与「用过多少次」压在图的底边上。
  卡上**只放有区分度的东西**：同一类里尺寸几乎总是一样，四行 `1920 × 1080` 一字不差等于没写；
  换成**用过多少次**——它正好回答用户此刻的问题，没被用过的就不写，那一行的空缺本身也是信息。
- **全屏演示屏**：没有任何编辑器 chrome，左右翻页，当场「就用这个」。

### 二、顶栏承载文档标签，标志是回页面库的门

这一条**推翻两条既有需求**（「应用顶栏」与「文档标签条」），理由写在下面的「影响」里。
画布列头**不取消**：标签搬走之后它留下来回答「正在编哪一份、哪一层」——一条文档面包屑。

那条需求原文写的是「面包屑加『设计 / 动画』切换器」，而**那半句已经过期**：那颗切换器随
「动画编辑开关」一并删除（布局那一半归工作区、语义那一半归时间线 chrome 上的开关），原文只是
没跟着改。照抄它等于把那次拆分原样撤销，因此这一份只留面包屑。

### 三、页面库是编辑器壳子的一种 body 状态

顶栏不变、body 换成页面库。做成两个应用会让「回库」与「切到另一份图」这两个同类动作
住在两个地方，而它们在屏幕上紧挨着。

### 四、全屏演示复用 `ComposePreview`，不新写渲染器

演示的是**真实渲染而不是缩略图**——客户要凑近看数值与线宽。另写一份的话，
「演示时好好的、上了大屏不一样」这类问题永远查不清是谁的。

### 五、「就用这个」只问一个问题

它做的是**复制一份**：客户指中的这张成为你自己那一份的底，此后两边再无关系。
客户就在旁边等着，所以这一步只问**必须问的那一个**——它叫什么。落地即打开。

### 六、缩略图由编辑器产出

保存成功**之后异步**渲染激活场景并上传，失败只出诊断、不阻断保存
（判据见 `add-service-ports` 的 D11）。

## 影响

- 受影响的规范：
  - 新增 `library-browser`
  - `editor-workspace-layout`：**MODIFIED**「应用顶栏」与「文档标签条」
- 受影响的代码：新增 `packages/library-browser/`；`packages/editor/` 的顶栏与画布列头；
  `AGENTS.md` 补新包边界
- **依赖** `add-service-ports`：没有 `ComposeLibraryPort` 时本变更无处取数

### 为什么推翻「文档标签住画布列头」

那两条的理由是**编辑器就是应用**——顶栏承载应用与视图作用域，文档属于画布那一列。
页面库成为入口之后，两条前提都不成立了：

1. **页面库那一屏没有画布列。**标签住画布列头意味着**一进页面库标签就消失**——而标签正是
   「我手上开着哪几张图」，去库里找下一张时最需要它。这不是审美问题，是那条需求在新入口下
   产出一个用户看得见的缺陷。
2. **标志与已开的文件是同一排去处。**回页面库与切到另一份图是同类动作（去哪儿），
   分两行会让它们住在两个地方，而浏览器早就把这件事的答案写在每个人的肌肉记忆里。
3. 原来那句「顶栏只承载应用与视图作用域」**没有错，是它的取值变了**：页面库成为入口之后，
   **「我开着哪几份」本身就是应用作用域**，不再是某一列的视图状态。

保留的那一半：顶栏 MUST NOT 承载保存按钮与模式切换器（它们仍是文档作用域），
顶栏上的任何操作 MUST NOT 产生事务。「恰好三段」放宽成四段。
