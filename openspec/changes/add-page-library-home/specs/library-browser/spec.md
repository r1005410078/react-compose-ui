## ADDED Requirements

### Requirement: 独立页面库浏览包边界

系统 MUST 提供 `@compose-ui/library-browser`：受控 React Widget，消费 `ComposeLibraryPort`，
可依赖 `library`、`components`、`preview` 与 `ui-context`，MUST NOT 依赖 `editor`、`stage` 或
`asset-browser`。

它 MUST 可独立嵌入——页面库是一个可以不加载编辑器的宿主；编辑器只是把它当作一个领域组件挂上。

#### Scenario: 不依赖编辑器

- **WHEN** 检查 `@compose-ui/library-browser` 的依赖
- **THEN** 其中没有 `@compose-ui/editor` 与 `@compose-ui/stage`

### Requirement: 左栏是两段，不是一棵树

左栏 MUST 分两段：上段是互斥的**去处**（最近打开 / 项目 / 模板 / 回收站），下段是**场景类型
筛选**，跟着上段选中的那一个求值。

它 MUST NOT 做成一棵「大分类 + 场景类型子级」的树：场景类型在项目与模板里都成立，树要把同样的
八项在两棵子树下各渲染一遍，而父行的总数与子项「全部」的总数是**同一个数写两遍**。

两段的选中 MUST 用**不同的画法**（位置一块实底、筛选一条竖条）：同一种画法会让两段读成并列的
两个选项，而它们回答的是两个不同的问题。

筛选行 MUST NOT 各带一个图标或色块——八个同性质的值不需要八个要学的记号，名字与计数已经够了。

切换去处时，下段的计数 MUST 跟着换成新去处的。

#### Scenario: 切到模板

- **WHEN** 用户从「项目」切到「模板」
- **THEN** 下段仍是同一组场景类型，计数换成模板里的数目
- **AND** 场景类型不因为切换去处而被清空

#### Scenario: 两种选中可分

- **WHEN** 同时选中「项目」与「PCS」
- **THEN** 两者的选中呈现不同，用户读得出哪个是去处、哪个是筛选

### Requirement: 主区是图墙，卡上只放有区分度的东西

主区 MUST 以图本身为对象，MUST NOT 为每张图再套一个带独立文字区的卡片容器——这一屏里唯一有
决定性的是图，套盒等于用两层 chrome 去托一张图。名称与使用次数 MUST 压在图自己的底边上。

常驻信息 MUST 只有名称与**使用次数**。尺寸与修改时间 MUST NOT 常驻：同一类里尺寸几乎总是相同，
逐行一字不差等于没写；它们 MUST 退到 hover。使用次数为零时 MUST 不写，那一行的空缺本身是信息。

主区 MUST 支持按类型分段、排序、按标题检索与滚动加载，并 MUST 与左栏读**同一次查询**的结果
——分两次取会让计数与图在用户改筛选时短暂不一致。

#### Scenario: 没被用过的不写次数

- **WHEN** 一张图的使用次数为 0
- **THEN** 它的标题旁不出现任何次数文字

#### Scenario: 尺寸只在 hover 出现

- **WHEN** 指针移到一张图上
- **THEN** 出现尺寸与修改时间，以及「就用这个」与「打开」

### Requirement: 全屏演示屏

系统 MUST 提供一屏**没有任何编辑器 chrome** 的全屏演示：整屏只有图与一条控制条，左右翻页，
可当场「就用这个」。

这一屏 MUST NOT 出现分类、文件名与修改时间——它们是我们自己的记账，而屏幕此刻正对着客户；
翻页位置 MUST 只写序号与总数。

演示 MUST 用**真实渲染**（复用既有的只读 Preview）而不是缩略图：客户要凑近看数值与线宽。
MUST NOT 为它另写一份渲染器——另写一份会让「演示时好好的、上了大屏不一样」这类问题永远查不清
是谁的。

#### Scenario: 演示屏上没有内部信息

- **WHEN** 进入全屏演示
- **THEN** 屏幕上没有分类、文件名与修改时间
- **AND** 只有图、序号与一条控制条

#### Scenario: 演示走真实渲染

- **WHEN** 演示屏呈现一张图
- **THEN** 它由既有的只读 Preview 渲染，而不是那张缩略图

### Requirement: 「就用这个」只问一个必须问的问题

以一条记录为底新建 MUST 只要求用户回答**名称**一项，MUST NOT 在这一步要求分类、落点或其它
可以之后再改的东西——客户就在旁边等着。

它 MUST 是**复制一份**：新页面与来源此后再无关系，改新的不影响来源。

落地成功后 MUST 直接打开新页面。

图墙上的按钮与演示屏上的按钮 MUST 落到同一条路径。

**「新建页面」MUST 是同一个框**（没有底、只问名称），并 MUST 走端口自己的 `create`：两条路各自
要回答的都只有这一个问题，分两个框写必然在焦点、回车与错误呈现上漂移。新页面落进哪个文件夹是
端口知道的事，而这一屏（应用入口）此刻还没有任何工作区上下文可谈，因此宿主 MUST NOT 需要为它
另接一个新建回调。端口没有 `create` 时 MUST 不画那颗按钮——一个按下去什么都不发生的按钮比
没有更差。

#### Scenario: 从演示屏直接开始改

- **WHEN** 用户在演示屏按下「就用这个」并填了名称
- **THEN** 新页面建好并被打开，可以立即编辑
- **AND** 来源记录的内容一个字节都没变

#### Scenario: 新建一张空白的

- **WHEN** 用户按下「新建页面」并填了名称
- **THEN** 打开的是同一个只问名称的框，落地走端口的 `create`
- **AND** 新页面建好之后被直接打开

### Requirement: 缩略图由编辑器在保存之后产出

编辑器 MUST 在页面保存成功**之后**异步渲染激活场景并上传缩略图。

上传失败 MUST NOT 使保存失败，MUST 只产生诊断。记录没有缩略图时图墙 MUST 画占位而不是留空或
报错。

#### Scenario: 上传失败不影响保存

- **WHEN** 保存成功而缩略图上传失败
- **THEN** 页面已保存，用户看到的是一条诊断而不是保存失败
