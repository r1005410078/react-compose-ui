# 设计

## 指示点是第一类状态，不是指针位置的渲染

**吸附的定义就是十字线不在鼠标那里。** `resolveCadPoint` 的三条优先级里有两条会让结果偏离
裸坐标（键入坐标直接返回、对象捕捉返回特征点），所以「十字线 = 指针」从一开始就不成立。

现在这个量是四个散落的 `useMemo`（`hover` → `snap` → `pointContext` → `pointerPoint`），
橡皮筋终点、坐标读数、捕捉标记各拼一遍，十字线再拼第四遍。四个消费者拼四次，迟早有一处拼歪，
而那种缺陷表现成「橡皮筋和十字线差几个像素」，极难归因。因此把它抽成一个具名会话状态，
四个消费者读同一个值。

**它不能被手势会话拥有。** 框选、平移、命令取点是三种互斥手势，而十字线在三种手势里都要继续
跟。住进任何一个 session 都会在换手势时需要交接状态，而仲裁器的前提恰恰是同时至多一个会话。

**存屏幕位置而不是世界坐标。** 鼠标给的就是屏幕坐标，先转成世界再存等于把一个会过期的量当
事实来源：凡是不以光标为锚点的视口变化（例如后续的「缩放到选择集」），世界坐标不变而屏幕
位置变了，十字线就会飘离真实光标。存屏幕、读时解算则天然免疫。

平移时图面**故意不上报悬停**是对的，不要「修」它：平移中光标下的世界坐标本来就不变
（`world = (screen - offset) / zoom`，两者同增）。

## 形态由 `prompt.accepts` 决定，不引入新状态

三种形态与我们已有的状态一一对应，不需要任何新概念：

| AutoCAD | 我们的判据 |
|---|---|
| 十字线 + 拾取框 | `prompt === null` |
| 只有十字线 | `prompt.accepts` 含 `point` |
| 只有拾取框 | `prompt.accepts` 含 `selection` |

`accepts` 本来就在协议里，而且**已经**是悬停高亮与捕捉求解的判据。第四种组合（既不取点也不
选对象，例如 INSERT 等块名）不画十字光标，交还系统指针——那一步键盘才是输入设备。

## 光标钉在解算后的落点上，这是对 AutoCAD 的一处有意偏离

AutoCAD 里栅格捕捉会让十字线跳到格点，而对象捕捉不跳——十字线留在手的位置，另用 AutoSnap
标记指出特征点，让用户同时看见「手在哪」和「会吸到哪」。

我们把十字光标钉在 `resolveCadPoint` 的结果上，两种捕捉都跳。理由是我们已经有橡皮筋终点和
坐标读数两个指示器，它们都落在解算点上；十字线单独停在别处会让三者互相矛盾。**三个指示器
不一致比偏离一处约定更糟。**捕捉标记仍然照常显示，「吸到哪」的信息不丢。

这处偏离是**一行策略而不是架构决定**：指示点同时持有裸屏幕位置与解算结果，十字线画哪一个是
渲染时的选择。想改回 AutoCAD 的行为不需要动结构——这正是把指示点抽出来的价值。

## 拾取框半边长 = 命中容差

不是「差不多大」而是相等。一旦两者可以分头调整，就会出现「框明明压住了却点不中」——那是比
没有拾取框更坏的状态，因为用户会信任它。实现上两者读同一个 `pickRadius`。

框在缩放下**保持屏幕尺寸不变**：命中判据本身就是屏幕概念（世界容差 = `pickRadius / zoom`），
框跟着缩放变大变小就不再等于容差。

## 十字线长度默认取 100 而不是 AutoCAD 的 5

`CURSORSIZE` 的语义照搬（1–100 的视口百分比），默认值改成贯穿全视口。AutoCAD 默认 5 是在
整块显示器上取的，而我们的图面是编辑器里的一块面板，5% 会小到看不出是十字线。贯穿全视口
同时让十字线兼任一条免费的对齐参考线，这也是多数 AutoCAD 老手会主动改成 100 的原因。
宿主可以调回任意百分比。

## 轴向留出接口而不是写死水平垂直

AutoCAD 的十字线对齐的是 UCS 轴，转了 UCS 或进等轴测就跟着转。我们现在没有 UCS，屏幕轴对齐
是对的，但十字线按一对轴向量绘制而不是写死 `x1=0/x2=width`，以后加 UCS 时改的是向量来源而
不是绘制代码。本次不引入 UCS 概念，只是不把它堵死。

## 系统指针必须隐藏，但这有三个代价

画了十字光标还留着系统箭头就会看到两个光标。`cursor: none` 只作用于图面，命令行与工具栏
不受影响。技术上可行（实测计算值为 `none`），但要认清代价：

**一帧的延迟消不掉。** 系统光标由合成器按显示刷新绘制，延迟接近零；DOM 画的十字线最好也是
落后物理鼠标一帧。这是把光标从合成层挪到页面层的结构性代价，不是可以优化掉的性能问题。
唯一的缓解是**不走 React 渲染路径**——在 pointermove 里直接改属性，拿到「最少一帧」。标尺
包里那条游标线已经是这个手法。

实测每帧耗时（真实鼠标移动、rAF 采样）在空文档、40 条线与命令取点三种情况下都是中位 8.3ms、
零掉帧，因此**重渲染本身不是瓶颈**，不需要为它做特别设计。真正会随规模变坏的是交点捕捉的
O(n²)，与本提案无关。

**可访问性会退步。** 隐藏系统光标会一并丢掉操作系统的光标辅助设置（放大光标、高对比光标、
光标轨迹），而我们没有任何办法探测用户是否开启了它们——没有对应的媒体查询。检测不到就只能
给出口：`showCrosshair` 开关默认开，宿主可以关掉。

**触摸没有光标。** 十字线对 touch 指针毫无意义，因此按 `pointerType` 判断：mouse 与 pen
绘制并隐藏系统光标，touch 两者都不做。
