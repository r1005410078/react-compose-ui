## 上下文

一张大屏上的文字只有三四种样子，而每一条都是逐个填出来的。产品定位写着「把重复的页面编码
工作转化为可视化编排」，而这一条恰恰是最密集的重复。

仓库里已经有两处**派生数据**的成熟做法：导线几何与填充几何都不存储，由**布局 Runtime 在每次
solve 里求出来，文档与快照成对返回**。AGENTS 明写了反面：「逐条路径回写几何是禁止的——移动、
方向键、Inspector、撤销、粘贴、导入与组件刷新都会改端口位置，漏一条的症状是『线错位』」。

## 目标/非目标

- 目标：定义一次文字样式，应用到 N 条文字；改样式，N 条一起变。
- 目标：下游渲染、测量、预览、导出**一行不改**。
- 非目标：颜色样式、效果样式、网格样式。v1 只做文字——先完成一条可运行的纵向流程。
- 非目标：样式跨文档共享（那要资源 Store 与 revision，是另一件事）。
- 非目标：样式的继承与嵌套。

## 决策

**决策一：解析住在布局 Runtime，与导线、填充并排。**
判据是**这条数据被多少路径读**：排版值被 Stage 渲染、Preview 渲染、文字测量与 Inspector 四条
路径读，而它们此前的共同上游只有「文档」这一件东西。把解析放在 Runtime 产出的那份已解算
文档里，四条路径一行不改；放在渲染层则要把样式表穿过 Stage、Preview、组件实例三棵树，而
漏掉任何一条的症状是「这处文字没跟着样式变」。

替代方案：给 `resolveComposeRendererRuntimeProps` 加一个可选的 `styles` 入参。否掉的理由是
上一段——四个调用点里有三个拿不到文档，要新穿一条 prop，而这正是「逐条路径」那条禁令的
形状。

**决策二：样式排在求解之前，不排在求解之中。**
导线与填充必须在求解**之中**（它们要用盒），而排版值不依赖几何，反过来**文字测量要用它**。
排在之中会造出一个循环。

**决策三：跟随样式的字段在文档里缺席，作者写下的值覆盖样式。**
这是仓库的既有惯用法（「缺席即…」）的直接应用，而且它让**一次覆盖**天然可见：文档里有那个
字段就是被覆盖了。推论：**「应用样式」必须删掉它管辖的那几个 props**，否则样式加上去什么都
不会变——而屏幕上没有任何东西解释为什么。「脱离样式」反过来：把解析出来的值写成作者值、
删掉引用，几何与呈现一个像素不变。

替代方案：样式压过本地值。否掉的理由是那样就没有「局部覆盖」这档能力了，而「这一条标题要
大一号」是常见需求。

**决策四：`Style` 是 Entity 的可选 Component，不是 `Renderer` 上的一个字段。**
与 `Interaction`、`Ports`、`Wire`、`Hatch` 同一条：能力是 Entity 的，不是某个物料的。将来
颜色样式加进同一个 Component 的另一个槽位，Renderer 协议一个字节不改。

**决策五：样式表住在文档上，不住在资源里。**
v1 的样式只在一份文档内复用，而资源要 Store、revision 与跨文档引用——那是组件资产那一套的
规模。可选字段**缺席即没有样式**，因此不需要迁移、协议版本不变。

**决策六：悬空引用不让文档非法。**
指向不存在的样式只是解析失败，该 Entity 保留作者写下的值。这与导线绑定那条逐字相同：
「还没配」「配错了」「配的东西没了」三者必须可区分，而把它做成非法会让删一个样式就阻断保存。

## 风险/权衡

- 风险：Runtime 产出的已解算文档与 `sourceDocument` 混用，身份判定读错 → 缓解：仓库已有这条
  约定（`ready.document` 是已解算、`sourceDocument` 是输入），本变更不新增第三份。
- 风险：Inspector 显示的是解析后的值，用户改一下就把它固化成本地覆盖 → 这**正是**想要的
  语义（改一条就是覆盖那一条），但面板上要能看出「这个值来自样式」；v1 以字段装饰标出。

## 迁移计划

无。`styles` 与 `Style` 都是可选，缺席即今天的行为。
