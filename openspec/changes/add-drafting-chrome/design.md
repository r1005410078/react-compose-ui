# 设计

## 1. 十字光标住 `canvas-kit`

准入判据是本包自己那条：**它认识文档或选择集吗**。十字光标吃的是一个屏幕点、两个布尔与两个
尺寸，一个都不认识。它也不是那三条禁入里的任何一条——不做命中测试（谁被点中由各画布自己判）、
不渲染场景、不定义手势语义。

理由与当初统一特征点捕捉次序一样：**两块画布的手感必须相同**。同一个动作在两边给出不同的
视觉反馈，用户会认为其中一边坏了，而没有任何办法判断是哪一边。

### 为什么输入是两个布尔而不是 `prompt`

形态由**当前等待的输入类型**决定，那个信息住在 `ComposeCommandPrompt.accepts` 里，而
`accepts` 来自 `@compose-ui/commands`。canvas-kit 不能依赖它：那是给一个 React 底座包塞进
命令协议，而命令协议正是「认识领域」的东西。

因此共享组件的输入是 `{ lines: boolean; box: boolean }`，各画布自己从 `prompt` 推导。两边
各写一行，但那一行正是各自的领域知识——CAD 侧已经有这一行，Stage 侧照抄同一条对应关系。

### 拾取框半边长由调用方给，而两块画布给得出的东西不一样

CAD 传 `pickRadius`——它那边命中判据是「点到几何的距离」，容差是一个真实存在的全局数，
因此「框边缘压住即命中」这条保证成立。

**Stage 给不出同样的数**：它的点选是 DOM 驱动的，命中由浏览器决定，容差散在各物料自己的
透明加宽 stroke 里（曲线是 `MIN_HIT_WIDTH`，普通 Entity 是整个盒）。硬凑一个数只会让框看起来
精确而实际上不准。

因此 v1 的取法是**按线状物料那条 stroke 的半宽画**——那是绘图模式下唯一真实存在的容差——并把
「Stage 的框不保证等于命中容差」明写进规范。这是一处诚实的不对等，不是疏忽；要抹平它得先让
Stage 的命中测试收敛出单一容差，那是另一刀。

## 2. 隐藏系统光标的作用域是整个图面子树

CAD 侧写的是 `.compose-cad-canvas__viewport[data-crosshair], …[data-crosshair] *`；Stage 现在
只写了 `.compose-stage__surface` 一层。`cursor` 虽然是继承属性，但任何自带 `cursor` 的后代
（锁定节点的 `not-allowed`、编辑中标签的 `text`）都会把系统箭头露出来——屏幕上于是有两个光标。

标记挂在容器自己身上而不是用 `:has()` 去够：`:has` 在旧一些的浏览器里整条规则会被丢弃，
表现正是「系统光标没隐藏」，而且只在部分浏览器上出现。这条判断 CAD 侧已经踩过并写在注释里。

## 3. 工具栏 → 命令会话的通道是命令式的

启动一条命令是**事件**，不是状态。受控 prop（`draftingCommand` + nonce）是把事件伪装成状态：
宿主要维护一个只为了触发而存在的计数器，而 React 严格模式下的重放会**重复启动命令**——这与
导航会话那条 `dispose` 教训同源，端到端跑生产构建看不出来。

因此走命令式 handle：`ComposeStageHandle.runDraftingCommand(id)`。仓库里已有同形状的先例
（`ComposeCanvasRulersHandle`）。

反方向需要一个回调：工具栏按钮的按下态要知道现在跑的是哪一条命令，因此
`onDraftingCommandChange(commandId | null)`。**不把整个 prompt 回传**——那会把会话状态搬去
宿主，而「会话状态住在 Stage」是既有的明文决定。

## 4. 绘图模式换掉工具组，不追加

模式回答的是「整块画布按哪套规矩工作」。两套工具同时摆着，用户会以为可以混用——点了「选择」
工具再敲 `L` 会怎样？答案是照常进 `LINE`，因为绘图模式下 tool 根本不参与命令。摆一个不参与
的按钮出来，就是在承诺一件不存在的事。

绘制五条与编辑三条之间用**细分割线**分组，与既有工具栏的分组手法一致：`LINE ARC CIRCLE
RECTANGLE PLINE` 产出新几何，`MOVE COPY ERASE` 作用于既有对象，这是用户脑子里本来就有的那
一刀。

## 5. 只去 `draw-line`，圆与箭头留着

判据是**能不能被严格更强的东西接管**：

| 工具 | 几何来源 | 绘图模式有对应物吗 |
|---|---|---|
| `draw-line` | 盒的对角线，角度由盒的长宽比决定（`direction` 只有三档） | 有，`LINE` 的端点是显式的，还带捕捉与特征点 |
| `draw-circle` | `<ellipse rx="50%" ry="50%">`，是**椭圆** | 没有，`ComposeArcCurve` 只有一个 `radius` |
| `draw-arrow` | 带 `marker` 的线段 | 没有，`CURVE_RENDERER_PROP_SCHEMAS` 里没有 marker |
| `draw-rectangle` | Rectangle 物料：填充盒、背景 paint、圆角、参与 Auto Layout | 没有，`REC` 是一条闭合多段线**描边** |

只有第一行是真重复。去掉后三者是丢能力，不是合并——等 Curve 补上椭圆与端点 marker 之后再谈。

**Line Preset 不删**：既有文档里的 Line Entity 必须继续渲染，`stage-asset-drop` 的映射表也
仍要认得它。删的是**工具**，不是**物料**。

## 6. 不做的

- **绘图工具栏做成可配置插槽**：`stageToolbar` slot 已经能整块换掉。为一块还没被第二个宿主
  用过的 UI 提前抽象，正是「不得以未来可能复用为理由提前抽象」那条。
- **把绘图会话状态搬去宿主**：提示文本、橡皮筋与捕捉标记是同一份状态的三种呈现，交给宿主
  渲染会凭空造出一个逐帧回传的跨包协议。既有决定，不动。
- **十字光标带坐标读数**：CAD 的读数在命令行上，页面这边也在命令行上。跟着光标走的读数会
  遮住用户正要对齐的地方。
- **十字线跟随 UCS 旋转**：没有 UCS。CAD 侧已经把线按一对轴向量画好，以后加 UCS 时改的是
  向量来源而不是绘制代码。
