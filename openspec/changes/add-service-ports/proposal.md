# 变更：把后端收成两个纯接口（资源存取 / 页面库）

配套设计稿（自包含 HTML，浏览器直接打开）：
[架构图](../../../docs/mockups/service-ports.html) —— 全景、身份、三条写路径与「就用这个」时序；
[产品形态](../../../docs/mockups/product-home.html) —— 首页那一屏长什么样、为什么。

前端那一半是 [`add-page-library-home`](../add-page-library-home/proposal.md)，它消费本变更的
`ComposeLibraryPort`。

## 原因

产品要长出后端，而**后端还不存在**。现在把服务端的形状定成一组前端端口，服务端照着实现即可；
在它出现之前，同一组端口由本地实现顶上，前端流程今天就跑得通。

盘过一遍之后，「后端」不是一件事，是**两件性质不同的事**，必须分成两个端口：

- **资源存取**：按 id 读写一个字节流、目录树、乐观并发。事实来源是**对象存储**。
  这一半**今天已经有协议**了——`ComposeAssetProvider`，而且它与对象存储贴得出奇地近
  （`revision` 就是 ETag、`expectedRevision` 就是 `If-Match`）。缺的是三样具体的东西，见下。
- **页面库**：首页那一屏要的分类计数、回收站、排序、检索、缩略图、「用过多少次」。
  事实来源是**数据库**。

**一个端口答不了两边**。`ComposeAssetProvider` 是一棵文件树，首页要的每一件事它都答不了——
「PCS 有 64 个」要遍历整棵树读每个文件的标签，而协议里没有标签；「回收站」要软删，而协议里
delete 就是删；「用过多少次」是业务计数，「最近修改排序」要先把 418 个全列出来。
反过来，页面库也答不了编辑器要的事——用户往资源里放 SVG 符号、DXF、脚本，那是目录与字节。

今天首页那份目录是 `listComposePageDescriptors` **走遍整棵树**拿到的（BFS，每个文件夹一次
`list`）。本地目录上这是对的；换成 HTTP 之后它就是**打开首页要几十个来回**，而且拿回来的
东西里没有一样是首页真正要的（标签、计数、缩略图都不在 entry 上）。

## 变更内容

### 一、新增 `@compose-ui/library`：页面库端口

无 React、无 DOM，只依赖 `core` 与 `assets`。**不放进 `@compose-ui/pages`**：那个包的边界是
页面清单、聚合 Store 与**运行时导航**，而首页是一个可以完全不加载编辑器的宿主；让它为了一份
业务目录把导航会话一起装上是多余的，而权限、审计、协作这些迟早要长在库端口上的东西，一样都
不该进 `pages`。

- **一条查询回答整屏**：`query()` 的返回里 `items` 与 `facets`（左栏那八个计数）**一起回来**。
  分两条会让用户改筛选时计数是旧的、图是新的，而那个不一致屏幕上没有任何东西解释。
- **游标分页，不是 offset**：图墙是滚动加载，offset 在并发写入下会漏项与重项。
- **性质是记录上的字段，不是文件夹**：`kind: 'project' | 'template'` 加一个正交的
  `deletedAt`。回收站**不能**做成第三个 `kind`——恢复必须回到它原来的性质，做成三元的话
  「恢复到哪儿」在数据里读不出来。UI 上它仍然是左栏第三个去处，**这两件事不必一一对应**。
- **场景类型是标签不是枚举**：`categories: string[]` 加一条 `listCategories()`。写死枚举意味着
  第九种场景要发版；完全自由会退化成 `PCS` / `pcs` / `PCS柜` 三种写法并存。**「未分类」不是
  一个标签**，它是 `categories` 为空——否则会出现「既打了未分类又打了 PCS」这种非法态，
  而且没有人需要去维护它。这与「不内置电压等级色表」是同一条判断：清单因项目而异，
  内置一份等于替宿主做了一个多半要改的决定。
- **`useCount` 只能由 `instantiate()` 加**，没有一条前端可以随便调的自增：那样打开一次就能刷，
  而这个数正是用来回答「哪个画法是大家在用的」。这是本设计里**唯一**要求服务端写业务数据的
  地方——别处它只管存取文件。
- **`createProviderLibraryPort({ provider })`**：用今天就有的 `ComposeAssetProvider` 实现同一个
  端口，业务字段落在根目录一份 `library.json` 里。**这是「现在没有后端」这句话的落点**——
  前端整条流程今天就能跑，后端到了只换端口的实现。

### 二、`@compose-ui/assets` 补三样，对上对象存储

协议本身不改形状，加的都是**可选**能力，既有两个 Provider（File System Access、内存）一行不改。

- **`resolveUrl?` / `createUploadUrl?`：字节不过业务服务。**
  今天 `resolve` 返回 `Blob`，一张接线图上几十个符号就是几十个 objectURL 要管生命周期，而内容
  还要穿过业务服务两次（对象存储 → 服务 → 浏览器）。对象存储的正解是**预签名 URL**，浏览器
  直连。返回值里 **MUST 带 `expiresAt`**：签名会过期而一张图可能开着几个小时，不带它的症状是
  图在某一刻**集体变成裂图**。缺席即退回既有的 `resolve`。
- **`assetKey` MUST 是服务端签发的不透明 id，对象 key 就是它。**
  协议已经写着 assetKey「在 rename/move 后保持不变」，而对象存储的 key 是路径——把路径当
  assetKey 的话，用户在资源浏览器里改一下文件夹名，**图上每一个引用它的实例同时断掉**，
  而这个错误只在改名之后才出现、屏幕上没有解释。因此服务端把名字与父级放在自己的表里，
  对象存储里是扁平的 `assets/{assetKey}`。顺带的好处：move 从「搬一个 GB」变成一次 UPDATE。
- **目录 MUST 是表上的 `parentId`，MUST NOT 用对象前缀模拟。**
  前缀表达不了**空文件夹**（前缀下没有对象就等于不存在），而资源浏览器允许建空文件夹。

变更通知 `subscribe?` **不用改**：协议今天就是「什么都变了，重新拉」这一种无参数失效通知，
SSE 与轮询都对得上它。

### 三、缩略图：客户端画，异步传，可以没有

设计稿第 08 节留的问题，这里给答案。服务端 headless 渲染要把整个渲染栈搬到服务端并跟着版本
走，不做；打开首页现画 418 张不可行。所以是**保存页面之后，客户端把激活场景画一张 PNG 传上去**
——渲染器只有一份，画出来的一定与编辑器一致。

关键是**把它从保存路径上摘下来**：保存成功之后异步上传，失败不阻断保存，`thumbnailUrl`
**可以为 null**，缺席时图墙画一格占位。这与仓库既有那条判断同源——把一个静默的错换成一个
看得见的错：缺一张缩略图用户看得见，而让保存因为一张缩略图失败是不可接受的。
DXF 导入、接口直写这类不经过编辑器的写入方因此也不必产出缩略图。

## 影响

- 受影响的规范：新增 `page-library`；`assets`（新增预签名 URL、assetKey 身份与目录语义三条需求）
- 受影响的代码：
  - 新增 `docs/mockups/service-ports.html`（架构图，四张）
  - 新增 `packages/library/`
  - `packages/assets/src/index.ts`：三个可选方法与返回类型
  - `AGENTS.md`：新增包的架构边界
  - 首页宿主（尚未存在）消费 `@compose-ui/library`；编辑器**一行不改**——它继续用
    `ComposeAssetProvider`，换的只是背后接的是谁
- **不受影响**：`ComposeDocument` 协议、`.page.json` 格式、`listComposePageDescriptors`
  （它降为 `createProviderLibraryPort` 的内部实现，不删）
