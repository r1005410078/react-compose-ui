## 上下文

Registry 的 Renderer Definition 就是宿主注册图表的扩展点，示例应用一直用它注册一个
`echarts-bar`。问题不是扩展点不好用，而是**产品没有把图表当成自己的能力**——而这个产品的
目标用户搭的每一张大屏上都有图表。

`@compose-ui/materials` 当前的依赖是 `core`/`assets`/`components`/`property-panel` 这一类
第一方包，加上 DOMPurify 与 Valibot 两个小库。echarts 的体积与它们不是一个量级。

## 目标/非目标

- 目标：折线、柱、饼三类图开箱可用，数据可由页面脚本绑定。
- 目标：不给「只画方块和文字」的宿主增加图表运行时的重量。
- 非目标：地图（它还要一份 GeoJSON 资源管线，是另一件事）。
- 非目标：把 echarts 的全部配置面暴露成属性。v1 只做标题、类目、系列、配色、图例、坐标轴。
- 非目标：图表动画。

## 决策

**决策一：独立成包 `@compose-ui/chart-materials`。**
判据是**这个能力自己带一个第三方运行时依赖**，而仓库对这一类已经有两次同样的答案：`dxf`
（无依赖但自成一包）与 `svg-import`（`fast-xml-parser` + `svgpath`）。后者还写明了配套的
那条边界——解析库「不出现在公共 API 的类型里，换掉解析库不该是一次破坏性变更」，本包对
echarts 照此办理：公共 API 只出 Compose 自己的类型。

替代方案 A：放进 `materials`，echarts 作 peer dependency。否掉的理由是每个宿主都得装它，
而大多数宿主不画图表。
替代方案 B：放进 `materials`，用动态 `import()` 代码分割。否掉的理由是依赖仍然写在
`materials` 的 `dependencies` 里——装还是要装，只是晚一点加载。

**决策二：一个 Renderer + `kind` 三元联合，而不是三个 Renderer。**
这是 `Curve` 那条判断的第二次应用：「另立类型会让归一化、平移、距离、特征点、渲染与校验
六条路径各多一支逐字相同的实现」。三种图只差 echarts 的 `series.type`。

**决策三：物料面板出三格 Preset。**
判据是**用户在面板上找什么**——他找的是「饼图」，不是「图表，然后去属性面板改类型」。
Preset 与 Renderer 是多对一，`rect` 与 `rectangle` 都是 `curve` Preset 的既有先例。

**决策四：数据模型三种 kind 共用。**
`categories: string[]` + `series: { name, data: number[] }[]`。饼图取第一条系列、类目作扇区名。
让饼图另立一套 `{name, value}[]` 会让「把柱图改成饼图」丢掉数据，而那正是用户最常做的一次
尝试。代价写在明处：饼图的多系列数据无处安放，它只读第一条。

**决策五：尺寸用 `ResizeObserver` 跟随，而不是 `window.resize`。**
示例那份监听的是窗口，而画布上图表的盒子会因为缩放、Auto Layout 与属性面板改动而变，窗口
一动不动——症状是「图表画在旧尺寸上」。这是抄示例时必须不抄的一处。

**决策六：不内置配色表。**
与「不内置电压等级色表」同一条：配色因项目而异，内置一份等于替宿主做了一个多半要改的决定。
默认取一组与画布对比度够的中性色，并写进 props，用户改得动。

## 风险/权衡

- 风险：echarts 6 的按需注册清单写漏一项，症状是空白图表而不是报错 → 缓解：注册集中在一处，
  并有一条端到端断言三种图都真的画出了 `<canvas>`。
- 风险：示例应用改用第一方物料后，既有 e2e 里对 `echarts-bar` 的断言会红 → 缓解：一并更新。

## 迁移计划

示例应用里的 `echarts-bar` Renderer 与 Preset 删除，改注册第一方物料。**不写文档迁移器**：
`echarts-bar` 从未是产品能力，没有任何线上资产使用它——与 Page Slot 删除时「为零份文档写
迁移是纯粹的负债」同一条判断。残留文档里的 `echarts-bar` Entity 落到 Registry 既有的
「未知 Renderer」占位上，几何与外观保留、不会静默丢失内容。
