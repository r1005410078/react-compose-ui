## 上下文

`ComposeDocument v7` 的几何有两套：绝对定位（`LayoutItem.offset`）与 Auto Layout
（`Layout` + Flow 子级，Yoga 求解）。仪表盘区域两套都不合适——见 `proposal.md`。

关键约束：v6 那次重构已经把**几何的事实来源**从 `Transform` 挪到了 `ComposeLayoutSnapshot`，
渲染、命中、捕捉、场景树、动画、导线求解全部读 Snapshot 的绝对 box，**没有一条读 `Layout`**。
因此第二种布局的成本主要在"解出这组 box"，而不在下游。

## 目标 / 非目标

- 目标：二维摆放 + 碰撞推挤 + 重力上浮，拖动与缩放都能实时看见结果
- 目标：既有文档逐像素不变，协议版本不动
- 非目标：CSS Grid 的模板声明（`grid-template-areas`）——那是声明式模板，会把
  "随便拖到哪儿"变成"只能拖到模板允许的地方"
- 非目标：响应式列数收缩——大屏分辨率由 `Frame.size` 定死，没有消费者
- 非目标：自动路由式的智能重排——推挤只回答"谁挡了谁"，不替用户决定构图

## 决策

### 1. 求解器住 `core`，不住 `layout-engine`

它有两个消费者：`layout-engine` 求解，`stage-engine` 在拖动时算「松手会落在哪一格」。
而 `stage-engine` 的依赖只有 `core`、`commands`、`interaction-kernel`，**不含
`layout-engine`**。放错包会逼出一条新的包依赖。

判据与 `core/curve-geometry.ts` 逐字相同：跨包契约读的几何运算住 core。同理**整个模块放
一起**而不按消费者拆——把推挤挪到用得最多的那个包，会让碰撞数学横跨两个包，那是"一半改了
另一半没改"的温床。

**考虑过的替代**：住 `layout-engine`，`stage-engine` 通过宿主注入一个 `solve` 回调。
否掉的理由是它把一个纯函数做成了运行期依赖注入，而注入点会成为第二个可以漂移的地方。

### 2. 网格解成绝对矩形之后交给 Yoga，不实现第二套布局运行时

预解算 pass：读容器的 `Layout(grid)` 与各子级的 `GridItem`，算出每个子级的绝对矩形，
然后把它当作 `POSITION_TYPE_ABSOLUTE` 节点喂给 Yoga（显式 position + width/height）。
容器自己的盒仍由 Yoga 按既有的 Hug / Fixed / 边框 / 内边距规则解。

这让网格**继承既有的一切**：border-box、Frame 隔离、增量样式缓存、预览通道、
导线解算次序。第二套运行时要把这些各写一遍。

**推论**：格中子级的 `LayoutItem.width/height` 不参与求解，其 `mode` 取值不再有意义——
因此 Inspector 里降为只读（而不是隐藏：「它现在多少像素」仍是正当问题）。

### 3. 格中子级的 `positioning` 是 `flow`

它确实参与父级排布；**怎么排**由父级 `Layout` 的类型决定。这让"根级与 free parent 下
必须 Absolute"那条既有校验规则原样成立，一个字不改。

**考虑过的替代**：给 `positioning` 加第三个值 `'grid'`。否掉的理由是 `positioning`
回答的是"参不参与父级排布"这个二元问题，加第三个值会让每一处 `=== 'flow'` 的判断
都要重读一遍，而它们中的绝大多数问的正是那个二元问题。

### 4. 坐标进 `GridItem` 而不是复用 `LayoutItem.offset`

`offset` 在全仓库的单位是像素。塞进格数是一个只有读过源码的人才知道的暗坑，而症状
（"位置差了 50 倍"）看起来像求解缺陷不像单位缺陷。

### 5. 实时推挤：把 move 接进既有的预览求解通道

今天 `use-stage-preview-documents.ts` 只对 resize 提交预览文档，注释明写
「resize 是唯一需要真实布局求解的手势」。那句话在网格下不成立。

改动：拖动的目标在网格容器内时，同样走 `previewDocument`。通道本身（rAF 合并、
`clearPreview` 配对、卸载兜底）一行不改。

**要重新论证的既有约束**：「预览 Snapshot 不进入交互 Controller 的 context，提交几何
始终以冻结的提交态 Snapshot 为准」。它在网格下**仍然成立且更强**——网格的提交几何是
**格坐标**，根本不从 Snapshot 反算像素。因此这条约束不放宽，只是它保护的东西在这里
本来就不受威胁。

**这是本变更唯一动既有架构的地方**，也是唯一有真实风险的一处。

### 6. 推挤只向下，不交换

GridStack 的默认行为。交换（两张同尺寸的卡对调）手感更聪明，但它有一个说不清的边界：
尺寸不同时换不了，于是同一个动作有时交换、有时推挤。用户无法预测的规则比笨一点的规则
更糟，而"拖上去、它下去"任何时候都成立。

### 7. 重力只向上，不向左

列是作者的构图意图（这张在左、那张在右），行不是。向左靠会把用户摆好的分栏冲掉。
GridStack 的重力也只有一个方向，这不是简化。

### 8. 行高固定像素，不做按列宽的比例

比例模式（如 `1:1` 方格）的价值要等到同一份页面投多种分辨率时才出现，而大屏的宽度在
一个项目里通常是定死的。它是纯粹的加法，以后补不破坏任何东西。

### 9. 不做 GridStack 的 `locked`

仓库里已经有一个 `Lock` Component，含义是"不可编辑"；GridStack 的 `locked` 是"不被
别人推走"。两个不同的东西共用"锁定"这个词，是用户只能靠试才能分辨的那一类缺陷。
真需要时另起一个词。

### 10. 子级侧的格坐标进「几何」分组，不另起分组

既有的几何 Inspector 本来就**按 `positioning` 切换**：`absolute` 时第一个字段是「位置」，
`flow` 时是「自身对齐」。网格是这个开关的第三档。

"格坐标来自 `GridItem` 所以要另起一个分组"这条理由不成立——几何分组**已经跨了两个
Component**：旋转与基点来自 `Transform`，尺寸与外边距来自 `LayoutItem`。而"用户找
『这东西在哪儿』只看一个地方"成立。

### 11. 不做 flex 那样的三节点实时预览

flex 需要它，是因为 `alignContent` / `justifyContent` / `alignItems` 三个词抽象、图标
难认。网格的字段全是数字，**画布本身就是预览**，再画一个小的等于同一句话说两遍。
只在列数字段下加一条内联的 N 段格子条——12 → 8 的差别在画布上要数格子。

## 风险 / 权衡

- **move 期预览求解**（决策 5）→ 它与 `transform-planning` 的既有分流（`positioning ===
  'flow'` 的目标被过滤出 `planTransformCommit`）有交互。缓解：网格目标走独立的规划路径，
  不改 `planTransformCommit` 的既有分支。
- **推挤的连锁**：A 推 B、B 推 C 的深度没有上界（成环不可能，因为只向下推）。缓解：
  求解器按行序单趟扫描，复杂度对子级数线性，并用一条"20 张卡的连锁推挤"用例钉住。
- **重力与推挤的次序**：先推后浮会把刚推下去的又浮回来。次序是**推挤 → 重力**且重力
  跳过本次手势的目标，用例钉住。
- **切换 flex ↔ grid 会丢信息**：切到 grid 丢 `alignSelf`，切回丢格坐标。缓解：
  菜单项上明写代价，且都是一条事务、撤销一步回去。

## 迁移计划

无迁移。`Layout` 的 `grid` 成员与 `GridItem` 都是新增，缺席即今天的行为，
协议版本不变。这与 `Transform.pivot`、`polyline.cornerRadius` 是同一条判断。

回滚：删掉两个可选字段的写入入口即可；已经写了网格的文档会落到 Registry 既有的
「未知 Component」路径上，几何由 `LayoutItem` 兜底，不会静默丢失内容。

## 落地时定下的两条

- **新建对象落格取第一块空位**（`findComposeGridVacancy`），不是指针所在格、也不是最下面
  一行。判据是这条路径**没有落点意图**——点击添加、从面板点一下、从场景树新建都没有指针
  落点；而 GridStack 的 `addWidget` 不给位置时也是这个行为。右边整片空着时甩到最下面是
  明显错的。真正带落点的那条路径（从画布拖进去）仍然取指针所在格。
- **多选拖动按选区包围盒左上角取格，只把首个目标写成格坐标**，其余跟随；缩放暂只处理单个
  目标，多选退回通用路径。逐张算会让选区内部的卡片互相推挤，而用户拖的是一整块。完整的
  多选语义（整块平移且内部相对位置不变）需要一条判别性用例先钉住，留在后续变更；两处都在
  源码注释里写明了这一点。
