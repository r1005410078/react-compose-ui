# 设计：打磨几何编辑

## 1. 独有能力是「二维捕捉」，不是「能移动」

移动这件事已经有入口：几何编辑模式下拖线身仍然是移动（`path` 插件优先级 1400 只在命中夹点时
认领，线身落到 `entity-select-move` 700），而且不退出顶点模式。

所以要证明的不是「能不能移动」，是**这个夹点给了什么拖线身给不了的东西**：

| | 拖线身 | 拖中点夹点 |
| --- | --- | --- |
| 走哪条查询 | `snapCandidates` → 对齐吸附 | `findStageFeaturePoint` → 特征点捕捉 |
| 候选是什么 | 其他 Entity **盒**的六条 `{axis, value}` 参考线 | 二维**点**：端口/端点/中点/圆心/象限 |
| 怎么吸 | x 与 y **各自独立**吸一次 | 整体落在一个点上 |
| 有标记吗 | 无 | 有捕捉标记 |
| 有优先级吗 | 无 | `port > endpoint > midpoint > center > quadrant` |

仓库自己写过这两条是**姐妹查询，不是一个**。

**一处诚实的补充**：直线的盒中心恰好等于它的几何中点，因此拖线身**有可能碰巧**让中点落到另一
条线的端点上——两个轴各自吸一次盒线，凑巧同时命中。但那是巧合而不是动作：没有标记、没有优先
级、也吸不到「另一条线的中点」这种非盒角的语义点。对多段线与弧这个巧合根本不成立，它们的盒
中心不是几何中点。

## 2. 为什么不是「照搬 AutoCAD」

AutoCAD 的直线中点夹点存在，有一部分原因是**它的主要移动入口就是夹点**。我们是 Figma 语义，
拖谁移谁，那个理由在这里不成立。

因此参考它的**形态**（中点是那个把手），但论证换成上一节那条。这与仓库既有的判断一致：
AutoCAD 是设计的来源，不是论证的替代。

## 3. 多段线的段中点留白

AutoCAD 的多段线段中点拖动是**插入顶点**。「顶点增删」在路线图的未定决策里已经立着，写的是
「要做，缺的不是新机制，是一种新手柄」——段中点正是那种手柄的天然位置。

如果这一刀把段中点做成「平移」，将来做顶点增删时要么改掉一个用户已经学会的动作，要么给顶点
增删另找一个不自然的位置。因此**多段线这一刀里没有平移夹点**，并把这条写进规范，避免下一个人
把它当成漏做去补上。

## 4. `move` 而不是 `mid`

`mid` 在弧上是「改半径」。夹点 id 是 per-kind 解释的（模块注释写明「只有本模块解释它对应哪个
自由度」），所以复用 `mid` 技术上没问题——但同一个字符串在两种 kind 上含义相反，读代码的人会
绊一下，而自解释的 id 不花钱。

## 5. 选区盒不画，而文字编辑只去填充

两者是**同一条判断在不同形状上的两个结论**，不是不一致：

| | 文字编辑 | 几何编辑 |
| --- | --- | --- |
| 盒是对象的轮廓吗 | **是**，文字占满自己的盒 | **不是**，对角线的盒里绝大部分是空的 |
| 结论 | 去掉填充，保留边框 | 整个矩形都不画 |

CSS 里那条注释（「填充会盖住正在编辑的文字，也容易和普通选中态混淆」）是这条判断的第一次
应用；本刀是第二次。

**顺带消掉一个不打算修的缺陷**：选区盒由手势的预览变换推出，而夹点拖动走的是本地几何预览、
不产生预览变换——因此拖动全程盒停在拖动之前的位置。会话期间不画之后它没有可观察的表现了。
真要让盒跟着预览走，得让路径手势也产出预览变换，那是另一件事。

## 6. 接受的代价

**短线上三个夹点会挤。**两个端点与中点在一条几十像素的线上会靠得很近。AutoCAD 有同样的问题
并接受它。真成为问题时的解法是按屏幕距离抽稀夹点，那是覆盖层的事，不是本刀。
