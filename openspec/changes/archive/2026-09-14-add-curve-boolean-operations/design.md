## 上下文

`Curve` 已经有四种 kind（`line` / `arc` / `polyline` / `path`）、有几何编辑会话、有命中与捕捉，
唯独没有「用一个形状去改另一个形状的轮廓」这件事。竞品那一格是 Figma 的
Union / Subtract / Intersect / Exclude / Flatten，AutoCAD 的 `UNION` / `SUBTRACT` / `INTERSECT`
说的是同一件事。

关键的既有事实：**布尔运算最难的那一半，仓库在做 `HATCH` 求面时已经写完了**。
`core/curve-region.ts` 里的 `buildGraph()` 是一次标准的平面细分——两两求交切子边、节点按容差
合并、叠在一起的边收成一条；`traceLoop()` / `rightmostTurn()` 是半边图上的绕环；`castRay()` 有
六方向退化重试；`resolveIslands()` 认岛并落 `evenodd`；尾段按「最窄 kind」决定落 `polyline`
还是 `path`。求面与布尔是**同一份数学的两种用法**：求面只要围住落点的那**一个**面，布尔要
**全部**的面加一次内外分类。

## 目标 / 非目标

- 目标：四条区域运算 + 拍平，产物是可以继续拖顶点的普通 `Curve` Entity，撤销一步回去。
- 目标：复用既有平面细分，不引入第二套求交/绕环实现。
- 非目标：活的布尔节点、嵌套布尔、贝塞尔操作数、描边转轮廓、图案填充、间隙容差。
- 非目标：布尔结果跟随边界变化（那是 `Hatch` 的事，它有边界清单；布尔结果没有）。

## 决策

### 决策 1：面分类法，不走边裁剪

- **内容**：把全部操作数的轮廓片段丢进**一张**平面图，枚举全部有界面，每个面取一个内点，
  问「在第 i 个操作数里面吗」，按运算的谓词决定留不留，最后把保留下来的面合并、绕出外环与岛。
  四条运算的谓词分别是：并「在任一个里」、减「在第一个里且不在其余任何一个里」、交「在全部
  里」、异或「在奇数个里」。**多于两个操作数时这四句话原样成立**，不需要两两归约。
- **原因**：边裁剪（Greiner–Hormann 那一类）要在每个交点上标「进 / 出」，而退化情形——共线
  重叠边、顶点恰好落在对方边身上、两条弧相切——各要一条特判，**而这些正是本产品最常出现的
  情形**：网格吸附让两个矩形共享一条边，是画柜体轮廓时的常态。面分类把退化交给**已经处理过
  它们的那一层**：`buildGraph` 的叠边去重（两条画在一起的边界线在图上就是一条边界）与
  `castRay` 的六方向重试。仓库已经为求面付过这笔账。
- **考虑过的替代方案**：
  - 引第三方库（`polygon-clipping`、`martinez`、Paper.js）。否掉：它们都只吃多边形，
    弧要先拍成折线，而这个产品里整圆与圆角是一等公民；`core` 还写着「与 React 和 DOM 无关」
    且当前零第三方几何依赖。
  - 两两归约（先 A∪B，再 ∪C）。否掉：每一步都要重建一次平面图，N 个操作数就是 N−1 次
    O(n²)；而且中间产物的浮点误差会逐级放大。

### 决策 2：破坏性，不做活的布尔节点

- **内容**：五条命令都产出**一个新的普通 `Curve` Entity**，操作数在同一个事务里删掉。
- **原因**：两条，各自独立成立。
  - **协议**：Figma 的布尔节点既是容器（有子级、可下钻）又是几何（有轮廓、有填充、参与命中），
    而 `curve.ts` 写着 `Curve` MUST NOT 与 `Hierarchy` 组合。绕开它要么新造一个既是容器又有
    几何的 Entity 类型（命中、框选、Auto Layout、场景树、动画各开一条新分支），要么拿 `Group`
    去当别的用——后者这个仓库已经拒绝过两次（DXF 图层、`HATCH` 自动分组）。
  - **产品**：判据是仓库反复用的那一句——*用户画完之后想对它做什么*。在这个产品里布尔运算的
    用途是柜体轮廓开一个口、母线搭接处去一块、给底板挖一个孔，而下一步全是**拖那个新轮廓的
    顶点**。活节点恰恰做不到：要改轮廓得先进到子级里去改原来那两个形状。Figma 自己也承认这
    一点——它提供 Flatten，用途正是把活节点拍掉。
- **代价写在明处**：改主意要撤销重来，而不是像 Figma 那样换一个运算。

### 决策 3：`composeCurveFromOutline` 是一个函数，用在两处

- **内容**：把 `curve-region.ts` 尾段那段「一列轮廓片段 → 最窄 kind 的 `ComposeCurve`」提成公开
  纯函数，入参是**环的列表**（外环加若干岛），出参是 `polyline` 或带 `fillRule` 的 `path`。
- **原因**：它同时是布尔的第 5 步（保留面合并之后落地）与**操作数的内外判定入口**——
  操作数的世界几何是一列片段，而 `isPointInsideComposeCurve` 吃的是 `ComposeCurve`。
  两处各写一遍的话，下一个改「最窄 kind」的人只会改到其中一处，而漏掉的那处的症状是
  「看得见的形状与点得中的形状不是同一个」。
- **考虑过的替代方案**：为片段列表另写一个内外判定 `isPointInsideComposeOutline`。否掉：
  `isPointInsideComposeCurve` 要按 `fillRule` 分派，而扁平的片段列表读不出子路径边界；
  真要做就得把它改成薄壳，那是一次有风险的重构，换来的只是省掉一次转换。

### 决策 4：操作数的次序是层序从下到上

- **内容**：`operands[0]` 是层序**最靠后**（画在最下面）的那一个。它同时决定四件事：
  `SUBTRACT` 的被减数、结果的 `Appearance` 与 `Renderer` props、结果的名称、结果的父级与插入位置。
- **原因**：一条规则四处用。取不同来源会让场景树上那一行与画布上那块颜色指向两个不同的对象。
  「上面的减最下面的」与 Figma 一致，从那边过来的用户直接会用；插入位置与 `HATCH` 把填充插在
  最靠后的边界之下同一条。
- **代价**：想换被减数要先调层序（`[` / `]`）。这比给命令加一个「选哪个当被减数」的关键字好——
  那个关键字问的问题，屏幕上已经用层序回答过了。

### 决策 5：`FLATTEN` 恒落 `path`，是最窄 kind 的唯一例外

- **内容**：拍平不求交、不分类，每条几何转成一条子路径拼成一个 `path`，`fillRule` 缺席
  （即 `nonzero`）。单选一个对象也成立。
- **原因**：「写入方 MUST 取最窄 kind」那条的理由是「落错 kind 的症状是这条线看起来一样却拖不动
  顶点」，而 Flatten 的**目的**正是把顶点换成控制手柄——把一个圆角矩形变成能拖控制手柄的路径，
  是 Figma 用户用 Flatten 的主要理由。规则的例外必须由规则自己的理由推出来，否则就是特例。
- **代价**：拍平一个矩形之后它不再有顶点方块与圆角手柄。这是用户明确要的，不是副作用。

### 决策 6：引擎不读文档，操作数合不合格由宿主注入的谓词回答

- **内容**：`StageDraftingContext` 加一项 `booleanOperandIssue?: (entityId) => 原因码 | null`，
  与既有的 `isGeometryEditable` 同形。会话据此在**选够对象的那一刻**就拒绝并说明。
- **原因**：判据要读文档（有没有 `Curve`、是不是 `path`、是不是 `line`、锁没锁、有没有导线绑着），
  而 `stage-engine` 的命令层不认识文档——这条边界已经由 `isGeometryEditable` 立过一次。
- **推论**：规划那一层（`stage`）会**再判一次**。这不是重复：会话那次是为了给用户一句话，
  规划那次是为了不写出非法文档，两者的失败后果不同。

### 决策 7：旋转与跨父级支持，因为布尔不跟随

- **内容**：投影走世界空间（与命中、框选、特征点同一条链），结果落成一条 `rotation` 为 0 的
  新曲线，几何里已经含了原来的旋转。
- **原因**：与 SVG 导入「变换在导入期烘进几何」同一条。`HATCH` 跟随之所以拒绝旋转过的边界，
  理由是它每帧要按 `snapshot.boxes` 重求而盒到父级只是平移；布尔是**一次性**的，事后不跟随，
  那条理由在这里不成立。**不因为另一个功能有限制就把限制抄过来**。

### 决策 8：结果为空时拒绝，不产出看不见的 Entity

- **内容**：两个不相交的形状取交集时，文档一个字节不动，命令行说「这两个形状没有重叠」。
- **原因**：Figma 在这一档给一个空的布尔节点——那是**静默**的错。把静默的错变成可见的错，
  是这条的全部价值，与 `HATCH` 把断口画出来同源。

## 风险 / 权衡

- **把 `buildGraph` 从 `curve-region.ts` 提出来，动的是已上线的 `HATCH` 核心** →
  提取 MUST 是纯搬迁、不改一行逻辑，单独一个提交；由 70 条既有用例兜底
  （`curve-region` 26 + `curve-intersections` 12 + hatch 三处 32）。剩余代价是一次 review
  面积偏大的提交。
- **两两求交与节点合并都是 O(n²)** → 布尔是**一次性**的，不进每帧路径（与 `HATCH` 跟随不同）；
  本领域的操作数是矩形、圆、折线，边数在几十。落地时拿一份真实符号图量一次上界，把数字
  写进用例。
- **相切、共线、顶点落在对方边身上** → 六方向射线重试 + 叠边去重已经在那里；面分类不需要逐
  交点的「进 / 出」标记。仍可能有算不出来的组合，那一档走第八种拒绝，**报出来而不是产出一个
  错形状**。
- **操作数上的动画轨道随删除消失** → 带端口或被导线绑着的**拒绝**；只有动画轨道的**照做并出
  一句说明**。判据是那条绑定坏了之后在屏幕上看不看得见：导线绑定只在 Inspector 里现形，
  动画轨道在时间线上那一行不动就能看出来。
- **两个几乎重合的形状可能求出一条零面积的细缝** → `NODE_EPSILON_RATIO` 按包围盒尺度取相对量，
  已经在那里，量级比用户画得出来的最小缝隙小七个数量级。

## 迁移计划

无文档迁移：不新增协议字段、不改 `schemaVersion`，既有文档逐字段不变。

实现按四段推进，每段自己是一条可运行的纵向流程，可以单独停：

1. **`FLATTEN`**：核心一个新函数、一条命令、菜单一格。零算法风险，先把命令与菜单的接线跑通。
2. **提取 `curve-arrangement.ts`**：纯搬迁，零行为变化，单独验一次。
3. **四条区域运算**：核心求解、引擎解算、宿主规划、split button、快捷键、八种拒绝。
4. **（本变更之外）贝塞尔进平面图**：`cubic` 进 `ComposeOutlinePiece` 加 cubic × cubic 求交。
   它**同时解锁 `HATCH` 用贝塞尔边界**，因此值得单独立项——收益是两份。

回滚：三段各自是独立提交，任何一段出问题单独回退即可；第 2 段回退后第 3 段自然失效，
因此第 3 段 MUST 排在第 2 段之后。

## 待解决问题

- 真实图纸里 `path`（贝塞尔）操作数的占比有多高——这个数决定迁移计划第 4 段的优先级。
  接线图里几乎为零（符号是直线加弧），大屏底板里可能不低（SVG 导进来的装饰形状就是 `path`）。
- `FLATTEN` 要不要顺带把**描边**转成轮廓（Figma 的 Outline Stroke 是另一条独立命令）。
  本变更按「不做」落地；真要做是另一条命令，不是这一条的关键字。
