## 上下文

预览对话框今天用一个 `PreviewDialogScale` 下拉（`'1' | '0.75' | '0.5'`，默认 `'0.75'`）
配 CSS `zoom` 表达「取景」。`zoom` 与 `transform: scale()` 的差别不是实现细节：`zoom` 会让
浏览器**在该比例下重新布局**，文字度量、亚像素取整与换行位置都与 100% 不同，因此缩小的
预览与真实输出**在像素上确实不一样**。这正是「预览跟实际不符」最根上的一条。

调研 UE4 的 UMG Designer 得到的分法是：Screen Size 下拉 + 拖画布边角（吸附到清单里的
分辨率）回答「这块屏多大」，画布自己的缩放回答「我把它看多大」。本仓库已经有这两半的
零件——`COMPOSE_SCENE_SIZE_PRESETS` 与 `core` 的视口代数——缺的只是把它们接上。

## 目标 / 非目标

- 目标：预览在任何缩放下与真实输出**逐像素同构**（只差一个整体缩放）；屏幕尺寸可选可拖；
  组件与场景各按自己的语义呈现。
- 非目标：整屏预览形态、`ComposePreviewSurface` 抽取、页面底色选择器、时间轴刮擦。
- 非目标：改动 `COMPOSE_SCENE_SIZE_PRESETS` 的取值（是否补拼接屏分辨率需要产品决定，
  见「待解决问题」）。

## 决策

### 屏幕尺寸与视图缩放是两份状态

- **屏幕尺寸**决定被预览的那块屏有多大，场景/组件按 `fit` 映射进去，改变**被预览的东西**。
- **视图缩放**只决定这块屏在对话框里画多大，改变**取景**。
- 「适应窗口」因此不是一个档位而是一个**动作**（按一下把当前这块屏取景到窗口里），
  与画布上的「适配选择 / 适配容器」同一类。做成常驻档位会让用户永远停在一个非 1:1 的
  状态里还不知道——这正是今天默认 75% 的毛病。
- 考虑过的替代方案：保留单一缩放下拉、只把默认值改成 100%。它修不掉「1920×1080 在
  1280 宽的对话框里放不下」，也答不了「这块大屏挂到现场那台 1366×768 上是什么样」。

### 吸附住在 core，是纯函数

`snapComposeScreenSize` 放在 `packages/core/src/frame.ts`，与 `COMPOSE_SCENE_SIZE_PRESETS`
同一个模块。判据与预设住在 core 的判据逐字相同：消费者是 `preview`（现在）与可能的
`stage` 场景 resize（以后），而这两个包之间没有依赖关系，各写一份必然漂移。

四条规则：

1. **优先级严格先于距离**：目标自身尺寸（回到 1:1）压过清单里的任何预设，即使某个预设
   更近。「拖回原尺寸」是最常落的那一次，不该被一档碰巧更近的分辨率抢走。
2. **容差是屏幕距离**：`|size − candidate| × zoom` 与容差比较，而不是比较分辨率差。
   同样 40px 的分辨率差在 25% 与 100% 视图下手感天差地别——与极轴用屏幕距离而不是
   角度差是同一条理由。
3. **粒度是整份分辨率**：候选是尺寸空间里的一个**二维点**（欧氏距离），不是两条独立的
   轴参考线。沿用 `findComposeSceneSizePreset` 已经判过的那条——「宽命中而高不命中
   不算匹配，预设是一整个分辨率」。
4. **返回命中了谁**，供读数写出通名；没命中就返回 `null`，读数保持普通样式。

`COMPOSE_SNAP_RADIUS`（12 屏幕 px）从 `stage` 的私有常量下沉到 core，`stage` 改为导入。
「多近算在上面」在这个产品里只该有一个数，与 `COMPOSE_CURVE_PICK_TOLERANCE` 同一条理由。

### `fit` 必须真的缩放

既有实现对 `contain` / `cover` 只设了 `max-width` / `min-width` 与 `objectFit`，对 `fill`
只设了 `width: 100%`——而 Frame 的后代是**绝对定位**的，改盒子尺寸不会让它们跟着缩。
换句话说这个 prop 从落地起就没生效过（仓库里没有任何消费者，也没有用例）。
改用 `transform: scale()`：`contain` 取两轴比例的较小者、`cover` 取较大者、`fill` 两轴
各自缩放、`none` 不缩放；`transform-origin` 由 `alignment` 决定。

判据与「用 `transform` 而不是 `zoom`」同源：先按真实尺寸布局，再整体缩放，布局结果
一个像素都不变。

### 目标种类由宿主显式给出

新增 `targetKind?: 'scene' | 'component'`，缺省 `'scene'`（既有宿主行为不变）。
**不从文档反推**：一份没有导航端口的页面文档与一份组件文档在结构上完全一样，反推必然
在其中一种上判错。它控制四样东西：第一组标题、默认 `fit`、横竖互换是否出现、
常见屏幕那组的标题。

组件默认 `fit: 'none'` 是这里唯一的实质分叉：组件是屏上的**一个零件**而不是那块屏的全部
内容，把一个 88 × 132 的符号拉伸去填满 1920 × 1080 是荒唐的。而常见屏幕那组对组件
**仍然保留**——组件作者真正的问题是「这个符号摆进大屏里有多小、标签还读不读得清」，
今天要回答它只能先在页面上放一个实例。

### 「自定义」不是组件的特例

组件根的尺寸是提取那一刻的选区包围盒（`createComponentExtractionPlan` 的 `safeBounds`），
因此 `findComposeSceneSizePreset` 对它几乎恒返回 `null`。菜单第一项读作「自定义」是
**既有两条规则的自然结果**（查不到预设 + `formatComposeSceneSizePresetLabel` 不留空括号），
不需要为组件写任何分支；把场景设成 1000 × 800 时场景预览的第一项同样读作自定义。

菜单底部那个打开输入框的动作因此叫**「输入尺寸…」**而不是「自定义…」：一个词描述状态
（这个尺寸不在清单上），一个词描述动作（打开两个输入框），共用一个名字会让菜单里出现
两个同名而含义不同的东西。

### 页面模式不再静默压过 `document`

`pageMode` 一旦成立，`activeDocument` 就只读 `hostPage.page?.document`，传入的 `document`
被整个忽略。而宿主手上是两份互不相干的会话事实（页面会话与组件会话），打开组件不会
清掉页面会话，于是画布上是组件、预览里是页面。

修法**不是**在对话框里加开关，而是把契约写明：`navigation` / `livePage` 只在画布上正在
编辑的就是那一页时提供。宿主侧由「画布上是哪一份文档」这**一个**答案派生——它本来就已经
被算出来了（`activeComponent?.runtime ?? activePage?.runtime`），只是没有用在这里。

## 风险 / 权衡

- **删除 `PreviewDialogScale` 是破坏性的**：它是组件内部状态而非 prop，但
  `messages.scale` 这条文案会失去意义。保留该字段但标注为 deprecated 会留下一条谁也
  不读的文案；因此直接替换成 `screenSize` / `zoom` 两组新文案，并在 proposal 里写明。
- **拖拽手柄新增了一个只有一个角的 resize 手势**，与画布上八个手柄的 resize 长得不同。
  这是**有意的**：预览里拖的是屏幕、不是场景，两个长得像的矩形做不同的事必须在屏幕上
  分得开——一个角、加上读数里一直写着「屏幕」。
- **宽高比是算出来的**，不进协议、不存文档。常见比例走一张小表加容差，落在表外时退回
  最简分数（分母 ≤ 20）或小数。这张表是显示层的，判错的代价是一个标签不好看。

## 迁移计划

无文档迁移：屏幕尺寸、视图缩放、`fit` 与 `targetKind` 全部是**预览会话状态或 props**，
MUST NOT 写入或读取 `ComposeDocument`，与既有的 `fit` / `alignment` 是同一条边界。
`targetKind` 缺省 `'scene'`，既有宿主一行不改即保持旧行为。

## 待解决问题

- `COMPOSE_SCENE_SIZE_PRESETS` 要不要补拼接屏分辨率（`3840 × 1080` 双拼、`5760 × 1080`
  三拼）？储能／光伏现场常见，但任何通用清单里都没有，且要改一个被用例逐项断言的常量。
  **本变更不动它**，等产品确认现场是否有拼接屏。
- 画布上场景 resize 手柄要不要也吸附到同一份清单？同一套数学、同一份清单，但那一条
  **是文档编辑**（`entity.frame.size.set`，进撤销历史），与本变更正交，单独排期。
