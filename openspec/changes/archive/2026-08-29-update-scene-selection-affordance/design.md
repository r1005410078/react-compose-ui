# 设计决策

## 1. 为什么删掉「已在选区内的容器不收敛」

这条例外原本的理由写在代码注释里：「否则从标签选中之后就再也无法拖动它」。这句话在标签本身
就是拖动入口的前提下并不成立——`hit.source === 'label'` 已经先于收敛返回 `false`，标签按下走
的就是普通 entity 命中，选中与移动语义与场景体完全一致。

而它的代价是误触里最主要的一条：用户从标签或场景树选中场景，接着想在场景里框选几个控件，
整块场景被拖走。**这一条与「点体收敛」互相抵消**——收敛保护的是未选中的场景，而用户几乎总是
先选中场景（看属性、改尺寸），此后保护就消失了。

## 2. 为什么删掉「空容器不收敛」

空场景是最需要在里面框选、也最容易手滑的时刻——整块 1920×1080 都是拖动把手，而里面什么都
没有可点。原本的理由是「空容器点体是它唯一的选中入口」，但场景一定有标签，因此这个前提对
`rootIds` 成员不成立。收敛的作用域本来就只有 `rootIds` 直接成员，嵌套空容器不受影响。

## 3. 为什么是 ⌘/Ctrl，以及一处已知耦合

抄 Sketch：「点标题，或按住 ⌘ 点场景体内的空白处」。选它而不是另造一个键，是因为它已经是
这类工具里表达「我要的是容器本身而不是容器里的东西」的既有词。

**已知耦合**：`⌘` 在移动手势里同时表示「临时关闭吸附」（`move-planning` 每帧读
`modifiers.command`）。因此 ⌘ 点下去开始拖场景的那一刻吸附是关的。这可以接受，两个理由：
修饰键是逐帧读取的，用户松开 ⌘ 之后吸附立即恢复；场景在工作区里的位置不影响产出，把场景
拖到精确坐标不是真实需求。不为此另造一个键——多一个键要用户多记一件事，而这个耦合只在
一次拖动的第一帧上可观察。

## 4. 为什么框选排除只作用于顶层 Frame

现有实现只排除「完全包住框选区」的 Frame，理由是「从画板外面框住它仍然选得中」。但从工作区
往左拖一个窗交框、蹭到场景边缘同样会选中场景，而那次拖拽表达的是「抓一把这片区域里的东西」，
不是「选这块画板」。

判据与命中收敛同源：**场景是容器不是内容**，框选表达「选这些内容」。因此把排除放宽成
「`rootIds` 的直接成员一律不进入框选结果」。**不放宽到全部 Frame**：嵌套 Frame 没有标签，
点体仍是它唯一的画布选中入口，把它一并排除会让它在框选里也够不着而没有补偿；它保持既有的
「包住框选区则排除」规则不变，这样本变更对嵌套 Frame 零影响。

## 5. 为什么默认背景是透明而不是换一个颜色

场景背景是**会被发布出去的真实像素**，不是编辑器配色。编辑器替用户先填一个颜色，等于替他做
了一个他迟早要改的决定，而且那个颜色一旦与工作区接近，边界问题又会回来。

更根本的是：**背景色解决不了边界问题**。用户随手把场景背景改成与工作区相同的颜色，边界就
又消失了——默认值只保护第一次。边界必须由不受 `Appearance` 影响的东西承担。

因此默认背景取 core 已有的透明 Paint（`{ kind: 'solid', color: 'transparent' }`），并解除
compose-document 里「场景背景 MUST 与 Container 相同」这条不变量。那条不变量的理由是「用户
会看到画容器和画场景颜色不一样」，但这正是需要看出来的区别。

**既有文档不迁移**：默认值只作用于新建，已有场景保留自己写下的 `#1e2229`。为一个默认值写
迁移器等于替用户改他已经选定的外观。

## 6. 为什么边界是 chrome 而不是文档描边

不用 `Appearance.borderWidth`：布局求解把边框计入内容盒（`node.setBorder`），而场景是绝对
坐标的原点，1px 边框会把每个直接子级整体推离网格 1 个单位——这正是场景默认边框宽度为 0 的
既有理由，不能为了画一条线把它推翻。

实现落在 `StageWorldUnderlay` 已有的 `.compose-stage__output-boundary` 矩形上：它已经按
`frameBounds` 逐场景渲染、已经在屏幕空间（因此 1px 恒定、不随 zoom 变粗）、已经
`pointer-events: none`、已经带 `data-testid`。只是今天 `fill="transparent"` 且没有描边。

**边界对所有场景一视同仁，不区分激活**：既有规范明写「哪一块会被发布 MUST 由标签上的激活
标记承担，MUST NOT 依赖边界颜色差异」，这条保留。

**不共用标签的 `MIN_LABEL_ZOOM` 阈值**：标签在缩得很远时隐藏是因为它比场景本身还大；边界
恰恰相反，缩得越远越是唯一能读出「有几块场景、在哪里」的东西。

## 7. 端到端里表达 command 只能用 `Meta`

macOS 上 `Ctrl` + 左键会被 Chromium 翻译成右键，因此 `page.keyboard.down('Control')` 包住一次
`mouse.click` 根本产生不了左键手势——症状是"点了没反应"，与命中收敛真的挡住了它无法区分。
用例统一用 `Meta`；产品代码两个键都认（`event.ctrlKey || event.metaKey`），这只是取证手段的
限制，不是行为差异。
