## ADDED Requirements

### Requirement: Rive 式变换指示器

宿主打开时，Stage MUST 在选区上画出变换指示器。它 MUST 由四种**形状不同**的把手组成，
MUST NOT 只靠颜色区分语义：

- **轴上的箭头**（两个）：沿该轴平移，只写位置
- **箭头下面的方块**（两个）：沿该轴缩放，只写尺寸
- **圆环**：只写角度
- **中心的圆点**：只显示，标明「绕这里转」，v1 MUST NOT 可拖
- **四角的缩放手柄**：既有的那一套，指示器打开时对曲线也显示

两个东西长得一样而按下去做的事不同，是最难自己发现的一类缺陷；这与夹点按角色分三种形状是同
一条规则。

**一条轴上三段的次序 MUST 是「方块 → 环 → 箭头」**：方块在环内、箭头尖在环外，三者的距离
MUST 全部是屏幕常量。

**看得见的与抓得住的 MUST 是同一段**：平移的命中带 MUST 覆盖画出来的那条轴线，缩放的命中区
MUST 大于画出来的方块。曾经的做法是命中只覆盖环外那 22px、方块只有画出来的 10px——于是圆环
（整圈 20px 宽的带）成了唯一不会抓空的把手，用户读出来就是「只有旋转能用，平移缩放都不行」。

判别性 MUST 落在**常量关系**上：点每个把手几何中心的用例永远打得中，对这一类缺陷全绿。端到端
则 MUST 抓**用户会抓的地方**——轴线的中段、方块中心偏几个像素。

唯一的例外是轴线**最里面一小段**（约 24px），它 MUST 留给对象本体：两条轴的命中带在中心交叉，
一路盖到中心的话，「按住对象中间拖」——这块画布上最常用的手势，也是自动记录位置关键帧的主要
入口——就变成了受轴约束的移动。中心那里还压着基点圆点与运动路径的关键帧顶点。

推论：**轴与环相交的两处归轴所有**（各约 20px 宽的窗口），因为轴画在环之上。环是一整圈，损失
可以忽略；反过来则是「按在看得见的轴线上却开始旋转」，那才是说不清的。

**缩放方块 MUST 按位移解算，MUST NOT 按绝对落点**：它画在离被拖的那条边有一段距离的地方，按
落点解算会让第一帧就把那条边挪到光标底下——用户只拖了一像素，对象却猛地长到把手那么大。四角
手柄画在角上、本来就没有这段偏移，行为 MUST 逐像素不变。

缩放走既有的 resize 会话，手柄 MUST 按该轴**当前指向**归到最近的正方向：对象转过 180° 时它的
+X 指向屏幕左，此时该拖的是 `w`，否则「往箭头方向拖」会把对象缩小。旋转到 45° 附近时缩放轴与
画出来的轴对不上，那是「非曲线 Entity 仍用 AABB」这条既有欠账的可见形态。

**中心与轴按选区大小分流**：

- 单选时中心 MUST 是该 Entity 的**旋转基点**，MUST NOT 是包围盒中心。指示器的价值正是把
  `Transform.pivot` 从 Inspector 下拉框里的一个属性变成图面上看得见的东西——绕错点转在第一帧
  就该看得见。两条轴 MUST 跟着该 Entity 的 `rotation` 转。
- 多选时中心 MUST 是选区包围盒中心、轴 MUST 轴对齐：那时没有单一基点，也没有单一 `rotation`。

推论 MUST 写在实现旁边：**斜轴上拖动会同时改 `offset.x` 与 `offset.y`**，因此「一个把手对应
一条轨道」不成立——指示器分开的是**位置与角度这两个通道**，不是位置的两个分量。视口没有旋转，
因此世界角等于屏幕角。

**圆点 MUST 自己就读得出是个点。** 它画在两条轴之后、压在两条轴的交点上,填充色难免撞上某个
对象的颜色——落在同色对象上时它整个消失,用户看到的不是「一个看不见的点」,而是**两条轴在中间
断了一截**。因此它 MUST 带一圈与填充不同的描边:填充可以撞色,描边在任何底色上都划得出边界。
（曾经的填充取 `--compose-stage-accent` 的 fallback `#3b82f6`,而那正是选中态的蓝。）

轴色 MUST 沿用 3D 工具的通行约定（X 红、Y 绿）。它是**结构色**而不是状态色：永远成对出现、
永远带箭头、永远钉在中心上，靠位置与形状先分开、颜色只作二次编码。为避让既有配色而另发明一套
的代价更大——用户从别的工具带来的直觉会全部作废，而那份直觉正是它不需要说明书的原因。

**指示器的全部尺寸 MUST 屏幕恒定**——环半径在内——MUST NOT 跟画布缩放、也 MUST NOT 跟选区
大小一起变。它是 chrome 不是画布上的内容；跟着选区走的话，一个 220×150 的盒子就把环推到 149、
箭头推到 199，指示器随对象无限长大，转过 90° 之后箭头会落到图面之外。Rive、Unity、Blender
的做法都是屏幕恒定。

推论 MUST 明写：**大对象上环会压在本体上**。它是一条以环线为中心、向两侧各展开半个带宽的
命中带，落在带上的拖动是旋转而不是移动。这是屏幕恒定的代价，是**接受**而不是遗漏——躲开它
的唯一办法是让环跟着选区走，而那正是上一条否掉的东西。对象本体上除这条带以外的任何地方拖动
仍然是移动，两条轴也仍然给出受约束的移动。

**四角的缩放手柄 MUST 压在环之上**：角正是用户预期抓到缩放手柄的地方，而环是一条必然穿过
四角某个尺寸的宽带。这条 MUST 由**层次**承担——环单独一层、排在缩放手柄之下，轴仍排在其上。
SVG 里绘制顺序就是命中顺序，因此重叠归谁由层序回答；靠常量之间的大小关系去躲开碰撞是上一版
的做法，它多出一条「留白必须大于命中带半宽」的不变量，而那条不变量只在环恰好擦过四角时才
起作用、平时无从验证。

**指示器 MUST 跟着预览一起走**：手势期间它的中心读**预览**几何而不是已提交的文档。停在原处的
症状是「抓着的东西跑了、指示器留在原地」，用户会以为自己根本没抓住。旋转不受影响——基点是那次
旋转的不动点。这一步 MUST NOT 为每个预览帧重建整份场景索引：那是一次整棵树的遍历，而中心只需要
目标那一条祖先链。

**指示器上每个可交互元素 MUST 显式声明 `pointer-events`**：覆盖层根是 `none`。漏掉的症状极
具欺骗性——点击穿透到场景节点，「沿轴拖」退化成自由拖动：对象确实动了、位置轨道也确实写了，
只是不沿轴。因此轴约束的用例 MUST 断**垂直方向不动**，断「对象动了」对这个缺陷永远绿。

拖环时的角度读数 MUST 走只读读数那一条通道（与缩放的宽高读数同一个纯函数与同一套呈现），
MUST NOT 自带第二套标签样式——同一个数在两处呈现里对不齐，是各画一套的必然结果。

开关是 **chrome 的可见性而不是模式**：关掉时既有手势 MUST 一个字节都不变。Stage MUST NOT
认识「动画模式」这个词，开关 MUST 由宿主经 prop 传入。

#### Scenario: 指示器画在基点上而不是盒中心

- **WHEN** 一个旋转基点设在左边中点的对象被单独选中，且指示器已打开
- **THEN** 中心圆点落在该对象盒的左边中点上

#### Scenario: 轴跟着对象的旋转

- **WHEN** 单选的对象已经转过 30°
- **THEN** 两条轴同样倾斜 30°，而不是保持水平与垂直

#### Scenario: 基点圆点带描边，压在交点上仍读得出

- **WHEN** 指示器打开
- **THEN** 中心圆点带一圈描边，且描边色与填充色不同——它压在两条轴的交点上，没有描边时
  两条轴看起来是在中间断开的

#### Scenario: 四种把手形状各不相同

- **WHEN** 指示器显示出来
- **THEN** 平移把手是箭头、缩放把手是方块、旋转把手是圆环、中心是圆点，四者形状互不相同

#### Scenario: 方块在环内、箭头在环外

- **WHEN** 指示器显示在一个对象上
- **THEN** 缩放方块的**命中区**整个落在环的命中带以内
- **AND** 箭头尖到中心的距离大于环的半径

#### Scenario: 按在轴线中段就能拖动

- **WHEN** 按在画出来的轴线中段（既不在箭头尖上，也不在方块上）斜着拖
- **THEN** 对象沿该轴移动

#### Scenario: 方块的靶区大于画出来的方块

- **WHEN** 按在缩放方块中心偏几个像素的地方拖
- **THEN** 对象沿该轴缩放，而不是被自由拖走

#### Scenario: 轴把手沿轴约束

- **WHEN** 抓住 X 轴的箭头斜着拖
- **THEN** 对象沿 X 轴移动，垂直方向的坐标不变

#### Scenario: 方块沿轴缩放且按位移

- **WHEN** 抓住 X 轴的方块，往右拖 64px
- **THEN** 宽度增加约 64px 而不是一下长到把手那么宽
- **AND** 左边不动、高度不变

#### Scenario: 拖动时指示器跟着对象走

- **WHEN** 按住对象本体拖动，松手之前观察指示器
- **THEN** 中心圆点的位移与对象的位移相同

#### Scenario: 角手柄不被环的命中带偷走

- **WHEN** 指示器打开，拖动右下角的缩放手柄
- **THEN** 对象被缩放，而不是开始旋转

#### Scenario: 环的半径与选区大小无关

- **WHEN** 同一个指示器分别显示在一个小对象与一个大对象上
- **THEN** 两次的环半径相同
- **AND** 在对象内部、环的命中带之外按下并拖动仍然移动该对象

#### Scenario: 角手柄压在环之上

- **WHEN** 覆盖层按绘制顺序排好
- **THEN** 环所在的层排在缩放手柄之下、轴所在的层排在缩放手柄之上

#### Scenario: 多选换成包围盒中心与轴对齐

- **WHEN** 同时选中两个对象
- **THEN** 中心落在选区包围盒中心，两条轴水平与垂直

#### Scenario: 关掉之后别处手势不变

- **WHEN** 指示器关闭
- **THEN** 图面上没有把手，拖动对象本体、盒手柄与空白框选的行为与打开前一致

## MODIFIED Requirements

### Requirement: 受控工具模式与专属选区反馈

Stage MUST 接受受控的 `tool` 值并按它改变手势语义。工具集 MUST 只包含**没有其他入口**的
动作：`select`、`draw-container` 与 `draw-text`。

以下工具值 MUST NOT 存在，因为各自都有严格不弱的既有入口：`marquee`（`select` 在空白处
拖拽即框选）、`move`（`MOVE` 命令能键入精确位移）、`pan`（空格与中键是随时可用的临时覆盖，
不占用工具状态）、`draw-line`、`draw-rectangle`、`draw-circle`、`draw-arrow`（各有对应的
绘图命令，且命令那一套严格更强——能键入精确坐标、能捕捉、能正交、能中途放弃上一点）、
`rotate` 与 `scale`（两者都并进变换指示器）。

**`rotate` 与 `scale` 的删除判据与上面几个不同，MUST 记在这里**：它们不是「有一个更强的等价
入口」，而是「它们是**模式**，而指示器不是」。切到那两个工具之后，画布上**每一次**拖动的
含义都变了；打开指示器之后，只有**把手上**的拖动有新含义，别处一个字节不变。这正是「模式
必须是对象作用域且有明确的进出」区分的两类东西。

`scale` 唯一独占的事是**让曲线拿回盒与手柄**（`select` 下曲线画的是几何轮廓），那与「打开
一层 chrome」是同一件事的两种说法。指示器 MUST 覆盖两者原本的全部能力——含多选绕包围盒中心
转，以及曲线的盒与手柄——否则删除会留下缺口。

**制图几何 MUST 只有命令一套入口。**留着绘制工具会让同一件事有两套机制，还会让一处已知的
仲裁器冲突**用鼠标就能触发**：取点插件（`drafting-point`，1650）高于绘制（`draw`，1000），
两者同时武装时 `pointerdown` 被前者吃掉，拖动永远起不来。

`draw-container` 与 `draw-text` MUST 保留：它们不是制图几何，没有命令等价物，也不与取点插件
争抢——它们本来就是拖一个盒出来。

`select` 工具在空白处拖拽 MUST 框选，判定由拖拽方向归约得出（见 stage-engine 的框选判定
Requirement）。MUST NOT 存在任何可以覆盖方向的模式参数或宿主开关。

Stage MUST 为当前工具提供专属选区反馈：绘制工具显示落点预览。缩放手柄不再由工具决定——
它随选区常驻，曲线那一档由变换指示器的开关决定。

**单选一条带 `Curve` 的 Entity 且工具是 `select` 时，选区 MUST 画它的几何轮廓，MUST NOT 画
选区矩形、Resize 手柄或边缘命中带。**判据是**盒是不是这个对象的轮廓**：矩形、图片、容器的盒
就是它们的轮廓，文字占满自己的盒，而一条对角线的包围盒里绝大部分是空的——那个矩形宣称了对象
并不占据的面积，且比线本身显眼得多。线越接近 45 度它越大，拖端点时还一直在变。

这条判据 MUST NOT 被读成「给曲线开特例」：同一句话在矩形上的答案就是画盒，在文字编辑态上的
答案是画盒但去掉填充。它也 MUST NOT 扩大到非曲线 Entity。

轮廓 MUST 与几何编辑会话画的是**同一条几何**（同一个派生入口），MUST NOT 另写一份——两份
实现的分叉症状是「双击前后线的轮廓差半个像素」，而那种偏移只在特定缩放下现形。几何编辑态下
它 MUST 由可编辑路径层绘制，选区层 MUST 让位：两层各画一条会重叠出一条更粗的线。覆盖层
MUST 保持不认识文档：世界折线由宿主派生后传入。

**变换指示器打开时 MUST 照旧画盒**与缩放手柄。盒不是错的，它只是不是轮廓；用户明确在做盒
操作时，盒就是他正在操作的那个东西。曲线的整体缩放能力因此没有消失，只是从「随时都在」变成
「打开指示器」。

**多选 MUST 照旧画整体包围盒**，MUST NOT 逐对象改画轮廓。多选框回答的是「这一堆的范围」，
那是一个用户接下来真的会操作的矩形，它不宣称任何单个对象的轮廓。

几何编辑会话 MUST 在轮廓之外**再加**夹点与十字光标，两态因此可区分；轮廓本身在两态都画，
进出会话时对象的呈现只**增减夹点**，不整体换一套。AutoCAD 把选中与夹点
合成一态是因为它没有单独的顶点模式；本产品有，而「能不能拖出一个新形状」必须一眼可辨。

#### Scenario: select 在空白处拖拽即框选

- **WHEN** 当前工具是 `select`，用户从空白处拖出一个矩形
- **THEN** 按拖拽方向归约出的判定选中命中的节点

#### Scenario: 专属选区反馈

- **WHEN** 选中一个矩形 Entity
- **THEN** 选区显示缩放手柄，不需要先切到任何工具

#### Scenario: 选中曲线不画包围盒

- **WHEN** `select` 工具下单选一条斜线曲线
- **THEN** 图面不绘制选区矩形，也不绘制 Resize 手柄

#### Scenario: 轮廓沿几何而不是沿盒

- **WHEN** `select` 工具下单选一条斜线曲线
- **THEN** 绘制的轮廓落在线身上；包围盒四角处没有轮廓

#### Scenario: scale 工具下盒与手柄回来

- **WHEN** 选中同一条曲线并打开变换指示器
- **THEN** 图面绘制选区矩形与缩放手柄

#### Scenario: 非曲线 Entity 不受影响

- **WHEN** `select` 工具下单选一个矩形 Entity
- **THEN** 图面照旧绘制选区矩形与 Resize 手柄

#### Scenario: 多选仍画整体包围盒

- **WHEN** 同时选中一条曲线与一个矩形 Entity
- **THEN** 图面绘制覆盖两者的整体包围盒，而不是逐对象的轮廓
