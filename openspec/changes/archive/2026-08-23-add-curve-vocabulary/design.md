# 设计

## D1 · 两条判断原样平移，理由一字不差

**整圆是扫掠 ±360 的 `arc`，不另立 `circle`。** 命中、捕捉、归一化、平移、渲染、校验六条路径
因此各只有一份实现，整圆自然退化成「角度包含判断永远为真」的那一支。渲染是唯一分支的地方
（SVG 的 `A` 命令在起终点重合时画不出东西，整圆走 `<circle>`）。

协议用**带符号的扫掠角**而不是终止角：单给终止角分不出 10° 的短弧与 350° 的长弧，而这个歧义
只在特定角度组合下现形。

**矩形是四顶点的闭合 `polyline`，不另立 `rect`。** 矩形没有任何多段线没有的性质，另立类型只会
让六条路径各多一支逐字相同的实现；它唯一多出来的「四角是直角」在用户拖动某个顶点之后就不再
成立。`closed` 是布尔而不是「首尾顶点重复」——重复表示法里 `[A,B,C,A]` 是闭合三角形还是回到
起点的开放折线无法区分，而两者在框选与捕捉上给出不同候选。

## D2 · 多段线在页面里是**一个** SVG 元素，这是比 CAD 更好的地方

`cad` 的遍历把多段线展开成 N 条线段，代价是「一条多段线在 DOM 里是 N 个 `<line>`」。页面这边
渲染成一个 `<polyline>`（闭合走 `<polygon>`），命中由 `pointer-events: stroke` 天然承担——
和直线用的是同一个机制，透明加宽 stroke 也照样加。

`cad` 那句「展开是恒等变换」在**几何**上仍然成立并且这一刀照用：顶点仍是各段端点、各段仍有
中点、距离取各段最小值。变的只是渲染载体。

## D3 · 归一化仍是「紧包围盒左上角恒为盒原点」，弧的紧盒要过象限

`normalizeComposeCurveGeometry` 的契约不变，只是 `composeCurveBounds` 逐 kind 分派：

- 线：两端点的包围盒。
- 弧：**不能**用两端点——90° 到 270° 的弧鼓出来的那一侧在端点之外。必须把落在扫掠范围内的
  象限点一起纳入（`arcBounds` 已经这么做）。用端点算的症状是**弧被自己的盒裁掉一块**，
  而这只在跨象限的弧上出现。
- 多段线：全部顶点的包围盒。

退化轴仍钳到 `COMPOSE_CURVE_MIN_EXTENT`：一段极小扫掠的弧和水平线一样会让某一轴为 0，而
`LayoutItem` 要求正数。几何不受影响——渲染与命中都读几何。

## D4 · 特征点：弧补圆心与象限点，多段线不补新语义

`findStageFeaturePoint` 的优先级仍是**端点 > 中点**、优先级严格先于距离。弧新增两类候选：

- **圆心**：它不是任何线段的端点，是弧独有的、用户真正要对齐的点（画同心圆、把符号钉在轴上）。
- **象限点**：0/90/180/270 落在扫掠范围内的那些。

多段线**不引入任何新语义**：顶点就是各段端点，段中点就是中点。这与 D2 的「展开是恒等变换」
是同一件事。

**仍然刻意不出盒的角点**——那是对齐吸附（`snapCandidates`）覆盖的语义，两套同时生效会在同一次
取点里给出互相拉扯的答案。这条不变量不因新 kind 而松动。

## D5 · 数学下沉到 `core`，`cad` 侧改别名转导

`cad-arc-geometry.ts`（约 220 行）与 `cad-polyline-geometry.ts`（约 44 行）是纯形状运算，
不认识 `CadDocument`。与步骤 2 搬点输入管线同一做法：搬进 `core`，`cad` 保留别名转导。

判据仍是「搬过去的是不是一整条求解」——这里是一整套闭式解（弧的角度包含判定、点到弧距离、
象限包围盒、拍扁），不是一个 `if`。**CAD 既有 87 项用例不改一行即全绿**是搬运没有改变行为的
证据；改了一行就说明搬运顺手改了语义。

## D6 · 四条命令，都复用既有的四态推进

| 命令 | 取点 | 备注 |
| --- | --- | --- |
| `ARC` | 起点 → 途经点 → 终点 | 复用 `arcThroughPoints`；三点共线时 `rejected`，不结束会话 |
| `CIRCLE` / `C` | 圆心 → 半径点 | 产出 `sweep: 360` 的弧 |
| `REC` | 一角 → 对角 | 产出四顶点闭合多段线 |
| `PLINE` / `PL` | 连续顶点 | 与 `LINE` 同构，但**攒成一个 Entity** |

`PLINE` 与 `LINE` 的差别值得写下来：`LINE` **逐段落地**（每段一个 Entity，撤销粒度一段），
`PLINE` 攒到结束才提交**一个** Entity。这不是不一致——它正是两条命令存在的理由，AutoCAD 同样
如此。因此 `PLINE` 需要 `U`（放弃上一点）关键字而 `LINE` 不需要：`LINE` 的「放弃」等于一次
文档撤销，而 `PLINE` 的还在会话里。

## D7 · 刻意不做

- **`bulge`（多段线里的弧段）**：现在没有命令产出它，加进来意味着归一化、距离、特征点、渲染
  四条路径各多一条没有用户走过的分支。位置已经让好了——逐段产出几何时把某一段从线换成弧即可。
  这与文字的 `rotation` 不同：那是标量，命中框与渲染必须从第一天就一致。
- **椭圆与样条**：主接线图上没有。等真实图纸里出现再说。
- **顶点夹点编辑**：与「端点夹点与盒 resize 的关系」是同一个未决问题，独立一刀。
  v1 的编辑入口是 Inspector 数值。
- **`ARC` 的其它十种起算方式**：AutoCAD 有十一种，三点式覆盖鼠标绘制的绝大多数。加一种起算
  方式是加一条会话分支，等有人真的需要再加。
