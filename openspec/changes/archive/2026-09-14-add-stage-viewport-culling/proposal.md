# Stage 视口裁剪

## Why

一份真实的现场图纸（`app/public/ems.dxf`，五千多个实体）导进来之后，画布**明显卡顿**：在有头
浏览器里按真实帧间隔量，拖动一个对象的 p95 帧时间是 116ms（生产构建）/ 367ms（dev），缩放
每一格滚轮都是一次 50–110ms 的长任务。

根因量得出来，而且是同一条：

> **DOM 里 5381 个实体，落在图面可视区内的只有 624 个。**

场景把文档里每一个实体都渲染进 DOM，不论它在不在屏幕上。于是 88% 的节点不产生任何像素，却
要为每一帧的样式重算、布局与绘制付账。缩放那一档尤其贵——`--compose-canvas-zoom` 是挂在场景
根上的**可继承** CSS 变量，3778 条曲线的 `stroke-width: calc(px / var(...))` 都吃它，它一变，
24538 个节点的样式全部作废。隔离实验（在导入后的图纸上单独改一样再强制一次样式读取）：

| 只改什么 | 一次强制样式重算 |
|---|---|
| `transform` | 0.0–0.3 ms |
| `--compose-canvas-zoom` | **200–400 ms** |

平移只改 `transform`，所以不卡；缩放两样都改，所以卡。**节点少一个数量级，这张账单就少一个
数量级**，而这正是裁剪要做的事。

这不是「图太大」的托辞：五千个实体对一份接线图是**平常规模**，而这个产品的目标用户手上的图
全都是这个量级。今天的表现是「导得进来，但没法用」。

## What Changes

### 场景只渲染与视口相交的子树

`StageSceneLayer` 的递归在进入一个 Entity 之前先问一句：它的**子树**包围盒与当前裁剪窗口相不
相交；不相交就整棵跳过。被跳过的 Entity 没有 DOM 节点，其余一个字节不变。

### 裁剪窗口是**量化**的，不是视口本身

这一条是本刀的关键约束，因为现状是**刻意**与视口解耦的
（[stage-scene-layer.tsx:129](packages/stage/src/stage-scene-layer.tsx#L129)：「平移与缩放只改变
根节点 transform……否则每个平移帧都要为全部 Entity 重建 element 并做 fiber diff，大场景下直接
掉帧」）。那条注释今天仍然成立——直接让内容 memo 依赖 viewport，会用一个每帧全量 diff 换掉一个
每帧全量重算，很可能更糟。

因此裁剪窗口 MUST 外扩且量化：外扩一整屏、并把结果吸到半屏的格子上。平移半屏才换一次窗口，
缩放按二次幂档位才换一次——内容子树因此**仍然不随帧变化**，一次手势通常只重建零到一次。

### 裁剪只影响渲染，不影响任何查询

命中、框选、吸附候选、场景树、选区几何全部读文档与布局快照（`entityAtPoint` 已确认是纯几何
判定，不碰 DOM），因此它们看不见裁剪。**「被裁掉了」MUST NOT 能从任何接口读出来**。

### 几类必须豁免

正在文字编辑的、正被手势作用的、选中集里的、以及组件实例下钻的宿主实例——判据是**任何按 id
查 DOM 的路径，它的目标必须豁免**，而今天全仓只有一处这样的查询
（`instance-selection-bounds.ts`）。

## 本步刻意不做

- **改 `--compose-canvas-zoom` 的机制**：裁剪把它的消费者减少约 8 倍，够不够要**量了才知道**，
  不在提案里承诺。若仍不达标，下一刀是一个单独的决定——它要拿「线宽反向除掉画布缩放」这条
  已写明的不变量去换帧时间（手势期延迟写入会让线宽在捏合过程里「呼吸」一下），那是产品取舍，
  不该混进一次纯性能改动里。
- **把场景换成 canvas 渲染**：那是推翻 DOM 场景，与本刀不是一个数量级，也会丢掉 HTML 物料。
- **LOD / 几何简化**：缩小时把细节换成粗略画法是另一条正交的路，且会改变「看见的就是画出来
  的」。
- **场景树虚拟化**：它已经虚拟化了，不在这条账单上。

## Impact

- **`@compose-ui/stage-engine`**：`StageSceneIndex` 新增子树包围盒查询；纯函数的窗口量化与
  可见集求解。
- **`@compose-ui/stage`**：`StageSceneLayer` 递归接裁剪与豁免集。
- **协议**：一个字段都不加。裁剪是**呈现**决定，不是文档事实。
- **`app/`**：真实图纸夹具已在（`ems.dxf`）。
