## MODIFIED Requirements

### Requirement: 场景只渲染与裁剪窗口相交的子树

Stage 的 Scene MUST 只为与**裁剪窗口**相交的 Entity 建立 DOM 节点；不相交的子树 MUST 整棵
跳过。

判据 MUST 是**子树**包围盒而不是 Entity 自身的盒：子级是绝对定位的，容器不裁剪时子级可以画在
父盒之外，按自身盒裁会让「父在屏外、子在屏内」的整棵子树消失。带 `Clip` 的容器是例外——它的
后代画不到自己盒外，因此子树包围盒**就是**自身盒。

**窗口之内，屏幕上小到读不出来的叶子 Entity 同样 MUST NOT 建节点**（细节裁剪）。「多小算读
不出来」由该 Entity 的 Renderer Definition 以屏幕像素声明（`minimumLegibleSize`，两轴各自可选），
Stage MUST 只做一件事：声明的每一轴上世界包围盒乘缩放都低于阈值，就不建节点。没有声明的
Renderer MUST NOT 因细节被裁。判定 MUST 按缩放**档位的下界**而不是真实缩放：一个 Entity 在
某一档被判可读，则档内任何缩放下都可读，可见集因此只随档位变。

理由是量出来的：整张图都在可视区的那几档，视口裁剪按定义裁不掉任何东西，而每帧 34ms 里 27ms
是 Blink 对每个节点固定要付的合成层划分，只能靠少建节点；这几档的文字字号不到 2 像素、近两千条
曲线整个落在一个像素之内，画出来的只是一片绒。

细节裁剪与视口裁剪 MUST 合成**同一个**「被裁掉的」集合交给渲染层：豁免、分批、「按被裁掉的而
不是该渲染的」全部沿用。推论：选中一个被细节裁掉的 Entity，它 MUST 当场出现。

小图上可见集等于全集，渲染输出 MUST 逐字节不变；细节裁剪只作用于编辑画布，Preview 与导出
MUST NOT 受影响。

#### Scenario: 屏外的子树不进 DOM

- **WHEN** 一份五千实体量级的文档打开且大部分内容落在可视区之外
- **THEN** DOM 里的 Entity 节点数与可视区相称，而不是与文档规模相称

#### Scenario: 父在屏外而子在屏内

- **WHEN** 一个不裁剪的容器自身盒完全落在窗口之外，但它的某个子级落在窗口内
- **THEN** 该子级仍然被渲染

#### Scenario: 可视区内的都在

- **WHEN** 任取一个落在图面可视区内、且在当前档位下可读的 Entity
- **THEN** 它在 DOM 里有对应节点

#### Scenario: 读不出来的文字不建节点

- **WHEN** 一份真实图纸适配到整张图都在可视区，其文字的屏幕字号不到两个像素
- **THEN** 这些文字没有 DOM 节点；放大到字号越过物料声明的阈值之后它们回到 DOM

#### Scenario: 长细线不因细节被裁

- **WHEN** 一条曲线的屏幕高度不到一个像素而宽度有几百像素
- **THEN** 它照常渲染——只有声明的每一轴都低于阈值才裁

#### Scenario: 没有声明的 Renderer 永不因细节被裁

- **WHEN** 一个组件实例或宿主自定义 Renderer 在屏幕上只有一个像素大
- **THEN** 它仍然渲染

#### Scenario: 被裁掉的小字选中即出现

- **WHEN** 用户在场景树里选中一个因细节被裁掉的文字
- **THEN** 它的节点当场出现，选区盒与属性面板照常工作

### Requirement: 裁剪窗口是量化的，内容不随帧重建

裁剪窗口 MUST 是一个**离散**值：以视口中心为心，尺寸只由**量化后的缩放档位**决定，外扩之后
四条边各自**向外**吸到格子上。场景内容的记忆化 MUST 依赖这个窗口的身份，MUST NOT 依赖视口
本身。

理由是既有的那条约束仍然成立：内容子树与视口解耦，是因为让它随帧变化会让每一个平移帧都为全部
Entity 重建 element 并做 fiber diff。裁剪若直接依赖视口，等于用一个每帧全量 diff 换掉一个每帧
全量样式重算。

**缩放 MUST 量化，窗口尺寸 MUST 只认档位而不认档内的真实缩放**：缩放是连续量，窗口按真实可
视区取尺寸时几乎每一帧都换一个窗口。窗口因此 MUST 按档内**最宽**的那个可视区取尺寸，
「窗口恒包含可视区」才在整个档内成立。

**吸附 MUST 向外**：向外吸让「窗口恒包含可视区」由构造成立。就近吸时每条边最多向内让半格，
于是要求外扩量严格大于半个步长，而那种数值关系一旦被后来者调参调破，症状是拖到某处边缘闪一下
空白——一个只在特定平移位置出现、极难复现的缺陷。

**窗口的格数 MUST 由档位定死，只有左上角随平移走**：两条边各自吸各自的时，格数会在相邻两个
整数之间来回跳，于是平移每过一格换**两次**窗口而不是一次。

**换窗那一帧 MUST NOT 一次性挂上或卸下整条带子**：新进窗口的与离开窗口的 Entity MUST 从
下一帧起分批逼近目标，每帧一批；一批装得下时 MUST 当帧到齐。没变的子树 MUST 交回同一个
元素对象，React 才能在它上面跳过。

这一条**只在外扩量存在时才成立，而它正是外扩的全部用途**：新进的带子按构造整条落在可视区
之外，晚几帧到达用户看不见。推论：大图平移时 DOM 里的节点数是**最终一致**的，读它的用例
必须先等它稳定；小图上换窗仍是同步的。

MUST NOT 把这一趟重建交给低优先级渲染：React 的低优先级渲染每收到一次高优先级更新就整个
重来，而平移每一帧都是一次高优先级更新，连续拖动时它永远完不成，直到过期强制刷出——用户看到
的是图要等很久才出来。

缩放跨档、豁免变化与文档变化引起的目标变化里，**由窗口带进来的** MUST 当帧到齐——新进的节点
可能已在可视区里，正在编辑或正被拖动的那个必须当场在。**由可读性带进来的 MUST 分批**：它们的
尺寸就在可读阈值上，放大跨过阈值那一帧一次性挂上一千八百个文字是一个 50–80ms 的长任务，而让
几像素高的字在几帧里按文档顺序补齐，用户看不出来。

#### Scenario: 换窗不落在平移帧上

- **WHEN** 用户连续平移越过量化步长，触发一次换窗
- **THEN** 那一帧不挂不卸任何 Entity，新进与离开的从下一帧起分批处理

#### Scenario: 停下之后图立刻补全

- **WHEN** 用户在大图上连续平移之后停下
- **THEN** 可视区内的每一个 Entity 在几帧之内进入 DOM，而不是等待数秒

#### Scenario: 连续平移不重建内容

- **WHEN** 用户连续平移不足一个量化步长
- **THEN** 裁剪窗口不变，场景内容不重建

#### Scenario: 档位内缩放不重建内容

- **WHEN** 用户以视口中心为锚点在同一个缩放档位内来回缩放
- **THEN** 裁剪窗口不变，场景内容不重建

#### Scenario: 任何位置上窗口都盖住可视区

- **WHEN** 视口停在任意平移位置、任意缩放
- **THEN** 可视区被裁剪窗口完全包含

#### Scenario: 跨过可读阈值时文字分批回来

- **WHEN** 用户放大跨过文字物料声明的可读阈值，一千多个文字同时变得可读
- **THEN** 那一帧不一次性挂上全部，它们从下一帧起按文档顺序分批进入 DOM；同一次换档由窗口带进
  来的节点仍当帧到齐
