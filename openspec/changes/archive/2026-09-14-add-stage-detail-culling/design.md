# 设计

## 决策 1：阈值住在 Renderer Definition，不住 Stage

Stage 不认识物料：它知道盒与缩放，不知道盒里是字还是线。「多小算读不出来」对文字是字号、对
曲线是整个形状是否落进一个像素，这两句话只有物料自己说得出。`ComposeRendererDefinition` 上
已经有 `measurement`（物料告诉布局引擎怎么量自己）这条先例，`minimumLegibleSize` 是同一条边界
的同一次应用：

```ts
readonly minimumLegibleSize?: {
  readonly width?: number   // 屏幕像素
  readonly height?: number
}
```

语义：**声明的每一轴都低于阈值时不建节点**。文字只声明 `height: 5`（一行 12px 字的盒高 15，
5px 盒高约合 4px 字号；多行文字的盒更高，因此更晚被裁——宁可多画）；曲线声明
`{ width: 1, height: 1 }`（一条 0.5×300 的线宽度轴不低于阈值，照画；只有整个形状落进一个像素的
才裁）。没有声明就是「永远可读」，容器、图片、组件实例与宿主自定义 Renderer 不受影响。

取盒而不取字号：Stage 手上只有盒；而字号是文字物料的 prop，读它等于让 Stage 认识文字。

## 决策 2：与视口裁剪合成同一个集合

`useStageCulling` 已经产出「被裁掉的」集合并处理豁免、近全集短路与批次键。可读性判定加在
可见集求解之后：窗口内且可读的才可见。推论：

- 豁免原样生效——选中一个小字它就出现（属性面板、选区盒都要它在），文字编辑中的更不用说。
- 「按被裁掉的交给渲染层」原样成立——索引不认识的 Entity 照常渲染。
- 近全集短路（可见集不比全集少一成就不裁）把两种裁剪加起来算：适配档窗口裁不掉任何东西，
  可读性却裁掉七成，短路自然不触发。

判定用档位的**最小**缩放：`resolveStageCullingWindow` 已经给出 `zoomStep`，档位下界是
`2 ** (zoomStep / 4)`；一个 Entity 在这一档被判可读，则档内任何缩放下都可读。

## 决策 3：可读性引起的增减一律分批

场景层今天按 `cullingBatchKey`（档位 + 豁免键）决定「当帧到齐」还是「分批」：键变了就当帧到齐。
细节裁剪的翻转恰好都发生在换档那一刻，照旧会被判成当帧到齐——放大跨过阈值那一帧挂一千八百个
文字，实测 50–80ms。

改法：`useStageCulling` 除了合成后的 `culledEntityIds`，再交出**只因可读性被裁的**那一份
`detailCulledEntityIds`。场景层在键变化的那一趟里，把目标差集拆成两半——落在可读性集合里的进
分批队列，其余当帧到齐。这一条不改「换窗那一帧不挂不卸整条带子」的既有语义，只把「跨档当帧
到齐」收窄到窗口带进来的那一半。

分批走既有的自适应批（最小 16，长队列八帧内摊完）：一千八百个文字八帧摊完，每帧二百多个，
每帧仍是一次可观的提交（估 10–15ms），但它们落在缩放帧上而不是平移帧上，且不再是一个 80ms 的
长任务。要不要给这一种再单独限批，等实测。

## 决策 4：不做迟滞

阈值只在档位边界翻转，档位是离散的，因此不存在「缩放 0.001 就翻一次」的抖动；剩下的是用户
恰好在边界上来回缩放，每次翻转一趟分批。迟滞要记住「上一次是显是隐」这份状态，而它会让同一个
缩放值下两次打开画面长得不一样——一个看得见的错换一个偶发的慢，先不换。

## 判别性用例

- **单测（stage-engine）**：同一份索引在档位 A 判为可读、在更低的档位 B 判为不可读；只声明
  `height` 的 Renderer 宽度轴不参与；两轴都声明时**只有两轴都低于阈值**才裁（长细线照画）；
  没有声明的 Renderer 在任何缩放下都不裁；档内任意缩放下判定结果与档位下界一致。
- **单测（stage）**：被可读性裁掉的 Entity 进入选择集后出现在 DOM；跨档时可读性带进来的走
  队列而窗口带进来的当帧到齐。
- **端到端**：EMS.dxf 适配后 DOM 里的文字节点数为 0；放大到工作档以上文字回来；在场景树里选中
  一个适配档下被裁掉的文字，它的节点出现。
- **帧时间**记在 tasks.md，不进断言。

## 残留

- 文字的盒高阈值对多行文字偏保守（盒高随行数涨，裁得晚）。
- 一片被裁掉的小曲线在这几档从「一片点」变成空白：这是可见的差异，也是这刀的全部代价。
