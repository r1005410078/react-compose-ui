# 设计

## 决策 1：绑定是文档写入，不是资源写入

判据很简单——**看这个字段住在哪里**：

| 字段 | 住处 | 写入方式 |
|---|---|---|
| `setupScript` | `ComposePageFile` | 资源写入，不进撤销历史 |
| `activeFrameId` | `ComposePageFile` | 资源写入，不进撤销历史 |
| `Animations.source` | **ComposeDocument 的 Frame 上** | 本变更前是资源写入 ← 错位 |

前两个确实不在文档里，所以只能走页面文件写入，也因此天然带着「页面文件里的文档是上次保存
的那份」这条约束（新建场景必须先保存才能激活）。`Animations.source` 不一样：它在文档里，
却被当成页面文件字段来写，于是同时继承了那条约束**和**「运行时文档不知情」的问题。

改成文档命令后两个症状一起消失：新场景无需保存即可绑定，保存也不再需要把 source 从页面文件
补回来。副作用是绑定进入撤销历史——这是对的，它本来就是一次文档改动，和「给容器加圆角」
同类；而文件资源的创建/删除仍然不可撤销，与既有「解除引用不删除动画资源」一致。

## 决策 2：新命令而不是复用 `updateComponent`

`Animations` 是一个整体写入的 Component：只写 `source` 会丢 `items`，只写 `items` 会丢
`source`（后者正是上一轮修掉的缺陷）。让调用方自己拼完整 Component 就是把这个陷阱复制到每个
调用点。因此由 `@compose-ui/animation` 提供 `animation.source.set`，与既有清单命令同源，
两边共用同一个「保留另一半」的写入函数。

命令属于动画领域包、通过 `TransactionRuntimeOptions.handlers` 注入，与 create/delete/configure
一致；core 仍然不认识 `Animations`。

## 决策 3：先确认能绑定，再落文件

现在的顺序是「建文件 → 绑定」，绑定失败就留下孤儿。改成文档命令后绑定几乎不会失败，但顺序
仍然要倒过来才稳妥：**没有可绑定的作用域场景就直接不建文件**。这样任何前置校验失败都不会在
用户的资源目录里留下垃圾。

## 已知遗留（本变更不做）

- Store 的 `setFrameAnimation` 在编辑器里不再有调用方，只留给宿主。它继续受规范约束，
  也继续按 Frame 校验；要不要收敛成「文档补丁工具」是独立话题。
- 一块场景仍只支持一条动画。
