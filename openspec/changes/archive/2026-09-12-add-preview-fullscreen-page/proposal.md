# 预览的第二个形态：整屏

## Why

预览今天只有一个形态——模态弹框，而它回答的是「我刚改的这个，动起来对不对」。
另一个问题它答不了：**交付出去之后，它长什么样**。弹框硬上限 1280 × 820，一块
1920 × 1080 的场景在 100% 下根本放不进去；而它的交付形态是整屏。

设计稿（`docs/mockups/preview-redesign.html` 第 04、08 节）把这两个问题分给两个形态，
第 11 节的落地顺序里它们是第 6、7 步。1–5 步已经落地（`update-preview-screen-size`），
这一条接着做完 6 与 7。

顺序不能颠倒。今天 `ComposePreviewDialog` 一个文件里同时握着六样东西：目标解析、页面宿主、
播放会话、屏幕尺寸、视图缩放、全屏。照原样再加一个整屏形态，前五样会被抄第二遍，
而**抄漏的那一份，症状就是「两个预览不一样」**——而这个产品的整个卖点就是预览要可信。

## What Changes

- **抽 `ComposePreviewSurface`**（包内，不出公共入口）：目标解析、屏幕、视图、播放会话
  四样收进一处。弹框改成「Surface + 模态 chrome」，**行为逐条不变**，既有用例全绿即为通过。
- **新增 `ComposePreviewPage`**（公共 API）：Surface 铺满视口 + 静息自动隐藏的控制条。
  默认屏幕 = 实际视口、视图 1:1，因此默认就是真像素。没有时间轴。
- **两个形态之间的桥**：弹框上新增一颗「整屏预览」，由宿主接管路由；返回时回到原来的
  场景、屏幕尺寸与播放头。**必须同标签页**——「页面预览必须包含未保存的改动」是既有硬规则，
  新标签页读不到编辑器手上的 live 文档。
- **「在新标签页打开」是次级动作**：仍然给，但它 MUST 先落盘，并且这件事 MUST 写在按钮上，
  而不是静默地给出上次保存的那一份。它由宿主实现——只有宿主知道怎么落盘、URL 长什么样。
- 示例应用接上路由（`history.pushState` + `popstate`，编辑器不卸载）与这两颗按钮。

**不在本变更内**：页面底色选择器与时间轴刮擦（第 11 节第 8 步），它们各自独立，排在本变更之后。
`ComposePreviewSurface` 保持包内私有——它是两个形态的共同实现，不是给宿主的 API。

## Impact

- `@compose-ui/preview`：新增 `ComposePreviewPage` 公共导出；`ComposePreviewDialog` 新增两个
  可选 prop（整屏动作、次级动作插槽），不传时行为与今天完全一致。
- `app/`：新增预览路由与两颗按钮。
- 规范：`compose-preview` 新增三条需求（整屏预览形态、两个形态共用同一层实现、形态之间的切换）。
- 不动文档协议、不动 `core`、不动任何既有公共 API 的签名。
