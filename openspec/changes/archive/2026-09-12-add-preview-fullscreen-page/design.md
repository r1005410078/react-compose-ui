# 设计

## 上下文

设计稿：`docs/mockups/preview-redesign.html`，第 04 节（两个形态）、第 08 节（整屏设计稿）、
第 10 节（Surface 的职责划分）、第 11 节（落地顺序第 6、7 步）。

既有约束（都已写进 `AGENTS.md` 或 `specs/compose-preview`）：

- 页面预览必须包含未保存的改动（`livePage` 不经 loader）。
- `@compose-ui/preview` 不依赖 `editor`、`stage`、`pages`，也不依赖任何组件库。
- 显式 `frameId` 按约定不回退，因此页面模式下只传用户的显式选择。
- 屏幕尺寸与视图缩放是两份互不影响的状态；视图缩放走 `transform` 不走 `zoom`。

## 目标 / 非目标

**目标**：让「交付出去长什么样」这个问题有一个能回答它的形态，并且它与弹框**由同一份实现产出呈现**。

**非目标**：页面底色选择器、时间轴刮擦、把 `ComposePreviewSurface` 做成公共 API。

## 决策

### Surface 是一个 Hook 加一个渲染组件，不是 render prop

`useComposePreviewSurface(options)` 持有全部会话状态（目标、屏幕、视图、播放），返回一个
value 对象；`<ComposePreviewSurface value={…} />` 只负责把台面、画板与屏幕画出来。
两个 chrome 各自调用这个 Hook，再把同一个 value 同时交给 Surface 组件与自己的控件。

**不用 render prop 或 slot**：chrome 要读的是「当前页 + 当前场景 + 可选场景列表 + 屏幕 + 视图」
这一整份状态，用 children-as-function 会让每一颗按钮都埋在一层回调里；而做成「Surface 持有
状态、经回调上报」会造出一个逐帧回传的协议——那正是命令会话状态留在 Stage 自己手上的理由。

**不导出**：它是两个形态的共同实现，不是宿主要用的东西。仓库规则是「内部实现默认不导出」，
而一旦导出，两个形态的呈现就可能被第三方 chrome 绕开，「两个预览一样」这句话就不再成立。

### 整屏的默认屏幕是「实际视口」，不是场景尺寸

弹框的默认屏幕 = 目标自身尺寸（因此默认 1:1 但常常放不下）。整屏反过来：默认屏幕 = 浏览器
视口本身，视图 1:1，于是**默认就是真像素**——这正是这个形态存在的理由。用户仍然可以挑一档
别的分辨率，那时就在真屏幕里套出那块屏、四周留黑。

「实际视口」是一档**会跟着窗口变**的取值，因此它不是一个尺寸值，而是一个模式：
`screen: { kind: 'viewport' } | { kind: 'fixed', size }`。做成「打开时量一次视口存成固定值」
的症状是拖动窗口之后读数还写着旧的数，而屏幕上已经变了。

### 桥由宿主接管路由，`preview` 只发请求

弹框拿到可选的 `onRequestFullscreenForm` 时才画那颗按钮；按下只是发出请求，**路由是宿主的事**
——`preview` 不认识 URL，也不该认识。返回同理：整屏形态的「返回编辑器」发
`onRequestExit`，宿主决定退到哪里。

「回到弹框原来的场景、屏幕尺寸与播放头」因此是**宿主把这三样传下去**而不是 `preview` 自己
记着：宿主是唯一同时看得见两个形态的人，而让 `preview` 跨形态记状态需要一个两边都挂着的单例。
本变更给出的形式是：切换请求带上当前的 `{ frameId, screen, playheadMs }`，宿主原样回传给另一个形态。

### 「在新标签页打开」不由 `preview` 实现

它要知道两件 `preview` 不知道的事：怎么落盘，以及 URL 长什么样。因此弹框只提供一个
**次级动作插槽**（`secondaryActions`），宿主把自己的按钮放进去。

设计稿要求「要先落盘，并且这一点在按钮上说清楚」——这是一条对**宿主**的要求，写进规范里，
由示例应用兑现：有未保存改动时按钮标明「保存并在新标签页打开」，没有时才是「在新标签页打开」。
静默给出上次保存的那一份是这条要求明确拒绝的做法。

### 控制条静息即隐，判据是指针有没有动过

零 chrome 是整屏存在的全部理由，因此控制条默认不画，指针移动时浮出、停两秒隐去。
键盘用户不会移动指针，所以**任何键盘焦点进入控制条时它必须保持可见**，且 `Tab` 能把它唤出来
——只按指针隐藏会让控制条对键盘用户永远不存在。

`Escape` 与浏览器返回键同样退出（设计稿第 08 节 pin 5）：零 chrome 意味着没有可见出口，
出口必须有多条。

## 风险

- **抽 Surface 是纯重构，但它动的是整个对话框**。判据是既有 69 条用例全绿且逐条不改——
  任何一条用例需要改写，都说明行为变了，那就不是第 6 步该做的事。
- 整屏形态没有既有用例，因此它的行为要靠新用例钉住，尤其是「默认真像素」与「控制条对键盘可达」。

## 待解决问题

- 整屏形态下 `Interaction` 的 `navigate-back` 与**浏览器返回键**同时存在，两者退的是不同的栈
  （预览内返回栈 vs 宿主路由栈）。本变更让浏览器返回键退出整屏形态；预览内返回栈仍由
  `navigate-back` 承担。把两者合并需要宿主把导航会话接进 History API，那是另一件事。
