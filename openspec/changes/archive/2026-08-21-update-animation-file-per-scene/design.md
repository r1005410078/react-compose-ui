# 设计：动画文件默认按场景独立

## 上下文

- `Animations.source` 是挂在每个根 Frame 上的独立文档字段；打开页面按 assetKey 去重
  逐文件加载（`use-page-workspace.ts` 的 `listFrameAnimationSources` + 水合循环），保存按
  assetKey 分组逐文件合并回写（`mergeFrameMirrorsIntoFiles`）。**读写基础设施天然支持
  多文件**，把"一页一份"钉死的只有编辑器创建路径里的引用复用逻辑。
- 绑定认 assetKey 不认文件名（协议要求 assetKey 在 rename/move 后稳定），因此文件名
  纯粹是显示名，命名策略不承担身份职责。
- 页面配置面板当前只渲染一行动画绑定（当前动画作用域场景的），数据模型却是 per-Frame
  的——UI 隐藏了真实结构。

## 目标/非目标

- 目标：新建动画默认一场景一份文件；页面配置面板逐场景如实呈现绑定；保存按文件聚合
  回写并报告部分失败。
- 非目标：不改动画文件格式（`frames` 分区表原样保留）；不改 `animation.source.set`
  命令；不迁移既有共享文件页面；不提供"共享文件拆分"工具；不改动画模式时间线的
  作用域规则。

## 决策

- **决策：文件命名取「`<页面名>-<场景名>.animation.json`」，冲突追加序号。**
  只用场景名会在同目录多页面时撞名；页面名前缀让文件在资源目录里自然按页面聚簇。
  场景改名不追改文件名——身份在 assetKey 上，追改只会引入一次多余的资源写入和冲突面。
  - 考虑过的替代方案：只用场景名（多页面同目录撞名概率高）；场景 id（对用户不可读）。
- **决策：既有共享文件不迁移，混合状态合法。** 协议本来就允许一份文件承载多块场景
  分区，旧页面继续原样工作；用户解绑后重建即可逐步过渡到独立文件。自动拆分需要删改
  用户资源目录里的文件，风险大于收益。
- **决策：保存放弃跨文件原子性，改为逐文件写入 + 部分失败显式报告。** 文档镜像是权威，
  某份文件写失败后下次保存会重试补齐；为 N 份小 JSON 实现两阶段提交不成比例。
- **决策：页面配置面板的动画分组按 `rootIds` 顺序逐场景渲染行，仍是共享 Property Panel
  Root 中的一个 Section。** 每行 = 场景名标签 + 绑定字段（绑定/更换/解绑/创建）；已绑定
  行提供该场景动画的播放控制变量绑定入口（复用既有绑定入口与 setup 作用域候选）。
  激活场景与当前动画作用域场景在行上标注——两者可能不同，面板正是解释这件事的地方。

## 风险/权衡

- 保存从一次写变最多 N 次写，跨场景轨道搬迁（`animation.tracks.relocate`）会同时改
  两份文件，第二份失败留下中间态 → 逐文件冲突/失败提示 + 文档镜像权威 + 下次保存补齐。
- 删场景/撤销建场景产生孤儿动画文件 → 与既有"解除引用不删除文件资源"规则一致；
  逐场景绑定列表让孤儿可见、可手动解绑清理。
- 根场景很多时面板变长 → 按 `rootIds` 顺序平铺即可，大屏项目根场景通常个位数，
  不提前引入折叠/虚拟化。

## 迁移计划

无数据迁移。行为切换随版本发布即时生效：新建动画走独立文件，旧页面共享文件照常
加载保存。回滚只需恢复创建路径的引用复用逻辑，已产生的独立文件仍是合法绑定。
