# 设计：缩放手柄的尺寸读数

## 1. 八个手柄一条规则

原点 = 与手柄对角的那个角；落点 = 手柄那一侧的角。两者都取自**新**包围盒，
`composePointToFields('cartesian', 落点, 原点)` 因此恒等于新包围盒的 `(宽, 高)`。

举两个端点验证这条规则真的统一：

- 左上角手柄：原点 = 新盒的右下角，落点 = 新盒的左上角 → `(宽, 高)` ✓
- 右边手柄：原点 = 新盒的左上角，落点 = 新盒的右下角 → `(宽, 高)` ✓，其中高在本次拖动中不变

**两点都取自新盒而不是冻结盒**：`alt`（从中心缩放）下冻结盒的对角**会动**——那一档固定不动
的是中心而不是任何一个角。取新盒的对角在两种情形下都给出宽高，且没有 `alt` 时它本来就等于
冻结盒的对角。按冻结盒写的症状是 `alt` 下读数悄悄变成另外两个数，而它只在按着那个键时出现。

**边手柄下那个不动的数照画**，MUST NOT 按手柄种类分流。两条理由：

1. 用户在改的是**盒**，盒的自然量纲是宽和高，两个数一起才回答「它现在多大」；
2. 等比约束（Entity 声明 `preserve-aspect`，或按住 `Shift`）一开，边手柄同样会改另一个轴。
   按「这次动不动」决定画不画，会让同一个手柄的读数时有时无，而屏幕上没有东西解释为什么。

这一条**不与**「一个永远不影响结果的只读字段比没有更差」冲突。那条规则的对象是**可键入的
动态输入里的一个字段**，理由有两半——占着屏幕、占着 `Tab` 的一个去处却什么也不回答。读数
没有 `Tab` 这一档，而前半句不成立：它回答的正是「现在多高」。被那条规则否掉的是矩形的角度，
那个数**恒为 0**，任何时候都不回答任何问题。

## 2. 为什么是只读，以及为什么这次不会被当成输入框

`resolveStageDynamicInput` 的框尾标记已经承担了「这里能不能打字」这件事：`active` 挂光标条、
`locked` 挂锁、`idle` 什么都不挂。读数的两个字段恒 `idle`，因此没有光标条——而光标条正是那个
记号。

这一点必须明写，因为它踩在本仓库自己的一条判断上：**两个东西长得一样而按下去做的事不同，
是最难自己发现的一类缺陷**（夹点按角色分三种形状就是这条）。这里的解法是复用既有的标记派生
而不是新造一套视觉——新造一套的代价是同一件事在屏幕上有两种说法。

「按住鼠标的同时用另一只手打字」在 AutoCAD 里之所以自然，是因为它的夹点编辑根本不按着按钮：
点一下夹点它变热、松开、移动光标、打数字、再点一下落位。本仓库的夹点会话已经复刻了这一档
（「松手时一步没动则会话留着、夹点点亮」），因此**给缩放手柄补可键入的正确路径是补「点亮」
态**，而不是想办法在按住的时候接键盘。那是独立的一条。

## 3. 上报走快照，而不是让渲染层反推

新增 `resizePreview: { origin, point } | null`，与 `rotationPreview` 同构。

渲染层 MUST NOT 自己反推手柄：手柄是插件内部状态，而预览期间选区框上八个手柄的位置**都在动**，
从包围盒的变化反推「拖的是哪一个」在等比约束下无解（等比时角手柄与边手柄改出的新盒可以完全
相同）。

值天然是**吸附解算之后**的：`nextBounds` 由 `snapResizePoint` 的结果推出，因此照抄它就满足
「与选区框、参考线同一个值」。读裸指针的症状是开着网格时框里的数与选区框对不上。

## 4. 两个来源构造上互斥

动态输入层同一时刻至多一个来源，两者不可能同时成立：

- 命令等着取点时，取点插件（优先级 1650）**在任何命中类型上都接管** `pointerdown`，
  缩放手势起不来；
- 缩放手势进行中指针已被捕获，命令开不起来。

因此实现是 `draftingSession.dynamicInput ?? resizeReadout`，MUST NOT 叠加渲染。写成叠加的话，
将来任何一侧放宽了接管条件，屏幕上会出现两组框而没人知道该信哪一组。
