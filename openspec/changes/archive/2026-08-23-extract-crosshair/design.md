# 设计：十字光标下沉

## 1. 组件是一个 `<g>`，不是一层 overlay

两块画布都已经有自己的 SVG 图层（CAD 是图面本身，Stage 是绘图覆盖层），把十字光标做成独立
overlay 会多一层定位与 `z-index` 要各自对齐。做成受控 `<g>` 之后，摆在哪里由调用方决定——
与标尺那条「只提供画布元素自身的样式，不规定自己坐在哪里」是同一个判断。

样式同理：本包给笔（描边色、线宽、不透明度、`fill: none`），不给位置。

## 2. 输入是两个布尔，不是 `prompt`

`accepts` 属于命令协议（`@compose-ui/commands`），而 canvas-kit 不能依赖它——这条边界由包
依赖承载，边界用例会把它挡下。因此组件收的是**画线**与**画框**两个布尔，由
`prompt.accepts` 推出它们的那一步留在各自的画布包里。

这条边界顺带保住了一处**刻意的不对称**：CAD 空闲时线与框都画（AutoCAD 惯例），Stage 空闲
什么都不画（页面编辑器的静息光标是箭头）。两边的推导规则不同，而共享组件不需要知道。

## 3. 解析函数是「是否在画」的唯一判据

```
resolveComposeCanvasCrosshair(input) → ComposeCanvasCrosshair | null
```

返回 `null` 的四种情形：宿主关掉了、指针是 touch、指针不在图面上、两个形态布尔都是 false。

调用方拿同一个返回值做两件事：传给组件，以及决定要不要给容器挂上隐藏系统光标的标记。
**两处各判一次必然漂移**，而漂移的样子正是 Stage 今天的样子——画了十字线，系统箭头还在。

`pointerType` 进解析函数而不是留给调用方：触摸豁免是一条不能分头实现的规则，而「不画」与
「不隐藏系统光标」必须同时成立。

## 4. 十字光标钉在解算后的落点上

`cad-document` 规范早就写了这一条，CAD 的实现却取了裸指针（`indicated.screen`）；同一个
`CadIndicatedPoint` 上，橡皮筋终点、坐标读数与捕捉标记取的都是 `indicated.world`。开着栅格
吸附时，用户看见的十字线停在他不会落笔的地方。

本刀把 CAD 改成传 `cadWorldToScreen(viewport, indicated.world)`。**这是本刀唯一一处 CAD 行为
变化**，其余用例一行不改即全绿——那正是「搬运没有改变行为」的证据。改动会让既有的
`reach()` 夹具读到栅格吸附后的中心，因此那几条用例的落点要按吸附后的值取，断言本身不变。

## 5. Stage 的拾取框不参与命中判定

CAD 的拾取框半边长等于点选命中容差，因此「框压住了就点得中」在那边成立。**Stage 没有那个
数**：它的点选是 DOM 驱动的（浏览器决定命中），容差散在各物料的 stroke 宽度里。

所以 Stage 的拾取框只表达**靶区在哪里**，不表达「压住了就命中」。这条不对等要写进规范：
留给下一个人去猜的话，他会去找那个不存在的全局容差，或者更糟——为了让框「准确」而去发明一个。

拾取框本来就不表达「当前是否命中」（那由图元自身的悬停高亮回答），因此这条限制没有削弱它
在 Stage 上的作用。

## 6. testid 前缀由调用方给出

与标尺一致。CAD 传 `cad` 得到 `cad-crosshair` / `cad-pickbox` 与 `data-cad-crosshair-line`，
既有用例因此一行不改；Stage 传 `stage`。

线元素带属性标记而不是只靠 testid：一副十字是四条线（两轴各两个方向），用 testid 逐条区分
没有意义，而「有几条线」正是形态断言要数的东西。
