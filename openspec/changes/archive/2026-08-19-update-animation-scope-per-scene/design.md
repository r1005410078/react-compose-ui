# 设计

## 决策 1：脚本保持页面级，动画按场景——这个不对称是设计，不是遗漏

评估过「脚本是否也要按场景分」，结论是**不分**，依据如下。这一条写在这里，是为了让后来者
不要把它当成没做完的一半：

1. **协议形状本来就不同。** `setupScript` 是 `ComposePageFile` 上的单个字段；
   `Animations.source` 在 Frame 的 Component 上。规范只对动画写了「多个根 Frame 各自绑定」。
2. **绑定是页面级平坦命名空间。** `ComposeRendererPropsBindings.fields` 映射的是「页面返回
   成员」，按名字解析。脚本按场景切分后，把一个 Entity 从场景 A 拖到场景 B 会静默打断它的
   绑定——多出一整类没有修复机制的悬空引用。
3. **动画自己就依赖共享脚本。** 动画的播放绑定解析 `scope.getExport(exportName)`，即页面
   作用域。「动画按场景 + 脚本共享」正是这套设计成立的前提；两边都按场景分会把这条链打断。
4. **与 Rive 的分法一致。** ViewModel／数据绑定是文件级共享，动画与状态机按 artboard。
   本项目的 setup script 对应前者。
5. **AGENTS 里「脚本作用域以 Frame 为界」指的是嵌套文档。** Page Slot 的 renderer 对每个内嵌
   页面单独建 scope，组件实例同理——那是「另一份文档带自己的脚本」，不是「同一页里每块根
   场景各有一份」。

## 决策 2：一页一份动画文件，按场景分区

备选是「每块场景一个文件」。选单文件的理由：

- 不需要发明命名策略。每场景一文件必须回答「第二块场景的文件叫什么」，无论带场景名（场景
  改名后文件名不跟着变）还是带序号（看名字认不出属于哪一块）都有明显缺点。
- 文件数量不随场景数增生，资源面板不会被同名近似的动画文件淹没。
- 保存回写是一次写入而不是 N 次，不存在「写到第二个文件时失败」的部分成功。

代价是文件内多了一层按 frameId 的索引，且该索引与文档 Entity id 耦合。这层耦合本来就存在
（`Animations.source` 就挂在 Frame 上），因此不是新增的约束。

引用**仍然逐 Frame 保存**：一块场景解除绑定不应牵动其他块。`pages` 规范里「各自绑定不同的
动画文件」相应放宽为「MAY 指向同一个文件」——原意是「不得退回页面级单一 `animation` 字段」，
这一点不变。

## 决策 3：水合时机——单文件让「惰性」失去意义

产品意图选的是「切到哪块载哪块」，那是在「每块场景一个文件」的前提下问的：惰性能省掉没在看
的场景的 IO。改成一页一份文件后，读文件只有一次，惰性省不下任何 IO，只会把「切场景时可能
出现未水合状态」这个额外状态引进来。

因此本变更采用：**打开页面读一次文件，把各分区一次性水合进各自 Frame 的镜像**。
现有的「载入绑定动画」手动入口保留，用于文件在会话期间被外部改动后的重新载入。

如果后续真的出现超大动画文件需要延迟解析，再单独提案，不在此处预留开关。

## 决策 4：时间线跟随选中所属场景

`resolveTargetFrameId(document, selectedIds, activeFrameId)` 正是为此而写的：选中优先、
没有选择时回退 `activeFrameId`。这与 `多画板下的 Frame 动作目标` 规范一致，也意味着
「哪一块会被发布」（`activeFrameId`）与「正在编辑哪一块的动画」可以不同——后者跟手，前者是
显式声明。

代价：在场景 A 打点时误点了场景 B 里的东西，时间线会跳。缓解办法是时间线头部始终显示当前
作用域场景名，让跳转可见；这条写进 `editor-workspace-layout` 的增量。

## 已知遗留（本变更不做）

- 一块场景仍只支持一条动画（`Animations.items[0]`）。多动画选择是独立提案。
- 跨场景复制实体时如何处理它的关键帧轨道，沿用现有 `animation.tracks.relocate` 语义，本变更
  不扩展。
