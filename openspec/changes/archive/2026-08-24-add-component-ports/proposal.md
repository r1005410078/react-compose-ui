# Entity 端口

## Why

**步骤 11 是两件事，中间有一条干净的缝。**端口是「符号身上有哪些可以接线的点」，导线是「两个
点之间那条会跟着走的线」。前者一落地就自己站得住——画线时能精确吸到刀闸的接线柱上，这本身就是
实施工程师每天要做的事；后者要动文档协议、求解时机与删除语义，是另一份账。8a/8b 拆过一次，
同一条判断在这里再用一次：**先把端口做完，导线在它上面盖**。

现状：接线柱在符号上是画出来的一段线，因此画线时**能吸到的只是那段线的端点**。符号一旦改画法
（把接线柱从一条短线换成一个小圆），原来的吸附点就没了，而图纸上没有任何东西说过「这里是接
线点」。端口就是把这句话写进文档。

## What Changes

- **`Ports` 是可选 Entity Component**（core），`items` 是 `{ id, position }` 的列表，`position`
  是 Entity 局部坐标。**它挂在任意 Entity 上**——与 `Interaction` 是同一条判断：端口是 Entity
  的能力，不是组件库的能力。画一个矩形给它两个端口，与用一个组件实例，在下游是同一件事。
- **组件实例的端口从离线快照读出，不复制**：组件根 Frame 上声明一次，全部实例都有。读取只有
  一个入口且住在 `core`，因此捕捉一侧不需要认识组件协议——8a 那条「命中与捕捉路径读的字段必须
  是文档级契约」由**入口的归属**满足。**原本写的是镜像**，实现时改掉了：镜像要在创建与每一次
  刷新快照的地方各写一遍，而刷新走的是 `setRendererProps`，漏一处的症状是「端口停在符号搬走
  之前的位置」，看起来像捕捉坏了而不是同步坏了。
- **端口进特征点捕捉，优先级排在端点之前**，与 CAD 的 `CAD_SNAP_MODES` 一字不差。理由也一样：
  端口几乎总是画在符号线段的端点上，端点若在同等距离下胜出，用户会画出一条**像素级正确但没有
  绑定**的导线——而这个错误在屏幕上完全不可见。绑定要等 11b，但**捕捉的次序必须现在就定对**，
  否则 11b 落地时用户的肌肉记忆已经错了。
- **端口经 Inspector 声明**：`Ports` 的内建 Component Inspector，走既有的
  `entity.component.update`，不新增命令。
- 变体覆盖端口**不需要任何新机制**：端口是根 Frame 上一个 Component 的字段，`set-field` 覆盖
  它本来就合法。

## Non-Goals

- **不做导线**（11b）：`Wire` Component、`WIRE` 命令、求解不存储、删除时端点冻结、以及
  「导线与它绑定的实例必须同父级」那条约束，全部留给下一刀。
- **不画端口标记。**CAD 也不画——端口在图面上不可见，是捕捉标记在光标靠近时把它显出来。
  在这里跟随同一个选择：画标记要新增一层 overlay 与一条「什么时候显示」的规则（只在选中时？
  只在取点时？），而这条规则的正确答案要等导线画起来才看得出。Inspector 里列得出端口。
- **不给端口名称或方向**（输入/输出/双向）。CAD 的 `CadPort` 只有 id 与位置，注释写着理由：
  面向用户的名称眼下没有任何消费者。方向同理——没有任何一条规则会读它。
- **不做端口的画布拖拽**。步骤 10 刚把夹点通道铺好，端口拖动理应复用它，但那要回答「组件文档
  里选中根 Frame 时显示的是端口还是几何」，而那个问题在导线落地之前没有足够的信息。
- **不动对齐吸附**。端口是**显式声明**的第三类候选，与「盒角点不出候选」那条不冲突——那条挡的
  是从盒**推**出来的点。

## Impact

- 包：`core`、`stage-engine`、`materials`
- Specs：`compose-document`（ADD 2）、`stage-engine`（MODIFY 1）、`basic-materials`（ADD 1）
- 破坏性：无。`Ports` 缺席即今天的行为；`StageFeatureSnapMode` 增一个成员 `'port'`，既有消费者
  按联合类型处理。
