# 设计：Entity 端口

## 1. 为什么把步骤 11 切成两半

| | 端口（本刀） | 导线（11b） |
| --- | --- | --- |
| 协议 | 一个可选 Component，缺席即今天 | 一个 Component **加**一条求解管线 |
| 求解 | 无——位置就是位置 | 求解不存储，还要与布局求解的帧序对齐 |
| 删除语义 | 无 | 被绑定的实体删掉时端点要冻结 |
| 落地即可用 | ✅ 画线能吸到接线柱上 | 依赖端口 |

**捕捉次序必须在本刀定对**：端口排在端点之前这一条，等 11b 再改就晚了——用户会先学会「吸到的
是那段短线的端点」，而那正是 11b 要防的错误。

## 2. 端口是 Entity 的能力，不是组件库的能力

`Interaction` 立过这条：跳转能挂在矩形、图片、容器上，因此它是 Entity Component 而不是某个物料
的属性。端口同理——画一个矩形给它两个端口，与放一个组件实例，在捕捉、校验与将来的导线求解眼里
必须是同一件事。这也让**端到端用例不必先造一个组件资产**才能验证捕捉。

`position` 是 **Entity 局部坐标**（盒左上角为原点），与 `Curve` 的盒局部几何同一个空间，因此
换算复用同一个世界矩阵，不需要第二套投影。

## 3. 实例上的端口是镜像，不是从快照里读出来的

组件文档的根 Frame 带 `Ports`；实例创建与刷新时把它**复制**到实例 Entity 上，与
`resolvedSnapshot` 同一处写入、同一生命周期。

**为什么不直接读 `resolvedSnapshot`**：那是 Renderer 的 prop，只有 `materials` 认识它
（`readComponentInstanceAnimations` 就是这么做的）。而捕捉住在 `stage-engine`，它不依赖
`materials`，也不该为了读一个点去认识组件协议。8a 立下的边界正是这一条——**命中与捕捉路径读的
字段必须是文档级契约**，曲线的填充因此住在 `Appearance` 而不是 Renderer prop。

镜像会随组件改动而过期，这与 `resolvedSnapshot` 完全同构，由既有的 Apply/Revert chrome 兜底；
不为它新造一套失效机制。

## 4. 捕捉：第三类候选，优先级最高

```
port > endpoint > midpoint > center > quadrant
```

与 `CAD_SNAP_MODES` 一字不差。端口几乎总是画在符号线段的端点上，两者常在同一个像素上；端点
若在同等距离下胜出，用户会画出一条**像素级正确但没有绑定**的线——屏幕上看不出任何差别，要等
到移动符号时才发现线没跟着走。

**这不是「优先级先于距离」的例外，而是它的第一次真正生效**：既有的四种候选里，端点与中点几乎
不会落在同一个点上，因此那条规则一直没被检验过。

候选来源因此从「只来自带 `Curve` 的 Entity」放宽成「带 `Curve` 或带 `Ports` 的 Entity」。
与「盒角点不出候选」不冲突：那条挡的是从盒**推**出来的点，而端口是作者**显式写下**的。

## 5. 校验

- 同一个 Entity 内端口 id MUST 唯一——id 稳定是 11b 绑定不断的前提，重复 id 会让绑定指向
  「其中一个」，而运行期没有正确答案。
- 位置必须是有限数。
- 空 `items` 的 `Ports` 是**非法**的：一个不带任何端口的端口声明读不出意图，与曲线外观
  「三项全清就整个删掉 Component」是同一条判断。
