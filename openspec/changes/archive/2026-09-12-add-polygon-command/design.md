## 上下文

AutoCAD 的 `POLYGON` 是这次调研的对象，官方命令参考给出的提示序列是：

```
Command: POLYGON
Enter number of sides <4>:
Specify center of polygon or [Edge]:
Enter an option [Inscribed in circle/Circumscribed about circle] <I>:
Specify radius of circle:
```

要点：产物是**等边闭合多段线**（LWPOLYLINE）；边数 3–1024，默认值记在系统变量 `POLYSIDES`
里并随图纸保存；**内接**指全部顶点落在圆上，**外切**指各边中点落在圆上；拾取半径同时决定
大小与旋转，而**键入**半径只给得出大小，因此 AutoCAD 规定「底边按当前捕捉旋转角画」。

本仓库这一侧的既有件全部就位：`@compose-ui/commands` 的四态推进与关键字、`radius` 单字段
参数化、`measured`、`preview(point)`、点输入管线（键入 > 捕捉 > 网格 > 角度约束）。约束是
「不新增协议字段」与「不为一条命令另开一套机制」。

## 目标 / 非目标

- 目标：把上面三个问题映射到三步会话；产出普通闭合多段线，因此几何编辑、填色、外观动画与
  数据绑定全部沿用曲线既有那套，不写任何新代码。
- 非目标：`Edge` 分支、单键快捷键、边数的光标旁数值框、裸滚轮、边数的持久化、星形与
  圆角多边形。理由见 `proposal.md`。

## 决策

### 决策 1：内接/外切是第一步上的一个档位字段，不单独占一步

> **本条经评审改过一次。**原先它是半径步上的 `I`/`C` 关键字，理由是「那时形状已经在跟着光标
> 转，答案是看出来的」。评审要求把它挪到边数旁边、并在后两步收干净。挪过去之后有两处要跟着
> 改：档位必须被**印出来**（否则又变回一份看不见的状态），以及它因此可以跨命令记住。

- **内容**：第一步同时问边数与档位，两者并排印在光标旁（`cursorInput`：数值框 + 圆头胶囊），
  `Tab` 换档、命令行的 `I`/`C` 是它的第二个入口。中心步与半径步**既不显示也不受理**。
- **原因**：它不是一道拦路的问题，而是第一步上一个**已经有值**的字段——直接确认就走。
  AutoCAD 那个做法被诟病的是「先问、且必须答」，不是「问得早」。
- **代价写在明处**：拿主意的时候屏幕上还没有形状。补偿有两条——不拦路，以及档位跨命令记住，
  选错重来一次只需按一下 `Tab`。
- **后两步必须收干净**：半个残留比全留或全删都糟。一个还印着却按不动的读数，用户按一下没
  反应会以为这条能力根本不存在；而列不出来却仍然受理，等于留一条只有读过源码的人才知道的
  暗门，与「命令行是这条能力唯一的说明书」直接冲突。判别性用例因此断的是「按了也不起作用」
  而不只是「没列出来」。
- **考虑过的替代**：照抄独立一步（多按一次回车，换来一个更差的提问时机）；留在半径步
  （评审否掉）；两处都能换（评审否掉——那会让同一件事有两个时机，而第一步那个已经够了）。
- **先例**：`CIRCLE` 的 `D`/`R` 仍然是这个形状的来源，「只列出能切过去的那一个」原样搬过来；
  **只有「不跨命令记忆」那一半没搬**，理由见决策 2 的同一条判据。

### 决策 1a：档位是圆头胶囊，不是第三个数值框

- **内容**：`variant: 'chip'` —— 圆头、永不出光标条、带一个 `⇥` 换档标记；`Tab` 直接派发
  `toggle.keyword`，**不参与字段轮转**。
- **原因**：档位是二选一，不是能键入的数。做成第三个方框、让 `Tab` 在框之间走，会把焦点带到
  一个打不了字的地方。形状先分开、颜色再分开是这块画布的既有规矩——两个控件长得一样而按下去
  做的事不同，是最难自己发现的一类缺陷。
- **`Tab` 的两种含义互斥，由构造保证**：有两个数值字段的步不声明 `toggle`（那一档归锁定），
  声明了 `toggle` 的步没有第二个数值字段。写成互斥的两支而不是一个优先级，是因为「同时成立时
  听谁的」在屏幕上没有可解释的答案。
- **胶囊文案与关键字标签分开**：标签进命令行的方括号（「外切(C)」，说的是**切过去**会得到
  什么），胶囊说的是**此刻**是哪一档。两处同一个词会让「外切」在屏幕上同时表示当前值与目标值。
- **框宽估算要认全角**：`DYNAMIC_INPUT_CHAR_WIDTH` 是拉丁字的前进宽度，「内接」宽近两倍，
  不认的症状是文字被框边压住。纯拉丁文本的宽度逐字节不变，既有用例因此不受影响。

### 决策 2：默认边数记在本次编辑会话，且必须印在提示里

- **内容**：`输入边数或指定中心点 <6>`，直接确认取用；上一次用过 8 就变成 `<8>`。
  不写文档、不持久化。**档位同判**（见决策 1）：它印在光标旁的胶囊里，因此同样跨命令记住。
- **原因**：这看起来与「`CIRCLE` 的档位不跨命令记忆」冲突，其实不。那一条的理由是**看不见的
  状态**——「用户过两天回来，同一条命令问的问题变了，而屏幕上没有任何东西解释为什么」。
  边数的默认值就写在提示里，屏幕上说了这件事，因此那条理由不适用。
- **推论**：默认值 MUST 印在尖括号里不是文案偏好，而是这条记忆能够成立的**前提**。哪天提示
  不写它了，记忆就必须一起去掉。
- **首个默认取 6**：四边形有 `RECTANGLE` 这个更快的入口，AutoCAD 的 4 在这里不成立。

### 决策 3：不实现「键入半径时底边水平」

- **内容**：键入半径只改半径，相位仍然由当前落点的角度给出。
- **原因**：AutoCAD 那条规则是对「键入的数值不携带方向」的补偿，而本仓库的裸数字走
  `applyComposeFieldOverride`——它从当前落点出发只替换**活动**字段，另一个分量保持不变；
  `radius` 与 `polar` 的数学逐字相同，第二个分量就是角度。于是「拖出一个大概的朝向，再打
  一个精确的半径」自然成立，一行特判都不用写。
- **已知边界**：指针从未进入图面时没有活动落点，裸数字够不着字段。这是 `CIRCLE` 今天就有的
  行为，本变更不为它新增特例——此时用完整坐标写法。

### 决策 3a：第一步收点，让十字光标真的能落点

- **内容**：第一步 `accepts` 含 `point`，收到点即取用当前边数与档位并把该点当作中心，直接进
  半径步。
- **原因**：十字光标在这一步是画着的，而「屏幕上不该出现一个鼠标动了也没反应的状态」。把它
  画成装饰是这条判据的反面；让它真的能落点还顺带省掉一次点击。
- **两条通道不撞车**：键盘走文本（裸数字是边数），指针走点。这一步**没有参考点**，直接距离
  输入无从谈起，因此裸数字只可能是边数。

### 决策 4：第一步用 `text`，宿主补一条从未走过的路由

- **内容**：边数步声明 `accepts: ['text']`；命令行在「接受 `text` 而不接受 `point`」时把
  非空文本原样以 `{ kind: 'text' }` 交给会话。
- **原因**：`ComposeCommandInputKind` 里的 `'text'` 一直定义着却从来没有生产者。不补的后果
  是**静默走错分支**——`6` 解析不成坐标、这一步又没有 `fields`，于是掉进最后那条兜底变成
  `{ kind: 'keyword', key: '6' }`。会话当然收得下，但命令行会把它渲染成一个**可点的关键字**，
  而关键字是一份枚举，边数不是。
- **边界**：宿主不解析也不校验这段文本。「3 到 1024 的整数」是命令自己的规则，放在宿主等于
  让同一条规则有两处来源。
- **考虑过的替代**：给协议加一种非点数值字段，让边数也有光标旁的输入框。眼下只有这一个
  消费者，而 `fields` 的语义是「这一步的**点**怎么参数化」，扩它要重新定义那个词。

### 决策 5：几何住 `core/curve-geometry.ts`

- **内容**：正多边形顶点求解放进既有的平面形状运算模块。
- **原因**：沿用那条既有判据——**整个模块放在一起而不按消费者拆**。把它放进 `stage-engine`
  的命令文件里，会让「弧、多段线、正多边形」的数学横跨两个包。

### 决策 6：边数用 `+` / `-` 关键字，滚轮是它的第二个入口且必须带修饰键

- **内容**：`+` / `-` 各增减一条边，在边数步与半径步两步都可用、都列进 `keywords`；
  `Alt` + 滚轮转成这两个关键字喂给会话。半径步的提示显示当前边数。
- **为什么是关键字而不是第五种输入**：滚轮增减 MUST NOT 推进状态机。这正是 `preview` 被设计
  成**查询**而不是输入的那条理由——「`advance` 是状态机，每帧一次 `pointermove` 就推进一次会让
  『取了几个点』跟着鼠标动」。关键字本来就是「改变后续流程但不取点」的那一档（`CIRCLE` 的
  `D`/`R` 就是这样），复用它一个字段都不用加。
- **为什么要列出来**：滚轮是一个不可发现的手势。列进 `keywords` 之后可点、可敲、可滚轮，
  三条路一个语义一份实现，而命令行是这条能力唯一的说明书。
- **为什么两步都生效**：只在半径步生效的话，用户在边数步试一下没反应，会以为这条能力不存在
  ——而「屏幕上不该出现一个鼠标动了也没反应的状态」。边数步上它改的是尖括号里的默认值，
  那个数就在屏幕上，因此同样有可见反馈。
- **为什么必须带修饰键**：裸滚轮是画布平移、`Ctrl`/`Cmd` + 滚轮是缩放。**平移在命令进行中是
  被明确保护的**——「取点接管排在画布平移之下」那条决定是对「命令取点最高」这条 CAD 惯例的
  有意偏离，理由就是「命令进行中仍要能平移画布去看远处那个点」。占用裸滚轮会把那条决定推翻，
  而它比这个便利更重要。`Shift` 也不行：浏览器把它映射成横向 delta，那就是横向平移。
- **考虑过的替代**：`↑` / `↓` 方向键（Illustrator 的多边形工具就是拖动时按上下键增减边数）。
  它零冲突、也不需要累加器。没有取它是因为**这条能力已经有键盘入口**——边数步直接键入一个数，
  而且更快（想要十二边就打 `12`，不必按十二下）。方向键在 Stage 上还占着「微调选中对象」，
  再解释一层是净增复杂度。

## 风险 / 权衡

- **1024 条边的多段线在几何编辑里是 2048 个夹点。** → 不为多边形另设更小的上界：`PLINE`
  今天就画得出同样多的顶点，多边形不是这个问题的来源；真要治要治在几何编辑那一侧。
- **边数步上右键仍然弹上下文菜单**（「取点命令进行中右键 = 回车」的判据是 `awaitingPoint`）。
  → 不动那条判据：放宽它要重新论证（它当初的两半理由里，「盖住正要落笔的地方」在这里不
  成立），而回车与命令行都够得着。
- **触控板的一次两指滑动会发出几十个小 delta**，每个事件走一格会让边数从 6 冲到 60。
  → 累加 `deltaY`、过阈值才走一格，方向反转时清零。**这个阈值是一个魔法数**，而本仓库在别处
  明确拒绝过魔法阈值（夹点的原地单击判定不用位移阈值，用的是「指针有没有离开过按下点」）。
  这里没有等价的替代：wheel 事件本身没有「一格」的语义。缓解是让阈值取自**浏览器自己的
  量纲**——`deltaMode` 为行时一行、为像素时一行文本的高度——它因此有来源，不是凭空定的。
- **工具栏那条需求正文与它的场景自相矛盾**（正文说导线占一个按钮，场景说「六个按钮，其中
  没有导线」）。 → 代码里导线按钮是在的，因此错的是场景。本变更要改按钮数量，绕不开它，
  顺带订正。
