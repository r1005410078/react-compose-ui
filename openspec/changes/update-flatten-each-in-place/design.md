# 设计：拍平逐个原地进行

## 判据是「拍平改的是表示还是呈现」

拍平改的是**表示**——顶点换成控制手柄，由作者接管形状。它 MUST NOT 改**呈现**：同一份图在
拍平前后应当逐像素相同。

按这条判据，合并那一支有两处违背，而且都是用户没有要求过的：

1. **颜色被挤掉**。一个对象只有一个填充，四个操作数合成一个，另外三份外观消失。这不是取哪个
   操作数的问题——取层序最下面那个已经是最好的答案了，问题在于「只能取一个」。
2. **透明的地方被填实**。两个空心圆并进同一条 `path` 之后按 `nonzero` 填充，两圆相交那块原本
   透明的区域被填上了。

逐个原地拍平两处都不发生：N 个对象还是 N 个，每个各自把自己的几何换成 `path`。

## 为什么不是「合并但颜色不同时拒绝」

那条会让同一条命令的行为按颜色分叉——两块同色填充照合、两块异色填充报错，而用户读不出这条
规则从哪儿来。更要紧的是它只挡住了两处违背中的一处：两个**空心**圆颜色相同（都没有填充），
合并之后透镜仍然被填实。

## 为什么不怕「想合并的人没得用了」

`UNION` 就是合并，而且它做得更对——它求的是真并集，不会把相交那块按 `nonzero` 填上。
把两条命令分开之后，菜单里那条分隔线的说明也终于成立了：**前四条改变轮廓，拍平不改变轮廓**。
按原先的合并语义，拍平其实是会改变轮廓的（它把若干条轮廓摞进一个对象）。

## 一个事务还是 N 个事务

**一个**。撤销一步 MUST 回到拍平之前，而不是回到「拍平了一半」。这与区域运算「新建与删除进
同一个事务」是同一条。每个操作数自己那条 `entity.curve.set` 与它的 `Hatch` 删除仍然先成对
批进一条，再把 N 条批进外层——批命令可以嵌套，撤销读的是最外层那一条。

## 选区

拍平之后**不挪选区**。「运算之后选中的是产物」那条规则的理由写得很清楚——操作数被删掉之后
不挪，选区就被静默清空。拍平不删任何东西，操作数就是结果，选区因此本来就是对的。
