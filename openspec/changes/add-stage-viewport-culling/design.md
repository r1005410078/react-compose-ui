# 设计

## 上下文

问题不是「怎么少渲染一些」，而是**怎么在不重新引入每帧全量 diff 的前提下少渲染**。现状的内容
子树是 `useMemo` 出来的，依赖里**刻意没有 viewport**，注释把理由写死在那里了。任何让它随视口
变化的做法，都是在拿一个已知的坏结果去换另一个坏结果。

因此本文档的一半在讲几何（裁谁），另一半在讲**什么时候重算**（怎么不每帧重算）。

## 目标 / 非目标

- 目标：大图（五千实体量级）上缩放、平移、拖动都回到可用；节点数与文档规模脱钩、与视口挂钩。
- 目标：裁剪对命中、框选、吸附、选区、场景树**完全不可见**。
- 非目标：改 `--compose-canvas-zoom` 的机制；canvas 渲染；LOD；小图上的任何行为变化。

## 决策 1 · 判据是**子树**包围盒，不是实体自己的盒

`StageSceneIndex.getWorldBounds` 给的是实体**自己**的旋转 AABB。按它裁会漏掉一整类情形：子级
是绝对定位的，容器不裁剪时子级完全可以画在父盒之外——一个盒子在屏幕外、而它的子级在屏幕里的
容器，会被连同子级一起裁掉，症状是「某些东西在特定平移位置整片消失」。

因此新增 `getSubtreeWorldBounds(entityId)`：自身盒与全部后代盒的并集，与既有的 `bounds` /
`parents` 在**同一次**索引构建里算出来（按 `order` 逆序一遍累加到父级即可，O(n)），共用
`StageSceneIndex` 已有的 `(snapshot, document, hidden)` 缓存。

**带 `Clip` 的容器是例外，而且是对我们有利的例外**：它的后代画不到自己盒外，因此子树包围盒
**就是**它自己的盒。这不是优化技巧，是 `Clip` 的定义；顺带让 Frame（恒裁剪与否由 `Clip`
决定）这一层的并集不必穿透整张图。

## 决策 2 · 窗口是一个离散值，因此内容记忆化仍不随帧失效

这是本刀唯一真正的风险点，正面回答它。[stage-scene-layer.tsx](../../../packages/stage/src/stage-scene-layer.tsx)
的内容 memo **刻意**不依赖 viewport，注释把理由写死在那里：让它随帧变化，每一个平移帧都要为
全部 Entity 重建 element 并做 fiber diff。因此裁剪窗口必须是一个**离散**值。

窗口是：**以视口中心为心 → 尺寸按缩放档位取 → 外扩 → 四条边各自向外吸到格子上**。

**落地时按实测改了三处**，原方案的三条都不成立，改动与理由一并记在这里：

1. **外扩量从「一屏」降到「四分之一屏」。** 窗口每轴宽度是 `档定尺寸 × (1 + 2×外扩) + 一格`，
   面积按平方走。外扩一屏时窗口是九倍视口面积——而 `ems.dxf` 整张图只有三四倍视口大，
   **实测五千多个节点一个都没裁掉**。裁剪省下的每一样都与留在 DOM 里的节点数成正比，外扩量
   直接吃掉这个win。
2. **窗口尺寸只认缩放档位，位置只认视口中心。** 原方案按真实可视区取尺寸，于是窗口是缩放的
   **连续**函数——量化了缩放却没量化窗口，等于没量化。实测一次四十帧的滚轮缩放产生**一万七千
   次 DOM 增删**，比根本不裁剪还慢。改成按档位取尺寸后，档内以中心为锚点的缩放窗口一动不动。
   代价是窗口要覆盖档内**最宽**的那个可视区，因此档位密度也从「一个八度一档」加密到**四档**：
   一档时余量是 √2（面积多留一倍），四档时降到 1.09，而跨一个八度的缩放也只重建四次。
3. **「外扩量必须严格大于量化步长」这条不变量取消了，换成「向外吸」。** 原方案是就近吸，每条
   边最多向内让半格，于是需要那个不等式来保证覆盖。向外吸让「窗口恒包含可视区」**由构造成立**
   ——一条读得出来的代码，而不是一个后来者调参就能调破的数值关系。它同时是更强的性质：任意平移
   位置、任意缩放都成立，用例因此是扫一遍而不是构造一个位置。

还有一条是实测才发现的：**格数必须由档位定死，只有左上角随平移走**。两条边各自吸各自的时，
格数会在 7 与 8 之间来回跳，于是平移每过一格换**两次**窗口，多出来的那次是一整趟内容重建，
换来的只是窗口偶尔窄一格。

量化与求解都是 `stage-engine` 的纯函数，喂矩形断言 id 集合，不需要 DOM。

**残留**：缩放方向**每一帧都反向**时（合成夹具那种 ±40 交替滚轮），档位边界上会来回跨，重建
随之来回发生。这是任何无迟滞量化器都有的性质，而真实的捏合/滚轮手势在一次行程内是单调的——
实测把夹具改成单调之后，同一个缩放档位的 p50 从 154ms 落到 11ms。加迟滞要给这个纯函数引入
状态，眼下不划算。

## 决策 3 · 裁剪是渲染决定，MUST NOT 能被任何查询读出来

命中（`entityAtPoint`，已确认按矩阵与 `layoutSnapshot.boxes` 做纯几何判定）、框选
（`resolveMarqueeSelection`）、吸附候选（`snapCandidates`）、场景树、选区包围盒——全部读文档与
布局快照，与 DOM 无关。因此裁剪对它们天然不可见，**而这一条要靠「不提供接口」来保持**：不导出
「这个 Entity 有没有被裁掉」的查询，也不把裁剪集合交给 `stage` 之外的任何一方。

一旦有第二个消费者按裁剪集合做判断，「看得见」与「点得到」就会分家，而那正是本仓在
`hiddenEntityIds` 上明写要避免的（「与 SceneIndex 共用同一个集合引用，保证『看得见』与
『点得到』始终一致」）。裁剪与它**语义相反**：`hidden` 是两边都没有，裁剪是**只在渲染这一边
没有**，因此两者 MUST NOT 合并成一个集合。

## 决策 4 · 豁免集按「谁会按 id 查 DOM」推出，不靠枚举场景

判据一句话：**任何一条会按 Entity id 去 DOM 里找节点的路径，它的目标必须豁免**。今天全仓只有
一处这样的查询（[instance-selection-bounds.ts](../../../packages/stage/src/stage-surface/instance-drilldown/instance-selection-bounds.ts)
的 `querySelector([data-entity-id=…])`），因此豁免集是：

- 正在文字编辑的 Entity——它的 `contentEditable` 持有焦点与输入法组合态；
- 正被手势作用的 Entity——预览变换决定它此刻的几何，而索引里的那份是已提交的；
- 选中集——实例下钻的那条 DOM 查询按选中的复合地址取宿主 id；
- 组件实例下钻的宿主实例。

豁免**沿祖先链向上传播**：豁免一个 Entity 必须同时豁免它的全部祖先，否则它的 DOM 父级不在，
它自己也挂不上去。

**落地时补了一条：豁免的作用范围由豁免的理由决定，分两级。**

- 理由是「有人按这个 id 去 DOM 里找节点」时，找的就是那**一个**节点 → 只豁免它自己加祖先链。
  选择集属于这一级，而这一点是**必须**的：做成整棵子树的话，「选中一块场景」这个最常见的动作
  会当场把整块场景的裁剪关掉。
- 理由是「这棵子树此刻的几何由预览变换决定」时，过期的是**整棵**子树 → 整棵豁免。手势作用的
  对象属于这一级；只豁免根的话，把一个容器拖出一屏之外时它自己还在、里面的东西却按旧位置被
  判掉，屏幕上是「抓着的盒子中途空了」。

`Frame` 不特别豁免——它的标题标签与轮廓画在 overlay 层，读的是快照几何。

**另补一条边界：交给渲染层的是「被裁掉的」而不是「该渲染的」。** 渲染层据此只跳过被点名的，
因此场景索引还不认识的 Entity（预览文档里刚建出来、尚未提交的那些）一律照常渲染。反过来传
「该渲染的」会让任何一个索引来不及认识的 Entity 静默消失，而那类缺陷只在建对象的那一帧出现。

## 决策 6 · 换窗那一帧要便宜，而不是晚一点

**这一条是落地之后用户报「平移时不时卡一下」才补上的，而它本该在提案里。** 提案只算了稳态
节点数，没算**换窗那一帧**：新进窗口的那条带子要建元素、跑物料渲染器、建 DOM，离开的要卸，
实测两千个节点的图纸上是 80ms 的一帧，而平移的 p50 只有 8ms。

**先试过的一版是错的，记在这里免得再走一遍**：把窗口过一道 `useDeferredValue`，让重建走低
优先级。React 18 的低优先级渲染每收到一次高优先级更新就整个重来，而平移每一帧都是一次高
优先级更新——连续拖动时它永远完不成，直到五秒的过期强制同步刷出。用户看到的是「图要等很久
才出来」。这不是调参能救的：让那一趟便宜才是答案，不是让它晚一点。

现在是四件事叠在一起，每一件都对应一条量出来的账：

1. **场景元素按输入缓存**（`stage-scene-layer`）。换窗时内容子树整棵重算，而 React 对 host
   元素只在 `oldProps === newProps` 时 bail out——元素对象换了，哪怕字段逐个相同也要把整棵
   子树走一遍。缓存以 Entity 对象为键（不可变、跨文档版本共享）、Stage 实例为第二层键（元素里
   的指针回调闭包捕获的是那个实例的 ref），输入全部按引用比较。没变的子树交回同一个元素，
   React 在那个 fiber 上直接跳过。
2. **分批逼近目标裁剪集**。换窗那一帧什么都不挂不卸，两条队列（该裁而没裁的、该露而没露的）
   从下一帧起每帧各消化一批。**队列住在场景层而不是宿主**：住宿主时每一批都让整个 Stage
   （覆盖层、标尺、命令行）重渲染一遍，与这一批改没改 DOM 无关。批次按 Chrome trace 定
   （一批 60 挂 60 卸时 React 那趟 JS 约 23ms，线性；40 落在一帧内）。**一批装得下就当帧
   到齐**——排队只为摊开装不下的，小图上换窗因此仍是同步的、可断言的。
3. **队列按文档顺序排，大容器的子级按 256 一桶包进 `memo` 组件**。一块场景直接挂着五千个
   子级时，子级数组只要换一个元素 React 就要克隆五千个子 fiber；分桶之后没变的桶交回同一个
   数组，整桶跳过。**前提是每一批在文档里连续**——第一版批次是随机顺序的，碰到每一个桶，
   实测比不分桶还慢。
4. **可见集不比全集少一成就不裁**。整张图基本都在可视区时裁掉那一成省不下什么，却要为每次
   换窗付整趟账；这一档交空集，与「没有裁剪」逐字相同。

两处**不**分批，理由相同——晚一帧就是看得见的错：缩放跨档（新进的节点可能已在可视区里）
与豁免变化或文档变化（正在编辑、正被拖动的那个必须当场在）。判据是宿主给的 `batchKey`
（缩放档位 + 豁免声明）与索引引用，任一变了就当帧到齐。

**推论：DOM 里的节点数在大图平移时是最终一致的**，读它的端到端要先等稳定；小图不受影响。

**量到但没动的**（不在这一刀里，各自另立）：
- `updateContext` 每帧对全部实体做 `unionRects` 算滚动范围、剪贴板 `availabilityFor` 每帧
  遍历整份文档，各约 0.7–0.9ms/帧，与裁剪无关。
- 换窗后几帧里 Blink 的 Layerize 5–9ms、分配抖动引来的 major GC sweeping 约 15ms 一次，
  不随批次走，是另一层的账。

## 决策 5 · 验收用**节点数**，不用帧时间

帧时间与机器、构建模式、后台负载都相关，写进 CI 就是一条会随机红的用例。而裁剪的**可观察
结果**是确定的：导入 `ems.dxf` 之后，DOM 里的 `[data-entity-id]` 数量应当与可视区相称而不是与
文档规模相称，且**可视区内的每一个实体都必须在 DOM 里**（后半句才是判别性的——只断「节点变少
了」的话，一个把什么都裁掉的实现照样绿）。

帧时间仍然要量，但量的结果记进 `tasks.md`，不进断言。

## 风险 / 权衡

- **窗口换格那一帧要建一批节点** → 外扩一屏让新节点在进入可视区之前就已经建好；换格频率是
  每半屏一次。
- **豁免集漏了一处按 id 查 DOM 的路径** → 判据写成「谁查 DOM 谁豁免」而不是枚举；新增这类查询
  时必须同时进豁免集，由 TSDoc 在那个查询处标注。
- **裁剪集合被第二个消费者读到** → 不导出。
- **缩放可能仍不达标** → 见提案的「刻意不做」；验收阶段量一次，不达标就是下一刀，而那一刀要
  动一条已写明的不变量。

## 迁移计划

无。纯呈现层改动，协议、文档与既有行为都不变；小图上渲染集合等于全集，一个像素不变。
